    Code Review: Python Metrics Engine (791-key Go port)¶

    Ветка: feat/go-to-python-metrics-engine
    Base: origin/main (9f88ca7)
    Head: d5fbb94
    Автор ревью: Senior Code Reviewer
    Дата: 2026-07-29

    Critical (Must Fix)¶

    1. aggregate.py:145 — Ложное предупреждение для валидных ликвидаций¶

    Файл: alpha_engine/metrics_engine/aggregate.py:140-149

    Проблема:

    size = f.orig_qty
if size <= 0:
    size = f.last_fill_qty
    if size <= 0:
        size = f.cum_fill_qty
        if f.last_fill_qty <= 0:   # <-- BUG: должно быть `size <= 0`
            logger.warning(...)

    Логика пытается найти ненулевой размер ликвидации: сначала orig_qty, затем last_fill_qty, затем cum_fill_qty. После того как size = f.cum_fill_qty (уже > 0), условие f.last_fill_qty <= 0 всё ещё проверяет старое значение, а не size. Это даёт ложное предупреждение для каждой ликвидации, где orig_qty <= 0 и last_fill_qty <= 0, но cum_fill_qty > 0.

    Решение:

    size = f.orig_qty
if size <= 0:
    size = f.last_fill_qty
    if size <= 0:
        size = f.cum_fill_qty
        if size <= 0:   # <-- FIX: проверяем актуальный size
            logger.warning(...)

    Риски: Низкие. Исправление тривиальное, логика не меняется. Ложные предупреждения перестанут засорять логи. При неверном патче (если кто-то заменит не ту строку) можно потерять реальные предупреждения о нулевых ликвидациях.

    2. live_bridge.py:346 vs engine.py:251 — Несогласованное имя ключа в warm-start¶

    Файлы: alpha_engine/metrics_engine/live_bridge.py:346, alpha_engine/metrics_engine/engine.py:251

    Проблема:

    warm_start_from_parquet сохраняет строку с ключом _bar_close_ms:

    # live_bridge.py:346
row["_bar_close_ms"] = ...

    Но emit_if_ready пишет:

    # engine.py:251
row["_bar_close_ts"] = ...

    Ни один код пока не читает эти ключи из warm-started данных, поэтому баг латентный. Но при первом же коде, который попытается сопоставить warm-start бары с live-барами по этому ключу, — сломается.

    Решение: Привести к единому имени. Рекомендуется _bar_close_ts (как в engine.py), так как это имя используется в emit_if_ready — горячем пути.

    # live_bridge.py:346
row["_bar_close_ts"] = ...

    Риски: - Если какой-то внешний код (ещё не написанный) уже проснулся и читает _bar_close_ms — сломается. Но на текущий момент такого кода нет. - Потенциально может быть несоответствие с Go-форматом, если Go-паркет пишет _bar_close_ms. Нужно проверить Go-код на предмет имени поля и синхронизировать.

    3. live_bridge.py:206-226 — Гонка данных: Engine не thread-safe¶

    Файл: alpha_engine/metrics_engine/live_bridge.py:206-266

    Проблема:

    LiveMetricsBridge работает в двух потоках: - WS поток вызывает on_tick() → eng.push(), eng.feed_book(), eng.emit_if_ready() - Trader поток вызывает exchange_data() → читает _bars под _bars_lock

    Проблема в том, что _bars_lock защищает только список _bars, но не защищает внутреннее состояние Engine (его кольцевой буфер, текущий агрегат, очередь ликвидаций). Если exchange_data() читает _bars пока on_tick() мутирует Engine, возможна гонка на объектах Aggregate внутри кольцевого буфера.

    Решение (вариант A): Расширить область _bars_lock на весь вызов on_tick():

    def on_tick(self, tick: Tick) -> None:
    with self._bars_lock:
        self.engine.push(tick)
        if tick.liquidation:
            self.engine.feed_liquidation(tick.liquidation)
        self.engine.feed_book(tick.book)
        bars, closed = self.engine.emit_if_ready()
        if closed:
            self._extend_bars(bars)

    Это гарантирует, что exchange_data() всегда видит консистентное состояние Engine.

    Решение (вариант B): Документировать, что exchange_data() должен вызываться только из того же event loop или после остановки подписки на bus. Для Phase 1 (сигнальный режим, бары раз в 30 минут) это приемлемо, но ловушка для будущих разработчиков.

    Риски: - Вариант A: Увеличение времени удержания блокировки может повлиять на latency WS потока, если push/emit_if_ready медленные (маловероятно, но теоретически возможно). - Вариант B: Следующий разработчик может вызвать exchange_data() из другого потока, не зная о требовании, и получить битые данные (hard-to-debug race condition).

    4. tick_reader.py:72-76 — Проверка колонок внутри цикла по строкам¶

    Файл: alpha_engine/metrics_engine/tick_reader.py:72-76

    Проблема:

    for _, row in df.iterrows():
    if "side" in df.columns:   # проверяется 1800 раз, не меняется ни разу
        is_buyer_maker = row["side"] == "sell"
    else:
        is_buyer_maker = bool(row["is_buyer_maker"])

    df.columns не меняется внутри цикла. Проверка инварианта на каждой итерации — O(n) вместо O(1).

    Решение: Вынести проверку до цикла:

    has_side = "side" in df.columns
for _, row in df.iterrows():
    if has_side:
        is_buyer_maker = row["side"] == "sell"
    else:
        is_buyer_maker = bool(row["is_buyer_maker"])

    Риски: Низкие. Косметический рефакторинг. Ошибка при переносе (например, забыть переименовать df.columns в has_side) приведёт к очевидному NameError или логической ошибке, которая быстро отловится тестами.

    5. tick_reader.py:90 — Избыточная сортировка в каждом read_*¶

    Файл: alpha_engine/metrics_engine/tick_reader.py:90 (и аналогично в других read_* методах)

    Проблема: Каждый read_trades, read_liquidations, read_books сортирует свой список тиков. Затем read_ticks (line 209) сортирует объединённый результат снова. Сортировка на каждом подсписке избыточна: если объединить n/k списков по k элементов, итоговая сложность O(k * (n/k) log (n/k) + n log n) против O(n log n) без под-сортировок.

    Решение: Убрать result.sort(key=attrgetter("ts")) из read_trades/read_liquidations/read_books и полагаться только на финальную сортировку в read_ticks.

    Риски: Низкие. Производительность исторического реплея не критична. Основной риск — если какой-то код полагается на отсортированность списка после вызова отдельного read_* (внешних вызовов нет).

    6. tools/replay_metrics.py:85 — Лямбда захватывает engine по ссылке¶

    Файл: alpha_engine/metrics_engine/tools/replay_metrics.py:85

    Проблема:

    book_replay.handle_tick(tick, lambda scalars: engine.feed_book(scalars))

    engine захватывается по ссылке. В данном случае engine не переопределяется в цикле, поэтому бага нет. Но это классический anti-pattern. В test_replay_parity.py:130 используется правильный подход:

    lambda s, eng=e: eng.feed_book(s)

    Решение: Привести к единому стилю:

    book_replay.handle_tick(tick, lambda scalars, eng=engine: eng.feed_book(scalars))

    Или обернуть в именованную функцию.

    Риски: Маловероятны — engine не переприсваивается в цикле. Но если в будущем код рефакторится и engine начинает пересоздаваться, баг проявится. Лучше исправить сейчас, когда контекст понятен.

    7. live_bridge.py:253-255 — Перестроение DataFrame на каждый __getitem__¶

    Файл: alpha_engine/metrics_engine/live_bridge.py:253-255

    Проблема: _LiveMetricsDict._build_frame строит DataFrame из сырого словаря bars при каждом __getitem__ (если нет в кеше). С 791 ключом, первый доступ от всех стратегий может перестроить 791 DataFrame. При warm_start с 30 днями x 48 баров x 5 символов ≈ 7200 баров — вызов has_key() для ~5 ключей из _KIND_PROBES приводит к ~36000 построений фреймов.

    Решение: - Кешировать DataFrame для каждого kind до следующего _extend_bars() - Или строить DataFrame лениво, только при первом обращении к ключу, и инвалидировать при появлении нового бара

    Текущее поведение приемлемо для 30-секундного каденса баров, но при scale-up (больше символов, чаще бары) может стать узким местом.

    Риски: Преждевременная оптимизация. Если исправлять, нужно быть аккуратным с инвалидацией кеша — устаревший DataFrame может привести к неверным сигналам.

    8. engine.py:152-153 — Тихий дроп тиков до первого валидного tick.ts¶

    Файл: alpha_engine/metrics_engine/engine.py:152-163

    Проблема:

    def push(self, tick: Tick) -> None:
    if tick.ts <= 0:
        return  # silently dropped
    ...

    Если в push передан тик с ts <= 0, он молча дропается. При этом _cur_open магическое значение False (line 152) — _open_slot устанавливает его при первом push. Таким образом, при вызове emit_if_ready до любого push, возвращается ({}, False) — корректно, но молчаливо.

    Решение: Добавить logger.warning для дропнутых тиков (по крайней мере debug-level), и документировать поведение в docstring push (уже есть частично).

    Риски: На production может быть поток тиков с битой меткой времени (например, из-за рассинхронизации часов на бирже). Без логирования это тихая потеря данных. С другой стороны, логирование на каждый такой тик может заспамить логи.

    9. Нет теста для _add_kline с kline_open > kline_close¶

    Файл: tests/test_metrics_engine_parity.py (отсутствует тесткейс)

    Проблема: Группа _add_kline делает hi = max(hi, kline_hi) и lo = min(lo, kline_lo). Если по какой-то причине приходит kline с high < low (что невозможно в нормальных данных, но может быть от бажного upstream), hi/lo могут не обновиться корректно. Поведение соответствует Go-версии, но не покрыто тестом.

    Решение: Добавить тест, проверяющий что при high < low значения hi/lo обрабатываются без падения и без стейт-коррупции. Это также защитит при портировании на другие языки.

    Риски: Низкие. Реальные данные с биржи гарантируют high >= low. Тест нужен скорее как регрессионная защита при рефакторинге и для документирования поведения.

    10. book_replay.py:86 — _resync_count инкрементируется на каждый снапшот¶

    Файл: alpha_engine/metrics_engine/book_replay.py:86

    Проблема: В Go live-версии resync_count отслеживает реальные ресинхронизации после разрыва WS-соединения. В реплее каждый снапшот считается ресинком. Это означает, что BookScalars из реплея несут завышенный resync_count по сравнению с live-версией Go.

    # Mirrors Go's cmd/replay: every snapshot is a resync
self._resync_count += 1

    Решение: - Задокументировать это расхождение в docstring BookReplay и/или в документации к реплею - Если resync_count используется где-то как фича (например, для взвешивания уверенности в book-метриках), нужно либо игнорировать его при реплее, либо нормализовать

    Риски: Если в будущем кто-то сравнивает реплей-метрики с live-метриками по resync_count, выводы будут неверными. На данный момент resync_count нигде не используется в стратегиях, но это может измениться.

    Minor (Nice to Have)¶

    11. ring.py:34-35 — setattr в цикле по 80 полям¶

    Файл: alpha_engine/metrics_engine/ring.py:34-35

    Проблема: Каждый append копирует 80 полей Aggregate через setattr/getattr:

    for slot in Aggregate.__slots__:
    setattr(target, slot, getattr(agg, slot))

    При 1800 слотах на бар это 144,000 операций атрибутов.

    Решение: Использовать copy.copy для быстрого поверхностного копирования (если все поля immutable/float), или определить метод copy() на Aggregate:

    target = copy.copy(agg)

    Риски: У copy.copy есть небольшой оверхед на создание объекта, но он всё равно быстрее 80 вызовов setattr + 80 getattr. Надо убедиться, что все поля Aggregate — примитивные типы (float, int) — для copy.copy это не проблема.

    12. book_scalars.py:24-30 — Поля-счётчики типизированы как float, не int¶

    Файл: alpha_engine/metrics_engine/book_scalars.py:24-30

    Проблема: Поля updates_count, seq_gaps, resync_count имеют тип float, хотя логически представляют целочисленные счётчики. Это сделано для соответствия Go-версии (где они хранятся как float64 в агрегате) и чтобы избежать преобразований типов, но аннотация float для счётчиков вводит в заблуждение.

    Решение: Оставить как есть (соответствие Go). Либо добавить комментарий, объясняющий причину выбора типа.

    Риски: Косметика. При попытке использовать эти поля в контексте, где ожидается int (например, range()), будет TypeError.

    13. groups/orderbook.py:364-565 — Вложенные функции переопределяются на каждой итерации¶

    Файл: alpha_engine/metrics_engine/groups/orderbook.py:356-565

    Проблема: Функции _vwap, _slope, _dr, _log_ret определены внутри цикла for a in buf::

    for a in buf:
    def _vwap(...): ...
    def _slope(...): ...
    def _dr(...): ...
    def _log_ret(...): ...
    # использование

    Python создаёт новый объект функции на каждую итерацию (до 1800 раз на бар).

    Решение: Вынести определения функций на уровень модуля или хотя бы на уровень метода (вне цикла).

    Риски: Требует аккуратного рефакторинга — функции могут захватывать переменные из области видимости цикла. При выносе на уровень модуля нужно передавать все зависимости через аргументы. Риск сломать логику при рефакторинге выше, чем профит от оптимизации.

    14. main.py:288-299 — run_replay импортирован, но вызывается с корректными аргументами¶

    Файл: main.py:288-299

    Заметка: В ходе ревью было проверено, что run_replay получает symbols как list[str] (после args.symbols.split(",")), что соответствует ожидаемому типу. Всё корректно. Не является проблемой — просто констатация.

    Рекомендации по процессу¶

    1. Добавить pre-commit хук на линтер (ruff/mypy) для новых файлов в metrics_engine/, чтобы отлавливать подобные issue на ранней стадии.
    2. Задокументировать thread-safety контракт LiveMetricsBridge в CLAUDE.md или в docstring класса — явно указать, из каких потоков можно вызывать какие методы.
    3. Добавить интеграционный тест с реальной гонкой потоков (thread sanitizer или стресс-тест с множественными вызовами on_tick / exchange_data).
    4. Синхронизировать имена ключей между Go и Python — завести константу где-то в общем месте (например, BAR_CLOSE_KEY = "_bar_close_ts") и использовать её везде, включая Go, если возможно.

    Итоговая оценка¶

    Ready to merge? С фиксами Critical #1, #2, #3.

    Обоснование: Реализация — добросовестный, хорошо протестированный порт Go metrics engine с 4400+ строк кода, 4 тестовыми файлами и покрытием ключевых сценариев. Три критических issue (ложный warning, неконсистентный ключ warm-start, незадокументированная thread-safety) должны быть исправлены перед мержем. Important issue — улучшения, которые стоит отследить и запланировать, но они не блокируют мерж. Архитектура и качество тестов — на высоком уровне.

    Critical¶

    AA. tick_adapter.py:65 — Case-sensitive сравнение side в _from_agg_trade¶

    Файл: alpha_engine/metrics_engine/tick_adapter.py:65

    PP. tick_adapter.py:85-86 — Тихая классификация неизвестной стороны ForceOrder как "SELL"¶

    Файл: alpha_engine/metrics_engine/tick_adapter.py:85-86

    Проблема:

    side_raw = str(e.side).upper()
side = "BUY" if side_raw == "BUY" else "SELL"

    Любое значение e.side, отличное от "BUY" (даже None, пустая строка, "UP", "DOWN"), молча классифицируется как "SELL". Это parity с Go-оригиналом, где аналогичный switch в cmd/replay имеет fallthrough-ветку "SELL" по умолчанию. Но в Go это дополняется проверками на уровне парсера; в Python такого валидационного слоя нет.

    Риски: - Если Binance когда-либо изменит спецификацию или пришлёт какое-то другое значение (например, локализованную строку), ForceOrder будет молча записан на противоположную сторону. - В отличие от #AA (agg-trade side), это не воспроизводится на каждом тике — ForceOrder-ы редки, поэтому баг может долго оставаться незамеченным.

    Решение (низкий risk, высокий confidence):

    side_raw = str(e.side).upper()
if side_raw == "BUY":
    side = "BUY"
elif side_raw == "SELL":
    side = "SELL"
else:
    logger.warning("ForceOrder unknown side=%r, defaulting to SELL", e.side)
    side = "SELL"

    Severity: Low-Medium (parity с Go, но без защитного логирования). Отличается от #AA тем, что не гарантированно ломает данные на каждом тике, а лишь при нестандартном значении.

    QQ. main.py:206,256,283 — Три идентичных logging.basicConfig в трёх функциях¶

    Файл: main.py:206,256,283

    Проблема:

    Три под-команды (_run_backtest, _run_live, _run_replay_metrics) содержат идентичный boilerplate:

    logging.basicConfig(
    level=...,
    format="%(asctime)s %(levelname)s [%(name)s] %(message)s",
)

    В отличие от описания в оригинальном ревью (которое утверждало, что main() вызывает basicConfig на ~140 строке — это неверно: main() не вызывает basicConfig), каждая из трёх под-функций действительно дублирует код. Хотя технически они вызываются mutually exclusive (работает только одна за запуск), дублирование — это maintenance hazard: если нужно изменить формат логов или добавить обработчик, менять придётся в трёх местах.

    Кроме того, _run_replay_metrics (line 283) хардкодит level=logging.INFO вместо того, чтобы принимать --log-level, в отличие от двух других команд (см. issue #OO выше).

    Решение:

    Вынести basicConfig в main() перед dispatch по под-командам, или сделать ленивую инициализацию через общую функцию:

    def _init_logging(level: str = "INFO") -> None:
    logging.basicConfig(
        level=getattr(logging, level.upper(), logging.INFO),
        format="%(asctime)s %(levelname)s [%(name)s] %(message)s",
    )

    Также добавить --log-level для replay-metrics (как описано в #OO).

    Severity: Low (maintainability). Не блокирует мерж.

    SS. Вложенные функции в orderbook.py:364-401 — подтверждение + контекст¶

    Связь: Полностью соответствует issue #13 выше. Внешнее ревью подтверждает:

    for a in buf:
    def _vwap(...): ...   # пересоздаётся 1800 раз
    def _slope(...): ...

    Дополнительная деталь: Функции захватывают a по ссылке (замыкание). Если бы они вызывались лениво (например, передавались как callback и вызывались позже), все они увидели бы последнее значение a. К счастью, они вызываются синхронно на той же итерации, поэтому бага нет. Но при любом рефакторинге это типичная ловушка.

    TT. engine.py:220 — LiqEvent notional использует orig_qty напрямую, а не цепочку fallback¶

    Файл: alpha_engine/metrics_engine/engine.py:220

    Проблема:

    notional=tick.force.price * tick.force.orig_qty,

    Но в aggregate.py:140-152 (_add_liquidation) per-second aggregate использует fallback-цепочку для определения размера:

    size = f.orig_qty
if size <= 0:
    size = f.last_fill_qty
    if size <= 0:
        size = f.cum_fill_qty

    Это означает, что если orig_qty == 0 (но есть last_fill_qty > 0 или cum_fill_qty > 0), то:

    • Per-second aggregate (_add_liquidation) — корректно считает ликвидацию с size = last_fill_qty
    • LiqEvent shock deque (engine.py:LiqEvent.notional) — записывает notional = 0, ликвидация не влияет на shock-метрики

    Несоответствие: Два компонента (aggregate vs shock deque) расходятся в интерпретации "размера" ликвидации для одного и того же ForceOrder-тика.

    Решение:

    Вариант A (рекомендуемый) — привести LiqEvent к той же логике fallback:

    f = tick.force
size = f.orig_qty or f.last_fill_qty or f.cum_fill_qty
notional = f.price * size

    Вариант B — задокументировать расхождение, если оно intentional (например, если Go-оригинал тоже использует orig_qty для shock deque).

    Риски:

    • Если ликвидации с orig_qty = 0 редки на практике — баг latent, не проявляется
    • Без фикса при реальной ликвидации с нулевым orig_qty shock-метрики (например, cumulative liq notional за window) будут занижены
    • Вариант B означает divergence от aggregate-логики, что усложнит поддержку

    Severity: Medium — зависит от частоты ForceOrder с orig_qty = 0.

    UU. run_trader.py:164-169 — --in-process-metrics молча игнорируется при --bars N¶

    Файл: alpha_engine/live/run_trader.py:164-169

    Проблема:

    if args.in_process_metrics and args.bars == 0:
    reader = LiveMetricsBridge(...)
else:
    reader = LiveGoMetricsReader(...)

    Условие args.bars == 0 означает, что --in-process-metrics молча игнорируется при любом --bars N > 0 (offline dry-run / bar replay). Пользователь указывает --in-process-metrics, но получает LiveGoMetricsReader без единого предупреждения.

    Дополнительно: LiveMetricsBridge не имеет метода preload_window, который ожидается для offline dry-run path. Если бы условие пропустило bridge в этот path, упало бы с AttributeError.

    Решение:

        reader = LiveGoMetricsReader(...)
    else:

    Или, альтернативно, добавить preload_window в LiveMetricsBridge.

    Риски:

    • Пользователь может думать, что метрики считаются Python-движком, а на деле используются Go-precomputed
    • Низкая вероятность — флаг --in-process-metrics пока экспериментальный

    Severity: Low — observable только если кто-то явно использует --in-process-metrics --bars N.

    VV. Gap catch-up emission — N идентичных строк после простоя (подтверждение + контекст)¶

    Связь: Полностью соответствует issue #II и #9 (оригинальное ревью). Упомянуто в review task output как Notable.

    Контекст: engine.py:248-253 — emit_if_ready в catch-up loop возвращает несколько строк бара с идентичными метриками и разными _bar_close_ts. Это per Go spec и intentional behavior. Но: стратегии PnL, вычисленные на этих дублированных барах, покажут нулевую доходность за период gap, что неотличимо от реального flat market.

    Дополнительный риск: Если стратегия использует bar-level метрики для принятия решений (например, волатильность, объём), дублированные бары исказят rolling-статистику — волатильность будет занижена (так как "нулевые" бары добавляются в выборку), а cumulative volume — завышен.

    Решение для стратегий: Стратегии могут проверять _bar_close_ts и пропускать дубликаты:

    if bar["_bar_close_ts"] == last_bar_ts:
    continue  # skip duplicate catch-up bar

    Severity: Low (Notable) — поведение intentional, но downstream потребители должны быть к нему готовы.
