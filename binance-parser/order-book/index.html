    Local L2 order book¶

    binance_parser/live/orderbook.py keeps a live in-memory L2 book per symbol per market by following Binance's official algorithm (spot and USD-M use the same algorithm; only the REST snapshot URL differs).

    Persistence and metric contract¶

    Identical for spot and USD-M futures. Code that violates any of these three points is a bug.

    # What Cadence Sink Purpose
    1 Live state — single OrderBook per (market, symbol), updated by every WS @depth diff every WS event in-memory only live metric input + 30-min snapshot source
    2 Full-depth BookSnapshotEvent to type=booksnapshot/ parquet LIVE_ORDERBOOK_SNAPSHOT_INTERVAL_MS (default 30 min, UTC-aligned) parquet durable record, 48 snapshots/day/symbol
    3 Full-depth BookSnapshotEvent to in-process bus LIVE_ORDERBOOK_BUS_INTERVAL_MS (default 1 s, UTC-aligned) live bus live metric aggregators subscribe and recompute on the diff-applied state at this cadence

    Diffs are never persisted to parquet. The bus stream is never written to disk (the file_writer sink excludes event_type="booksnapshot"). Both loops use _sleep_until_next_aligned_tick so ticks land on multiples of the interval irrespective of process start time. Books not in live state at a tick are skipped — half-bootstrapped data never reaches a sink.

    Lifecycle¶

    stateDiagram-v2
  [*] --> bootstrapping
  bootstrapping --> live: snapshot received and<br/>buffered diffs replayed
  live --> resyncing: gap detected (U != prev.u + 1)
  resyncing --> bootstrapping: re-fetch snapshot

    States:

    • bootstrapping — buffering incoming @depth diffs, no book state yet. Triggers a REST snapshot fetch; the book is "live" once the snapshot lands and the first diff with U <= snapshot.lastUpdateId+1 <= u is applied.
    • live — every diff is applied; last_update_id is checked to be contiguous (U == last_update_id + 1).
    • resyncing — gap detected. Drop existing state and re-bootstrap. resync_count is incremented (good metric to watch).

    The bootstrap sequence¶

    1. Subscribe to {symbol}@depth and start buffering events.
    2. Fetch GET /api/v3/depth?symbol=…&limit=1000 (spot) or GET /fapi/v1/depth?symbol=…&limit=1000 (USD-M). The response has a lastUpdateId.
    3. Drop all buffered events with u <= lastUpdateId.
    4. Find the first buffered event with U <= lastUpdateId + 1 <= u — this is the "matching" event that bridges snapshot and diff stream.
    5. Apply that event and every subsequent buffered event in order.
    6. State transitions to live. Future diffs apply directly.

    If no buffered event "straddles" lastUpdateId (e.g. the buffer is entirely too old or too new), bootstrap fails — return False, sleep, retry from step 1. The test test_bootstrap_returns_false_when_buffer_does_not_straddle_snapshot exercises this path.

    Gap detection¶

    In the live state, every incoming diff must satisfy U == last_update_id + 1. If not:

    • Flip state to resyncing.
    • Increment resync_count.
    • Drop the bid/ask books.
    • Restart bootstrap from step 1.

    This happens on:

    • Lost WS messages (rare with Binance's pings, but possible).
    • Server-side state resets.
    • Network blip during reconnect (the writer reconnects automatically; the in-flight diffs may not align).

    Tests test_gap_detection_flips_state_to_resyncing and test_resync_replays_buffered_events_after_gap cover the recovery sequence.

    qty == 0 means "remove"¶

    Per Binance spec, a level with qty == 0 in a diff means delete that price level. OrderBook.apply_diff does:

    for px, sz in updates:
    if sz == 0:
        book.pop(px, None)
    else:
        book[px] = sz

    Test: test_zero_quantity_removes_level.

    Sorted by price¶

    SortedDict from sortedcontainers keeps both sides ordered. Top-N queries (book.top(n)) are O(N) since N is small (Binance gives up to 5000 levels per side; we typically only inspect the top 25).

    For bids, "best" means highest price; for asks, lowest. The top() helper handles the direction so consumers don't have to.

    Snapshot loops¶

    Two cadences emit the same BookSnapshotEvent for two different consumers. WS @depth diffs are never persisted on their own — they only update the in-memory OrderBook. Periodic snapshots are the only thing on disk.

    loop interval (default) sink purpose
    snapshot_to_parquet_loop LIVE_ORDERBOOK_SNAPSHOT_INTERVAL_MS = 1_800_000 (30 min) parquet (type=booksnapshot/) durable record, UTC-aligned to :00 / :30
    snapshot_to_bus_loop LIVE_ORDERBOOK_BUS_INTERVAL_MS = 1_000 (1 Hz) in-process bus live metric aggregator (alpha_engine)

    Both loops use _sleep_until_next_aligned_tick so ticks always land on a multiple of the interval — independent of process start time. Snapshots carry the full book; the previous top-N truncation is gone.

    async def snapshot_to_parquet_loop(self, interval_ms, writer, writer_market):
    interval_s = interval_ms / 1000
    while True:
        await self._sleep_until_next_aligned_tick(interval_s)
        for book in self.books.values():
            if book.state != "live":
                continue
            evt = self._build_snapshot_event(book, int(time.time() * 1000))
            await writer.write(writer_market, evt)

    The bus loop has the same shape but writes to a LiveTickBus which fans the snapshot to subscribed LiveRawDataReader instances without forwarding to the parquet sink — the bus's attach_sink(file_writer, exclude_types={"booksnapshot"}) opts out of that.

    LiveRawDataReader keeps kind="orderbook" rows in its rolling deque with a per-kind lookback of 1 day (vs 60 days global default), so even 1 Hz × full depth fits in single-digit GB per symbol of memory.

    Manager¶

    OrderBookManager is the multi-symbol container:

    mgr = OrderBookManager(market="usdm", symbols=["BTCUSDT", "ETHUSDT"])
await mgr.start()                          # bootstrap all books
mgr.handle_raw_depth(stream, payload)      # called by ws_client
await mgr.snapshot_loop(interval_ms, top_levels, writer, market)

    The handle_raw_depth entry point is the bridge to the WS listener — ws_client.listen pulls raw @depth payloads off the socket and tees them to both the DTO path (truncated, written to parquet) and the manager (full levels, kept in memory).

    Operational notes¶

    • Memory: ~5000 levels × 2 sides × ~32 bytes/entry × N symbols. At 20 symbols, comfortably under 10 MB.
    • Initial REST fetch is slow — the first ~5 s after launch are spent bootstrapping every book. Subsequent restarts are similar (no on-disk persistence).
    • Resyncs are fine. A few per day per symbol is normal; dozens per hour suggests network problems or you're behind a flaky proxy.
    • Snapshots are point-in-time copies. They share no memory with the live book — safe to send across an asyncio.Queue without locks.
