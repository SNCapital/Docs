    Live Trading

    Purpose¶

    Defines the live trading runtime of alpha_engine (live/): the CLI entry (main.py live-trade), the component wiring in LiveService (tick bus, order book manager, snapshot loops, warm-start reader, bar orchestrator), the UTC-aligned BarClock with exchange drift correction (BinanceTimeSync), the signal-only bar evaluation loop (LiveEngine), and the full trader loop (LiveTrader, RiskGuard, OrderExecutor, LiveBlotter, StateStore) that Phase 3 wires into paper execution. Phase 1 is signal-only by contract: signal_only=True is hard-coded at the CLI, and any non-signal-only invocation raises NotImplementedError.

    Requirements¶

    Requirement: Live CLI contract¶

    The system SHALL expose a live-trade subcommand in the root main.py (and treat a flag-only or empty invocation as live-trade for backwards compatibility) accepting --alphas (nargs+, choices from ALPHA_REGISTRY, default trade_imbalance), --symbols (default: the parser's configured symbols), --bar-minutes (default 30), --settlement-seconds (default 5.0), --lookback-days (default 30), --max-w (default 0.03), --end-range (default 50), --market (spot|usdm, default spot), --no-order-book, --snapshot-interval-ms, --data-root (default ./data), and --log-level. The invocation SHALL always run in signal-only mode (Phase 1); attempting to disable it SHALL raise NotImplementedError because execution lands in Phases ¾.

    Scenario: Default invocation¶

    • WHEN python main.py is run with no subcommand
    • THEN it behaves as live-trade with defaults (spot, trade_imbalance, 30-minute bars)

    Scenario: Execution mode not implemented¶

    • WHEN the engine is asked to run with execution enabled
    • THEN it raises NotImplementedError (Phases ¾)

    Requirement: Live service wiring¶

    The system SHALL compose the live runtime in run_live in a fixed order: uppercase the symbols; resolve the venue tag (spot -> "binance", usdm -> "binance-f"); build a LiveTickBus with a FileWriter sink (excluding booksnapshot); create a shared HealthCounters; build the OrderBookManager unless enable_order_book is false; register the OrderBookUpdatesAggregator as a diff observer when the book is enabled; build LiveRawDataReader with a lookback of lookback_days + 30; warm-start it from parquet under data-root (missing root logs a warning and continues; a warm-start exception is logged and the reader proceeds with empty deques); construct LiveEngine with its config, BinanceTimeSync, and a 30-minute Bar; validate symbols with the parser's pre-flight check; then start everything in one asyncio.TaskGroup: file writer, time sync poller, WS listener, order book manager plus watchdog, order-book parquet snapshot loop (UTC bar-aligned interval, 30 minutes from the parser's live-snapshot setting unless overridden by --snapshot-interval-ms; skipped entirely when the effective interval is <= 0), order-book bus snapshot loop (1 Hz default; skipped when <= 0), reader consumer, and engine. All snapshot cadences: the parquet loop simply runs at the effective interval - the "5000 ms fallback" in the stale run_live docstring does not exist in code (the parser allows no interval and the loop is skipped) - and the loop must keep serving snapshots because the live reader needs them to populate the orderbook deque; the bus snapshot stream never lands on disk (the FileWriter sink excludes booksnapshot).

    Scenario: Warm-start failure¶

    • WHEN the warm-start bootstrap raises or finds no rows under the data root
    • THEN the runtime logs the failure and starts with empty deques rather than aborting

    Scenario: Book disabled¶

    • WHEN --no-order-book is given
    • THEN no OrderBookManager, watchdog, snapshot loops, or diff-observer are created

    Requirement: Live tick bus¶

    The system SHALL fan out every parser event through LiveTickBus, which implements the same write(market, record) contract as the parser's FileWriter so it can serve as the WS listener's writer. Every written event SHALL be delivered to each subscriber (one asyncio.Queue each) and forwarded inline to every attached sink. Backpressure SHALL be lossy: a subscriber whose queue is full (default 10,000 events) SHALL drop the event, increment its dropped counter, and log at power-of-two thresholds, while the other subscribers still receive the event. A subscription SHALL optionally restrict event_types at the publish edge so high-rate streams (e.g. raw orderbook diffs) never consume queue slots. Sinks SHALL support exclude_types (canonical use: booksnapshot excluded from the parquet writer because the dedicated snapshot loop writes parquet snapshots at a different cadence). The live reader's subscription SHALL be filtered to aggtrades, klines, booksnapshot, funding, markprice, forceorder, trades, deliberately excluding raw orderbook diffs.

    Scenario: Slow subscriber drop¶

    • WHEN a subscriber's queue fills
    • THEN the event is dropped for that subscriber only and the drop counter increments

    Scenario: Publish-edge filter¶

    • WHEN a subscription specifies event_types
    • THEN events outside the set are not enqueued, saving queue slots for the events that matter

    Requirement: Bar clock and time synchronization¶

    BarClock SHALL yield one pd.Timestamp per UTC-aligned bar boundary, strictly after the current time, computed as base + (floor(minutes_into_hour / bar_minutes) + 1) * bar_minutes where base is the current minute-zero UTC; each yield SHALL be delayed by settlement_seconds (default 5.0) after the boundary so the WS can deliver the last ticks of the just-closed bar. bar_minutes <= 0 or settlement_seconds < 0 SHALL raise ValueError. The clock SHALL accept an injectable time_source so boundaries align to the exchange even on a host with a skewed clock. BinanceTimeSync SHALL poll the exchange server-time endpoint once per minute (/api/v3/time on spot, /fapi/v1/time on USD-M), timestamp local time at request start and end (midpoint correction), maintain an EWMA of the server - local offset with alpha=0.3, and expose now() / now_ms(). Until the first sample the offset SHALL be 0 (fall back to local clock); a poll failure SHALL keep the previous EWMA rather than resetting. A drift over 500 ms SHALL log a warning; over 2000 ms SHALL log an error and record a clock-drift alert on the shared HealthCounters.

    Scenario: Settlement delay¶

    • WHEN a bar boundary is reached
    • THEN the clock sleeps settlement_seconds past the boundary before yielding the bar timestamp

    Scenario: Cold-start clock¶

    • WHEN no server-time sample has landed yet
    • THEN BinanceTimeSync.now() falls back to the local clock unchanged, and the engine still starts immediately

    Requirement: Live raw data reader¶

    LiveRawDataReader SHALL serve the aggregator contract (DataFrame views over [since, until], same column normalization as the parquet reader) from rolling in-memory deques keyed by (exchange, kind, ticker), fed from a bus subscription. Event routing SHALL be fixed: aggtrades -> aggregated trades (canonical), raw trades -> trades_raw only when the parser flag LIVE_RECONSTRUCT_MULTILEVEL is set (otherwise dropped, preventing double-counting), forceorder -> liquidations, closed klines only, booksnapshot -> long-form orderbook rows (one per bid/ask level at the snapshot timestamp), funding -> realized_funding column only, markprice -> all four mark-price columns, and raw orderbook diff updates SHALL be ignored. bootstrap_from SHALL seed the deques from prior parquets (trades, trades_raw, orderbook, klines, funding, markprice, liquidations). Eviction SHALL be lazy: rows older than since - grace are dropped during read(), plus periodic global eviction after every 10,000 accumulated rows (the counter advances by len(rows) per event, so a full-depth booksnapshot counts as hundreds of rows, not one event), using per-kind retention (the orderbook deque SHALL keep only 1 day because full-depth 1 Hz books are too large for the general 60-day lookback). Late-event accounting SHALL count events with timestamps strictly before the last processed bar after mark_bar_processed(bar_ts), logging periodically, so an operator can watch for WS reconnect/load spikes.

    Scenario: Double-count protection¶

    • WHEN a raw trades event arrives and LIVE_RECONSTRUCT_MULTILEVEL is off
    • THEN it is routed to nothing, keeping the aggregated trades deque aggtrade-only

    Scenario: Orderbook memory bound¶

    • WHEN full-depth booksnapshots accumulate
    • THEN the orderbook deque is bounded by a 1-day window while cheaper kinds keep the 60-day window

    Scenario: Late event accounting¶

    • WHEN an event's timestamp is strictly before the last bar the engine has processed
    • THEN it is counted as late and logged periodically, not silently mixed into the wrong bar

    Requirement: Bar boundary evaluation (signal engine)¶

    LiveEngine SHALL run once per bar: build an ExchangeData view over [bar_ts - lookback_days, bar_ts] via the live reader, run all configured strategies through run_strategies, take the latest weight row at or before bar_ts per strategy, combine (single strategy -> pass-through; multiple -> equal-weight blend across the union of tickers; PnL-driven Markowitz is deferred to Phase 3), log the bar summary (bar number, strategy count, gross, non-zero count, late-events count - the weight vector itself is not logged), signal mark_bar_processed(bar_ts), and record the bar in weights_history. Strategy evaluation failure at a bar SHALL log the exception and return None (no opinion) rather than crashing the loop, and a bar whose strategies produce no rows SHALL also yield None.

    Scenario: Multiple strategies blend¶

    • WHEN two or more strategies produce weights for a bar
    • THEN the target is the equal-weight average of their latest rows across the union of tickers

    Scenario: Strategy failure is not fatal¶

    • WHEN strategy evaluation raises at a bar
    • THEN the bar logs the exception and continues no-op; the loop keeps running

    Requirement: Trader bar loop¶

    LiveTrader SHALL run the full round-trip bar loop (paper mode, Phase 3): read a rolling metrics window from its reader - the file-based LiveGoMetricsReader, which rebuilds a GoMetricsStore over [bar_ts - lookback_days, bar_ts] from the Go parser's type=metrics parquet per bar, or serves cheap in-memory slices from a single preload_window store for offline dry-runs (run_trader --bars N); the reader's latest_metric_ts SHALL report the newest metrics bar on disk for parser-health display (cached after the first successful scan: the value is frozen for the rest of the run, which is fine for offline dry-runs where the newest on-disk bar never moves, but in a live run it reflects the state at first call, not the newest bar). (The in-process LiveMetricsBridge of alpha-engine/metrics-engine supersedes this file handoff on the signal-only path.) - then compute the target via an injectable weight_fn (default: run the named alphas and combine with risk_parity - the estimation-free default, since on short histories the Markowitz tangency chases noise; markowitz / ew selectable); enforce a predictability freshness guard that drops symbols whose order-book metrics are frozen (fewer than 2 distinct values over the last 6 bars of ob__minor__imbalance_top25__mean) - and if every symbol is stale, HOLD (return None) instead of liquidating; optionally rescale to a target_leverage gross when > 0; apply execution smoothing toward the current marked book by at most smooth_delta weight per symbol per bar (live mirror of the backtest's cap smoothing; empty targets still wind down at the same rate); then reconcile/mark prices, run the risk check, rebalance via the executor, re-reconcile, and persist state. Semantics: None from the weight function means "no opinion this bar - HOLD the current book" and never trades; an explicit (possibly empty) Series is a real target (an empty one flattens every position); the two cases SHALL stay distinct so warm-up or degenerate input cannot accidentally flatten a live book. A failing bar SHALL be non-fatal for the trader: LiveTrader.run wraps each bar in a catch-all, logs LiveTrader.step failed at <bar>, and continues the loop - an exception in the weight function or executor never kills the loop (state is simply not persisted for that bar).

    Scenario: Stale-book freshness guard¶

    • WHEN a symbol's orderbook metric is identical across the last 6 bars (dead depth stream)
    • THEN the symbol is dropped from the target; if every symbol is stale the loop holds the book

    Scenario: HOLD vs flatten¶

    • WHEN the combiner is degenerate during warm-up
    • THEN the weight function returns None (hold the book) rather than an empty target that would liquidate every position

    Scenario: Execution smoothing¶

    • WHEN the target moves by more than smooth_delta per symbol
    • THEN the executor receives only the clipped step toward the target (except the kill-switch flatten path, which bypasses smoothing because safety exits must be immediate)

    Requirement: Risk guard¶

    Every target weight vector SHALL pass through RiskGuard.check before execution, failing safe toward less risk: non-finite weights SHALL be scrubbed to 0; |w_i| SHALL be clipped to max_per_symbol_pct (0.05); the gross sum|w| SHALL be scaled down to max_total_leverage (1.0) when over; net exposure beyond max_net_exposure (0.20) SHALL be recorded as a warning (not corrected); rebalance within min_rebalance_seconds SHALL return a "held" decision that keeps the current actual weights (the knob defaults to 0.0, i.e. the rate limit is disabled unless explicitly configured); and a daily drawdown breaching max_daily_drawdown_pct (0.02) SHALL LATCH a kill-switch: from then on every check returns an all-zero flatten target until manually reset() - and the latch SHALL be re-applied from persisted state on restart (latch()), so a crash cannot silently re-arm trading inside a losing day. NAV SHALL be the smaller of the blotter's equity and max_nav_usd (default 200.0) passed to the executor.

    Scenario: Kill-switch lattice¶

    • WHEN the daily drawdown breaches the threshold
    • THEN the kill-switch latches and every later check returns a flat target until an operator resets it

    Scenario: Rate-limited hold¶

    • WHEN two rebalances land within min_rebalance_seconds
    • THEN the second is a held decision that trades nothing

    Requirement: Execution layer¶

    The system SHALL trade each target vector through an OrderExecutor that diffs target quantity against the blotter's current quantity and trades only the difference, skipping dust below min_notional_usd (default 5.0). target_quantities(weights, prices, nav) SHALL map missing/invalid prices or NaN weights to 0.0. PaperExecutor SHALL model fills at price * (1 +- slippage_bps / 1e4) charged against trade direction (default 1.0 bps) plus a fee of |delta| * fill_price * fee_rate (default 1.6 bps), mirroring the backtest cost model so paper PnL tracks the backtest net PnL; its reconcile SHALL be a no-op (the paper blotter is authoritative). The real BinanceFuturesExecutor SHALL be testnet-by-default (testnet.binancefuture.com unless testnet=False), SIGNED by signed REST with timestamp + recvWindow + HMAC-SHA256, round quantities DOWN to the symbol's step size with a min-notional check before sending, rebalance only the delta between the exchange's reported position and the target (a restart reconciles rather than double-trades), and its reconcile SHALL overwrite the blotter from the venue's real positions/equity each bar so ambiguous order states self-correct. Until the first successful account mirror (_reconciled_once), rebalance SHALL return no orders rather than size a restart book off the blank initial snapshot. Positions whose symbol vanished from the universe SHALL be priced from the venue's mark_prices() so their target (0) still values them for closing (orphan guard). Target position notional SHALL be capped to the exchange's tightest leverage bracket for that symbol (max_notional_cap), so thin symbols can never trigger a -2027 "exceeded max position at current leverage" rejection.

    Scenario: Dust skipped¶

    • WHEN the delta for a symbol is below min_notional_usd in notional terms
    • THEN no order is placed for that symbol

    Scenario: Restart reconciliation¶

    • WHEN the executor starts with an already-open venue position
    • THEN it trades only the difference between the venue's position and the target, never re-opening the full position

    Requirement: Position and PnL accounting¶

    LiveBlotter SHALL book every fill with the average-cost method: same-direction fills weight the average entry; reducing, closing, or flipping fills realize PnL on the closed quantity as (exit_price - avg_entry) * closed_qty * direction; a flip leaves the leftover quantity at the open price; fees are non-negative and reduce equity. Equity SHALL be initial_capital + realized + unrealized - total_fees, with unrealized marked from the latest prices. The daily drawdown reference SHALL reset at each UTC date change (roll_day_if_needed), be restored from persisted state on restart (restore_day_reference), and adjust for net wallet transfers so deposits are not profit and withdrawals are not loss. In live-venue mode the exchange is the source of truth: reconcile_from_exchange overwrites positions/marks/equity/wallet/unrealized, WITHOUT corrupting initial_capital (kept as true deposit so PnL stays meaningful). snapshot() SHALL return a plain dict consumed by the dashboard and the state file.

    Scenario: Average-cost entry¶

    • WHEN a position is increased in the same direction
    • THEN the average entry price is recalculated weighted by the new fill; realized PnL is not booked

    Scenario: Flip realized PnL¶

    • WHEN a fill flips a position from long to short
    • THEN realized PnL books on the closed long quantity and the leftover short opens at the fill price

    Requirement: State contract for the dashboard¶

    The system SHALL persist one JSON state file per run, written atomically (temp file + os.replace) once per bar - fills are folded into the same bar's update and there is no fill-triggered write - with the schema: updated_ts, mode, bar_count, last_bar_ts, next_bar_eta_s, parser_last_metric_ts, killed, risk_violations, account (initial/equity/realized/unrealized/total fees/gross/leverage/daily dd/day baseline/n_fills), positions[], target_weights, actual_weights, equity_curve (capped at 5000 points), recent_fills (capped at 200), weight_history (capped at 96 entries). A restart SHALL seed the rolling history from the existing file (so the equity curve and weight tape survive frequent restarts); an unreadable/corrupt file SHALL warn and start empty rather than crash. The file SHALL be read-only for the dashboard process and never written by it.

    Scenario: Restart seeding¶

    • WHEN the trader restarts and a state file exists
    • THEN equity curve, recent fills, and weight history are pre-seeded from the file

    Scenario: Corrupt state file¶

    • WHEN the state file is unreadable at startup
    • THEN the trader warns and continues with empty history instead of crashing

    Requirement: Standalone trader entry¶

    The system SHALL provide an operator entry point (python -m alpha_engine.live.run_trader) with explicit safety-ordered modes --mode paper|testnet|mainnet (paper default, no exchange contact), --bars N offline dry-run over the latest N metric bars instead of waiting on live boundaries, and testnet/mainnet reading API keys from env (BINANCE_API_KEY / BINANCE_API_SECRET). --execution taker|maker SHALL select the rebalance flow: taker uses the base BinanceFuturesExecutor (marketable diff), maker uses MakerFuturesExecutor, which posts post-only GTX limit orders at the touch; the fallback to a market order has three distinct outcomes - a GTX bounce (the venue rejects the limit as crossing or reports status EXPIRED) is repriced and re-posted up to reprice_attempts (default 2) and only then falls back to market; a resting order still unfilled after --maker-wait seconds (default 45) is cancelled and the remainder is sent to market; and if the resting order's final state is unknown after both cancel and re-query fail, the market fallback is deliberately skipped (fail-closed: the order is left for the next reconcile to settle). The standalone trader SHALL drive its BarClock with settlement_seconds = 10.0 (the CLI and BarClock default of 5.0 does not apply here), and in testnet/mainnet live runs the clock SHALL be venue-synced: client.sync_time() is called on startup and a time_source shifts the clock by client.offset_ms(), so bar boundaries align to the venue rather than a drifted host clock (mirroring the BinanceTimeSync contract used on the signal path). On startup the runtime SHALL re-apply persisted safety state, but only when the persisted mode matches the current --mode (safety state never leaks across paper/testnet/mainnet): a previously latched kill-switch SHALL stay latched unless --reset-kill is given, and the persisted day-start drawdown baseline SHALL be restored when it belongs to the current UTC day (a next-day restart deliberately skips the restore, since a stale baseline would corrupt the new day's drawdown reference) - so a crash-restart inside a losing day cannot silently reset the daily kill reference.

    Scenario: Offline dry-run¶

    • WHEN --bars N is given
    • THEN the trader runs over the latest N metric bars without waiting on bar boundaries and without exchange contact

    Scenario: Persisted kill-switch survives restart¶

    • WHEN the trader restarts inside a losing day and the persisted state has killed: true
    • THEN the kill-switch stays latched unless --reset-kill is given, and the day's drawdown baseline is restored so the daily kill can still fire
