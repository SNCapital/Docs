    Live Trading

    Purpose¶

    Defines the live trading runtime of alpha_engine (live/): the CLI entry (main.py live-trade), the component wiring in run_live (tick bus, order book manager, snapshot loops, warm-start reader, bar orchestrator), the UTC-aligned BarClock with exchange drift correction (BinanceTimeSync), the signal-only bar evaluation loop (LiveEngine), and the full trader loop (LiveTrader, LiveGoMetricsReader, RiskGuard, OrderExecutor / PaperExecutor / BinanceFuturesExecutor / MakerFuturesExecutor, LiveBlotter, StateStore) driven by the standalone operator entry python -m alpha_engine.live.run_trader. The main.py path is signal-only by contract: signal_only=True is hard-coded at the CLI and any non-signal-only invocation raises NotImplementedError; real execution is reached only through run_trader.

    Requirements¶

    Requirement: Live CLI contract¶

    The system SHALL expose a live-trade subcommand in the root main.py (and treat a flag-only or empty invocation as live-trade for backwards compatibility) accepting --alphas (nargs+, choices from ALPHA_REGISTRY, default trade_imbalance), --symbols (nargs+, default None meaning the parser's configured SYMBOLS, which is ["BTCUSDT", "ETHUSDT"]), --bar-minutes (default 30), --settlement-seconds (default 5.0), --lookback-days (default 30), --max-w (default 0.03), --end-range (default 50), --market (spot|usdm, default spot), --no-order-book, --snapshot-interval-ms (default None), --data-root (default None, resolved to the data/ directory that sits next to binance_parser/, NOT a CWD-relative path), and --log-level (default INFO; an unrecognised level name falls back to INFO rather than erroring). Symbols SHALL be accepted either as repeated arguments or as a single comma-separated string (parse_symbols), and SHALL be uppercased. The invocation SHALL always run in signal-only mode (Phase 1): no flag exposes execution and run_live(signal_only=False) SHALL raise NotImplementedError. KeyboardInterrupt SHALL print [Main] Stopped. and exit with status 0. The heavy parser imports SHALL be deferred into _run_live so --help does not pull parser dependencies.

    Scenario: Default invocation¶

    • WHEN python main.py is run with no subcommand
    • THEN it behaves as live-trade with defaults (spot, trade_imbalance, 30-minute bars)

    Scenario: Execution mode not implemented¶

    • WHEN run_live is called with signal_only=False
    • THEN it raises NotImplementedError (Phases ¾)

    Scenario: Operator interrupt¶

    • WHEN the operator sends Ctrl-C to a running live-trade
    • THEN the process prints [Main] Stopped. and exits 0 instead of dumping a traceback

    Requirement: Live service wiring¶

    The system SHALL compose the live runtime in run_live in a fixed order: reject non-signal-only mode; uppercase the symbols; resolve the venue tag (spot -> "binance", usdm -> "binance-f", falling back to the raw market string for an unknown market); build a LiveTickBus and attach a FileWriter sink with exclude_types={"booksnapshot"}; create a single shared HealthCounters that is passed to the OrderBookManager, the WS listener and BinanceTimeSync; build the OrderBookManager only when enable_order_book is true; register an OrderBookUpdatesAggregator as a diff observer when the book is enabled; build LiveRawDataReader with max_lookback_days = lookback_days + 30; warm-start it from parquet under the resolved data root; construct LiveEngineConfig + LiveEngine, a BinanceTimeSync for the market, and a BarClock using bar_minutes and the config's settlement_seconds with time_source=time_sync.now; run the parser's pre-flight symbol validation; print a banner; subscribe the reader to the bus with the publish-edge event filter; then start every long-running task inside one asyncio.TaskGroup.

    The task set SHALL be: file writer, time-sync poller, WS listener, and - only when the book is enabled - the order book manager, its watchdog loop, the order-book parquet snapshot loop and the order-book bus snapshot loop; plus the reader consumer and the engine. The parquet snapshot loop SHALL use --snapshot-interval-ms when given and otherwise the parser's LIVE_ORDERBOOK_SNAPSHOT_INTERVAL_MS (1_800_000 ms = 30 minutes, UTC-aligned), and SHALL be skipped entirely when that effective value is <= 0. The bus snapshot loop SHALL use the parser's LIVE_ORDERBOOK_BUS_INTERVAL_MS (1_000 ms = 1 Hz) only - --snapshot-interval-ms does NOT override it - and SHALL be skipped when that value is <= 0. Both loops sleep to the next epoch-aligned tick, floor the interval at 0.01 s, and snapshot only books that report is_ready(); the parquet loop writes straight to the FileWriter (bypassing the bus) while the bus loop writes to the bus, whose FileWriter sink excludes booksnapshot, so the 1 Hz stream never lands on disk. The bus snapshot loop SHALL keep running because it is the only live source that populates the reader's orderbook deque.

    Warm-start SHALL be best effort: a data root that does not exist logs a warning and continues with no warm-start; a successful bootstrap logs the buffer count and total row count and logs an extra warning when 0 rows were loaded; any exception during bootstrap is logged with a traceback and the reader proceeds with empty deques. The OrderBookUpdatesAggregator registration SHALL only keep per-bar diff counters running - nothing consumes flush_for_bar yet, so its metrics do not reach strategies (TODO NSC-48). Because all tasks share one TaskGroup, an unhandled exception in any task SHALL cancel the whole runtime rather than leave a partially-live system.

    Scenario: Warm-start failure¶

    • WHEN the warm-start bootstrap raises or finds no rows under the data root
    • THEN the runtime logs the failure or a 0-row warning and starts with empty deques rather than aborting

    Scenario: Book disabled¶

    • WHEN --no-order-book is given
    • THEN no OrderBookManager, watchdog, snapshot loops, or diff-observer are created

    Scenario: Snapshot interval override scope¶

    • WHEN --snapshot-interval-ms 0 is given
    • THEN the parquet snapshot loop is not started while the 1 Hz bus snapshot loop still runs at LIVE_ORDERBOOK_BUS_INTERVAL_MS

    Scenario: Soft pre-flight validation¶

    • WHEN the parser's _validate_symbols finds a symbol that is not TRADING, or the exchangeInfo request fails
    • THEN it prints a warning and the runtime proceeds anyway - validation never aborts the run

    Requirement: Live tick bus¶

    The system SHALL fan out every parser event through LiveTickBus, which implements the same write(market, record) contract as the parser's FileWriter so it can serve as the WS listener's writer and as a snapshot-loop writer. Every written event SHALL be offered to each subscriber (one asyncio.Queue each) and then awaited inline on every attached sink, so sinks share the listener's backpressure. Backpressure toward subscribers SHALL be lossy: a subscriber whose queue is full (default 10,000 events, DEFAULT_QUEUE_SIZE) SHALL drop the event, increment its dropped counter, and log a warning only when the drop count is a power of two, while the other subscribers still receive the event. A subscription SHALL optionally restrict event_types at the publish edge so high-rate streams (e.g. raw orderbook diffs) never consume queue slots; events rejected by that filter SHALL NOT count as drops. Sinks SHALL support exclude_types (canonical use: booksnapshot excluded from the parquet writer because the dedicated snapshot loop writes parquet snapshots at a different cadence). The live reader's subscription SHALL be filtered to aggtrades, klines, booksnapshot, funding, markprice, forceorder, trades, deliberately excluding raw orderbook diffs. write SHALL be a no-op once the bus is closed; close() SHALL push a sentinel into every subscription so iteration exits cleanly; flush() SHALL forward to sinks only; start() SHALL be an idle keep-alive loop so a caller can spawn it as a task; and the bus SHALL expose subscriber_count and total_dropped for diagnostics.

    Scenario: Slow subscriber drop¶

    • WHEN a subscriber's queue fills
    • THEN the event is dropped for that subscriber only, the drop counter increments, and a warning is logged only on power-of-two drop counts

    Scenario: Publish-edge filter¶

    • WHEN a subscription specifies event_types
    • THEN events outside the set are not enqueued and are not counted as drops, saving queue slots for the events that matter

    Requirement: Bar clock and time synchronization¶

    BarClock SHALL yield one pd.Timestamp per UTC-aligned bar boundary, strictly after the current time, computed as base + (floor(minutes_into_hour / bar_minutes) + 1) * bar_minutes where minutes_into_hour includes the sub-minute fraction and base is the current hour truncated to minute zero; each yield SHALL be delayed by settlement_seconds (default 5.0) past the boundary so the WS can deliver the last ticks of the just-closed bar, and the sleep SHALL be skipped when the computed wake time is already in the past. bar_minutes <= 0 or settlement_seconds < 0 SHALL raise ValueError. The clock SHALL accept an injectable time_source (default datetime.now(timezone.utc)) so boundaries align to the exchange even on a host with a skewed clock, and it SHALL re-read time_source after computing the boundary so an injected offset is honoured. FakeBarClock SHALL exist as the test harness that yields whatever tick(ts) supplies and stops on close().

    BinanceTimeSync SHALL poll the exchange server-time endpoint every poll_interval_sec (default 60) inside a single aiohttp.ClientSession (/api/v3/time on spot base https://api.binance.com, /fapi/v1/time on USD-M base https://fapi.binance.com, 5-second total request timeout), timestamp local time at request start and end and use the midpoint as the local reference, then feed server - local_mid into an EWMA with alpha = 0.3 - except that the FIRST sample is adopted verbatim (no smoothing). It SHALL expose offset_ms() (integer-truncated), now_ms(), now(), has_sample and n_samples. Until the first sample the offset SHALL be 0 (fall back to the local clock); a poll failure SHALL log a warning, return None and keep the previous EWMA rather than resetting. The smoothed absolute drift SHALL be compared against thresholds: over 500 ms (WARN_DRIFT_MS) logs a warning; over 2000 ms (ERROR_DRIFT_MS) logs an error AND calls HealthCounters.record_clock_drift() on the shared counters. Construction SHALL raise ValueError for an unknown market or a non-positive poll interval.

    Scenario: Settlement delay¶

    • WHEN a bar boundary is reached
    • THEN the clock sleeps settlement_seconds past the boundary before yielding the bar timestamp

    Scenario: Cold-start clock¶

    • WHEN no server-time sample has landed yet
    • THEN BinanceTimeSync.now() falls back to the local clock unchanged, and the engine still starts immediately

    Scenario: Transient poll failure¶

    • WHEN a server-time request raises
    • THEN a warning is logged, sample_once returns None, and the previously smoothed offset is retained instead of being reset to 0

    Requirement: Live raw data reader¶

    LiveRawDataReader SHALL serve the RawDataReader contract (DataFrame views over [since, until], inclusive at both ends, with the same column normalization as the parquet reader) from rolling in-memory deques keyed by (exchange, kind, ticker), fed from a bus subscription tagged with the venue's exchange at consume(...) time. Event routing SHALL be fixed: aggtrades -> trades rows carrying timestamp, price, size, side, agg_id, first_trade_id, last_trade_id; raw trades -> trades_raw (with trade_id) only when the parser flag LIVE_RECONSTRUCT_MULTILEVEL is true, otherwise dropped to prevent double-counting - and if the parser package is not importable the flag SHALL be treated as false with a debug log; forceorder -> liquidations rows (timestamp, side, size from orig_qty, price); klines -> klines rows keyed by open_time with a derived volume_usd = close * volume, and only when the kline is closed; booksnapshot -> long-form orderbook rows, one per bid and ask level at the snapshot timestamp with full depth preserved; funding -> realized_funding only, timestamped by funding_time_ms (the REST row's mark_price is deliberately dropped as a settlement-time snapshot); markprice -> mark_price, index_price, predicted_funding, next_funding_time_ms; and raw orderbook diff updates SHALL be ignored. bootstrap_from SHALL seed the deques from prior parquets for the kinds trades, trades_raw, orderbook, klines, funding, markprice, liquidations, defaulting until to now and since to until - max_lookback.

    Eviction SHALL be lazy and two-tiered: read() drops leading rows older than since - eviction_grace (grace default 1 day, no per-kind override on this path), and a periodic global _evict_all runs once evict_every_n_events (default 10,000) rows have accumulated - the counter advances by len(rows) per event, so one full-depth booksnapshot counts as hundreds of rows, not one event - using the per-kind cutoff now - lookback - grace, where KIND_LOOKBACK_OVERRIDES gives orderbook a 1-day lookback while every other kind uses max_lookback_days (constructor default 60; the live service passes lookback_days + 30). read() SHALL return None (not an empty frame) when the key is unknown, the deque is empty after eviction, or the rows carry no timestamp column, and SHALL tz-localize naive timestamps to UTC before slicing. Late-event accounting SHALL count rows whose timestamp is strictly before the last bar passed to mark_bar_processed(bar_ts) (which only ever moves forward), exposing late_events_dropped and logging a warning every late_event_log_every (default 100) additional late rows, so an operator can watch for WS reconnect/load spikes. available_tickers SHALL return the sorted set of tickers seen per (exchange, kind) and buffer_sizes() SHALL expose per-key row counts.

    Scenario: Double-count protection¶

    • WHEN a raw trades event arrives and LIVE_RECONSTRUCT_MULTILEVEL is off
    • THEN it is routed to nothing, keeping the aggregated trades deque aggtrade-only

    Scenario: Orderbook memory bound¶

    • WHEN full-depth booksnapshots accumulate
    • THEN the periodic eviction bounds the orderbook deque by a 1-day window while cheaper kinds keep the general lookback window

    Scenario: Late event accounting¶

    • WHEN an event's timestamp is strictly before the last bar the engine has processed
    • THEN it is counted as late and logged every 100 further late rows, not silently mixed into the wrong bar

    Scenario: Unknown key read¶

    • WHEN an aggregator reads a (exchange, kind, ticker) triple that has never been seen
    • THEN read returns None rather than an empty DataFrame

    Requirement: Bar boundary evaluation (signal engine)¶

    LiveEngine SHALL run once per bar: build an ExchangeData view over [bar_ts - lookback_days, bar_ts] via the live reader, run all configured strategies through run_strategies (which itself skips any strategy whose required_kinds are not backed by data, logging a warning), take the latest weight row at or before bar_ts per strategy, then combine - a single surviving strategy passes through as a copy; multiple strategies are blended equal-weight across the sorted union of tickers with missing tickers filled as 0 (PnL-driven Markowitz is deferred). It SHALL then, in order, append (bar_ts, combined) to weights_history, increment bar_count, call reader.mark_bar_processed(bar_ts), and log the bar summary (bar timestamp, bar number, strategy count, gross, non-zero count, cumulative late-event count) - the weight vector itself is never logged - and return the combined Series.

    Failure handling SHALL be narrow by design: only the run_strategies call is wrapped, so a strategy exception logs and returns None, and a bar where no strategy produced a usable row logs and returns None. In both None cases bar_count, weights_history and mark_bar_processed SHALL be left untouched. LiveEngine.run SHALL simply iterate the bar clock and await step, with NO catch-all - an exception raised outside run_strategies (e.g. in the blend) propagates and, via the shared TaskGroup, tears the runtime down. LiveEngineConfig defaults SHALL be exchanges=["binance", "binance-f"], max_w=0.03, end_range=50, lookback_days=30, settlement_seconds=5.0.

    Scenario: Multiple strategies blend¶

    • WHEN two or more strategies produce weights for a bar
    • THEN the target is the equal-weight average of their latest rows across the union of tickers

    Scenario: Strategy failure is not fatal¶

    • WHEN run_strategies raises at a bar
    • THEN the bar logs the exception, returns None, and neither the bar counter nor the late-event boundary advances; the loop keeps running

    Requirement: Go metrics window reader for the trader¶

    LiveGoMetricsReader SHALL serve the trader a GoExchangeData over [bar_ts - lookback_days, bar_ts] built from the Go parser's market=<market>/type=metrics parquet (market default usdm), by default rebuilding a GoMetricsStore per bar. Disk caching SHALL default to OFF (cache_dir=None) because the store's cache key contains the moving (since, until) window, so a live cache never hits while rewriting most frames per bar. preload_window(since, until) SHALL load one store for a whole offline run; subsequent exchange_data calls whose window falls inside the preloaded range SHALL be served as a _SlicedExchangeData view that truncates every frame to [since, until] (so frame.iloc[-1] lands on the bar with no look-ahead), while any window outside the preloaded range SHALL fall back to building a fresh store. latest_metric_ts() SHALL scan dt= partitions newest-first, skip empty days with only a directory glob, return the max ts of the first populated day as a UTC timestamp, log a warning and skip a day whose shards are unreadable, and return None when no metrics exist. The result SHALL be cached after the first successful scan and never refreshed for the rest of the process - correct for offline dry-runs where the newest on-disk bar does not move, but in a live run the dashboard's parser_last_metric_ts reflects the state at first call, not the newest bar.

    Scenario: Offline preload¶

    • WHEN preload_window has covered the run and the trader asks for a bar inside it
    • THEN the reader returns a cheap in-memory sliced view instead of re-reading the lake

    Scenario: Unreadable metrics day¶

    • WHEN the newest populated dt= partition has a corrupt shard
    • THEN latest_metric_ts logs a warning and continues to the next-older day instead of raising

    Requirement: Trader bar loop¶

    LiveTrader.step SHALL run the full round-trip bar: read the metrics window from LiveGoMetricsReader, compute the target via an injectable weight_fn, resolve prices, reconcile, risk-check, trade, re-reconcile and persist state, in that order.

    make_portfolio_weight_fn SHALL be the default weight function: run the named alphas via run_strategies (returning None when no strategy ran); pass a single strategy through; for multiple strategies call combine_strategies with prices taken from the hard-coded data["binance-f"]["mark_price"] frame (NOT TraderConfig.price_key), method=combine (default risk_parity - the estimation-free default, since on short histories the Markowitz tangency chases noise; markowitz and ew are the other choices) and lookback=mk_lookback_bars (default 48 * 30 bars). Only ValueError and numpy.linalg.LinAlgError from the combiner SHALL be caught, logged and turned into a HOLD (None); any other exception propagates. It SHALL then take the last row at or before bar_ts, dropna() it, and return None if empty. A predictability freshness guard SHALL then drop symbols whose order-book metrics are frozen - fewer than 2 distinct values over the last 6 bars of ob__minor__imbalance_top25__mean on the binance-f frame - and if the lookup itself fails or the recent window is empty the guard SHALL be skipped entirely (every symbol kept); if every symbol is stale it SHALL log and HOLD (None) instead of emitting an empty target that would liquidate the book. Only after the guard SHALL target_leverage > 0 rescale the book so sum|w| == target_leverage.

    step SHALL treat None as "no opinion this bar - HOLD the current book": the target becomes an empty Series, no rebalance is issued, and the log line is suffixed HOLD; an explicit (possibly empty) Series is a real target and an empty one flattens every position - the two cases SHALL stay distinct so warm-up or degenerate input cannot accidentally flatten a live book. Prices SHALL be taken from the last row of data["binance-f"][price_key] (TraderConfig.price_key, default mark_price) over the union of that row's index, the target index and the currently held symbols, keeping only finite strictly-positive values. executor.reconcile SHALL run BEFORE the risk check so equity, positions and daily drawdown reflect venue reality, and again after trading so an ambiguous fill self-corrects before the snapshot is persisted; mark_to_market follows each reconcile. Trading SHALL happen only when the price map is non-empty: a latched kill-switch rebalances toward an empty target (an immediate flatten that bypasses smoothing), otherwise a decision that is neither held nor a HOLD rebalances toward _smooth_toward(decision.approved_weights, prices). Execution smoothing SHALL move from the blotter's current marked weights toward the approved target by at most smooth_delta (TraderConfig.smooth_delta, default 0.005, 0/None disables) per symbol per bar, dropping exactly-zero entries from the result; an empty target still winds down at the same rate. step SHALL then increment bar_count, record the fills, and write the state file with decision.approved_weights as target_weights and reader.latest_metric_ts() as parser_last_metric_ts. LiveTrader.run SHALL wrap each bar in a catch-all that logs LiveTrader.step failed at <bar> and continues, so an exception in the weight function, executor, reconcile or state write never kills the loop (state is simply not persisted for that bar).

    Scenario: Stale-book freshness guard¶

    • WHEN a symbol's ob__minor__imbalance_top25__mean is identical across the last 6 bars (dead depth stream)
    • THEN the symbol is dropped from the target before leverage scaling; if every symbol is stale the loop holds the book

    Scenario: HOLD vs flatten¶

    • WHEN the combiner is degenerate during warm-up and raises ValueError or LinAlgError
    • THEN the weight function returns None (hold the book) rather than an empty target that would liquidate every position

    Scenario: Execution smoothing¶

    • WHEN the target moves by more than smooth_delta per symbol
    • THEN the executor receives only the clipped step toward the target (except the kill-switch flatten path, which bypasses smoothing because safety exits must be immediate)

    Scenario: No usable prices¶

    • WHEN the price frame yields no finite positive price for the bar
    • THEN no rebalance is attempted at all, yet the bar is still counted and the state file is still written

    Requirement: Risk guard¶

    Every target weight vector SHALL pass through RiskGuard.check before execution, failing safe toward less risk and in this order: roll the blotter's day reference when ts is given; return a flat, nav_usd=0.0, killed=True decision if the kill-switch is already latched; latch the kill-switch and return the same flat decision when blotter.daily_drawdown() <= -abs(max_daily_drawdown_pct) (0.02); return a held decision carrying the blotter's current actual weights reindexed onto the target's index when min_rebalance_seconds > 0 and the previous rebalance was more recent than that (the knob defaults to 0.0, i.e. the rate limit is disabled unless explicitly configured); then scrub non-finite weights to 0; clip |w_i| to max_per_symbol_pct (0.05); scale the whole vector down when gross sum|w| exceeds max_total_leverage (1.0); and record - without correcting - a violation when |sum w| exceeds max_net_exposure (0.20). NAV SHALL be min(blotter.equity, max_nav_usd) (default 200.0) and is 0.0 on both kill paths. _last_rebalance_ts SHALL be updated at the end of any non-kill, non-held check where ts was supplied, whether or not trading actually follows. Every applied correction SHALL append a human-readable string to RiskDecision.violations, which the state file publishes. The kill-switch SHALL latch permanently until reset() is called by an operator, and SHALL be re-appliable from persisted state on restart via latch(), so a crash cannot silently re-arm trading inside a losing day.

    Scenario: Kill-switch latch¶

    • WHEN the daily drawdown breaches the threshold
    • THEN the kill-switch latches and every later check returns a flat target with nav_usd=0.0 until an operator resets it

    Scenario: Rate-limited hold¶

    • WHEN two rebalances land within min_rebalance_seconds and that knob is greater than 0
    • THEN the second is a held decision carrying the current actual weights, so nothing trades

    Requirement: Order sizing and paper execution¶

    The system SHALL express execution through the abstract OrderExecutor, whose rebalance diffs a target against the current book and whose reconcile defaults to a no-op (paper trading has no external venue and its blotter is authoritative). target_quantities(weights, prices, nav) SHALL map each weight to w * nav / price and SHALL yield 0.0 for a None/NaN weight or a missing, non-positive or NaN price. PaperExecutor SHALL mark to market, compute target quantities, walk the sorted union of target symbols and currently held symbols, skip any symbol without a valid positive price (so a held position with no price cannot be closed that bar), and trade only the delta, skipping any delta whose notional is below min_notional_usd (class default 5.0). Fills SHALL be modelled at price * (1 + sign(delta) * slippage_bps / 1e4) (class default 1.0 bps, charged against the trade direction) with a fee of |delta| * fill_price * fee_rate (class default 1.6e-4), mirroring the backtest cost model so paper PnL tracks backtest net PnL. Note that run_trader constructs PaperExecutor from its own CLI defaults (--fee-bps 4.0 -> 4e-4, --slippage-bps 1.0, --min-notional 5.0), so the operator-facing fee default is 4 bps, not the class default.

    Scenario: Dust skipped¶

    • WHEN the delta for a symbol is below min_notional_usd in notional terms
    • THEN no order is placed for that symbol

    Scenario: Unpriced holding¶

    • WHEN a currently held symbol has no valid price in the bar's price map
    • THEN the paper executor skips it entirely rather than filling at a bogus price

    Requirement: Binance USD-M futures client¶

    BinanceFuturesClient SHALL be testnet-by-default: the base URL is https://testnet.binancefuture.com unless testnet=False, which selects https://fapi.binance.com. Signed requests SHALL append timestamp and recvWindow (default 5000) and an HMAC-SHA256 signature over the urlencoded parameters, and SHALL be sent with the X-MBX-APIKEY header; public requests SHALL send no headers. The HTTP transport SHALL be injectable (default requests with a 10-second timeout and raise_for_status, imported lazily) so signing and rebalance logic are testable without a network. The client SHALL keep a venue clock offset: sync_time() samples /fapi/v1/time, RTT-corrects via the request midpoint, warns when the host is more than 1000 ms off, and on failure keeps the previous offset while still backing off; _signed SHALL auto-sync when no explicit time_fn was injected and the last sync is older than SYNC_INTERVAL_S (1800 s). Endpoints SHALL cover /fapi/v2/account, /fapi/v2/positionRisk (non-flat positions only), /fapi/v1/premiumIndex mark prices (unparseable rows warn and are omitted), /fapi/v1/income with incomeType=TRANSFER and limit=1000 for day transfers, /fapi/v1/exchangeInfo filters (step_size, min_qty, min_notional from MIN_NOTIONAL or NOTIONAL, tick_size, qty_precision, price_precision, status), /fapi/v1/leverageBracket (the per-symbol MINIMUM notionalCap, best effort - a failure logs a warning and returns an empty map), POST /fapi/v1/order for MARKET and GTX/GTC LIMIT orders with newOrderRespType=RESULT (so the response carries the final executed qty and average price instead of a bare ACK), GET/DELETE /fapi/v1/order, /fapi/v1/ticker/bookTicker, and /fapi/v1/userTrades. Quantities SHALL be serialised as fixed-point strings because Binance rejects scientific notation, and round_step SHALL round magnitude DOWN to the step while preserving sign.

    Scenario: Testnet by default¶

    • WHEN a client is constructed without testnet=False
    • THEN every request targets testnet.binancefuture.com; mainnet must be chosen explicitly

    Scenario: Clock offset compensation¶

    • WHEN the host clock has drifted and a signed request is about to be sent more than 1800 s after the last sync
    • THEN the client re-syncs against /fapi/v1/time and signs with the offset-corrected timestamp, so orders do not fail with -1021

    Requirement: Real futures execution and reconciliation¶

    BinanceFuturesExecutor SHALL rebalance real USD-M positions toward the target. Until the first successful account mirror (_reconciled_once), rebalance SHALL log a warning and return no orders rather than size a restart book off the blank initial snapshot. It SHALL lazily load exchange filters once (attaching max_notional_cap from the leverage brackets, with a warning when brackets are unavailable), mark to market, and read the venue's signed positions as the source of truth for "current". Positions whose symbol vanished from the universe SHALL be priced from mark_prices() so their target (0) still values them for closing (orphan guard); if that call fails the executor SHALL log an error and leave those positions unmanaged. Per symbol it SHALL skip symbols without a valid price, skip symbols absent from exchangeInfo or whose status is not TRADING, cap the TARGET notional to max_notional_cap so a thin symbol cannot trigger a -2027 "exceeded max position at current leverage" rejection, diff against the venue position, round the delta DOWN to step_size, additionally clamp it to qty_precision decimals when the step size was missing (avoiding -1111), skip a zero delta, and skip any delta whose notional is below max(config.min_notional_usd, filter min_notional). reduce_only SHALL be sent only when reduce_only_on_decrease is enabled and the trade strictly shrinks a same-signed position.

    Order failures SHALL never retry: a -1007/408/timeout body logs a warning and is left for the post-rebalance reconcile (the order may have executed, so a retry risks a double fill); any other error logs at error level; both continue to the next symbol. Fills SHALL be booked from executedQty and avgPrice (falling back to the bar price), with a zero-executed response logged as "order not filled" and left for reconcile. Fees SHALL come from /fapi/v1/userTrades for the order when every commission is paid in a quote asset (USDT, USDC, BUSD, FDUSD), otherwise from the response's fills[] commissions, otherwise estimated as notional * default_fee_rate (4e-4 taker, 2e-4 maker).

    reconcile SHALL overwrite the blotter from one /fapi/v2/account call - positions with entry prices, totalMarginBalance as equity, totalWalletBalance as wallet, totalUnrealizedProfit as unrealized - plus today's net transfers from day_transfers since UTC midnight (a failure there logs a warning and keeps the previous transfer adjustment), and SHALL set _reconciled_once. An account() API error SHALL be swallowed with a warning, keeping local state; but an unparseable positionAmt SHALL log an error and RE-RAISE out of reconcile (rather than silently dropping a live position), which aborts the bar via LiveTrader.run's catch-all and leaves _reconciled_once unchanged. An unparseable entryPrice SHALL warn and fall back to 0.0.

    Scenario: Restart reconciliation¶

    • WHEN the executor starts with an already-open venue position
    • THEN the first rebalance is skipped until reconcile succeeds, after which it trades only the difference between the venue's position and the target, never re-opening the full position

    Scenario: Ambiguous order timeout¶

    • WHEN an order request fails with -1007/timeout
    • THEN the executor logs a warning, does not retry, and lets the post-rebalance reconcile read the venue's real position

    Requirement: Maker (post-only) execution¶

    MakerFuturesExecutor SHALL extend the futures executor by replacing the single market order with a post-only-first flow: price at the touch on our own side (best bid for BUY, best ask for SELL) from bookTicker, rounded DOWN to tick_size and formatted to price_precision, and post a GTX limit. A GTX bounce - the venue rejecting with -5022/"Post Only" or the response reporting status EXPIRED - SHALL be repriced and re-posted up to reprice_attempts (default 2, floored at 1 attempt) and only then fall back to a market order; any other order exception SHALL propagate to the caller's per-symbol error handler. A resting order SHALL be polled every poll_seconds (default 2.0) until its status is one of FILLED, CANCELED, EXPIRED, REJECTED or wait_seconds (default 45.0) elapses, with a failed poll logged and the previous state retained; a still-open order is then cancelled and the remainder sent to market. If the cancel races a fill (-2011) the order SHALL be re-queried; if BOTH the cancel and the re-query fail the final state is unknown and the market fallback SHALL be deliberately skipped (fail-closed - the order is left for the next reconcile to settle). The market fallback SHALL size only qty - executedQty, rounded down to the step, and SHALL be skipped when that remainder is below max(min_notional_usd, filter min_notional). MakerExecConfig SHALL inherit the futures config and default default_fee_rate to 2e-4 (maker).

    Scenario: GTX bounce reprice¶

    • WHEN the venue rejects the post-only limit as crossing, or returns status EXPIRED
    • THEN the executor reprices at the new touch and retries up to reprice_attempts before falling back to a market order

    Scenario: Unknown final state fails closed¶

    • WHEN both the cancel and the follow-up query of a resting maker order fail
    • THEN no market fallback is sent and the order is left for the next reconcile to settle

    Requirement: Position and PnL accounting¶

    LiveBlotter SHALL require a positive initial_capital and book every fill with the average-cost method: same-direction (or from-flat) fills recompute the weighted average entry; reducing, closing, or flipping fills realize (exit_price - avg_entry) * closed_qty * direction on the closed quantity; a position within 1e-15 of zero snaps to flat with a zero entry; a flip leaves the leftover quantity at the fill price. apply_fill SHALL raise ValueError on a negative fee or a NaN quantity/price, SHALL accumulate per-symbol and total fees, SHALL update that symbol's mark to the fill price, and SHALL append to the fill log. mark_to_market SHALL ignore missing, NaN or non-positive prices.

    In paper mode equity SHALL be initial_capital + realized + unrealized - total_fees, with unrealized marked from the latest prices (falling back to the average entry when no mark exists). In live-venue mode the exchange is the source of truth: after reconcile_from_exchange the equity is the venue's margin balance, realized PnL becomes wallet - initial_capital, and unrealized is the venue's figure - all WITHOUT corrupting initial_capital (kept as the true deposit so PnL stays meaningful). Flat or NaN venue positions SHALL be dropped from the mirrored book. Leverage SHALL be gross_exposure / equity, or infinity when equity is non-positive, and actual_weights SHALL return all-zero weights when equity is non-positive. The daily drawdown reference SHALL reset at each UTC date change (roll_day_if_needed, which also zeroes the day's transfers), be restorable from persisted state on restart (restore_day_reference), and adjust for net wallet transfers so deposits are not profit and withdrawals are not loss; the result SHALL be clamped to <= 0 and SHALL be 0.0 when the day reference or the deposit-adjusted base is non-positive. snapshot() SHALL return a plain dict (including day_utc, day_start_equity, n_fills and a per-symbol position table) consumed by the dashboard and the state file.

    Scenario: Average-cost entry¶

    • WHEN a position is increased in the same direction
    • THEN the average entry price is recalculated weighted by the new fill; realized PnL is not booked

    Scenario: Flip realized PnL¶

    • WHEN a fill flips a position from long to short
    • THEN realized PnL books on the closed long quantity and the leftover short opens at the fill price

    Scenario: Deposit-adjusted drawdown¶

    • WHEN a mid-day wallet transfer is mirrored from the venue
    • THEN the daily drawdown nets the transfer out of today's PnL and out of the capital base, so a deposit cannot blind the kill-switch and a withdrawal cannot false-trigger it

    Requirement: State contract for the dashboard¶

    The system SHALL persist one JSON state file per run, written atomically (a temp file created in the same directory, then os.replace; on any failure the temp file is unlinked and the error re-raised) once per bar - fills are folded into the same bar's update via record_fills and there is no fill-triggered write - with the schema: updated_ts, mode, bar_count, last_bar_ts, next_bar_eta_s, parser_last_metric_ts, killed, risk_violations, account (initial_capital/equity/realized_pnl/unrealized_pnl/total_fees/gross_exposure/leverage/ daily_drawdown/day_utc/day_start_equity/n_fills), positions[], target_weights, actual_weights, equity_curve (capped at 5000 points), recent_fills (capped at 200), and weight_history (capped at 96 entries, about 48 h of 30-minute bars). target_weights SHALL be serialised as a dict with NaN and exactly-zero entries removed. The equity-curve and weight-history points SHALL be appended only when bar_ts is not None. The parent directory SHALL be created on construction. JSON SHALL be written with allow_nan=False, so a non-finite value in the snapshot raises rather than emitting invalid JSON. A restart SHALL seed the rolling history from the existing file (so the equity curve, fills tape and weight tape survive frequent restarts); an unreadable or corrupt file SHALL log a warning and start empty rather than crash, and individual malformed history entries SHALL be skipped. StateStore.read SHALL return an empty dict for a missing file. The file SHALL be read-only for the dashboard process and never written by it.

    Scenario: Restart seeding¶

    • WHEN the trader restarts and a state file exists
    • THEN equity curve, recent fills, and weight history are pre-seeded from the file

    Scenario: Corrupt state file¶

    • WHEN the state file is unreadable at startup
    • THEN the trader warns and continues with empty history instead of crashing

    Requirement: Standalone trader entry¶

    The system SHALL provide an operator entry point (python -m alpha_engine.live.run_trader) with explicit safety-ordered modes --mode paper|testnet|mainnet (paper default, no exchange contact; mainnet additionally logs a warning naming the NAV cap, leverage and DD kill), a required repeatable --metrics-root, and these defaults: --market usdm, --symbols "" (comma-separated; empty means all), --alphas book_depth_imbalance (comma-separated), --combine risk_parity (markowitz|risk_parity|ew), --price-key mark_price, --capital 10000.0, --max-nav 200.0, --max-per-symbol 0.05, --max-leverage 1.0, --target-leverage 0.0, --max-daily-dd 0.02, --fee-bps 4.0, --slippage-bps 1.0, --min-notional 5.0, --execution taker, --maker-wait 45.0, --lookback-days 30, --alloc-lookback-days 14, --smooth-delta 0.005 (0 disables), --state-file live_state.json, --reset-kill, --bars 0, --bar-minutes 30, --log-level INFO. The combiner's bar lookback SHALL be derived as alloc_lookback_days * (1440 // bar_minutes). An empty --alphas list SHALL leave weight_fn unset so LiveTrader builds the default one from its config. min_rebalance_seconds SHALL NOT be exposed, so the risk guard's rate limit stays disabled.

    --bars N SHALL run an offline dry-run: anchor on latest_metric_ts() floored to the bar size (exiting with SystemExit when no metrics exist), build the last N bar timestamps, preload the whole window once, step each bar without waiting on boundaries or contacting an exchange, and print a completion line with the final equity and the state-file path. Otherwise the run SHALL be live on a BarClock with settlement_seconds = 10.0 (the CLI and BarClock default of 5.0 does not apply here); when the executor exposes a client with offset_ms (testnet/mainnet), client.sync_time() SHALL be called on startup and a time_source SHALL shift the local clock by client.offset_ms() so bar boundaries align to the venue - in paper mode no client exists and the local clock is used unchanged. --execution SHALL select the rebalance flow: taker uses BinanceFuturesExecutor, maker uses MakerFuturesExecutor with --maker-wait as its rest window. Testnet and mainnet SHALL read BINANCE_API_KEY / BINANCE_API_SECRET from the environment and SHALL exit with SystemExit when either is missing.

    On startup the runtime SHALL re-apply persisted safety state, but only when the persisted mode matches the current --mode (safety state never leaks across paper/testnet/mainnet): a previously latched kill-switch SHALL stay latched with a CRITICAL log unless --reset-kill is given (which logs a warning and re-arms), and the persisted day-start drawdown baseline SHALL be restored only when its day_utc is the current UTC day (a next-day restart deliberately skips the restore, since a stale baseline would corrupt the new day's drawdown reference) - so a crash-restart inside a losing day cannot silently reset the daily kill reference.

    Scenario: Offline dry-run¶

    • WHEN --bars N is given
    • THEN the trader preloads the metrics window once and runs over the latest N metric bars without waiting on bar boundaries and without exchange contact

    Scenario: Persisted kill-switch survives restart¶

    • WHEN the trader restarts inside a losing day and the persisted state has killed: true and the same mode
    • THEN the kill-switch stays latched unless --reset-kill is given, and the day's drawdown baseline is restored so the daily kill can still fire

    Scenario: Missing API credentials¶

    • WHEN --mode testnet or --mode mainnet is used without BINANCE_API_KEY and BINANCE_API_SECRET
    • THEN the process exits with SystemExit before any executor is constructed
