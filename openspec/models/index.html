    Data models

    Purpose¶

    Defines the typed data contracts of binance_parser: market abstraction, live WebSocket DTOs, historical row schemas, REST response DTOs, and the shared rate limiter that all Binance-facing callers rely on.

    Requirements¶

    Requirement: Market abstraction¶

    The system SHALL model a market as one of exactly two values: spot or usdm (USD-M perpetual futures). All venue-specific URLs (WebSocket base, REST base, exchange-info path, depth-snapshot path, history base) SHALL be defined per market in single configuration maps. CLI parsing of a market argument SHALL accept spot, usdm, or both (expands to both markets); any other value SHALL be rejected with an error.

    Scenario: CLI market parsing¶

    • WHEN the market argument is both
    • THEN the system resolves it to the ordered list ["spot", "usdm"]

    Scenario: Invalid market value¶

    • WHEN the market argument is not spot, usdm, or both
    • THEN the system raises a ValueError naming the offending value

    Scenario: Adding a new market¶

    • WHEN a new market value is introduced
    • THEN it requires a corresponding entry in the five venue-specific configuration maps (WebSocket base, REST base, exchange-info path, depth-snapshot path, history base), plus per-market entries in the depth snapshot max-limit and bootstrap-stagger maps (indexed by market at bootstrap time); other REST endpoints (funding, market-stats, margin interest) remain fixed constants outside the maps

    Requirement: Live WebSocket DTOs¶

    The system SHALL deserialize every subscribed Binance stream event into a typed DTO with a fixed pyarrow schema. Every DTO SHALL expose its schema, an event_type identifier, and a row serializer for parquet persistence. All timestamps SHALL be int64 milliseconds; wire-derived timestamps are UTC, and a depth event without a wire timestamp falls back to the local clock, while a mark-price event prefers the event time E over T. Price and quantity columns SHALL be float32, except mark-price fields which SHALL be float64.

    Scenario: Depth diff DTO¶

    • WHEN a @depth payload is parsed
    • THEN it becomes an orderbook event carrying symbol, event timestamp, first/last/previous update ids, and parallel bid/ask price and size lists, and is dispatched to the in-memory book only - never persisted as a row

    Scenario: Depth diff market difference¶

    • WHEN a @depth payload arrives on spot
    • THEN the previous-update id is always null (spot diffs carry no pu), while usdm diffs carry it

    Scenario: Trade DTO¶

    • WHEN a @trade payload is parsed
    • THEN it becomes a trades event with trade id, timestamp, price, quantity, and side (buy when the payload's m flag is falsy, else sell)

    Scenario: AggTrade DTO¶

    • WHEN an @aggTrade payload is parsed
    • THEN it becomes an aggtrades event with aggregate trade id, first/last constituent trade ids, timestamp, price, quantity, and side

    Scenario: Mark price DTO¶

    • WHEN a @markPrice@1s payload is parsed
    • THEN it becomes a markprice event with mark price, index price, predicted funding rate (all float64), and next funding time

    Scenario: Liquidation DTO¶

    • WHEN a @forceOrder payload is parsed
    • THEN it becomes a forceorder event whose fields are read from the nested o object, with the side mapped from uppercase BUY/other to buy/sell

    Scenario: Kline DTO¶

    • WHEN a closed @kline_<interval> payload is parsed
    • THEN it becomes a klines event with open/close times, OHLCV, quote volume, taker-buy volumes, trade count (int32), and closed flag

    Requirement: Stream event dispatch¶

    The system SHALL map a raw stream message to its DTO by substring matching on the stream name, in a fixed precedence order: @depth, then @markPrice, then @aggTrade, then @forceOrder, then @trade, then @kline. Messages whose stream matches none of these SHALL be rejected as unknown (the rejection is a ValueError subclass); a @kline payload whose bar is not yet closed SHALL also be rejected as unknown (running bars are dropped).

    Scenario: Dispatch precedence of force order over trade¶

    • WHEN a stream name contains both @forceOrder and @trade
    • THEN the payload is parsed as a forceorder event, not a trades event

    Scenario: Running kline rejection¶

    • WHEN a @kline payload has its x (closed) flag false
    • THEN the system rejects the message as an unknown running-kline stream and it is not persisted

    Requirement: Historical row schemas¶

    The system SHALL define pyarrow schemas for historical archive rows: klines (11 columns, trades int32), aggTrades, trades, bookTicker, and funding rate. These schemas SHALL be available in a registry keyed by archive data type, and SHALL map to pandas read dtypes for CSV ingestion. All timestamps SHALL be int64 milliseconds UTC; prices and quantities float32.

    Scenario: Schema registry coverage¶

    • WHEN a historical data type is klines, aggTrades, trades, bookTicker, or funding
    • THEN a schema exists for it in the registry

    Scenario: CSV dtype mapping¶

    • WHEN pandas dtypes are derived from a schema for CSV reading
    • THEN bool columns are excluded from the mapping so they are not coerced to object strings during read

    Requirement: Funding rate row¶

    The system SHALL parse REST funding-rate records into a funding row with symbol, funding time (ms), funding rate (float32), and optional mark price (float32, null when absent). The symbol, funding time, and funding rate are required keys in the source payload (accessed with [], so a missing one raises KeyError); only mark price is optional via .get().

    Scenario: Funding row with mark price¶

    • WHEN a REST record contains fundingTime, fundingRate, and markPrice
    • THEN the parsed row carries all four fields and serializes to a single row dict

    Scenario: Funding row without mark price¶

    • WHEN a REST record omits markPrice
    • THEN the parsed row has a null mark price and still serializes successfully

    Requirement: REST exchange metadata DTOs¶

    The system SHALL parse exchange-info payloads into a per-symbol row with symbol, status, contract type, tick size (from PRICE_FILTER), step size (from LOT_SIZE), min notional (from MIN_NOTIONAL, falling back to NOTIONAL variants), max leverage (maximum initialLeverage across leverage brackets), maintenance margin rate (of the lowest bracket), default maker/taker fees, and the full leverage-bracket curve. Missing filters SHALL become NaN; missing brackets SHALL yield zero max leverage, NaN maintenance margin rate, and an empty bracket list. Exchange-info payloads SHALL also be parsed into a simpler ExchangeInfoSymbol DTO (symbol, status, base asset, quote asset, optional contract type - empty for spot) with is_trading and is_perpetual convenience properties, used for the non-persisted exchangeInfo shape.

    Scenario: Spot vs USD-M notional shape¶

    • WHEN the source payload exposes min notional only through the NOTIONAL filter
    • THEN the system falls back to that filter's minNotional and then notional field

    Scenario: No leverage brackets¶

    • WHEN a symbol has no leverage-bracket data
    • THEN its row has max leverage 0, maintenance margin rate NaN, and an empty bracket list

    Requirement: Market-stats REST rows¶

    The system SHALL parse five distinct market-statistics responses into rows with namespaced columns and float64 numeric fields: open interest now, global long/short account ratio, top long/short account ratio, top long/short position ratio, and spot margin daily interest rate. Ratio and quantity strings in responses SHALL be cast to float; column names SHALL be namespaced by the source endpoint so identical concepts from different endpoints do not collide; event types SHALL be distinct from the legacy periodic-metrics event types.

    Scenario: Symbol absent from ratio payloads¶

    • WHEN the global/top long-short payloads do not carry the symbol
    • THEN the caller injects the symbol into the row during parsing

    Scenario: Hourly to daily interest rescale¶

    • WHEN a spot margin payload provides the next hourly interest rate
    • THEN the parsed row stores the rate multiplied by 24 as a daily rate

    Requirement: Legacy periodic futures metrics¶

    The system SHALL parse three /futures/data/ responses (open-interest history, taker long/short ratio, top long/short position ratio) into rows that keep numeric values as strings, with all columns non-nullable: open_interest, taker_ratio, and long_short_ratio events. These SHALL use event types distinct from the market-stats rows and SHALL persist sum_open_interest, sum_open_interest_value, buy_sell_ratio, buy_vol, sell_vol, long_short_ratio, long_account, and short_account as string columns.

    Scenario: Taker ratio symbol injection¶

    • WHEN a taker-ratio payload omits the symbol (Binance does not include it)
    • THEN the fetch helper injects the symbol into the row before parsing

    Scenario: Numeric strings preserved¶

    • WHEN a /futures/data/ response contains a numeric value
    • THEN the row keeps it as its original string representation, never casting to float

    Requirement: Rate limiter¶

    The system SHALL throttle Binance REST requests with token-bucket limiters. A multi-bucket limiter SHALL route each request to the first bucket whose pattern is a substring of the request URL, with an empty-string pattern as the catch-all default; an empty bucket list SHALL be rejected at construction, and a request matching no bucket at all SHALL trip an internal assertion. The canonical USD-M limiter SHALL provide a /futures/data/ bucket of 400 weight per 300 seconds and a default bucket of 2000 weight per 60 seconds. A request costing more than a bucket's capacity SHALL be rejected with an error.

    Scenario: URL-to-bucket routing¶

    • WHEN a request URL contains /futures/data/
    • THEN it is charged to the 400-weight/300-second bucket, and all other URLs to the 2000-weight/60-second bucket

    Scenario: Bucket exhaustion waits¶

    • WHEN a bucket lacks tokens for a request
    • THEN the limiter sleeps until enough tokens refill before releasing the request

    Scenario: Over-capacity cost¶

    • WHEN a request costs more than the target bucket's capacity
    • THEN the limiter raises an error rather than waiting

    Requirement: Rate-limit error semantics¶

    The system SHALL treat HTTP 429 (rate limited) and 418 (IP banned) as rate-limit responses: parse Retry-After from headers (falling back to 60 seconds), and cap consecutive rate-limit waits per REST call at 3.

    Scenario: Retry-After parsing¶

    • WHEN a rate-limit response carries a Retry-After header
    • THEN the system uses that value as the wait duration, defaulting to 60 seconds when absent or malformed
