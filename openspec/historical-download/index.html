    Historical download

    Purpose¶

    Defines the historical bulk-download pipeline of binance_parser: the standalone tools/history.py CLI (download and funding subcommands), per-market file address resolution on the public data archive (data.binance.vision), batch download with checkpoint resume and SHA-256 verification, CSV-to-parquet conversion, and the funding-rate REST backfill.

    Requirements¶

    Requirement: History CLI contract¶

    The system SHALL expose a standalone tool at binance_parser/tools/history.py that boots its own sys.path so it works both as python tools/history.py ... and python -m tools.history ..., owning only the CLI surface while delegating logic to the download service. It SHALL offer a download subcommand with --market (spot|usdm|both, default spot), --group (all|major, default all), --symbols (explicit list that overrides the group), --types (defaults to klines, aggTrades and bookTicker), --months (default 12), --intervals (defaults to 1s and 1m; applied to klines only), --workers (default 8), --dry-run, and -y/--yes. It SHALL offer a funding subcommand with --group (all|major, default major), --symbols, --months, and --dry-run. Symbols passed explicitly SHALL be checked against the static pair list with a warning for unknown ones; without --symbols the group resolves to the major pair list (or all pairs for all).

    Scenario: Default download run¶

    • WHEN python tools/history.py download is run with no flags
    • THEN it resolves the spot market, the all group (all pairs), the default types (klines, aggTrades, bookTicker), the default kline intervals (1s, 1m), and 12 months of lookback, then prepares download entries

    Scenario: Dry-run estimate¶

    • WHEN download is run with --dry-run
    • THEN it prints the estimated file count and exits without any network I/O

    Scenario: Large run confirmation¶

    • WHEN a download resolves to more than 1000 files and -y/--yes was not passed
    • THEN it prompts for confirmation via input() before starting

    Scenario: Unknown symbol warning¶

    • WHEN --symbols contains a symbol outside the static pair list
    • THEN the tool prints a warning naming the unknown symbols

    Requirement: Download address resolution¶

    The system SHALL build one download entry per (market, symbol, data type, period) via the spec builder. Past months SHALL resolve to a single monthly ZIP; the current month SHALL resolve to one daily ZIP per day up to and including today. Klines SHALL be multiplied by the configured intervals; all other data types SHALL be single un-intervaled entries. Address bases SHALL come from the venue map: spot https://data.binance.vision/data/spot, usdm https://data.binance.vision/data/futures/um. Interval filenames SHALL omit the data type (BTCUSDT-1m-2024-03.zip); un-intervaled filenames SHALL be SYM-{data_type}-{period}.zip. Every ZIP SHALL have a sibling .CHECKSUM address.

    Scenario: Monthly archive file¶

    • WHEN a spot klines entry targets a past month for BTCUSDT with interval 1m
    • THEN the address is https://data.binance.vision/data/spot/monthly/klines/BTCUSDT/1m/BTCUSDT-1m-2024-03.zip with sibling BTCUSDT-1m-2024-03.zip.CHECKSUM

    Scenario: Daily archive file¶

    • WHEN a usdm aggTrades entry targets a day in the current month
    • THEN the address is https://data.binance.vision/data/futures/um/daily/aggTrades/BTCUSDT/BTCUSDT-aggTrades-2024-03-01.zip

    Scenario: Kline intervals only¶

    • WHEN a non-klines data type (aggTrades, bookTicker, trades) entry is built
    • THEN it carries no interval and its filename has no interval segment

    Requirement: Download, verification, and conversion loop¶

    The system SHALL download entries concurrently with a worker pool, skipping any entry whose output parquet already exists. Each ZIP SHALL be fetched together with its sibling .CHECKSUM file and verified with SHA-256. A 404 for the ZIP SHALL return no path (the file is not on the archive); the batch loop SHALL count it as a failed entry (there is no separate not-found counter). A checksum fetch that raises (connection error or timeout) SHALL log a warning and proceed WITHOUT verification (a documented trade-off); a non-200 checksum response (e.g. a 404 on the .CHECKSUM itself) SHALL be treated silently as unavailable and verification SHALL be skipped without a log. A checksum mismatch SHALL retry the entry, and after three failed attempts SHALL log it as failed. The CSV SHALL be parsed from the first .csv inside the ZIP with fixed column names per data type (12 for klines including the ignore column; 7 for aggTrades; 7 for trades; 7 for bookTicker), cast to the anchored parquet schema, and written atomically; schema-less fallback writing SHALL be unreachable because all four data types have schemas. Columns absent from the anchored schema (such as ignore) SHALL be dropped.

    Scenario: Existing output skipped¶

    • WHEN the output parquet path already exists
    • THEN the entry is resolved without any network I/O and counted as done (only entries already recorded in the checkpoint are counted as skipped on a resumed run)

    Scenario: Checksum mismatch retry¶

    • WHEN the downloaded binary does not match its checksum
    • THEN the entry is downloaded again, and after three failed attempts it is logged as failed and counted as a failure

    Scenario: Missing archive file¶

    • WHEN the archive returns 404 for a ZIP
    • THEN the entry logs the not-found at debug level and returns no path; the batch loop counts it in the failure counter (there is no separate not-found counter)

    Scenario: Checksum fetch unavailable¶

    • WHEN the sibling .CHECKSUM fetch raises a connection error or times out
    • THEN the system warns and writes the parquet without verification
    • AND WHEN a checksum request returns a non-200 status (e.g. 404)
    • THEN no log is emitted at all and the parquet is written unverified

    Requirement: Checkpoint and resume¶

    The system SHALL persist a checkpoint JSON file listing the URLs of successfully downloaded entries after every 50 successful downloads and again on shutdown; on restart it SHALL skip already-done URLs. The checkpoint SHALL live at the data root as .download_checkpoint.json, keyed by full URL so spot and usdm entries do not collide. A corrupt or unreadable checkpoint SHALL log a warning, rename the file to a .corrupt sibling, and start over. SIGINT SHALL trigger a graceful shutdown: remaining tasks are canceled, already-finished results are checkpointed, a final checkpoint is saved, and a later invocation resumes.

    Scenario: Interrupted run resumes¶

    • WHEN a download run is interrupted with Ctrl+C and restarted
    • THEN previously completed URLs are skipped and the run continues from the checkpoint

    Scenario: Corrupt checkpoint¶

    • WHEN the checkpoint file cannot be parsed
    • THEN the system warns, renames/resets it, and redownloads from scratch without crashing

    Requirement: Funding-rate REST backfill¶

    The funding subcommand SHALL backfill USD-M funding rates from the REST API for the resolved symbol set over the requested months, paginating with a fixed page size and an exclusive cursor (last funding time + 1). Pagination SHALL stop when a page is shorter than the page size or when the cursor passes the requested end; a non-advancing cursor SHALL break the loop instead of looping forever. Rows SHALL be bucketed by UTC day and written as part-backfill.parquet per (day, symbol) under type=funding. Rate-limit responses SHALL be honored via Retry-After, and transient errors SHALL use a bounded backoff. A --dry-run run SHALL print an estimated row count (about 3 rows per symbol per month) and exit.

    Scenario: Funding dry-run¶

    • WHEN funding runs with --dry-run
    • THEN it prints an estimated row count (roughly months times 3 rows per symbol) and exits without requests

    Scenario: Non-advancing pagination cursor¶

    • WHEN a funding page returns data that does not advance the cursor
    • THEN the backfill breaks out of the loop instead of continuing forever

    Scenario: Partial last page¶

    • WHEN a page returns fewer rows than the page size
    • THEN pagination stops because that was the last available funding rate

    Requirement: Output layout and request policy¶

    The system SHALL write parquet under the data root with the partitioned layout market={market}/type={data_type}/dt={YYYY-MM-DD}/symbol={SYM}/part-{granularity}[-{interval}].parquet, where the granularity is monthly or daily and the interval suffix appears for klines only; month-long entries SHALL use dt=YYYY-MM-01. Each entry SHALL be attempted at most three times with an effective backoff of 2 then 5 seconds, the third attempt being terminal (the 15-second value from the shared backoff constant is unused). The pipeline SHALL depend on aiohttp for downloads, pandas/pyarrow for CSV-to-parquet conversion, and the stdlib hashlib/zipfile for verification and unpacking (no aiofiles).

    Scenario: Monthly dt bucket¶

    • WHEN a monthly entry is written
    • THEN its path uses dt=YYYY-MM-01 and a part name of part-monthly (or part-monthly-1m for klines)

    Scenario: Daily part naming¶

    • WHEN a daily klines entry for interval 1m is written
    • THEN its parquet part name includes the interval (part-daily-1m.parquet)
