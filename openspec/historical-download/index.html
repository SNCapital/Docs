    Historical download

    Purpose¶

    Defines the historical bulk-download pipeline of binance_parser: the history CLI entry point, per-market endpoint address resolution, klines and aggTrades download loops, pagination and size limits, HTTP retry and rate-limit behavior, deduplication, and row-level schema mapping. It covers the classical CLI (binance_parser/main.py history) and the one-shot tool (binance_parser/tools/history.py).

    Requirements¶

    Requirement: History CLI contract¶

    The system SHALL expose a history subcommand accepting --market (spot|usdm|both, default spot) and --symbols (comma-separated, default BTCUSDT and ETHUSDT), with support for fetching both klines and aggTrades data types. The download SHALL proceed until end-of-history and SHALL be resumable.

    Scenario: Default history run¶

    • WHEN the history command is run with no flags
    • THEN it downloads spot klines for BTCUSDT and ETHUSDT

    Scenario: Resume after interruption¶

    • WHEN a history run is interrupted and restarted
    • THEN it resumes from where it stopped rather than re-downloading from the start

    Requirement: Endpoint address resolution¶

    The system SHALL resolve klines and aggTrades base URLs per market from the model's venue maps: spot history base https://data-api.binance.vision/, spot market history path data/spot/daily/, usdm history base https://data.binance.vision/, usdm market history path data/futures/usdt/daily/. The resulting download URLs SHALL take the form <base><market-path><data-type>/<SYMBOL>/<SYMBOL>-<data-type>-<date>.zip, where dates are the earliest end-date start and walk backward.

    Scenario: Resolved spot URL shape¶

    • WHEN a spot klines URL is resolved for BTCUSDT on 2024-03-01
    • THEN the URL is https://data-api.binance.vision/data/spot/daily/klines/BTCUSDT/BTCUSDT-klines-2024-03-01.zip

    Scenario: Resolved usdm URL shape¶

    • WHEN a usdm aggTrades URL is resolved for ETHUSDT on 2024-03-01
    • THEN the URL is https://data.binance.vision/data/futures/usdt/daily/aggTrades/ETHUSDT/ETHUSDT-aggTrades-2024-03-01.zip

    Requirement: Klines download loop¶

    The system SHALL download klines day by day with adjustable lookback. Each daily file SHALL be zipped with a CSV of rows (open time, open, high, low, close, volume, close time, quote volume, count, taker buy volume, taker buy quote volume, ignore), deduplicated by open time, and written as parquet in data/market={m}/type=klines/dt=YYYY-MM-DD/symbol={SYM}/part-*.parquet. The loop SHALL stop at the earliest date before the current date (end-of-history detection) and SHALL print a log line per successfully written day.

    Scenario: Daily file dedup¶

    • WHEN a daily klines file contains duplicate open times
    • THEN duplicates are removed before writing

    Scenario: End-of-history stop¶

    • WHEN the loop reaches the earliest available date
    • THEN it stops and reports completion

    Requirement: AggTrades download loop¶

    The system SHALL download aggTrades day by day with a hard cap of 100,000 rows per day. When a day exceeds the cap, the system SHALL fall back to the REST API for the whole day (with native pagination and 1000-row pages), and when the REST fallback also exceeds the 100,000 cap, the day SHALL be split into hour ranges and downloaded per hour. Each daily file SHALL be deduplicated by aggregate trade id, converted row-wise from the CSV to the schema's aggTrades column set, and written as parquet in data/market={m}/type=aggTrades/dt=YYYY-MM-DD/symbol={SYM}/part-*.parquet.

    Scenario: CSV cap fallback¶

    • WHEN a daily aggTrades file exceeds 100,000 rows
    • THEN the day is re-downloaded from the REST API with pagination

    Scenario: REST cap hour split¶

    • WHEN the REST fallback for a day also exceeds 100,000 rows
    • THEN the day is downloaded in per-hour ranges

    Scenario: aggTrades dedup¶

    • WHEN a daily file contains duplicate aggregate trade ids
    • THEN duplicates are removed before writing

    Scenario: Row-wise CSV mapping¶

    • WHEN a CSV row is written
    • THEN its fields are mapped in row order to the schema's aggTrades columns (aggregate trade id, price, quantity, first trade id, last trade id, timestamp, buyer maker flag, best price match flag)

    Requirement: HTTP client policy¶

    The system SHALL use a shared HTTP session with Retry-After honoring on 429/418, exponential backoff (1, 2, 4 seconds) on connect errors, and a maximum of 3 retries. Failed downloads SHALL be retried at the next invocation (resume), and requests SHALL rate-limit globally via the shared rate limiter where applicable. Out-of-window dates SHALL be treated as end-of-history (not errors).

    Scenario: Rate-limited download pause¶

    • WHEN a download receives 429 with a Retry-After header
    • THEN the client waits that long, plus a random 5-30 second jitter, before retrying

    Scenario: Missing day is end-of-history¶

    • WHEN a requested date is beyond the venue's earliest data window
    • THEN the download treats it as end-of-history and stops, without raising an error
