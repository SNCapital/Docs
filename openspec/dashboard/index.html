    Dashboard

    Purpose¶

    Defines the read-only live-trading dashboard of alpha_engine (dashboard/): the FastAPI app (dashboard/app.py) that serves the on-disk state written by alpha_engine.live.state.StateStore, the single self-contained page it ships (dashboard/static/index.html plus the styled dashboard/static/login.html), and the venue-snapshot sidecar (dashboard/venue_snapshot.py) that feeds it live account data. The dashboard process can only observe - it has no write path to the state file and exposes no order or trade endpoint of any kind. The persisted state contract itself is specified under alpha-engine/live-trading.

    Requirements¶

    Requirement: Read-only dashboard app and endpoints¶

    The system SHALL expose a FastAPI app built by create_app(state_path: str | None = None) plus a module-level app = create_app() for uvicorn alpha_engine.dashboard.app:app, titled Live Trading Dashboard. The routes SHALL be: GET /healthz (always {"ok": true}, never auth-gated); GET /login (serves static/login.html as text/html, or a 302 redirect to / when auth is disabled); POST /login (JSON body parsed into a pydantic Creds model whose username and password both default to "", so a missing field yields a 401 credential mismatch rather than a 422 validation error - it returns {"ok": true} and sets the session cookie on match, {"ok": false} with status 401 on mismatch, and {"ok": true} with no cookie when auth is disabled); GET /logout (deletes the dash_session cookie at path / and 302-redirects to /login, and is itself never gated); GET /api/state (the StateStore.read document with the heavy weight_history key popped, or {"status": "no_state_yet"} whenever that document is empty); GET /api/weights ({"weight_history": [...]} read from the same file, defaulting to []); GET /api/venue (the parsed JSON of <state-dir>/venue_snapshot.json, or {"status": "no_snapshot"} when that file does not exist); GET /api/orders ({"recent_fills": [...], "risk_violations": [...]} read from the state file, each key defaulting to []); GET / (serves static/index.html as text/html when authed, else a 302 redirect to /login); and a StaticFiles mount at /static (mount name static) over dashboard/static. The app SHALL have no write path to the state file, no order/trade endpoint of any kind, and SHALL never hold exchange API keys: its only filesystem access is reading the state file, reading the sibling venue snapshot, and serving the two static pages.

    Scenario: Missing state file¶

    • WHEN GET /api/state is called before any state has been written
    • THEN it returns {"status": "no_state_yet"} instead of a schema-shaped empty doc

    Scenario: Weights on own cadence¶

    • WHEN GET /api/weights is called
    • THEN it returns the capped weight_history tape, which /api/state omits

    Scenario: Orders and weights without a state file¶

    • WHEN /api/orders or /api/weights is called and no state file exists
    • THEN every list key answers with [], with no no_state_yet marker and no error

    Scenario: Missing venue snapshot¶

    • WHEN GET /api/venue is called and <state-dir>/venue_snapshot.json does not exist
    • THEN it returns {"status": "no_snapshot"} rather than 404

    Requirement: State-file resolution and per-request reads¶

    The state file path SHALL resolve in the order explicit state_path argument, then env LIVE_STATE_PATH, then the module default ./live_state.json (DEFAULT_STATE_PATH), and SHALL be captured once as a Path when the app object is constructed; because the resolution is state_path or os.environ.get(...), an empty-string argument falls through to the environment. Every state-file read SHALL go through the static helper StateStore.read, which returns {} for a path that does not exist; /api/venue is the one exception and reads its file with a plain open plus json.load guarded by an exists() check. There SHALL be no in-process cache, TTL, ETag or Last-Modified handling of any kind: /api/state, /api/weights and /api/orders each re-open and re-parse the whole JSON document on every request (so /api/state still parses the heavy weight_history it then discards), and /api/venue re-parses the snapshot on every request. Because reads are unsynchronised with the writer, correctness relies on the writers renaming a temp file into place rather than on any locking here.

    Scenario: Explicit path beats the environment¶

    • WHEN create_app(state_path=...) is called with an explicit path while LIVE_STATE_PATH is also set
    • THEN the explicit argument wins and the resolved path is fixed for the life of that app object

    Scenario: Corrupt state file¶

    • WHEN the state file exists but is not valid JSON
    • THEN /api/state propagates the parse error (HTTP 500); only a missing file or a document that parses to an empty object yields no_state_yet

    Scenario: Every request re-reads the file¶

    • WHEN two /api/state requests arrive back to back
    • THEN the file is opened and parsed twice, with no cached document and no conditional-request headers

    Requirement: Authentication¶

    The system SHALL enable cookie-session authentication only when both DASH_USER and DASH_PASS are set and non-empty at app construction; otherwise / and all /api/* endpoints are open (local dev only) and GET /login 302-redirects to /. The session token SHALL be the hex sha256("<user>:<pass>") digest, so knowing the credentials yields the cookie value - an accepted trade-off for a read-only viewer - and both the submitted username and the submitted password SHALL be checked with constant-time secrets.compare_digest, as SHALL the cookie value on every gated request. On a matching POST /login the cookie dash_session (module constant COOKIE) SHALL be set httponly, samesite=lax, path=/, max_age=7*24*3600 (7 days) and deliberately WITHOUT the Secure flag, because uvicorn is served over plain HTTP behind a TLS-terminating reverse proxy and a Secure cookie set from that scheme would never round-trip. Unauthenticated access to any /api/* endpoint SHALL return 401 with body {"detail": "Unauthorized"}; GET / is protected too but SHALL redirect (302) to /login rather than return 401; /healthz and /logout SHALL never be gated, and the /static mount SHALL NOT be gated either, so the page shell is fetchable at /static/index.html without a session - harmless because every data endpoint it calls is gated. FastAPI's interactive docs SHALL be disabled (docs_url=None, redoc_url=None). Because the credentials and derived token are read once inside create_app, changing DASH_USER / DASH_PASS SHALL require rebuilding the app (process restart or module reload). The shipped login page SHALL POST the form as JSON to /login and navigate to / on a 200; on any non-200 or network error it SHALL show a single "Wrong username or password" message, shake the card and refocus and select the password field, without revealing which field was wrong. The dashboard page itself SHALL ship no logout control - /logout has to be visited by hand.

    Scenario: Auth disabled¶

    • WHEN DASH_USER / DASH_PASS are unset
    • THEN all endpoints answer without authentication, /login redirects to /, and POST /login returns {"ok": true} while setting no cookie

    Scenario: Wrong credentials¶

    • WHEN POST /login receives a mismatched username or password
    • THEN it returns 401 with body {"ok": false}, no session cookie is set, and the login page shows the generic failure message

    Scenario: Successful login then logout¶

    • WHEN POST /login matches and the browser then calls GET /logout
    • THEN the first call sets dash_session and gated routes answer 200, and the logout deletes that cookie, 302-redirects to /login, and gated routes return 401 again

    Scenario: Static shell is not gated¶

    • WHEN an unauthenticated client fetches /static/index.html
    • THEN the HTML shell is served, but every /api/* call it makes still returns 401 so no data leaks

    Scenario: Session expires while the page is open¶

    • WHEN the cookie stops matching while index.html is polling
    • THEN /api/state answers 401, the page shows connection error: HTTP 401 in the footer and keeps the last render - it never redirects itself to /login

    Requirement: Dashboard page polling and connection status¶

    The system SHALL serve a single self-contained page (all CSS and JS inlined, no external requests, no build step, no chart library) that polls /api/state every 3000 ms (POLL_MS) with cache: "no-store", /api/weights every 30000 ms (WEIGHTS_MS, the tape only changes once per 30-minute bar) with cache: "no-store", and /api/venue every 15000 ms with default fetch caching, with each poller also fired once immediately at load, and that re-renders the last received document once per second so the next-bar countdown ticks between polls. The 1 Hz re-render SHALL be a no-op while no document is cached. The countdown SHALL be next_bar_eta_s minus the seconds elapsed since the last /api/state response (recorded even for a no_state_yet response), clamped at 0, and rendered as whole rounded seconds. Freshness SHALL be judged client-side only: the page marks the parser-age tile stale (amber) when parser_last_metric_ts is strictly more than 90 seconds (STALE_S) old, and shows -- with no stale styling when that field is null; the server never computes staleness. While /api/state answers {"status": "no_state_yet"} the page SHALL write "waiting for live trader to write state..." into the #conn footer status line, clear its cached document so the 1 Hz re-render stops, and leave the panels at whatever they last showed. A rejected fetch or a non-200 response SHALL write "connection error: " into that same footer line (with the message HTTP <status> for a non-200) while keeping the last render; a successful poll SHALL write "updated "; before the first poll resolves the line SHALL read "connecting...". Failures of /api/venue and /api/weights SHALL be swallowed silently so the previous values stay on screen. The shipped page SHALL render fills and risk violations from the /api/state document; the /api/orders endpoint exists for the contract but is not consumed by the shipped page.

    Scenario: Waiting status line¶

    • WHEN the trader has not yet written a state file
    • THEN the footer status line reads "waiting for live trader to write state..." instead of the page rendering an empty dashboard

    Scenario: Stale parser metrics¶

    • WHEN parser_last_metric_ts is older than 90 seconds
    • THEN the page marks the parser-age tile stale (amber) while continuing to render the last document

    Scenario: Poll failure keeps the last render¶

    • WHEN an /api/state poll rejects or returns a non-200 status
    • THEN the footer shows "connection error: ..." and the previously rendered panels stay on screen

    Requirement: Deposit-adjusted PnL and live venue tile¶

    The system SHALL treat the venue transfer history as the single source of truth for how much money was ever put into the account. Total PnL SHALL be equity - cumDepositsAt(now) where cumDepositsAt(ms) sums every [epoch_ms, amount] transfer with epoch_ms <= ms, and the displayed equity curve SHALL map each point to equity - cumDepositsAt(point_ts), so a deposit plots as nothing-happened instead of a fake profit spike or drawdown cliff. When the venue snapshot carries no transfers the page SHALL fall back to account.initial_capital as the PnL base and SHALL plot the raw equity_curve unmodified. The total-PnL percentage SHALL be the deposit-adjusted PnL divided by that same base and SHALL render -- when the base is null or zero; the pair SHALL be shown as a signed value then the signed percentage in parentheses, colored green above zero, red below, and neutral at exactly zero. The "Live (15s)" tile SHALL be driven only by the venue snapshot: it SHALL adopt a payload only when the parsed body has a defined equity field (so the {"status": "no_snapshot"} marker leaves the tile at -- and keeps the initial_capital fallback in force), and SHALL render "$" + equity to 2 fixed decimals (no thousands grouping) followed by (PnL <signed>) computed as equity - cumDepositsAt(snapshot_ts) to 2 fixed decimals, colored green when that PnL is non-negative and red otherwise. The tile SHALL be updated inside the venue poller itself, not by the 1 Hz re-render, so it survives a state-file outage.

    Scenario: Deposit-adjusted curve¶

    • WHEN the venue snapshot carries transfer history
    • THEN the page plots equity minus cumulative deposits, so wallet top-ups do not appear as profit spikes or drawdown cliffs

    Scenario: No venue snapshot yet¶

    • WHEN /api/venue answers {"status": "no_snapshot"} or the fetch fails
    • THEN the Live tile stays at --, the equity curve is plotted unadjusted, and total PnL falls back to equity - initial_capital

    Requirement: Status bar tiles and formatting¶

    The system SHALL render a header status bar of ten tiles from the /api/state document: Mode (badge showing mode lowercased, styled paper, testnet or mainnet, and unknown for anything else or a missing field); Equity (account.equity, with the deposit-adjusted Total PnL as a sub-line beneath it); Live (15s) from the venue snapshot; Realized / Unreal. (account.realized_pnl and account.unrealized_pnl, each signed and colored independently); Leverage (account.leverage to 2 decimals with an x suffix, -- when null); Gross / Net Exp (account.gross_exposure prefixed with $, then the signed sum of every positions[].notional, shown amber when the absolute net exceeds 25 percent of equity - falling back to a divisor of 1 when equity is missing - which flags a book that is no longer market-neutral); Positions (the length of positions); Daily Drawdown (account.daily_drawdown as a percentage, red when negative); Bar # / Next In (#<bar_count> then the last_bar_ts hour and minute as HH:MMZ, then | and the live countdown in seconds); and Parser Age (<n>s ago). A full-width KILLED banner reading "KILLED - trading halted" SHALL be shown whenever killed is truthy and hidden otherwise. Money SHALL be formatted with en-US grouping and exactly 2 decimals and SHALL NOT carry a currency symbol of its own, signed values SHALL carry an explicit + when non-negative, percentages SHALL be the raw fraction times 100 with 2 decimals and a % suffix (unsigned for fmtPct, explicitly signed for fmtSignedPct), and any null or NaN input SHALL render as -- rather than NaN. The page SHALL deliberately ignore the state fields updated_ts, account.total_fees, account.day_utc, account.day_start_equity and account.n_fills - they are written by the trader but shown nowhere.

    Scenario: Kill switch fired¶

    • WHEN the state document has killed: true
    • THEN the red KILLED banner is shown above the status bar and stays until a document with killed falsy arrives

    Scenario: Book drifts away from neutral¶

    • WHEN the absolute sum of position notionals exceeds 25 percent of equity
    • THEN the net-exposure figure is rendered amber as a warning

    Scenario: Missing numbers¶

    • WHEN a numeric field is absent or NaN in the state document
    • THEN the corresponding tile renders -- instead of NaN or an empty cell

    Requirement: Positions, weights, violations and fills panels¶

    The system SHALL render four data panels from the /api/state document. Positions SHALL be a table of Symbol, Qty (6 decimals), Avg Entry (2), Mark (2), Notional (money), Unrealized (signed, colored), Realized (signed, colored) and Fees (money), showing "no open positions" when the list is empty. Target vs Actual Weights SHALL show one row per symbol in the lexicographically sorted union of target_weights and actual_weights keys, with a blue target bar above an amber actual bar, both scaled to the largest absolute weight in the set (floored at 0.0001 so an all-zero book cannot divide by zero) and a header reading t <target%> / a <actual%>, showing "no weights" when both maps are empty. Risk Violations SHALL render each risk_violations entry as a plain amber text box, showing "none" when the list is empty. Recent Fills SHALL render the last 20 entries of recent_fills reversed to newest-first, with Time as HH:MM:SSZ from the ISO fill timestamp, Symbol, a signed Qty at 6 decimals colored green when qty_delta is greater than or equal to zero and red only when it is strictly negative, Price at 2 decimals and Fee at 4 decimals, showing "no fills" when the list is empty. Every symbol and violation string SHALL be HTML-escaped before interpolation (&, <, >, ", '), and any unparseable timestamp SHALL render as --. Before the first render lands, the static markup SHALL show its own placeholders ("no data" in the Positions table body and the weights box, "none" for violations, "no fills" for fills).

    Scenario: Fills tape is capped client-side¶

    • WHEN the state document carries more than 20 recent fills
    • THEN only the last 20 are shown, newest first, while the endpoint still returns the trader's full capped tape

    Scenario: Empty panels¶

    • WHEN positions, weights, violations or fills are empty in the state document
    • THEN each panel shows its own placeholder text rather than an empty table body

    Requirement: Equity curve canvas¶

    The system SHALL draw the (deposit-adjusted) equity_curve on a plain 2D canvas with no charting library: 180 CSS pixels tall, as wide as its own client width (falling back to the parent panel's width), scaled by devicePixelRatio so it stays sharp on retina displays, and redrawn on every render pass - which means a window resize is picked up by the next 1 Hz re-render rather than by a resize handler. An empty curve SHALL draw the text "no equity data yet" instead of axes. Otherwise the chart SHALL use a fixed padding of 60 left, 12 right, 12 top and 22 bottom, map x linearly across the epoch-millisecond range and y across the value range (expanded by plus and minus 1 when every point is identical so a flat curve still has a scale, and with either span floored at 1), draw five horizontal gridlines at equal fractions of the y span with right-aligned y labels formatted with en-US grouping and no decimals, stroke the line green when the last value is greater than or equal to the first and red otherwise, and fill the area under the line with the same hue at 8 percent opacity.

    Scenario: No equity points yet¶

    • WHEN the equity curve is empty
    • THEN the canvas shows "no equity data yet" instead of an empty axis frame

    Scenario: Flat curve¶

    • WHEN every equity point has the same value
    • THEN the y range is widened by plus and minus 1 so the line renders instead of dividing by a zero span

    Requirement: Weight-history heatmap¶

    The system SHALL draw a "position tape" heatmap of the /api/weights history on its own canvas: one column per bar and one row per symbol. The tape SHALL therefore show the trader's TARGET weights, because weight_history entries are [epoch_ms, target_weights] and the trader stores only nonzero, non-NaN targets. It SHALL require at least two history entries; with fewer it SHALL hide the canvas, show "building weight history..." and clear the hover layout so hovering does nothing. Rows SHALL be selected by summing the absolute weight of each symbol across the window, dropping every symbol whose total is at or below 1e-4 (rotated-out tails), sorting the rest by that total descending and capping at 90 rows (HM_ROWS), then re-sorting the surviving rows by the most recent bar's weight so the biggest longs sit on top and the biggest shorts at the bottom; the panel title SHALL be rewritten to "Portfolio Weights - History" suffixed with the resulting row count as " names". The number of columns is bounded by the trader's weight_history_max (96 bars, about 48 hours of 30-minute bars), not by the page. Cell color SHALL diverge from teal rgb(38,208,160) for long through near-black rgb(16,22,31) at zero to red rgb(248,81,73) for short, normalized by the largest absolute weight among the DRAWN rows (floored at 1e-6) and lifted by a 0.68 gamma so small weights stay visible. Layout SHALL use a 70 pixel label gutter, 8 pixel right pad, 4 pixel top pad, 18 pixel bottom pad, 13 pixel rows, 1 pixel cell gaps and 2 pixel rounded corners, scaled by devicePixelRatio, so the canvas height grows with the row count. Row labels SHALL be the symbol with the first occurrence of USDT removed by a plain string replace (not an anchored suffix strip); up to 7 evenly spaced HH:MM UTC time labels SHALL run along the bottom. Hovering a cell SHALL show a floating tooltip, clamped to the viewport width, with the symbol, the bar time as HH:MMZ and the weight as a percentage with 2 decimals colored green or red - rendered with a plain toFixed, so negatives keep their minus sign but positives carry NO leading +. The tooltip SHALL be hidden when the pointer leaves the grid or the canvas. A window resize SHALL redraw the heatmap after a 150 ms debounce, and the heatmap SHALL otherwise be redrawn only by the /api/weights poller, not by the 1 Hz re-render.

    Scenario: Not enough history¶

    • WHEN fewer than two bars of weight history exist
    • THEN the heatmap canvas is hidden and the panel shows "building weight history..."

    Scenario: Only the actively-held book is shown¶

    • WHEN the window contains symbols whose total absolute weight is at or below 1e-4
    • THEN those rows are dropped, the remaining names are capped at 90 rows and ordered longs-first by the latest bar, and the title reports how many names are drawn

    Scenario: Cell hover¶

    • WHEN the pointer rests on a heatmap cell
    • THEN a tooltip shows that symbol, the bar time in UTC and the weight as a colored percentage with no explicit plus sign on longs

    Requirement: Page layout¶

    The system SHALL lay the page out as a wrapper capped at 1280 pixels wide, a flex-wrapping status bar, then a two-column CSS grid that collapses to a single column at or below 860 pixels of viewport width. The Equity Curve, weight-history heatmap, Positions and Recent Fills panels SHALL span the full grid width, while Target vs Actual Weights and Risk Violations SHALL sit side by side in the two-column layout. The connection status line SHALL sit right-aligned at the bottom of the page. The palette SHALL be a dark theme with green for gains, red for losses and amber for warnings, and all numeric cells SHALL use the monospace class.

    Scenario: Narrow viewport¶

    • WHEN the browser viewport is 860 pixels wide or less
    • THEN the panel grid collapses to one column and every panel spans it

    Requirement: Venue snapshot sidecar¶

    The system SHALL provide a separate venue-snapshot sidecar (dashboard/venue_snapshot.py, run as python -m alpha_engine.dashboard.venue_snapshot and documented to run under its own systemd service trading-venuesnap with EnvironmentFile=secrets/binance.env; no unit file for it is checked into deploy/systemd/ and deploy/RUNBOOK.md never mentions it). At import it SHALL read VENUE_SNAP_SECONDS (default "15", parsed with int, so a non-numeric value raises ValueError at import), VENUE_SNAPSHOT_PATH (default /opt/trading/state/venue_snapshot.json) and the required BINANCE_API_KEY / BINANCE_API_SECRET (a missing key raises KeyError at import, so the process fails fast instead of polling unauthenticated). Every loop iteration it SHALL call the signed USD-M REST endpoint /fapi/v2/account and, when more than 60 seconds have passed since the last successful transfer refresh, re-page the whole /fapi/v1/income history with incomeType=TRANSFER; the base URL https://fapi.binance.com is hard-coded (mainnet only, no testnet switch). Each call SHALL append timestamp (epoch ms) and recvWindow=10000, sign the url-encoded query with HMAC-SHA256 over the secret, send the key in the X-MBX-APIKEY header, and time out after 10 seconds. Transfer history SHALL be paged in explicit 30-day [startTime, endTime) windows walking forward from the hard-coded account epoch 1783468800000 (2026-07-08 00:00 UTC) up to now + 60000, with limit=1000 per page and the cursor advanced to the last row's time plus 1 ms while a full page comes back, because the income endpoint honours explicit bounds while an open-ended query silently serves only recent history; consequently one further REST call is added for every extra 30 days elapsed since the epoch. Amounts SHALL be taken as float(row["income"]) with no asset filtering - the module documents that stable-asset amounts (USDT/USDC) are treated as $1 units, but it does not check the field. The result SHALL be written atomically (temp file created with mkstemp in the destination directory, then os.replace; the temp file is NOT unlinked if the write raises) as compact JSON {ts, equity, wallet, unrealized, transfers[[epoch_ms, amount], ...]} where ts is the writer's own epoch ms, equity is totalMarginBalance, wallet is totalWalletBalance and unrealized is totalUnrealizedProfit. The loop SHALL then sleep VENUE_SNAP_SECONDS, so the effective cadence is the interval plus request latency. Any exception in an iteration SHALL be printed as venue_snapshot: <error> on stdout (flushed, for the journal) and the loop SHALL continue, keeping the previously fetched transfers in memory and leaving the last snapshot file in place; because the write is the last statement in the try block, a transfer-fetch failure also skips that iteration's account-number write. The dashboard SHALL serve that file read-only from the state file's own directory as the hard-coded name <state-dir>/venue_snapshot.json and SHALL NOT read VENUE_SNAPSHOT_PATH itself, so in production the sidecar's output path and the state file must share a directory; the web-facing process never holds API keys. A snapshot file that exists but is not valid JSON SHALL propagate the parse error (HTTP 500) exactly as the state file does - only a missing file yields the no_snapshot marker. The dashboard SHALL expose no staleness signal for the snapshot, so a sidecar that has died keeps serving its last file with an old ts and the page shows those numbers as if they were live.

    Scenario: Snapshot refresh¶

    • WHEN the poll interval elapses
    • THEN the sidecar overwrites the snapshot atomically with the fresh account numbers and the cached transfer history

    Scenario: Transfers are cached¶

    • WHEN less than 60 seconds have passed since the last transfer fetch
    • THEN the sidecar reuses the in-memory transfer list and only refreshes the account numbers

    Scenario: Poll failure keeps loop alive¶

    • WHEN a REST call fails
    • THEN the sidecar prints the failure and sleeps until the next poll instead of crashing, the previous snapshot file stays on disk, and no snapshot is written for that iteration

    Scenario: Missing credentials¶

    • WHEN BINANCE_API_KEY or BINANCE_API_SECRET is not set
    • THEN importing the module raises KeyError and the sidecar never starts polling

    Requirement: Launch and deployment contract¶

    The system SHALL have no dashboard subcommand in the repo CLIs: the root main.py only exposes live-trade and nothing under tools/ starts a web server, so the only entry point is an ASGI server pointed at the module-level app, canonically uvicorn alpha_engine.dashboard.app:app --host 127.0.0.1 --port 8000 with LIVE_STATE_PATH set. The shipped systemd unit (deploy/systemd/trading-dashboard.service) SHALL run exactly that command from /opt/trading/venv/bin/uvicorn as the unprivileged trader user with Type=simple, WorkingDirectory=/opt/trading/backend, Environment=LIVE_STATE_PATH=/opt/trading/state/live_state.json, EnvironmentFile=/opt/trading/secrets/dashboard.env for DASH_USER / DASH_PASS (whose example file ships DASH_USER=viewer and a placeholder password), After/Wants=network-online.target, Restart=on-failure with RestartSec=5, MemoryMax=512M, stdout/stderr to the journal, and WantedBy=multi-user.target. The app SHALL be bound to loopback only and fronted by Caddy (deploy/Caddyfile), which auto-provisions a Let's Encrypt certificate for kolyan.tech, adds a second basic_auth layer (user viewer, bcrypt hash placeholder REPLACE_WITH_BCRYPT_HASH that the operator must replace) in front of the app's own cookie auth, gzip-encodes responses via encode gzip, reverse-proxies to 127.0.0.1:8000, sets X-Content-Type-Options: nosniff, X-Frame-Options: DENY and Referrer-Policy: no-referrer, and logs to /var/log/caddy/kolyan.tech.log. Provisioning SHALL be handled by deploy/install.sh, which installs Caddy and the Python venv and instructs the operator to copy deploy/systemd/*.service and deploy/Caddyfile into place; it installs no sidecar unit for venue_snapshot. The runtime dependencies SHALL be fastapi>=0.115 and uvicorn[standard]>=0.30 from the root requirements.txt. The app SHALL provide no rate limiting of its own.

    Scenario: Production start¶

    • WHEN systemctl enable --now trading-dashboard is run on the deployed host
    • THEN uvicorn serves the app on 127.0.0.1:8000 reading /opt/trading/state/live_state.json, with app-level auth from dashboard.env and Caddy terminating TLS in front
