    Live WebSocket pipeline

    Purpose¶

    Defines the live WebSocket pipeline of binance_parser: the live CLI entry point, per-market subscription sets, connection and reconnect policy, stream dispatch to parquet, buffered writer semantics, local order-book lifecycle and snapshots, health/stats accounting, and task composition of the live run.

    Requirements¶

    Requirement: Live CLI contract¶

    The system SHALL expose a live subcommand accepting --market (spot|usdm|both, default spot), --symbols (space-separated, default BTCUSDT and ETHUSDT, upper-cased), --order-book (flag), and --with-funding (flag). The command SHALL run until interrupted, and a keyboard interrupt SHALL stop it with exit code 0.

    Scenario: Default live run¶

    • WHEN the live command is run with no flags
    • THEN it starts a spot-market pipeline for BTCUSDT and ETHUSDT without the order book or funding poller

    Scenario: Symbols upper-cased¶

    • WHEN symbols are passed in lowercase
    • THEN the pipeline operates on the upper-cased symbols

    Requirement: Stream subscription sets¶

    The system SHALL subscribe per symbol, per market, to a fixed stream set: always @depth, @aggTrade, and @kline_1m; plus, on usdm only, @markPrice@1s and (when enabled) @forceOrder. The raw @trade stream SHALL be subscribed only when trades are preferred over aggregate trades (or multilevel reconstruction is enabled); by default it is not subscribed and aggregate trades are the canonical trade source.

    Scenario: Default spot subscription¶

    • WHEN a spot listener starts for a symbol with default settings
    • THEN exactly @depth, @aggTrade, and @kline_1m streams are subscribed

    Scenario: Default usdm subscription¶

    • WHEN a usdm listener starts for a symbol with default settings
    • THEN @depth, @aggTrade, @kline_1m, @markPrice@1s, and @forceOrder are subscribed

    Scenario: Raw trades opt-in¶

    • WHEN aggregate-trade preference is disabled
    • THEN @trade is additionally subscribed and raw fills are written as trades events alongside aggtrades

    Requirement: WebSocket persistence semantics¶

    The system SHALL persist via the writer only: aggtrades, closed klines, markprice (usdm), forceorder (usdm, when enabled), trades (when subscribed), and booksnapshot (order-book snapshots). Depth diffs SHALL never be persisted: they feed only the in-process order book and health counters. Running (unclosed) klines and unknown streams SHALL be dropped silently.

    Scenario: Depth diff bypass¶

    • WHEN a @depth message arrives and an order-book manager is present
    • THEN it is routed to the book manager and health counters only, and the writer is never invoked

    Scenario: Depth-diff debug logging hook¶

    • WHEN the depth-log interval setting is configured to a positive value
    • THEN the first and then every Nth depth diff per stream is logged at debug level

    Scenario: Silent unknown-stream drop¶

    • WHEN a message matches no known stream
    • THEN it is ignored without failing the connection

    Requirement: WebSocket reconnect policy¶

    The system SHALL reconnect a closed or failed connection with exponential backoff starting at 1 second and doubling, capped at 60 seconds, reset to 1 on any successful connection. The connection SHALL keep an application-level heartbeat (ping every 20 seconds, timeout 10 seconds, close timeout 5 seconds). After 30 consecutive reconnect failures the listener SHALL raise an error to its supervisor instead of retrying forever. Unexpected (non-network) exceptions SHALL propagate immediately, never being masked as reconnects. Every reconnect except the first SHALL be recorded with the disconnection gap.

    Scenario: Backoff reset on success¶

    • WHEN a connection attempt succeeds after prior failures
    • THEN the backoff timer resets to 1 second and the failure counter clears

    Scenario: Give-up escalation¶

    • WHEN 30 consecutive reconnect attempts fail
    • THEN the listener raises a runtime error describing the failure count

    Scenario: Code error escalation¶

    • WHEN a frame handler raises an unexpected exception
    • THEN the exception propagates immediately and the loop does not attempt a reconnect

    Requirement: Buffered parquet writer¶

    The system SHALL buffer records in memory and flush them to parquet under a Hive-partitioned layout: data/market={m}/type={t}/dt=YYYY-MM-DD/symbol={SYM}/part-*.parquet. Flush SHALL trigger when the total buffered record count reaches 100,000 or a 60-second timer elapses. At flush, records SHALL be grouped by their own event-UTC-date so buckets straddling midnight land in the correct dt= partition. Writes SHALL use zstd compression (level 3), write to a sibling temp file, and atomically replace the target path. A failed partition write SHALL be retried (3 attempts, escalating backoff) and the failure SHALL be raised after the flush completes the remaining partitions.

    Scenario: Midnight partition correctness¶

    • WHEN a flush contains records whose event times fall on different UTC dates
    • THEN each record lands in the parquet file of its own event date partition

    Scenario: Atomic part write¶

    • WHEN a parquet part is written
    • THEN it is first written to a temporary sibling file and then atomically renamed, so a crash never leaves a corrupt file at the canonical path

    Scenario: Flush by record count¶

    • WHEN the total buffered record count reaches 100,000 before the 60-second timer
    • THEN a flush occurs immediately

    Requirement: Order-book state lifecycle¶

    The system SHALL maintain one in-memory order book per (market, symbol), seeded from a REST depth snapshot and kept in sync with @depth diffs. The book SHALL have states bootstrapping, live, and resyncing. Spot and usdm SHALL apply the venue-specific contiguity rules: spot drops diffs with u <= snapshot id, bridges when U <= snapshot id + 1 <= u, and requires U == previous u + 1; usdm drops diffs with u < snapshot id, bridges when U <= snapshot id <= u, and requires pu == previous u. A level with quantity zero SHALL remove the level. A non-contiguous live diff SHALL move the book to resyncing and re-bootstrap.

    Scenario: Level removal by zero quantity¶

    • WHEN a diff carries a level with quantity zero
    • THEN the corresponding price level is removed from the book

    Scenario: Gap triggers resync¶

    • WHEN a live diff is not contiguous with the previous one
    • THEN the book transitions to resyncing, the gap is counted, and a re-bootstrap is scheduled

    Scenario: Usdm overlapping ranges tolerated¶

    • WHEN a usdm diff overlaps the previous range instead of extending it exactly
    • THEN the diff is applied and the book remains live (usdm contiguity is defined by pu)

    Scenario: Diff observers¶

    • WHEN observers are registered on a live book and a diff arrives
    • THEN each observer is invoked before the diff is applied, with the touched price levels and the mid price; an observer failure is logged and never interrupts the dispatch loop

    Requirement: Order-book bootstrap¶

    The system SHALL bootstrap a book by fetching the venue's deepest snapshot (spot up to 5000 levels, usdm up to 1000), then replaying buffered diffs sorted by final update id: stale diffs dropped, the first surviving diff must bridge the snapshot, and subsequent diffs must be contiguous, else bootstrap repeats. Cold-start snapshot fetches SHALL be staggered per symbol (spot 2.5s, usdm 0.5s) with at most 2 concurrent fetches. USD-M snapshot fetches SHALL charge the shared rate limiter (weight 20 at max depth); spot bootstrap in the standalone run passes no limiter and relies on the stagger plus the concurrency cap. A 200 response without lastUpdateId (delisted or renamed symbol) SHALL raise an error that is absorbed by the retry backoff. Rate-limit responses SHALL be honored via Retry-After plus 5-30 seconds of jitter; other failures SHALL back off exponentially to 30 seconds.

    Scenario: Snapshot-limited bootstrap¶

    • WHEN a book cannot bridge the snapshot with the buffered diffs
    • THEN bootstrap is retried after a fixed 2-second wait and the book stays bootstrapping

    Scenario: Rate-limited bootstrap wait¶

    • WHEN a depth snapshot fetch returns 429 or 418
    • THEN the retry sleeps for the response's Retry-After plus a random 5-30 second jitter

    Scenario: Buffered diffs after failed bridge¶

    • WHEN a bootstrap attempt fails contiguity after applying the bridging diff
    • THEN the buffered diffs are discarded and the next bootstrap re-seeds from a fresh snapshot (only the no-bridge case keeps the buffer)

    Scenario: Watchdog force-resync¶

    • WHEN a live book receives no diffs for more than 30 seconds, or a resyncing book stays resyncing for more than 60 seconds
    • THEN the watchdog forces a resync and counts it

    Requirement: Order-book snapshots¶

    The system SHALL persist the full book (bids and asks as parallel float32 price/size arrays, one row per event, carrying also the symbol, snapshot timestamp, and the book's last update id) into type=booksnapshot partitions at a UTC-aligned cadence of 30 minutes (configurable; zero disables persistence), i.e. at :00 and :30 UTC, 48 snapshots per symbol per day. Only books in live state SHALL be snapshotted; a half-bootstrapped book SHALL be skipped. A separate 1-second in-process bus snapshot loop SHALL exist for metric consumers and SHALL never touch disk; it is not started in standalone parser runs.

    Scenario: UTC-aligned snapshot ticks¶

    • WHEN the snapshot loop runs with the default 30-minute interval
    • THEN snapshots are written at :00 and :30 UTC regardless of process start time

    Scenario: Unready book skipped¶

    • WHEN a book is not in live state at snapshot time
    • THEN no snapshot row is written for it for that tick

    Scenario: Snapshot persistence disabled¶

    • WHEN the snapshot interval is set to zero
    • THEN no booksnapshot parquet files are written and a notice is printed

    Requirement: Health and pipeline statistics¶

    The system SHALL track health counters (trade-id gaps - incremented when a trade id is not exactly the previous plus one; WS reconnects; order-book force resyncs; clock-drift alerts) plus per-symbol last-event timestamps. It SHALL expose a snapshot of these counters for external scraping. The pipeline SHALL report periodic statistics: message counts and lag per stream, reconnect count, and depth-resync counts per symbol, reported every 60 seconds; a high-frequency stream (aggtrades) that has never delivered a message, or whose lag exceeds 10 times its 30-second threshold (i.e. 300 seconds), SHALL trigger a warning.

    Scenario: Trade id gap detection¶

    • WHEN a trade arrives whose id is not the previously seen id plus one
    • THEN the trade-id-gap counter increments and a warning is logged

    Scenario: Silent stream warning¶

    • WHEN the aggtrades stream has never received a message after the first report, or its lag exceeds 300 seconds (10 times its 30-second threshold)
    • THEN the reporter logs a stream-silent or stream-lag warning

    Requirement: Live run composition¶

    The system SHALL run the live pipeline as a task group sharing one writer, one stats object, one health object, and one shared USD-M rate limiter across all components. It SHALL start, per selected market: a WS listener; on usdm, the exchange-info poller and market-stats poller; and, conditionally: the order-book manager and its snapshot/watchdog loops (--order-book), the funding poller (--with-funding, usdm only, ignored with a printed notice otherwise), the legacy periodic metrics pollers (when enabled), and the spot margin-interest poller (when enabled and spot is selected). Symbol validation against exchange-info SHALL be a soft check: network, timeout, and JSON-parse failures, as well as invalid symbols, SHALL warn but never abort (non-network parse bugs SHALL still propagate). The first task exception SHALL cancel all sibling tasks.

    Scenario: Funding flag without usdm¶

    • WHEN --with-funding is set but usdm is not among the markets
    • THEN the flag is ignored with a printed notice and no funding poller starts

    Scenario: Soft symbol validation¶

    • WHEN the exchange-info validation request fails or a symbol is not trading
    • THEN the pipeline continues with a warning

    Scenario: First-exception cancels all¶

    • WHEN any task in the group fails
    • THEN all sibling tasks are cancelled and the failure propagates out of the run
