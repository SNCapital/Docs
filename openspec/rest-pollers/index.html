    REST pollers

    Purpose¶

    Defines the REST polling pipelines of binance_parser that run alongside the live WebSocket listener: funding-rate polling aligned to exchange settlements, the daily exchange-metadata poll, futures market-stats polling, the optional signed spot margin-interest poll, and the periodic-metrics pollers. It pins the polling cadences, the shared retry and rate-limit policy, and the parquet types each poller writes.

    Requirements¶

    Requirement: Poller session and retry policy¶

    All REST pollers SHALL follow one retry policy: transient errors (network, 5xx) SHALL back off over (1, 3, 10) seconds, and 429/418 rate-limit responses SHALL be honored by sleeping per Retry-After, up to 3 waits per call. Non-retryable 4xx (any 4xx other than 408/429/500/502/503/504) SHALL cause the current cycle to be skipped (return None), without retries; the notification medium differs by poller - funding and exchange-info pollers print(...) to stdout, while market-stats and periodic pollers use log.warning (nothing printed). Each poller SHALL open its own HTTP session (no shared session object); the endpoint weight of every USD-M call SHALL be acquired from the shared multi-bucket rate limiter before the request, and the USD-M limiter SHALL be shared by all USD-M pollers and the depth bootstrap. The spot-margin poller passes no limiter and relies on its own hourly alignment.

    Scenario: Connect-error backoff¶

    • WHEN a poll fails with a connection error
    • THEN it is retried after 1, then 3, then 10 seconds, then the cycle is skipped

    Scenario: Rate-limit wait¶

    • WHEN a poll returns 429 with a Retry-After header
    • THEN the client sleeps for the announced duration (up to 3 waits per call) and then retries

    Scenario: Non-retryable 4xx¶

    • WHEN a poll returns 403
    • THEN it is printed as a permanent failure and the cycle is skipped without retry

    Requirement: Funding-rate poller¶

    The system SHALL poll the USD-M funding-rate endpoint (/fapi/v1/fundingRate, weight 1) once per symbol per cycle with limit=1, for the configured symbol set, and persist rows under type=funding (market usdm) with a single flush() per cycle (one partition per day/symbol instead of one file per row). The first cycle SHALL run immediately; later cycles SHALL sleep until the next UTC settlement hour (00/08/16) plus 30 seconds (minimum 1 second). Requests SHALL be bounded by the configured funding parallelism (5); an empty response SHALL yield no row.

    Scenario: Settlement-aligned poll¶

    • WHEN the funding poller finishes a cycle at 05:00 UTC
    • THEN it sleeps until 08:00 UTC plus 30 seconds, then polls again

    Scenario: Empty funding response¶

    • WHEN the endpoint returns no rows for a symbol
    • THEN no row is written for that symbol for the cycle

    Requirement: Exchange-info poller¶

    The system SHALL poll the USD-M exchange metadata once per UTC day: the first cycle SHALL run immediately, later cycles SHALL run daily at 00:05 UTC. Each cycle SHALL fetch exchangeInfo (weight 10) and leverageBracket (weight 1) in parallel and build one row per symbol by cross-joining the two payloads (filtered to the configured symbols), persisted under type=exchange_info (market usdm). Each persisted row SHALL carry maker_fee / taker_fee defaulted to the USD-M VIP-0 schedule (0.0002 / 0.0005) rather than real account fees. The poller SHALL run only when USD-M is part of the live run. When MIN_QUOTE_VOLUME_24H_USD is set, the cycle SHALL additionally fetch the full-market 24-hour ticker batch (weight 40) and drop symbols whose 24h quote volume is below the threshold; a failed volume fetch SHALL skip the filter entirely (symbols are not silently lost), unparsable quote volumes SHALL count as 0 with a warning, and non-finite values SHALL count as 0 silently.

    Scenario: Daily schedule with immediate first cycle¶

    • WHEN the live run starts at 12:00 UTC
    • THEN the exchange-info cycle runs immediately, then every day at 00:05 UTC

    Scenario: Empty payload body¶

    • WHEN the exchange-info endpoint returns HTTP 200 with an error body that has no symbols (e.g. Binance code -1003)
    • THEN the cycle is skipped with a printed message

    Scenario: Missing leverage brackets¶

    • WHEN the leverageBracket payload is not a list
    • THEN the cycle continues with empty brackets: max_leverage persists as 0 (the schema is int32 and cannot hold NaN), while maintenance_margin_rate persists as NaN

    Scenario: Volume filter¶

    • WHEN MIN_QUOTE_VOLUME_24H_USD is set and the 24h ticker fetch succeeds
    • THEN symbols below the quote-volume threshold are dropped from the persisted rows

    Requirement: Market-stats poller (futures)¶

    The system SHALL poll, for the configured symbol set, four endpoints per symbol in parallel: open interest (/fapi/v1/openInterest, rows open_interest_now), global long/short account ratio, top long/short account ratio, and top long/short position ratio (rows global_long_accounts, top_long_accounts, top_long_positions). Cycles SHALL align to 5-minute UTC slots (always the next slot, so the same bucket is never polled twice), with the first cycle immediately; a slow cycle that crosses a slot boundary SHALL skip that slot rather than queue up. Requests SHALL be bounded by the market-stats parallelism (5). For ratio endpoints Binance returns arrays oldest-first, so only the LAST element SHALL be used; an empty array SHALL yield no row. A row SHALL be written only when the result is not None, and an open-interest parse error (missing key or wrong type) SHALL log a warning and skip that row without stopping the cycle.

    Scenario: Five-minute slot alignment¶

    • WHEN the market-stats poller starts mid-slot
    • THEN the first cycle fires immediately, and from the second cycle on the polls are issued at the next 5-minute UTC boundary

    Scenario: Last-array-element ratio¶

    • WHEN a ratio endpoint returns a non-empty array
    • THEN only the last (latest) element is persisted

    Scenario: Parse error survival¶

    • WHEN an open-interest row cannot be parsed
    • THEN the row is skipped with a warning and the cycle continues

    Requirement: Market-stats spot interest poller¶

    The system SHALL optionally poll the signed margin interest endpoint (/sapi/v1/margin/next-hourly-interest-rate, per the configured margin-interest URL) with hourly UTC alignment, persisting rows under type=daily_interest_rate (market spot). The poller SHALL run only when the margin-interest flag is enabled AND spot is part of the live run, with the asset list taken from the configured MARGIN_INTEREST_ASSETS. The request SHALL be signed (HMAC-SHA256 over the query with the margin API secret, signature in the query string, API key in the X-MBX-APIKEY header). The poller SHALL refuse to start when the feature flag is disabled (info log), when the API key/secret are empty (one warning), or when there are no assets, no symbols, or no matches (info log and exit). The endpoint returns a per-hour rate; the stored value SHALL be that hourly rate multiplied by 24 (daily-equivalent daily_interest_rate = hourly x 24). Each interest rate SHALL be duplicated onto every symbol that matches its asset (symbol.startswith(asset) and symbol != asset).

    Scenario: Disabled margin poller¶

    • WHEN the margin-interest flag is disabled
    • THEN the poller logs an info message and does not start

    Scenario: Asset-to-symbol matching¶

    • WHEN an asset matches several symbols
    • THEN the same interest rate is written for each matching symbol

    Requirement: Periodic-metrics pollers¶

    The system SHALL provide a generic periodic poller over three USD-M metric kinds: open-interest history, taker long/short ratio, and top long/short position ratio (type={kind}). Each poller SHALL be constructed per (kind, symbol) with a polling interval (default 300 seconds), a Binance period parameter (default 5m), and a limit of 2 candles (the latest and the previous one), and SHALL run an endless loop sleeping interval between cycles. An unknown kind SHALL raise ValueError listing the valid kinds. Rate-limit exhaustion inside a cycle SHALL produce an empty cycle (no rows, no crash); any unexpected exception SHALL be logged with log.exception and re-raised (escalation instead of silent continuation). The pollers SHALL run only when the periodic-poller flag is enabled and USD-M is part of the live run.

    Scenario: Unknown kind rejected¶

    • WHEN a poller is constructed with a kind outside the three supported ones
    • THEN it raises ValueError naming the valid kinds

    Scenario: Rate-limit exhaustion¶

    • WHEN a cycle exhausts the rate-limit retry budget
    • THEN the cycle produces no rows and the loop continues without crashing

    Scenario: Unexpected error escalation¶

    • WHEN a cycle hits an unexpected exception
    • THEN it is logged with log.exception and re-raised rather than silently swallowed
