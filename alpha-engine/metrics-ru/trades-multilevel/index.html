    trades-multilevel — реконструкция и ml/sl-метрики¶

    Документ описывает: 1. Алгоритм multilevel-реконструкции — как из последовательности @aggTrade-событий восстановить логические агрегированные трейды, охватывающие несколько ценовых уровней. 2. ml/sl-метрики — те, что явно различают multilevel (_ml) и single-level (_sl) трейды. Все остальные базовые трейд-метрики (общий cost, count, vwap, OHLC, kyle, asr) — в trades-v2.md.

    Документ описывает целевую спецификацию.

    Зачем нужна реконструкция¶

    Когда маркет-ордер выходит на N ценовых уровней, биржа matching-engine исполняет его атомарно через все эти уровни. Binance отдаёт результат как N отдельных @aggTrade событий (по одному на уровень) — каждое агрегирует raw fills на одной цене.

    Чтобы посчитать «настоящий» multilevel ордер (агрессия одного трейдера по нескольким ценам), эти N aggTrades нужно склеить обратно.

    Источник данных¶

    Тот же что у trades-v2: партиции type=aggtrades/ (live) + type=aggTrades/ (historical). Reader через kind="trades".

    Используемые поля aggTrade (после нормализации):

    timestamp_ms        # время engine'а, миллисекунды UTC
side                # сторона агрессора: "buy" if !is_buyer_maker else "sell"
price               # цена уровня
size                # объём агрегата на этой цене
first_trade_id      # id первого raw fill'а в агрегате
last_trade_id       # id последнего raw fill'а в агрегате

    Алгоритм реконструкции¶

    Идея: соседние aggTrades — части одной агрессии, только если выполнены все четыре условия:

    extends(A, B):
    same_side       = (A.side == B.side)                              # обязательно
    same_timestamp  = (A.timestamp_ms == B.timestamp_ms)               # ML.A: ε = 0, строго
    contiguous_ids  = (B.first_trade_id == A.last_trade_id + 1)        # обязательно
    price_monotonic = (B.price > A.price  if  A.side == "buy"
                       else B.price < A.price)                         # ML.C: проверяем

    return same_side AND same_timestamp AND contiguous_ids AND price_monotonic

    Псевдокод¶

    def reconstruct_multilevel(aggTrades_sorted_by_time_then_id):
    chains = []
    chain  = [aggTrades_sorted[0]]
    for i in range(1, len(aggTrades_sorted)):
        A = chain[-1]                       # последний в цепочке
        B = aggTrades_sorted[i]
        if extends(A, B):
            chain.append(B)
        else:
            chains.append(chain)
            chain = [B]
    chains.append(chain)
    return chains   # каждая chain → один LogicalTrade

    Сортировка входа¶

    aggTrades сортируются по (timestamp_ms ASC, first_trade_id ASC). Вторичный ключ нужен на случай совпадения timestamp'ов.

    Обоснование строгого ε = 0¶

    Сочетание (same_side ∧ contiguous_ids ∧ price_monotonic) уже даёт очень сильный сигнал — две независимые агрессии не могут иметь contiguous trade_ids (между ними должен быть хотя бы один трейд другой стороны или другого taker'а, который сломает последовательность). При строгом ε = 0 мы рискуем разрезать на части агрессии, в которых engine разнёс их на ±1мс из-за внутреннего jitter'а — но это редкое событие, и false-negatives тут менее вредны чем false-positives.

    Поведение при нарушении price_monotonic¶

    Если same_side ∧ same_timestamp ∧ contiguous_ids ∧ ¬price_monotonic — это аномалия данных (matching engine так не работает). Не склеиваем. Текущая chain закрывается, B становится началом новой.

    Такие случаи стоит логировать на DEBUG-уровне — могут быть индикатором багов парсинга или corrupted feed.

    LogicalTrade¶

    Каждая chain после реконструкции = один LogicalTrade со свойствами:

    LT = {
    side               : "buy" | "sell"               # = chain[0].side
    timestamp_first    : int                          # = chain[0].timestamp_ms
    timestamp_last     : int                          # = chain[-1].timestamp_ms
                                                      #   при ε=0 равен timestamp_first
    n_levels           : int                          # = len(chain)
    is_multilevel      : bool                         # = (n_levels ≥ 2)

    total_size         : float                        # Σ aggTrade.size
    total_cost         : float                        # Σ aggTrade.size × aggTrade.price (USD)
    vwap               : float                        # = total_cost / total_size

    price_first        : float                        # = chain[0].price       (best price)
    price_last         : float                        # = chain[-1].price      (deepest level)
    price_delta_pct    : float                        # = (price_last − price_first) × side_sign / price_first
                                                      #   side_sign = +1 if buy, −1 if sell
                                                      #   ≥ 0 для нормальной агрессии
}

    price_delta_pct интерпретация. Для buy-агрессии taker идёт вверх по ask-стороне, price_last > price_first, side_sign = +1, delta положительная — «цена ушла на X% вверх». Для sell-агрессии аналогично через минус. То есть price_delta_pct ≥ 0 для нормальной multilevel-агрессии; ровно 0 для single-level (is_multilevel = False).

    Назначение бара (ML.B = (а))¶

    LogicalTrade попадает в бар B если LT.timestamp_first ∈ B. Если агрегация теоретически пересекает границу бара (что при ε=0 невозможно — все aggTrades имеют один timestamp — но защитно): timestamp_last может оказаться в следующем баре, но трейд считается в баре своего timestamp_first.

    Почему различаем ml и sl¶

    После реконструкции каждый логический трейд попадает в одну из двух категорий:

    • ML (multilevel) — крупный/голодный ордер, пробил несколько ценовых уровней. Симптом сильного давления, спешки, информированного flow.
    • SL (single-level) — обычный ордер, поместился в один уровень. Фон рынка, retail и пассивные trades.

    Раздельная статистика по этим двум классам даёт сигналы о структуре агрессии в баре. Например, если объём ml резко вырос относительно sl — кто-то «ломится» через стакан, ожидаемо повышение волатильности и направленное движение цены. Метрики ниже описывают это под разными углами: количество, объём, средний размер, цена исполнения, ценовое влияние.

    Конвенция имён¶

    Применяется унифицированная конвенция (см. trades-v2.md):

    <side>_<metric>_<tag>            # без квантильного фильтра
<side>_<metric>_<tag>_quantile_q  # с квантильным фильтром

side    ∈ {buy, sell}             (или отсутствует для no-side метрик)
tag     ∈ {ml, sl}
q       ∈ {0.25, 0.5, 0.75, 0.9, 0.95}

    Спецификационные имена buy_ml_cost_* стали buy_cost_ml_quantile_q (тег перенесён к метрике, фильтр в конец).

    Нотация¶

    LogicalTrades(B) = [LT : LT.timestamp_first ∈ B]
BuyLT(B)     = [LT ∈ LogicalTrades(B) : LT.side == "buy"]
SellLT(B)    = [LT ∈ LogicalTrades(B) : LT.side == "sell"]

BuyLT_ML(B)  = [LT ∈ BuyLT(B)  : LT.is_multilevel]
BuyLT_SL(B)  = [LT ∈ BuyLT(B)  : not LT.is_multilevel]
SellLT_ML(B) = [LT ∈ SellLT(B) : LT.is_multilevel]
SellLT_SL(B) = [LT ∈ SellLT(B) : not LT.is_multilevel]

LT_ML(B)     = [LT ∈ LogicalTrades(B) : LT.is_multilevel]      # обе стороны
LT_SL(B)     = [LT ∈ LogicalTrades(B) : not LT.is_multilevel]

    L_ML.1 — Counts¶

    Количество логических трейдов по типу:

    buy_trade_count_ml(B)  = |BuyLT_ML(B)|              ≥ 0  (0 если пусто)
buy_trade_count_sl(B)  = |BuyLT_SL(B)|              ≥ 0
sell_trade_count_ml(B) = |SellLT_ML(B)|             ≥ 0
sell_trade_count_sl(B) = |SellLT_SL(B)|             ≥ 0

    Что говорит. Соотношение ml/sl — индикатор «температуры» бара. Много ml → крупных агрессий было непропорционально много (информированный flow). Перекос ml в одну сторону → направленное давление.

    4 ключа.

    L_ML.2 — Cost totals¶

    Суммарный USD-ноционал по типу:

    buy_cost_ml(B)  = Σ LT.total_cost  for LT ∈ BuyLT_ML(B)             ≥ 0
buy_cost_sl(B)  = Σ LT.total_cost  for LT ∈ BuyLT_SL(B)             ≥ 0
sell_cost_ml(B) = Σ LT.total_cost  for LT ∈ SellLT_ML(B)            ≥ 0
sell_cost_sl(B) = Σ LT.total_cost  for LT ∈ SellLT_SL(B)            ≥ 0

    Пустой бар → 0.0.

    Инвариант с trades-v2: 

    buy_cost(B) = buy_cost_ml(B) + buy_cost_sl(B)
sell_cost(B) = sell_cost_ml(B) + sell_cost_sl(B)

    Что говорит. Доля cost_ml от общего cost показывает сколько USD-объёма пришло через крупные агрессии. Если 80% денег в ml — рынок двигают пара китов, а не толпа retail. Полезно как нормализатор перед сравнением баров между собой.

    4 ключа.

    L_ML.3 — Mean cost (per trade)¶

    Средний размер логического трейда по типу:

    buy_mean_cost_ml(B)  = mean(LT.total_cost  for LT ∈ BuyLT_ML(B))
                     = NaN  if BuyLT_ML(B) is empty
buy_mean_cost_sl(B)  = mean(LT.total_cost  for LT ∈ BuyLT_SL(B))
                     = NaN  if BuyLT_SL(B) is empty
sell_mean_cost_ml(B) = аналогично
sell_mean_cost_sl(B) = аналогично

    Пустой подмножество → NaN (не 0.0 — нет трейдов, чтобы усреднить).

    Что говорит. Средний размер ml-трейда показывает «насколько крупными были крупные» в этом баре. Если средний ml одного бара $5k, а другого $500k — у второго совсем другой класс игроков.

    4 ключа.

    L_ML.4 — VWAP¶

    Средневзвешенная по объёму цена ml/sl-трейдов:

    buy_vwap_ml(B)  = Σ(LT.total_cost) / Σ(LT.total_size)  for LT ∈ BuyLT_ML(B)
                = NaN  if Σ(LT.total_size) = 0  (включая случай BuyLT_ML(B) is empty)
buy_vwap_sl(B)  = аналогично
sell_vwap_ml(B) = аналогично
sell_vwap_sl(B) = аналогично

    Что говорит. Разница vwap_ml − vwap_sl ≈ effective price impact крупных ордеров. На толстом стакане разница маленькая (ml едва уходит вглубь), на тонком — большая. Полезно как proxy для ликвидности.

    4 ключа.

    L_ML.5 — Quantile-filtered cost (top q% по размеру)¶

    Сумма USD-ноционала ml/sl-трейдов из топ-q% по total_cost:

    threshold_buy_ml_q(B) = quantile([LT.total_cost  for LT ∈ BuyLT_ML(B)], q)

buy_cost_ml_quantile_q(B) = Σ LT.total_cost  for LT ∈ BuyLT_ML(B)
                                              with LT.total_cost ≥ threshold_buy_ml_q(B)
                          = NaN  if BuyLT_ML(B) is empty
buy_cost_sl_quantile_q(B) = аналогично через BuyLT_SL
sell_cost_ml_quantile_q(B) = ...
sell_cost_sl_quantile_q(B) = ...

    Что говорит. Концентрируемся на хвосте распределения. q = 0.95 для ml = «сколько USD прошло через топ-5% самых жирных multilevel-агрессий». Изолирует сигнал «китов» от шума мелких ml.

    Для каждого q ∈ {0.25, 0.5, 0.75, 0.9, 0.95} — 4 базы × 5 = 20 ключей.

    L_ML.6 — Quantile boundary¶

    Значение total_cost на границе квантиля q (не сумма, а сама граница):

    buy_trade_cost_ml_quantile_q(B) = quantile([LT.total_cost for LT ∈ BuyLT_ML(B)], q)
                                = NaN  if BuyLT_ML(B) is empty
buy_trade_cost_sl_quantile_q(B) = quantile([... for LT ∈ BuyLT_SL(B)], q)
sell_trade_cost_ml_quantile_q(B) = ...
sell_trade_cost_sl_quantile_q(B) = ...

    Что говорит. Сама граница топ-q% (USD-размер на этой границе). Если buy_trade_cost_ml_quantile_0.95 = $30k — значит топ-5% multilevel buy этого бара начинаются от $30k. Прямое сравнение «насколько крупно было то что считалось крупным» между барами / тикерами.

    Для каждого q — 4 базы × 5 = 20 ключей.

    L_ML.7 — Mean price delta (только для ml)¶

    Средний процент изменения цены, который вызывает multilevel-агрегация, среди топ-q% самых крупных multilevel трейдов по total_cost:

    threshold_buy_ml_q(B) = quantile([LT.total_cost for LT ∈ BuyLT_ML(B)], q)
top_buy_ml_q(B)       = [LT ∈ BuyLT_ML(B) : LT.total_cost ≥ threshold_buy_ml_q(B)]

buy_mean_price_delta_ml_quantile_q(B) = mean(LT.price_delta_pct  for LT ∈ top_buy_ml_q(B))
                                      = NaN  if top_buy_ml_q(B) is empty
sell_mean_price_delta_ml_quantile_q(B) = аналогично через SellLT_ML

    Sl-версия не определена — для single-level трейдов price_delta_pct = 0 по построению, метрика бы была тривиальной.

    Что говорит. На сколько % цена двигалась во время самых крупных multilevel-агрессий. Большие значения = тонкий стакан, цена «уезжает» под крупным ордером. Прямой proxy для близости волатильности.

    Для каждого q — 2 стороны × 5 = 10 ключей.

    L_ML.8 — No-side aggregates¶

    Метрики без разделения по сторонам — на всех multilevel/single-level трейдах бара.

    Mean cost (no side)¶

    mean_cost_ml(B) = mean(LT.total_cost  for LT ∈ LT_ML(B))
                = NaN  if LT_ML(B) is empty
mean_cost_sl(B) = mean(LT.total_cost  for LT ∈ LT_SL(B))
                = NaN  if LT_SL(B) is empty

    Что говорит. «Средний размер ml/sl-агрессии без учёта стороны». Полезно когда направление неважно, нужен общий уровень крупности.

    2 ключа.

    Mean price delta (no side, quantile-filtered)¶

    threshold_ml_q(B) = quantile([LT.total_cost for LT ∈ LT_ML(B)], q)
top_ml_q(B)       = [LT ∈ LT_ML(B) : LT.total_cost ≥ threshold_ml_q(B)]

mean_price_delta_ml_quantile_q(B) = mean(LT.price_delta_pct  for LT ∈ top_ml_q(B))
                                  = NaN  if top_ml_q(B) is empty

    Что говорит. Аналог L_ML.7 без сторон — общая «волатильность под ml». Если значение растёт от бара к бару → стакан истончается, готовится крупное движение в любую сторону.

    Для каждого q — 5 ключей.

    Ограничения и зависимости¶

    • Реконструкция доступна на чистых Binance aggTrade-данных. Для других источников требуется наличие first_trade_id/last_trade_id.
    • Алгоритм — аппроксимация L3 (полной book-by-order информации). False positives крайне редки благодаря contiguous_ids; false negatives возможны при engine timestamp jitter (ε=0 строгое равенство).
    • Все метрики per-bar, без 9-агг разворачивания.
    • В live доступно сразу. В backtest — тоже (aggTrade parquet содержит все нужные поля).
    • Нарушения price-monotonic во входных данных закрывают цепочку (трейды не склеиваются), потенциально логируются на DEBUG.
