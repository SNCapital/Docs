    L2-метрики ордер-бука¶

    Этот документ описывает L2-подмножество метрик ордер-бука — метрики, которые используют не только верхушку стакана, но и глубину по уровням. Метрики L1 (best, last_best, spread) живут в orderbook-l1.md.

    Документ описывает целевую спецификацию — то, как метрики должны считаться. Текущая реализация в коде может отличаться.

    Общий контекст для всех L2-метрик¶

    Источники данных¶

    L2-метрики делятся на две группы по источнику:

    1. Snapshot-based (L2.1–L2.7, L2.10): считаются из периодических снапшотов локальной книги. Снапшоты восстанавливаются из L2-апдейтов @depth алгоритмом Binance, сэмплируются с настраиваемой частотой (см. orderbook-l1.md → «Сэмплирование»). Default 1 Гц = ~1800 снапшотов на 30-минутный бар.

    2. Diff-stream-based (L2.8, L2.9): считаются из потока сырых @depth-диффов в реальном времени. Не требуют снапшотов, но и не доступны в backtest (диффы на диск не пишутся, см. бэклог B3).

    Дubст filter¶

    Сейчас не применяется — все метрики считаются по всем уровням. Реализация — в бэклоге пункт B1.

    NaN-семантика¶

    Та же, что и в L1 (см. orderbook-l1.md → «NaN-семантика»): - Тики массива снапшотов сохраняются даже когда обе стороны NaN. - Длины массивов bid и ask time-aligned. - NaN отбрасываются перед агрегацией.

    Дубликат цены в снапшоте¶

    (side, price) встречается ровно один раз. Дубликат → InvariantError.

    Нотация¶

    Используется нотация из orderbook-l1.md — snapshot(t).bids/asks, size_at(t, side, p), Snapshots(B), S_M(B), F_M(B), F'_M(B), n_M(B), n'_M(B). Здесь только специфичная для L2 нотация (зоны).

    Оффсеты¶

    L2-метрики параметризованы оффсетом X. Поддерживаются два типа:

    Процентные оффсеты — 12 значений: 

    {0.01, 0.05, 0.1, 0.25, 0.5, 1, 2, 5, 10, 25, 50, 100}

    top_x оффсеты — 8 значений: 

    {1, 5, 10, 25, 50, 100, 500, 1000}

    Итого 20 оффсетов на большинство метрик. Для liq_shock (L2.10) набор сокращён до 12 — см. соответствующий раздел.

    Зона для процентного оффсета X¶

    Анкер на best каждой стороны:

    zone_bid_pct_X(t) = { (p, s) ∈ snapshot(t).bids : p ≥ best_bid_price(t) × (1 − X/100) }
zone_ask_pct_X(t) = { (p, s) ∈ snapshot(t).asks : p ≤ best_ask_price(t) × (1 + X/100) }

zone_bid_pct_X(t) = ∅  if best_bid_price(t) = NaN
zone_ask_pct_X(t) = ∅  if best_ask_price(t) = NaN

    Зона для top_x оффсета¶

    Требует mid(t) (определён только когда обе стороны finite) и tick_size τ(t) из биржевого exchange_info на день снапшота.

    Якорь — ближайший тик строго по другую сторону от мида, чтобы p_1 гарантированно лежал в правильной полуплоскости (по решению L2.1.b — вариант «б»):

    floor_strict_tick(m, τ) = highest tick price < m on the τ-grid     # для bid
ceil_strict_tick(m, τ)  = lowest tick price > m on the τ-grid      # для ask

         floor_strict_tick(m, τ) = (floor(m / τ) − 1) × τ   if m / τ is integer
                                 = floor(m / τ)         × τ   otherwise
         ceil_strict_tick(m, τ)  = (ceil(m / τ) + 1)   × τ   if m / τ is integer
                                 = ceil(m / τ)           × τ   otherwise

zone_bid_top_x(t) = [ p_i = floor_strict_tick(mid(t), τ(t)) − (i−1) × τ(t)  : i = 1..x ]
zone_ask_top_x(t) = [ p_i = ceil_strict_tick(mid(t), τ(t))  + (i−1) × τ(t)  : i = 1..x ]

zone_bid_top_x(t) = []  if mid(t) = NaN  OR  τ(t) недоступен
zone_ask_top_x(t) = []  if mid(t) = NaN  OR  τ(t) недоступен

    Если τ(t) недоступен (нет exchange_info за день) → ошибка (по решению L2.1.c).

    Расчёт cost, size, vwap в зоне — один проход¶

    Для всех snapshot-based метрик в каждой зоне используется единый расчёт:

    def compute_zone_metrics(zone_pairs):     # zone_pairs = list of (price, size)
    cost = 0.0
    size = 0.0
    for (p, s) in zone_pairs:
        cost += p × s
        size += s
    vwap = cost / size  if size > 0  else NaN
    return cost, size, vwap

    Для процентной зоны zone_pairs = zone_bid_pct_X(t) (множество из снапшота). Для top_x зоны zone_pairs — список из x пар, где для каждой p_i берётся size_at(t, side, p_i) (или 0 если в снапшоте такой цены нет).

    Этот один проход даёт сразу bid_X_cost(t), bid_X_size(t), bid_X_vwap(t) (и симметрично для ask).

    Шаблоны агрегации¶

    Используются 9-агг и 10-агг шаблоны из orderbook-l1.md. Никакого нового агг-стиля для L2 нет.

    L2.1 — {ask/bid}_X_cost¶

    Смысл. Суммарный USD-ноционал ордеров стороны bid/ask в зоне X.

    Per-snapshot¶

    bid_X_cost(t) = Σ p × s   для (p, s) ∈ zone_bid_X(t)        if zone определена
              = NaN                                          otherwise

ask_X_cost(t) = Σ p × s   для (p, s) ∈ zone_ask_X(t)        if zone определена
              = NaN                                          otherwise

    «Zone определена» означает: для процентного — соответствующий best finite; для top_x — mid finite и tick_size доступен.

    Для top_x зоны пустые слоты дают вклад p × 0 = 0 — то есть суммируем только реально заполненные позиции грида, но в формальном смысле итерируем по всем x.

    Edge cases¶

    Тип оффсета bid_X_cost = NaN когда ask_X_cost = NaN когда
    Процентный best_bid_price(t) = NaN best_ask_price(t) = NaN
    top_x mid(t) = NaN (любая сторона пуста) mid(t) = NaN
    top_x τ(t) недоступен → ошибка τ(t) недоступен → ошибка

    Процентный обрабатывает каждую сторону независимо, top_x — обе валятся вместе при пустоте mid.

    Per-bar — 9-агг шаблон¶

    Подставляем M(t) := bid_X_cost(t) (или ask_X_cost(t)) в 9-агг шаблон. На каждый оффсет — 9 ключей × 2 стороны = 18.

    Всего: 18 × 20 оффсетов = 360 ключей.

    L2.2 — {ask/bid}_X_size¶

    Смысл. Суммарный объём (в монете) ордеров стороны в зоне X.

    Per-snapshot¶

    bid_X_size(t) = Σ s   для (p, s) ∈ zone_bid_X(t)        if zone определена
              = NaN                                      otherwise

ask_X_size(t) = Σ s   для (p, s) ∈ zone_ask_X(t)        if zone определена
              = NaN                                      otherwise

    Edge cases идентичны L2.1.

    Per-bar — 9-агг шаблон¶

    18 × 20 = 360 ключей.

    L2.3 — {ask/bid}_X_vwap¶

    Смысл. VWAP — средневзвешенная по объёму цена ордеров в зоне X. Эффективная цена для маркет-ордера, который выкупил бы всю зону.

    Per-snapshot¶

    bid_X_vwap(t) = bid_X_cost(t) / bid_X_size(t)
              = NaN  if  bid_X_size(t) = 0  OR  bid_X_size(t) = NaN

ask_X_vwap(t) = ask_X_cost(t) / ask_X_size(t)
              = NaN  if  ask_X_size(t) = 0  OR  ask_X_size(t) = NaN

    Численно равен прямому вычислению (Σ p×s) / (Σ s) в одном проходе по зоне (см. «Расчёт cost, size, vwap в зоне» в общем контексте).

    Когда bid_X_size = 0¶

    • Процентный: zone содержит хотя бы один уровень (best_bid сам входит в зону), значит size > 0. Случай size = 0 невозможен пока best_bid finite.
    • top_x: возможен, если все x грид-позиций пусты в снапшоте — тогда cost = 0, size = 0, vwap = NaN.

    Per-bar — 9-агг шаблон¶

    18 × 20 = 360 ключей.

    L2.4 — cost_imbalance_X (две формы)¶

    Смысл. Соотношение USD-ноционала bid и ask в зоне X — индикатор давления на стороне ордерной книги.

    Per-snapshot — две независимые базовые метрики¶

    Ratio (по букве спеки, асимметрично): 

    cost_imbalance_X_ratio(t) = bid_X_cost(t) / ask_X_cost(t)
                          = NaN  if  bid_X_cost(t) = NaN
                                OR  ask_X_cost(t) = NaN
                                OR  ask_X_cost(t) = 0

# Диапазон: [0, +∞);  значение 1 = баланс, > 1 = bid тяжелее

    Norm (нормализованная, симметрично с liq_shock_ratio): 

    cost_imbalance_X_norm(t) = bid_X_cost(t) / (bid_X_cost(t) + ask_X_cost(t))
                         = NaN  if  bid_X_cost(t) = NaN
                               OR  ask_X_cost(t) = NaN
                               OR  bid_X_cost(t) + ask_X_cost(t) = 0

# Диапазон: [0, 1];  значение 0.5 = баланс, > 0.5 = bid тяжелее

    Edge cases¶

    Состояние ratio norm
    top_x, mid finite, bid грид пуст (size = 0) 0 (валидное) 0 (валидное)
    top_x, mid finite, ask грид пуст NaN (деление на 0) 1 (валидное)
    top_x, mid finite, обе пустые NaN (0/0) NaN (0/0)
    top_x, mid = NaN NaN NaN

    Per-bar — 9-агг шаблон¶

    Каждая из двух форм через 9-агг = 18 ключей на оффсет.

    Всего: 18 × 20 = 360 ключей.

    L2.5 — vwap_X_midprice¶

    Смысл. Среднее арифметическое VWAP'ов bid и ask в зоне X. «Глубинный mid» — оценка fair-цены, учитывающая объёмы в зоне, не только верхушку.

    Per-snapshot¶

    vwap_X_midprice(t) = (bid_X_vwap(t) + ask_X_vwap(t)) / 2
                   = NaN  if  bid_X_vwap(t) = NaN
                         OR  ask_X_vwap(t) = NaN

    Это простое среднее, не volume-weighted. Если хотим взвесить по объёмам — это уже не midprice, а «глобальный VWAP zone».

    Per-bar — 9-агг шаблон¶

    9 × 20 = 180 ключей (одна метрика на оффсет, без сторон).

    L2.6 — Cross-snapshot diff / logreturn варианты¶

    Применяется 10-агг шаблон с zero-drop и _sum (см. L1).

    Метрики¶

    Базовая Тип Сторон
    bid_X_cost_diff, ask_X_cost_diff diff (аддитивная: cost) 2
    bid_X_size_diff, ask_X_size_diff diff (аддитивная: size) 2
    bid_X_vwap_logreturn, ask_X_vwap_logreturn logreturn (мультипликативная: цена) 2
    vwap_X_midprice_logreturn logreturn (мультипликативная: цена) 1

    Per-snapshot формулы¶

    Diff (для аддитивных cost/size): 

    M_diff(t_i) = M(t_i) − M(t_{i−1})        if M(t_i), M(t_{i−1}) finite, i ≥ 2
            = NaN                         otherwise

    Logreturn (для мультипликативных vwap/midprice): 

    M_logreturn(t_i) = log(M(t_i) / M(t_{i−1}))    if M(t_i), M(t_{i−1}) finite > 0, i ≥ 2
                 = NaN                          otherwise

    i = 1 (первый снапшот бара) → всегда NaN, предшественника нет.

    Почему diff vs logreturn¶

    Семейство Природа Может быть 0? Тип изменения
    cost, size аддитивная (USD/монеты) да абсолютная (diff)
    vwap, midprice мультипликативная (цена) нет (>0) относительная (logreturn)

    log(0) неопределён → к нулевой cost нельзя применить logreturn. К нулевой vwap тоже, но vwap не нулевой пока есть ликвидность.

    Per-bar — 10-агг с zero-drop и _sum¶

    Берём массив cross-snapshot значений, выкидываем NaN и нули: - 10 ключей на (стороне × оффсете) для двусторонних метрик - 10 ключей на оффсете для односторонней vwap_X_midprice_logreturn

    Сводка¶

    Метрика Ключей на оффсет × 20 оффсетов
    bid_X_cost_diff 10 200
    ask_X_cost_diff 10 200
    bid_X_size_diff 10 200
    ask_X_size_diff 10 200
    bid_X_vwap_logreturn 10 200
    ask_X_vwap_logreturn 10 200
    vwap_X_midprice_logreturn 10 200
    Итого L2.6 1400

    Спека не определяет cost_imbalance_X_diff, vwap_X_midprice_diff, bid_X_cost_logreturn — пропускаем.

    L2.7 — Levels metrics¶

    Смысл. Распределение размеров ордеров по уровням в зоне X.

    Три базовые per-snapshot метрики¶

    {bid/ask}_X_levels_size_count¶

    Количество уровней в зоне. Семантика зависит от типа оффсета:

    # Процентный
bid_X_levels_size_count(t) = | zone_bid_pct_X(t) |       if best_bid_price(t) finite
                           = NaN                         otherwise

# top_x
bid_top_x_levels_size_count(t) = x                       if mid(t) finite AND τ доступен
                               = NaN                     otherwise

    Для процентного — реальное число уровней в зоне (всегда ≥ 1, т.к. best_bid сам в зоне). Для top_x — всегда x (число слотов грида).

    {bid/ask}_X_levels_size_count_nonzero¶

    Количество уровней с реальной ликвидностью (size > 0):

    # Процентный
bid_X_levels_size_count_nonzero(t) = | zone_bid_pct_X(t) |       (то же, что count)
                                   = NaN if best_bid NaN

# top_x
bid_top_x_levels_size_count_nonzero(t) = | { i : size_at(t, "bid", p_i) > 0,  i = 1..x } |
                                       = NaN  if mid(t) = NaN

    Для процентного _count и _count_nonzero идентичны (в L2-снапшотах по контракту нет уровней с s = 0). Для top_x _count_nonzero ≤ x — сколько слотов из x реально заполнены.

    {bid/ask}_X_levels_size_mean¶

    Средний размер на уровень в зоне. Знаменатель = count (с учётом семантики типа оффсета):

    bid_X_levels_size_mean(t) = bid_X_size(t) / bid_X_levels_size_count(t)
                          = NaN  if bid_X_size(t) = NaN  OR  count = 0  OR  count = NaN

    Различие в знаменателе — критическое: - Процентный: делим на count = реальное число уровней (== count_nonzero). - top_x: делим на x (count) включая пустые слоты — соответствует примеру из спеки (5 + 24×0) / 25 = 0.2.

    Edge cases¶

    Состояние count count_nonzero mean
    Процентный, best_bid NaN NaN NaN NaN
    Процентный, best_bid finite ≥ 1 = count well-defined
    top_x, mid NaN NaN NaN NaN
    top_x, mid finite, грид заполнен x ≤ x well-defined
    top_x, mid finite, грид пуст x 0 0.0 (= 0/x)

    Per-bar — 9-агг шаблон¶

    Каждая базовая через 9-агг × 2 стороны:

    Базовая Ключей на оффсет (× 2 стороны) × 20 оффсетов
    levels_size_count 18 360
    levels_size_count_nonzero 18 360
    levels_size_mean 18 360
    Итого L2.7 1080

    Для процентных оффсетов _count и _count_nonzero будут идентичны по значению — но эмитим обе для единообразия схемы (по решению L2.D).

    L2.8 — OB updates: bar-level счётчики¶

    Смысл. Активность ордеров в стакане за бар — сколько было размещено / отменено / исполнено, какой объём прошёл через place- и remove-события.

    Источник. Поток сырых WS @depth-диффов, классифицируемых in-process в реальном времени. Bar-level аккумуляторы. В backtest из parquet недоступно (см. бэклог B3).

    Классификация события¶

    При diff-апдейте (side, price, new_size) сравниваем с prev_size из локальной книги:

    prev_size = local_book.size_at(side, price)    # 0 если уровня не было

if new_size == 0 AND prev_size > 0:
    record(REMOVE, side, price, delta = prev_size)
elif new_size > prev_size:
    record(PLACE, side, price, delta = new_size − prev_size)
elif new_size < prev_size:
    record(REMOVE, side, price, delta = prev_size − new_size)
else:    # new_size == prev_size  OR  (new_size == 0 AND prev_size == 0)
    no-op    # подтверждение или повтор пустого

    События во время bootstrap/resync книги не считаются (replay исторических, не реальный flow).

    Метрики¶

    Для каждой стороны и действия (place/remove) — три счётчика:

    bid_place_count(B)  = число PLACE-событий стороны bid в баре B
bid_place_size(B)   = Σ delta по всем bid PLACE-событиям
bid_place_cost(B)   = Σ delta × price по всем bid PLACE-событиям

bid_remove_count(B) = число REMOVE-событий стороны bid
bid_remove_size(B)  = Σ delta по всем bid REMOVE-событиям
bid_remove_cost(B)  = Σ delta × price по всем bid REMOVE-событиям

    Симметрично для ask.

    Edge cases¶

    • Бар без diff-событий → все 12 метрик = 0.0 (валидное «нет активности», не NaN).

    Семантика remove¶

    REMOVE включает и отменённые, и исполненные ордера. На L2 мы не можем различить — оба видны как падение size_at_level. Различение требует сопоставления с трейдами того же бара.

    L2 → L3 аппроксимация¶

    L2 не различает множественные place/cancel на одной цене. Real L3 дал бы точные счётчики, но Binance L3 не отдаёт.

    Per-bar агрегация — НЕ применяется¶

    Все 12 метрик уже bar-level скаляры. Через 9-агг не идут.

    Сводка¶

    {bid/ask}_{place,remove}_{cost,size,count}    # 6 × 2 = 12 ключей

    Итого L2.8: 12 ключей.

    L2.9 — OB updates: per-zone метрики¶

    Смысл. Те же diff-события, что в L2.8, но отфильтрованные по зоне X на момент события.

    Источник. Тот же поток @depth-диффов. Доступно только в live.

    Зональный фильтр события¶

    При diff-событии (side, price, delta, t_event) парсер знает mid(t_event), best_bid(t_event), best_ask(t_event) из локальной книги. Для каждого оффсета X проверяет:

    in_zone_pct_X(price, side, t) =
    (side == "bid" AND price ≥ best_bid(t) × (1 − X/100))
  OR (side == "ask" AND price ≤ best_ask(t) × (1 + X/100))

in_zone_top_x(price, side, t) =
    price ∈ zone_{side}_top_x(t)            # тиковые позиции грида

    Если событие попадает в зону — оно учитывается в аккумуляторах этой зоны. Одно событие может попасть в несколько зон (вложенные зоны имеют независимые счётчики).

    Три базовые метрики (per-zone, bar-level)¶

    1. {bid/ask}_X_place_vwap¶

    VWAP всех place-событий в зоне X за бар:

    bid_X_place_vwap(B) = (Σ price × delta) / (Σ delta)
                       где сумма по всем bid PLACE событиям с in_zone(price, "bid", t_event)
                    = NaN  if  Σ delta = 0  (нет place-событий в зоне)

    (remove_vwap не определена в спеке — пропускаем.)

    2. {bid/ask}_X_place_size_skew¶

    Скос распределения размеров place-событий в зоне:

    deltas_bid_X(B) = [delta : bid PLACE events with in_zone(price, "bid", t_event)]
bid_X_place_size_skew(B) = scipy.stats.skew(deltas_bid_X(B), bias=False)
                         = NaN  if  | deltas | < 3  OR  std(deltas) ≈ 0

    3. {bid/ask}_X_remove_quantile_q¶

    Квантиль распределения размеров remove-событий в зоне:

    deltas_bid_remove_X(B) = [delta : bid REMOVE events with in_zone(price, "bid", t_event)]
bid_X_remove_quantile_q(B) = numpy.quantile(deltas_bid_remove_X(B), q)
                           = NaN  if  deltas пустой

    Для каждого q ∈ {0.25, 0.5, 0.75, 0.9, 0.95} (фиксированный набор).

    Per-bar агрегация — НЕ применяется¶

    Все per-zone метрики уже bar-level (одно число на бар на оффсет на сторону), не через 9-агг.

    Сводка¶

    Метрика На (зону × сторону) × 2 стороны × 20 оффсетов
    {bid/ask}_X_place_vwap 1 40
    {bid/ask}_X_place_size_skew 1 40
    {bid/ask}_X_remove_quantile_q (× 5 квантилей) 5 200
    Итого L2.9 280

    L2.10 — liq_shock метрики¶

    Смысл. «Шок ликвидности» — насколько текущий объём в зоне отклонился от 10-секундного среднего. Детектор резких изменений плотности стакана.

    Сокращённый набор оффсетов¶

    В отличие от остальных L2-метрик (20 оффсетов), liq_shock использует 12 оффсетов — компромисс между покрытием и количеством ключей:

    Процентные:  {0.05, 0.1, 0.25, 0.5, 1, 5, 25, 50}    # 8
top_x:       {1, 5, 10, 100}                          # 4

    Per-snapshot — три базовые метрики¶

    1. liq_shock_{side}_X — отклонение от 10с-baseline¶

    Использует уже вычисленный bid_X_size(t) (или ask_X_size(t)) из L2.2.

    In-memory rolling-окно длиной 10 секунд хранит пары (τ, bid_X_size(τ)). На каждом снапшоте:

    W_bid_X(t) = [ (τ, bid_X_size(τ))  :  t − 10s ≤ τ ≤ t,  bid_X_size(τ) finite ]

mean_bid_X(t) = mean( v  :  (τ, v) ∈ W_bid_X(t) )

liq_shock_bid_X(t) = bid_X_size(t) / mean_bid_X(t)
                   = NaN  if  W_bid_X(t) пуст
                         OR  mean_bid_X(t) ≤ 0
                         OR  bid_X_size(t) = NaN

    Симметрично для liq_shock_ask_X(t).

    Окно фиксировано 10 секунд, не конфигурируемо.

    Cross-bar state. Окно переезжает через границы баров — на момент t в начале нового бара часть окна ещё в предыдущем. Это in-process состояние, не сбрасывается на bar tick'е.

    2. liq_shock_ratio_X — нормализованный imbalance в зоне¶

    liq_shock_ratio_X(t) = bid_X_size(t) / (bid_X_size(t) + ask_X_size(t))
                     = NaN  if  bid_X_size(t) = NaN
                           OR  ask_X_size(t) = NaN
                           OR  bid_X_size(t) + ask_X_size(t) = 0

    Диапазон [0, 1]. 0.5 = баланс, > 0.5 = bid тяжелее. Аналогично cost_imbalance_X_norm из L2.4, но взвешено по size, не по cost.

    Edge cases¶

    Состояние liq_shock_bid_X liq_shock_ratio_X
    Окно пустое (первая секунда после рестарта) NaN well-defined (от окна не зависит)
    top_x, обе зоны пусты если mean=0 → NaN, иначе 0 NaN (0/0)
    top_x, mid = NaN NaN NaN
