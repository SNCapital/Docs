    Maker orders — реконструкция исполненных лимитников¶

    Альтернативный источник для трейд-метрик. В то время как trades-* файлы описывают агрегации со стороны taker'а (агрессора), этот файл — агрегации со стороны maker'а (того, чьё лимитное предложение исполнили).

    Только spot. Только на споте Binance отдаёт оба фида параллельно (aggTrades и trades/raw fills), что и позволяет реконструировать maker-сторону. На USDM raw trades-фид недоступен.

    Документ описывает целевую спецификацию.

    Зачем нужно отдельно¶

    Один taker-ордер может исполниться об несколько maker-ордеров на одном уровне цены. То есть:

    • 1 taker buy 1.5 BTC → может пройти через 3 разных maker'а по 0.5 BTC
    • В trade-tape мы видим 3 raw matches (по одному на maker'а)
    • Эти 3 матча агрегируются в 1 aggTrade (один уровень, один taker)

    В terms трейд-метрик: - Taker-сторона (trades-v2): этот taker = 1 логический трейд - Maker-сторона (maker-orders): эти 3 maker'а = 3 отдельных «логических трейда» на стороне maker'а

    Это даёт другую перспективу на тот же flow: вместо «как агрессивно рынок ел» → «насколько крупны были лимитники, которые рынок съел».

    Источник данных¶

    Парсер пишет на споте две партиции: 

    data/market=spot/type=aggtrades/dt=…/symbol=…/   (live)
data/market=spot/type=aggTrades/dt=…/symbol=…/   (historical)
data/market=spot/type=trades/dt=…/symbol=…/      (raw fills, опт. — см. ниже)

    type=trades/ (raw, по одной записи на каждый maker-fill) пишется парсером только при LIVE_PREFER_AGGTRADES=False или LIVE_RECONSTRUCT_MULTILEVEL=True. По умолчанию выключено.

    Без type=trades/ partition восстановление maker-стороны невозможно. Это блокирующее условие — отдельный пункт в backlog.md B5 потенциально (для расширения по умолчанию).

    Raw trade поля¶

    timestamp_ms     : int64
trade_id         : int64    # уникальный id в пределах символа
price            : float
qty              : float
quote_qty        : float    # = price × qty
is_buyer_maker   : bool     # True → maker был на стороне bid (купить); taker продавал
                            # False → maker был на стороне ask (продать); taker покупал

    Связь raw trades и aggTrades¶

    Каждое aggTrade-событие имеет first_trade_id/last_trade_id — диапазон raw trade id'ов, которые оно агрегирует. По спецификации Binance: aggTrade объединяет raw trades с одинаковой ценой, одной стороной (одинаковый is_buyer_maker) и одним временем (в пределах одной обработки matching engine'ом).

    То есть raw trades внутри одного aggTrade-диапазона = последовательные maker-fills, которые taker съел на одном уровне цены.

    Алгоритм реконструкции maker fills¶

    Для каждого raw trade record создаём один логический «maker fill»:

    maker_fill = {
    timestamp     : trade.timestamp_ms,
    side          : "ask" if not trade.is_buyer_maker  # maker продавал → был на ask
                    else "bid",                         # maker покупал → был на bid
    price         : trade.price,
    size          : trade.qty,                          # размер этого fill'а maker'а
                                                          # (= размер raw trade'а)
    notional      : trade.price × trade.qty,
}

    size здесь — объём, который у этого maker'а был исполнен, не полный размер его ордера. Если maker имел 1 BTC лимитник, а taker взял 0.5 BTC — мы видим maker_fill с size = 0.5.

    То есть size это размер matching event'а, а не размер исходного maker-ордера. Это компромисс L2 → реконструкция не даёт нам полный размер исходного maker-ордера (для этого нужен L3-фид).

    Multilevel reconstruction — НЕ применяется¶

    В отличие от taker-стороны (где один agressor может пройти через 3 уровня и мы реконструируем его обратно как один LogicalTrade), для maker'а каждый matching event — это один уникальный maker-fill, независимо от того, был ли он частью taker'ского multilevel ордера или нет. Каждый raw trade = один maker fill = один логический трейд.

    Префикс maker_ в коде¶

    Important — naming convention deviation. Реализация (PR #38) префиксирует все ключи maker_ для collision avoidance с L2 orderbook namespace (bid_25_cost_*, ask_5_size_* etc.). Спека ниже использует bare ask_*/bid_* для clarity; в коде они становятся maker_ask_*/maker_bid_* (а side-less ключи — maker_vwap, maker_volatility, maker_kyle_lambda, …). См. PR #38.

    spec name              implementation name
─────────────────────────────────────────────
ask_count              maker_ask_count
bid_cost_quantile_0.95 maker_bid_cost_quantile_0.95
vwap                   maker_vwap
kyle_lambda            maker_kyle_lambda
asr_count              maker_asr_count

    MAKER_ORDERS_METRICS = list(_empty_maker_orders_metrics().keys()) — public schema, потребляется в metrics_dict._METRIC_SOURCE. Каждый ключ начинается с maker_; ивариант пинится тестом test_every_key_has_maker_prefix. Routing-инвариант (ветка metric_name.startswith("maker_") ДО общей bid_*/ask_* orderbook ветки) пинится test_no_collision_with_other_aggregators + test_maker_metrics_resolve_to_maker_orders.

    Конвенция имён¶

    Применяется к именам метрик из trades-v2.md:

    buy_*  →  ask_*       (taker buying = maker selling = ask side maker)
sell_* →  bid_*       (taker selling = maker buying = bid side maker)

    Метрики без side-префикса (vwap, volatility, hh, kyle_lambda, asr_*, OHLC) переносятся как есть — они не зависят от стороны и считаются на всех maker fills бара.

    Пример¶

    Слева — taker-side (trades-v2); посредине — спека maker-orders; справа — фактический ключ в коде (maker_ prefix).

    trades-v2 метрика     →   maker-orders (спека)   →   maker-orders (код)
──────────────────────────────────────────────────────────────────────────
buy_cost              →   ask_cost               →   maker_ask_cost
sell_cost             →   bid_cost               →   maker_bid_cost
buy_count             →   ask_count              →   maker_ask_count
sell_count            →   bid_count              →   maker_bid_count
buy_count_above_T     →   ask_count_above_T      →   maker_ask_count_above_T
buy_cost_quantile_q   →   ask_cost_quantile_q    →   maker_ask_cost_quantile_q
buy_vwap              →   ask_vwap               →   maker_ask_vwap
sell_vwap             →   bid_vwap               →   maker_bid_vwap
max_buy_trade_cost    →   max_ask_trade_cost     →   maker_max_ask_trade_cost
buy_trade_cost_quantile_q → ask_trade_cost_quantile_q → maker_ask_trade_cost_quantile_q

vwap                  →   vwap                   →   maker_vwap
volatility            →   volatility             →   maker_volatility
hh                    →   hh                     →   maker_hh
hh_buy                →   hh_ask                 →   maker_hh_ask
hh_sell               →   hh_bid                 →   maker_hh_bid
kyle_lambda           →   kyle_lambda            →   maker_kyle_lambda
asr_count             →   asr_count              →   maker_asr_count
asr_volume            →   asr_volume             →   maker_asr_volume
open / high / low / close → open/high/low/close  →   maker_open / maker_high / maker_low / maker_close

    Замечание про спеку. В исходном спеке пример переименования дан как buy_cost → bid_cost, что некорректно семантически — taker buying соответствует maker'у на ask-стороне, а не bid. Используем семантически верную конвенцию (buy → ask, sell → bid), которая согласуется с указанной в спеке тождественностью buy_cost (taker) = ask_cost (maker).

    Метрики¶

    Все метрики применяют формулы из trades-v2.md к списку maker_fills бара (вместо taker-trades). Все формулы идентичны, только данные другие.

    Counts¶

    ask_count(B), bid_count(B)                        →  maker_ask_count, maker_bid_count
ask_count_above_T(B), bid_count_above_T(B)    × 5 порогов T
                                                  →  maker_ask_count_above_T, maker_bid_count_above_T

    Что говорит. Сколько maker-ордеров было исполнено в баре. Высокий ask_count → много продавцов выставили лимитники, и их съели агрессивные покупатели. Прямой счётчик «активности на стороне предложения».

    12 ключей.

    Costs¶

    ask_cost(B), bid_cost(B)                          →  maker_ask_cost, maker_bid_cost
ask_cost_quantile_q(B), bid_cost_quantile_q(B)    × 5 квантилей
                                                  →  maker_ask_cost_quantile_q, maker_bid_cost_quantile_q

    Что говорит. Тот же total что у taker (тождество ниже), но доступ к квантильному разрезу maker-стороны.

    12 ключей.

    Trade cost quantile boundaries¶

    ask_trade_cost_quantile_q(B), bid_trade_cost_quantile_q(B)    × 5 q
                          →  maker_ask_trade_cost_quantile_q, maker_bid_trade_cost_quantile_q

    Что говорит. Размер maker-fill'а на границе топ-q% по баре. Большие значения → крупные maker'ы (киты-маркетмейкеры) активны.

    10 ключей.

    Max¶

    max_ask_trade_cost(B), max_bid_trade_cost(B)      →  maker_max_ask_trade_cost, maker_max_bid_trade_cost

    Что говорит. Самый крупный maker-fill в баре. Может быть индикатором китового лимитника, который был исполнен.

    2 ключа.

    VWAP¶

    ask_vwap(B), bid_vwap(B), vwap(B)                 →  maker_ask_vwap, maker_bid_vwap, maker_vwap

    Что говорит. Средневзвешенная цена исполнения maker-fills по сторонам. ask_vwap ≥ bid_vwap всегда (по построению ask > bid в момент сделки). Разница — implied effective spread.

    3 ключа.

    OHLC¶

    open(B), high(B), low(B), close(B)                →  maker_open, maker_high, maker_low, maker_close

    Те же определения что в trades-v2 — усреднение между ask/bid сторонами.

    4 ключа.

    Volatility¶

    volatility(B)                                     →  maker_volatility

    Std минутных log-returns цен maker-fills.

    1 ключ.

    Herfindahl-Hirschman¶

    hh(B), hh_ask(B), hh_bid(B)                       →  maker_hh, maker_hh_ask, maker_hh_bid

    Что говорит. Концентрация объёма maker-fills в нескольких крупных событиях. Высокий hh_ask → один крупный maker-sell доминировал над всеми остальными ask-fills бара.

    3 ключа.

    Kyle's lambda¶

    kyle_lambda(B)                                    →  maker_kyle_lambda

    Что говорит. Аналог taker-лямбды, но взвешено по maker-fills с инвертированной signed-volume конвенцией (side == "bid" → +1, side == "ask" → -1, противоположно taker'у). Для одних и тех же raw fills maker_kyle_lambda == -kyle_lambda (taker) — это anti-identity, пиннается тестом test_maker_kyle_lambda_equals_negative_taker_kyle_lambda.

    1 ключ.

    ASR¶

    asr_count(B), asr_volume(B)                       →  maker_asr_count, maker_asr_volume

    «Убыточный» fill для maker'а: цена через 60s ушла в сторону, выгодную maker'у. То есть для ask-maker'а (продал по высокой) убыток если цена упала ниже его выходной цены — ему пришлось продать дёшево, а надо было ниже. Для bid-maker'а наоборот.

    Wait — переформулирую корректно. Maker исполнился когда цена была P. Через 60s цена стала P'. Maker «прав», если цена ушла в его сторону (ask-maker продал по P, цена стала P' < P → можно было продать дешевле, но maker всё равно «продал когда цена была выше»). Это значит ask-maker «прав» если P' < P (цена упала после его продажи). Если P' > P, maker «не угадал».

    asr метрика измеряет «не угадал» = adverse selection для maker'а.

    Что говорит. Высокий ASR на maker-стороне = makers систематически исполнялись на «неудачных» уровнях, что говорит о наличии informed flow с другой стороны (умные takers).

    2 ключа.

    Сводка финальных ключей¶

    Все ключи в коде префиксированы maker_ (см. раздел «Префикс maker_ в коде» в начале документа).

    Раздел Ключей Префикс ключей в коде
    Counts (с USD-порогами) 12 maker_ask_count, maker_bid_count, maker_{ask,bid}_count_above_T
    Costs (с квантилями) 12 maker_ask_cost, maker_bid_cost, maker_{ask,bid}_cost_quantile_q
    Trade cost quantile boundaries 10 maker_{ask,bid}_trade_cost_quantile_q
    Max 2 maker_max_{ask,bid}_trade_cost
    VWAP 3 maker_vwap, maker_ask_vwap, maker_bid_vwap
    OHLC 4 maker_{open,high,low,close}
    Volatility 1 maker_volatility
    HH 3 maker_hh, maker_hh_ask, maker_hh_bid
    Kyle 1 maker_kyle_lambda
    ASR 2 maker_asr_count, maker_asr_volume
    Итого 50 все начинаются с maker_

    Те же 50 ключей что в trades-v2, с другими именами (с префиксом maker_ для collision avoidance с L2 orderbook namespace) и на других данных. MAKER_ORDERS_METRICS = list(_empty_maker_orders_metrics().keys()) — public schema, регистрируется в metrics_dict._METRIC_SOURCE через source="maker_orders".

    Тождества с trades-v2 / v1¶

    Поскольку каждый maker-fill = один raw trade, а все raw trades агрегируются в aggTrades по taker-стороне, существуют точные тождества (в коде с maker_ префиксом):

    maker_ask_cost  = buy_cost(taker)               # обе стороны видят одну и ту же сделку
maker_bid_cost  = sell_cost(taker)
maker_vwap      = vwap(taker)                   # тот же поток сделок, просто разная группировка

maker_ask_count ≥ buy_count_v2(taker)           # один taker = один логический trade в v2,
                                                 # но 1+ maker fills
maker_ask_count = buy_count_v1(taker)           # v1 без multilevel-агрегации тоже считает
                                                 # каждый aggTrade отдельно — но один aggTrade
                                                 # = один уровень = один или несколько maker fills
                                                 # → maker_ask_count ≥ buy_count_v1 (равно если на каждом
                                                 #   уровне ровно один maker)

maker_kyle_lambda = -kyle_lambda(taker)         # signed-volume convention inverted (anti-identity)
maker_asr_count   ≠ asr_count(taker)            # ASR sign inverted: ask-maker "right" on price fall

    То есть *_cost, *_volume, vwap совпадают между maker и taker вьюхами — это identity с разной перспективы. А *_count для maker'а больше или равно taker'у (один taker может «съесть» нескольких maker'ов). kyle_lambda для maker'а — точная инверсия taker'ского λ (anti-identity) для одного и того же набора raw fills.

    Метрики типа *_cost_quantile_q, *_trade_cost_quantile_q, *_count_above_T — различаются между maker и taker, потому что они смотрят на распределение размеров агрегатов, а у maker и taker эти размеры разные (maker fills меньше или равны taker'ским logical trades).

    Доступность¶

    Режим Статус
    Live (spot, парсер с LIVE_PREFER_AGGTRADES=False) ✓
    Live (spot, default config) ✗ — нет type=trades/ partition
    Backtest (spot, есть raw trades в parquet) ✓
    Backtest (spot, исторический период до собственной записи raw) ✗ — на data.binance.vision raw trades есть, но reader не использует их по умолчанию
    USDM (любой режим) ✗ — для USDM мы пишем aggTrades, raw trades-фид не подключён
    spot, символ-новичок ✗ до накопления

    Maker-orders metrics — самый «специфический» источник: требует raw trades в parquet, которых по умолчанию нет. Активация — через конфиг парсера.

    Замечание про L3¶

    Maker-orders это аппроксимация L3 на споте Binance. Она даёт нам: - ✓ Размер каждого matching event'а (= частичный fill maker'а) - ✓ Время каждого fill'а - ✓ Сторону maker'а

    Не даёт: - ✗ Полный размер исходного maker-ордера до начала исполнения - ✗ Время постановки maker-ордера в стакан - ✗ Owner / id maker-ордера

    Для полного L3 нужны private feeds (которые Binance не отдаёт публично).
