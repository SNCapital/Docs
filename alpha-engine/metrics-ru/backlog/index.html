    Бэклог по метрикам¶

    Список задач, которые мы сознательно отложили при фиксации спеки. Добавляется по мере того, как при обсуждении метрик всплывает что-то, что требует отдельной проработки и не хотелось блокировать основной прогресс.

    Открытые задачи¶

    B1. Dust filter (фильтр пыли)¶

    Контекст. При фиксации L1.1 / L1.2 (best_{side}_price, best_{side}_size) обсуждали, как отбрасывать «пыльные» уровни (test-ордера, бот-зонды, мусор от нестандартных источников), чтобы они не становились best.

    Что обсуждали. Перебрали: - % × Σ(side_size) — bias к стенкам. - IQR / log-IQR / MAD — нестабильно на скошенных и бимодальных распределениях, плюс шумит на малом числе уровней. - Per-bar pool + 5%-перцентиль — устойчиво, но lookahead на бар. - USD-floor через min_notional — экономически осмыслено, требует mid-price на снапшот. - Гибрид нескольких критериев.

    Ни один одиночный критерий не идеален на всех патологичных кейсах.

    Что сейчас. Фильтр выключен. best_*_price / best_*_size / производные считаются по всем уровням как есть, включая пыль.

    Что сделать. Реализовать настраиваемый dust filter с одним из двух кандидатов (или комбинацией): 1. USD-floor — порог = min_notional / mid_price снапшота. Завязать на exchange_info-feed, который у нас уже пишется. 2. Per-bar pool + перцентиль — threshold = quantile(pool, q), pool из всех sizes бара, q конфигурируемый, дефолт 0.05.

    Реализация должна быть глобально-выключаемой через конфиг. По умолчанию — выключено (соответствует текущему состоянию спеки).

    Когда приоритетно. Когда пойдём проверять метрики на реальных non-Binance данных или на mock'е — там пыль реально мешает. На чистых Binance-данных биржа сама не пускает sub-min_notional ордера, поэтому в большинстве кейсов filter будет no-op.

    B2. Расширить exchange_info-поллер на spot¶

    Контекст. Для всех L2-метрик с оффсетом top_x (а это много — {ask/bid}_top_x_{cost,size,vwap,levels_*,...} для всех восьми top-оффсетов в нашем наборе) нужен tick_size символа на момент снапшота. tick_size — минимальный шаг цены, который определяет дискретную сетку, на которую кладутся все ордера. Без него невозможно построить top_x грид (p_i = floor_tick(mid) ± (i−1) × τ).

    Где должно быть. tick_size приходит с биржи через REST endpoint: - spot: GET /api/v3/exchangeInfo - usdm: GET /fapi/v1/exchangeInfo

    В ответе для каждого символа есть массив filters. Из них берётся запись с filterType == "PRICE_FILTER", поле tickSize. Это и сохраняется в parquet type=exchange_info/. Для BTCUSDT spot тик = 0.01, для BTCUSDT usdm = 0.10, и т.д.

    Что сейчас. Парсер запускает exchange_info_poller только если в markets есть usdm (см. binance_parser/services/live.py). Комментарий объясняет: «у спота нет leverage tiers, поэтому пока скоупом ограничились USD-M». Для spot exchange_info на диск не пишется, и tick_size для spot символов недоступен в alpha_engine.

    Эффект на метрики. Без tick_size для spot: - ВСЕ top_x метрики на spot невозможны → выпадают из датасета по всем 50+ spot-тикерам. Это ~50% всех L2 top_x ключей (8 оффсетов × ~12 базовых метрик × 9 агрегаций × 2 стороны ≈ 1700 ключей, половина из которых на spot). - Процентные оффсеты не страдают — они не зависят от tick_size. - На usdm всё работает как должно.

    Что сделать. 1. Снять условие if "usdm" in markets для запуска exchange_info_poller — пусть запускается также если в markets есть spot. 2. Адаптировать сам поллер под spot endpoint. Сейчас он жёстко завязан на EXCHANGE_INFO_REST_URL (futures URL) и LEVERAGE_BRACKET_REST_URL (только usdm). 3. На spot leverage_bracket не существует — поллер должен корректно эмитить запись с max_leverage = 1 и пустым leverage_brackets. tick/step/min_notional — есть и в spot exchange_info. 4. Storage path: parquet пишется в market=spot/type=exchange_info/dt=…/symbol=…/. Симметрично текущей usdm-партиции. 5. Reader (alpha-engine) уже умеет читать spot/usdm одинаково — изменений не требуется.

    Когда приоритетно. Блокирует L2 top_x метрики на spot. Если в фазе тестирования стратегий мы хотим top_x только на usdm — можно отложить. Если нужно симметричное покрытие spot+usdm — это prerequisite.

    B3. Backtest-доступность L2.8 OB updates метрик¶

    Контекст. L2.8 определяет 12 bar-level счётчиков ({bid/ask}_{place,remove}_{cost,size,count}) из потока WS @depth-диффов. На L2-уровне это лучшая доступная аппроксимация L3-активности. Для live-режима эти метрики собираются in-process diff-observer'ом на парсере. Но для backtest на исторических данных метрики пустые, потому что @depth-диффы на диск не пишутся — мы храним только 30-минутные booksnapshot'ы (полное состояние книги, без дельт).

    Эффект. В backtest 12 ключей L2.8 (×50 тикеров на каждом баре) = NaN или 0. Стратегии, использующие их, не работают на истории, только на live.

    Что можно сделать.

    1. Сохранять @depth diffs в parquet. Большой объём данных (~100мс кадры × 50 тикеров × 24ч ≈ десятки ГБ/день в несжатом виде, ~5-10 ГБ в zstd). Партиция type=depth_diff/, формат — массив дельт на снапшот. Плюс: точные метрики на истории. Минус: x10 объём parser'а; дополнительный reader/aggregator.

    2. Купить исторические depth-feeds у вендора.

    3. tardis.dev — записывает полный L2 поток Binance, ~$200/мес для одного символа, дороже для пакета.
    4. kaiko, cryptocompare — аналогично.

    5. Преимущество: backfill за прошлые годы (мы не сможем сами сгенерировать без машины времени). Недостаток: платно; формат вендора нужно нормализовать в наш schema.

    6. Аппроксимация из booksnapshot'ов. Вместо реальных 100мс-диффов сравнивать 30-минутные снапшоты подряд: delta_30min = booksnapshot[t] − booksnapshot[t−30min] уровень за уровнем. Получим псевдо-place/remove события на 30-минутном масштабе, а не реальные мс-события. Из этого считать те же counts/sums. Плюс: бесплатно, использует то что уже есть. Минус: грубая аппроксимация — пропускает быстрые place-cancel пары, объединяет несколько событий в одно. На 30-минутах информация о flow сильно усредняется.

    7. Ничего не делать, оставить L2.8 как live-only. Стратегии, использующие эти метрики, тестируются только в live.

    Когда приоритетно. Если стратегии активно используют L2.8 в сигналах — сразу. Если только experimentально — можно отложить.

    B4. Расширить парсер на сбор market-stats endpoints¶

    Контекст. Спека market-stats.md описывает 5 метрик, источник которых — отдельные REST-эндпойнты Binance:

    Метрика Endpoint Каденс
    open_interest /fapi/v1/openInterest?symbol=… (usdm) real-time, поллим 5 мин
    global_long_accounts /futures/data/globalLongShortAccountRatio (usdm) 5 мин
    top_long_accounts /futures/data/topLongShortAccountRatio (usdm) 5 мин
    top_long_positions /futures/data/topLongShortPositionRatio (usdm) 5 мин
    daily_interest_rate Margin API (/sapi/v1/margin/…) ~раз в сутки

    Что сейчас. Парсер этих endpoint'ов не поллит. Соответствующая парquet-партиция отсутствует. В backtest и live все 5 метрик = NaN.

    Что сделать. 1. Создать новый поллер в binance_parser/live/market_stats_poller.py по аналогии с funding_poller.py и exchange_info_poller.py. 2. Поллер дёргает каждый из 5 endpoint'ов с подходящей частотой (4 ratio'а — 5 минут синхронно; OI — 1–5 мин; interest rate — раз в час). 3. Складывает в parquet data/market={spot|usdm}/type=market_stats/dt=…/symbol=…/part-*.parquet с колонкой timestamp и колонками-значениями (одна строка на цикл опроса на символ). 4. Расширить reader (raw_data_reader.py) с kind="market_stats", реализовать алгоритм агрегации last value at boundary (как у markprice). 5. Зарегистрировать метрики в _METRIC_SOURCE.

    Когда приоритетно. Если стратегии используют sentiment-сигналы (top_long_*, global_long_*) или OI-flow → высокий приоритет. Если нет — можно отложить.
