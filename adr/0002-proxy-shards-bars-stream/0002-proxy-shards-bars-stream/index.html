    1. Overview¶

    Масштабируется всё, по трём осям: биржи (на каждую — свой collector, calculator и trader), очереди (очередь одна логически, скейлится по нодам; внутри — три семейства: стакан/диффы, трейды, всё остальное, по которым калькулятор делится ещё на 2–3, если метрики не пересекаются), ноды (PG в будущем тоже понодово). На старте биржа одна — значит collector, calculator и trader тоже по одному. Ключевое свойство: рост — это добавление единиц деления, а не переписывание; трейдер видит только закрытые бары своей биржи со штампом качества.

    2. Goals / Non-Goals / Deferred¶

    Goals (этот док фиксирует):

    • G1. Масштабирование всего: collector × E (по коллектору на биржу), calculator × E, trader × E (трейдер скейлится по биржам); очередь одна логически, скейлится по нодам; PG в будущем понодово. Старт: E = 1, всё по одному.
    • G2. Контракт bars.* между калькуляторами и трейдером: 1 сообщение = 1 закрытый бар со всеми ключами и штампом качества; биржа в теме (md.binance.usdm..., bars.binance...), добавление биржи трейдер не меняет.
    • G3. Трейдер на биржу (на аккаунт): ордера напрямую в Trade API своей биржи мимо шины, позиции — из user data stream со сверкой.
    • G4. Штамп качества и ingress time как часть контракта данных (иначе live и replay/backтест расходятся).
    • G5. Калькулятор делится по трём семействам очередей (стакан/диффы, трейды, остальное) до ×2–×3 тогда и только тогда, когда метрики между семействами не пересекаются (условие проверяется в Phase 3).

    Non-Goals (осознанно исключено):

    • N1. Тьюнинг пулов/тредов/TCP/батчей — runbook, по RULES.md I.2 (в доке только формулы и инварианты).
    • N2. PII/GDPR-механика — в контуре только маркет-дата (как в ADR-0001 §13).
    • N3. Мультиаккаунт внутри одной биржи и мультирегион — один аккаунт на биржу, один контур (триггер в шапке).

    Deferred / Open (решает встреча с доски, см. «Вопросы на встречу»):

    • O1. NATS на той же машине, что прокси, или отдельно (вопрос 1). Очередь одна логически в обоих случаях; отдельно — нужен кластер, не одиночка.
    • O2. Решения по символам независимо или портфельно — определяет форму bars-контракта: одиночные бары vs комплект баров за окно + правило ожидания опоздавшего шарда (вопрос 2). Без ответа нельзя финализировать §5/§8.
    • O3. Retention по возрасту или по ack: limits + max_age (отставший архиватор тихо теряет) vs interest/workqueue (залипший консьюмер забивает диск) — выбрать, какой отказ терпим (вопрос 3).
    • O4. Гранулярность консьюмеров внутри шарда: консьюмер на шард (в 2.10+ несколько filter subjects) vs 1 символ = 1 консьюмер для порядка дифов (вопрос 4 + пометка с доски).
    • O5. Метрика слепых секунд на /public (вопрос 5).
    • O6. Каденция снапшотов depth (вопрос 6): в данных ~1220 снапшотов/сутки (интервал ~61.6 сек) против 30 мин в конфиге — разница ~25x и главный драйвер объёма.
    • O7. Паттерн чтения (символ×период vs все символы×дата) для партиционирования parquet (вопрос 7).

    3. Constraints¶

    Технические (наследуются из ADR-0001 §3, не дублирую: C2 лимит REST 2400 weight/мин, C3 срез REST depth, C4 каденции подписок, C5 роутинг fstream двумя соединениями). Новые с доски:

    • C6. Подписка на ~12000 стримов стартует ~32 сек (measured, доска) — старт контура не мгновенный, заложить в RTO и порядок поднятия.
    • C7. Сырьевой объём estimate доски ~13 ГБ/день (сжатый parquet) против measured 22–40 ГБ/день из measurements.md §6 — расходятся в ~2x, см. ASSUMPTION A2.
    • C8. Parquet «1 файл/день/тип» (доска) против текущей Hive-раскладки part-*.parquet — смена формата архива требует окна миграции (Phase 3, Migration).
    • C9. Биржа — часть темы (md.binance.usdm.btcusdt.depth, bars.binance..., доска) против текущих md.{market}.{kind}.{symbol} — смена контракта с простоем (Phase 3). Направление решено (биржа в теме сразу, «потом больно»), механика переезда — в Phase 3.

    Допущения (ASSUMPTION с ценой ошибки):

    • A1. NATS живёт рядом с прокси (один VM/loopback), пока не отвечен O1. Ошибка: разъезд по хостам без кластера и пересмотра буфера — разрыв минутами вместо рестарта секундами.
    • A2. Объём сырья для сайзинга retention/disk — 22–40 ГБ/день (measurements.md, не 13 с доски). Ошибка в меньшую сторону: диск очереди переполняется раньше расчёта (discard: old начнёт есть окно реплея).
    • A3. DECIDED 2026-09-12: PG-чеkпойнты книги (ADR-0001 D5) остаются источником восстановления книги. Bars-стрим — производное (пересчитывается из сырья + чекпойнтов), не замена. Пересмотр отложен с триггером: окно retention доказуемо покрывает все рестарты И операционная цена PG становится связывающей — тогда отдельным ADR с миграцией. Понодовый скейл PG — будущее, не этот док.
    • A4. Snapshot-каденция depth для сайзинга — текущая живая (вопрос O6 открыт). Ошибка: при 1/мин дифф-поток и объём — на порядок выше, чем при 1/30мин.

    4. Context (C4-L1)¶

    Исследовательская live-платформа (как в ADR-0001 §4): стримит маркет-дату, считает метрики по 30-минутным барам, торгует трейдерами по одному на биржу, пишет архив в parquet → S3. Новое против ADR-0001: масштабируются все измерения (биржи, очереди/ноду, будущий PG), метрики вынесены в отдельный слой, трейдер потребляет только готовые бары своей биржи.

    volumes / dashboard Parquet, read-only фид S/A

    Trust boundary: как в ADR-0001 §5/§13 (internal — контур, untrusted — Binance/S3/браузер); управляющей связи proxy ↔ trader нет; каждый трейдер — единственный writer в Trade API своей биржи.

    Phase 1 Summary¶

    Инварианты Phase 1 (constraint для следующих фаз): масштабируется всё — оси биржи (collector/calc/trader ×E, старт E=1), очереди (одна логическая на нодах, внутри три семейства для сплита ×2–3 при непересекающихся метриках), ноды (PG понодово в будущем); два семейства стримов (md.* сырьё, bars.* закрытые бары), биржа в теме; контракт трейдера — только бары своей биржи со штампом качества + ingress time; ордера и позиции — вне шины. Открыто и блокирует Phase ⅔: O2 (форма bars-контракта), O1/O3 (топология и retention-семантика), судьба PG-чеkпойнтов (A3), каденция снапшотов (O6). Числа до замеров — только как measured(доска)/estimate с ценой ошибки (A2, A4). [Phase 1 rev.3: A3 decided — чекпойнты остаются в PG.]

    6. Components¶

    Только нетривиальные границы:

    • metric calc внутри: книга + движок + штамп качества на единицу деления. Сплит ×2–3 идёт по семействам очередей (диффы/книга, трейды, остальное) тогда и только тогда, когда метрики семейств не пересекаются (G5): пересечение — общий шард, иначе дубли состояния и сшивка. Проверка непересекаемости — Phase 3 (решение D-серии).
    • trader intake: подписка на бары своей биржи, stale-drop, исполнение. Комплект баров за окно (портфельный вариант O2) собирается здесь же, если O2 решится в его пользу, — движок баров при этом не меняется.

    7. Runtime¶

    Дедупликация везде: брокер оппортунистически (Nats-Msg-Id), консьюмер обязательно; out-of-order внутри символа невозможен по построению (u монотонен, нарушение = дырка).

    sequenceDiagram
  participant B as Binance WS/REST
  participant P as data-proxy (своя биржа)
  participant J as JetStream md.*
  participant A as raw archiver
  participant C as metric calc (шард)
  participant G as PG checkpoints
  B->>P: depth diff / trade / kline(mark/liq) / REST
  alt невалидный payload
    P->>P: WARN + dropped_invalid, без публикации (fail loud)
  else валидное событие

    P->>J: publish raw + Nats-Msg-Id (асинхронно, не из цикла чтения)
    J-->>P: PubAck (duplicate:true при повторе в окне)
    J->>A: live deliver (свой durable-курсор) -> дописывание row groups в открытый writer дня -> S3 (копия, проверка, удаление; ack после верификации)

    C->>G: read checkpoint @ bar boundary
    C->>C: apply diff (u-check), ring, close bar + quality stamp
    C->>G: COMMIT checkpoint (A3)
    C->>J: publish 1 msg = 1 closed bar (пустое = NULL, всегда эмитим)
  end

    T->>T: решение (per-symbol; O2-форк ниже)

    T->>V: user data stream + REST reconcile (listenKey renew ~30 мин)

  alt рестарт трейдера

    T->>J: resume live с последнего (bars короткого retention хватает)
  else рестарт калькулятора
    T->>T: ждём бары (трейдер не рестартится, гэп виден по штампу)
  end

    O2-ФОРК (открыт, обе ветки живут до решения встречи): - Ветка S (per-symbol): калькулятор публикует бары посимвольно, трейдер реагирует на каждый бар; разделение дешёвое, комплектов не нужно. - Ветка P (портфельно): трейдеру нужен КОМПЛЕКТ баров за окно от N калькуляторов — тогда в §8 добавляются правило «сколько ждём» и поведение «шард не прислал» (таймаут комплекта + неполный флаг, без блокировки). База Phase 2 — ветка S (совпадает с текущим движком и ADR-0001); ветка P не должна ломать формат одиночного бара, только добавлять сборку.

    8. Data¶

    Парадигма: лог как источник истины (JetStream md.*) + регенерируемый чекпойнт книги (PG, A3) + пересчитываемое производное (bars, ring, позиции). Bars-стрим — производное и выкидываемое: пересчитывается из сырья + чекпойнтов, долгим не хранится.

    Владельцы стейта: книга — calc (RAM) + чекпойнт в PG; сырьё — JetStream; бары — JetStream коротким окном; позиции — биржа (user data + reconcile); архив — parquet → S3.

    Контракты на уровне инвариантов:

    • Темы (принцип решён, C9; точный шаблон — решение Phase 3): биржа первая, далее рынок/вид/символ; бары — bars.<exchange>...30m-формой с интервалом в теме. Своей схемы между сервисами нет, payload сырья 1:1 с Binance (D7 из ADR-0001).
    • Nats-Msg-Id — из явных полей Binance (таблица ADR-0001 §8) + для баров bars:{exchange}:{symbol}:{bar_ts}; невалид — громко, без публикации.
    • Ingress time пишется рядом с биржевым временем в каждом событии: без него live и replay расходятся на границах баров (доска).
    • Штамп качества в каждом баре (поля контракта): разрывы U/u/pu и agg id (точный счёт потерянных), счётчик markPrice = слепые секунды (1800 на 30-мин бар), измерение по коннектам отдельно (/public vs /market), трёхуровневый статус (норм / деградация / плохо), флаг полноты. Бэктест фильтрует так же, как живой трейдер.
    • Ключ партиционирования: биржа → символ (книги независимы → параллельный реплей и шарды без skew по построению).
    • Консистентность: per-symbol strong order (через u), глобально eventual (бары закрываются по settlement); read-your-writes не требуется.
    • Доставка: at-least-once + идемпотентные консьюмеры; exactly-once не заявляется. Ордера идемпотентны через newClientOrderId=(символ + ts бара).

    Design Limits (формулы; числа — только measured или конфиг):

    Parameter / Invariant Value / Formula Rationale Consequence of Violation
    Retention md.* >= возраст старейшего чекпойнта + худший простой + буфер drain Пережить рестарт/откат без потери книги Retention hole → остаёмся на книге, бары неполные (явный флаг)
    Retention bars.* >= простой трейдера + окно скоса шардов (короткое: бары пересчитываемы) Трейдеру нужен только хвост, не история Долгий простой трейдера → холодный старт ленты (позиции — с биржи, D10)
    Dedup window W_dedup >= max_retry + max_reconnect + clock_skew Покрыть ретраи и простой на деплое Дубль бизнес-операции (для ring — удвоение объёма)
    Proxy buffer buffer_bytes >= throughput_peak * T_repair, переполнение — дроп со счётчиком + алерт, без spill-файла (доска) Без буфера рестарт NATS теряет данные у источника Дырка в диффах → бары неполные
    Checkpoint cadence строго на границу бара; keep >= 2 (D5) Снапшот среди бара не восстанавливает его начало Невосстановимые секунды / двойной реплей при краше на границе
    Book depth stored целиком, без среза (D6) Срез ломает бакеты непредсказуемо по символам Недостоверные книжные метрики
    Stale bar bar_age > N → не торгуем, ack и выкидываем Протухший сигнал хуже отсутствия сигнала Торговля по протухшему бару
    ListenKey renew ~каждые 30 мин + сверка по таймеру и после ордера Без подтверждения позиция/филлы расходятся с биржей Тихий разрыв учёта (пример с доски: 4 символа молчали 2 суток)

    Phase 2 Summary¶

    Инварианты Phase 2 (constraint для Phase 3): сырьё 1:1 + MsgId + ingress time; бары — производное с полным контрактом (все ключи + штамп качества + NULL вместо forward fill); PG-чеkпойнты — восстановление книги; ордера идемпотентны по (символ + ts бара); потоки replay/live/hole/cold — как на диаграммах; O2 несётся форком (база — per-symbol). Следующая фаза: решения D-серии (сплит калькулятора по G5, точный шаблон тем, retention-семантика O3, число шардов O4) + риски и лимиты.
