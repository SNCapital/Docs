    ADR-0002. Раздельные сервисы + JetStream: proxy / archiver / calc / trader¶

    0. Шапка¶

    1. Overview¶

    Исследовательская live-платформа делится на раздельные сервисы через NATS JetStream: data proxy держит край биржи, raw archiver пишет архив, metric calc считает бары со штампом качества, trader торгует только готовыми барами своей биржи. Ключевое свойство: рост — это добавление единиц деления (биржи × очереди/ноды × шарды символов), а не переписывание; тишина и дыры никогда не молчат (NULL-бары + штамп + явные состояния трейдера).

    2. Goals / Non-Goals / Deferred¶

    Goals (этот док фиксирует):

    • G1. Разделение на четыре сервиса с replayable очередью как границей: proxy × E (по одному на биржу), archiver, calc × E (шарды по символам, старт E = 1), trader × E (один на биржу/аккаунт). Очередь одна логически, скейлится по нодам.
    • G2. Контракт bars.*: 1 сообщение = 1 закрытый 30-минутный бар со всеми ключами и штампом качества; биржа в теме (bars.binance.usdm.*); трейдер видит только бары своей биржи.
    • G3. Трейдер на биржу (на аккаунт): ордера напрямую в Trade API мимо шины, позиции — из user data stream со сверкой, локально не хранятся (D10 из ADR-0001).
    • G4. Штамп качества и ingress time как часть контракта данных: без них live и replay/backtest расходятся на границах баров.

    Non-Goals (осознанно исключено):

    • N1. Тьюнинг пулов/тредов/TCP/батчей — runbook, по RULES.md I.2 (в доке только формулы и инварианты).
    • N2. PII/GDPR-механика — в контуре только маркет-дата (как в ADR-0001 §13).
    • N3. Мультиаккаунт внутри одной биржи и мультирегион — один аккаунт на биржу, один контур (триггер в шапке).
    • N4. S3 lifecycle/compression tuning сверх copy-verify-delete; детальный security-дизайн сверх trust boundary.

    Deferred (с триггерами возврата):

    • Сплит калькулятора по семействам очередей ×2–×3 — только когда метрики между семействами доказуемо не пересекаются; решением человека отложен («пока без шардов»).
    • Понодовый шардинг PG — будущее, не этот док.
    • Стартап ~32s на 12000 стримов (board-measured) — пункт soak, не constraint, пока не замерен на нашем хосте.

    3. Constraints¶

    Нумерация C* — локальная для этого ADR и НЕ продолжает нумерацию ADR-0001 (там C6/C7/C8 — про универсум/бар/конфиг, другой смысл). Ссылки на наследуемые constraints даются по их номерам в ADR-0001.

    Технические (наследуются из ADR-0001 §3, не дублирую: его C2 лимит REST 2400 weight/мин, C3 срез REST depth, C4 каденции подписок, C5 роутинг fstream двумя соединениями). Новые и изменённые (локальные номера):

    • C6. Нагрузочный базис measured: сырьё 22–40 ГБ/сутки @60 символов (measurements.md §6 L6/L7; cross-check — measurements.md §9 sustained 350 КБ/с ×86400 ≈ 30.24 ГБ/сутки, середина диапазона). Отвергнуто как sizing-вход: 13 ГБ/день (board-estimate сжатого parquet) и 61.6s/1220 снапшотов (O6; арифметически несостоятельно: 86400/1220 = 70.8, не 61.6).
    • C7. Retention сырья D-001: 48h + max_bytes hard stop (conscious deviation от 72h из ADR-0001; формула «простой + худший + буфер» соблюдена, число другое — bound диска + S3-прогресс архиватора). S2 ratio measured 0.37 ± 0.01 (bulk; мелкосообщённые потоки overhead-dominated, ratio ≥ 1.0) — X-004.
    • C8. Формат архива D-002: 1 файл/день/тип, все символы внутри; сборка дописыванием row groups в один открытый writer за сутки; ack после S3 copy-verify-delete. Файловый диск в тени ≤ ~1–2 суток локала (Q-005(b) daily merge).
    • C9. Темы: сырьё остаётся md.{market}.{kind}.{symbol} (переезд на md.binance.usdm.<symbol>.<type> закрыт отказом); биржа-в-теме только для нового семейства bars.binance.usdm.* (без .30m, заморожено кодом+тестом).
    • C10. Бар 30 минут, UTC-aligned; deduplication window 300s < 1800s окна бара (ретрай старше окна требует идемпотентного приёмника — арифметика, не решение).

    Организационные: пилот paper → testnet → mainnet; деплой stop-first для писателя/calc/трейдера (overlap невозможен — fencing порядком деплоя, Q-005; для calc аддитивный ring делает перекрытие вредным, единственность держит только порядок деплоя — без локов, решение 2026-09-13), start-first для коллектора (перекрытие на ingress допустимо — дубликаты гасятся детерминированным MsgId-дедапом 300s).

    Внешние: схема событий принадлежит Binance; сырьё повторяем 1:1 (D7 из ADR-0001).

    Допущения (ASSUMPTION с ценой ошибки):

    • A1. NATS same host, single VM loopback, no auth (Gate 0 decided). Ошибка (разъезд по хостам): пересмотреть буфер D9, Security §13 (NATS creds + TLS) — триггер в шапке.
    • A2. Объём для сайзинга — 22–40 ГБ/день (не 13 с доски). Ошибка в меньшую сторону: диск очереди переполняется раньше расчёта (discard: old начнёт есть окно реплея).
    • A3. PG-чеkпойнты книги (ADR-0001 D5) остаются источником восстановления книги (владелец — calc); курсоры calc и intake-чекпойнт трейдера — в той же PG16 trader DB отдельными таблицами/схемами (calc владеет своими миграциями, трейдер — своими). Один инстанс на всех троих — общий SPOF (§11), осознанно на одном VM; понодовый шардинг PG отложен. Bars-стрим — производное (пересчитывается из сырья + чекпойнтов), не замена.

    4. Context (C4-L1)¶

    Система — исследовательская live-платформа: стримит маркет-дату, считает метрики по 30-минутным барам, торгует трейдерами по одному на биржу, пишет архив в parquet → S3. Новое против ADR-0001: метрики вынесены в отдельный слой (calc), архив — отдельный сервис, трейдер потребляет только готовые бары своей биржи.

    Phase 1 Summary¶

    Инварианты Phase 1 (constraint для следующих фаз): четыре сервиса (proxy × E, archiver, calc × E, trader × E; старт E = 1) + одна логическая очередь с двумя семействами (md.* сырьё 48h + max_bytes, bars.* короткие пересчитываемые); контракт трейдера — только бары своей биржи со штампом качества + ingress time; ордера и позиции — вне шины; сырьё остаётся на темах ADR-0001, биржа-в-теме только для bars.binance.usdm.*. Открыто и блокирует Phase ⅔: детали полей штампа Q-003, soak-замеры (S2-база, occupancy пилота, волатильная сессия), файловый предел тени. Числа — только measured (22–40 ГБ/день; S2 0.37 ± 0.01 bulk) или формулой.

    6. Components¶

    Только нетривиальные границы (остальное — код, не док):

    • metric calc внутри: книга + движок + штамп качества на единицу деления. Сплит ×2–×3 идёт по семействам очередей (диффы/книга, трейды, остальное) тогда и только тогда, когда метрики семейств не пересекаются: пересечение — общий шард, иначе дубли состояния и сшивка. Проверка непересекаемости и сам сплит — deferred решением человека («пока без шардов»).
    • trader intake: подписка на бары своей биржи, stale-drop, исполнение. Комплект баров за окно (wait-full-set 5 мин, D-001) собирается здесь же: deadline T+5 мин от закрытия окна, дальше торгуем доступным набором + маркируем отсутствующие шарды в штампе; отсутствующий шард никогда не блокирует past deadline.
    • archiver assembly: daily-файл собирается дописыванием row groups в один открытый writer за сутки; ack после S3 copy-verify-delete; слияние идемпотентно (рестарт среди слияния = повторное слияние, владелец — archiver).

    7. Runtime¶

    Дедупликация везде: брокер оппортунистически (Nats-Msg-Id, окно 300s), консьюмер обязательно. Out-of-order внутри символа невозможен по построению (u монотонен, нарушение = дырка). Публикация бара: calc читает PG-чекпойнт на границу бара → применяет диффы (u-check), ведёт ring, закрывает бар + штамп → COMMIT чекпойнта (A3) → публикует 1 msg = 1 закрытый бар (пустое = NULL, эмитим всегда, тихие символы не скипаем).

    Протокол старта calc (норматив; детали — research-notes.md §S-offset/§S-bar):

    1. Читает PG: для каждого символа свой курсор per-(symbol|type) (stream seq + U/u)
    2. блоб книги на новейшую завершённую границу именно этого символа.
    3. Диффы per-symbol от seq+1 (exact-subject ephemeral consumer — X-001 воспроизведён на nats-server 2.10.29: первое доставленное = первое совпавшее на/после start seq; expired/future start → пустой fetch без ошибки брокера, дыра детектится кодом retention_hole + stream_first_seqs probe).
    4. Фильтр u > u_snapshot; сделки и события — идемпотентность по MsgId обязательна.
    5. Engine в replay (эмит баров подавлен) — цель дойти до «сейчас».
    6. Лаг < слота по всем стримам → live. Бар в трейдер — только с полным штампом; тихий символ = бар из NULL + bar_complete=false + blind_sec=1800.
    7. Нет чекпойнта / PG пуст / codec неизвестен → холодный старт; ретеншн превышен при живом чекпойнте → не холодный старт, а "hole": остаёмся на книге из чекпойнта, бары за окно неполные.
    8. Дырка при живом чекпойнте → без ресинка: остаёмся на книге, бары неполные, дальше реплей.

    9. NFR + Scale¶

    Нагрузочный профиль входа (measured; пилот 60 символов USD-M, активный рынок):

    • Живой поток в очередь: ~380 msg/s @60 при max-периоде подписок (120 diffs + 20 mark + ~240 trades); ~3800 msg/s @600.
    • Дифф-байты: ~250–450 КБ/с @60 (max-период режет msg/s, не байты).
    • Суточный объём сырья: 22–40 ГБ/сутки (без booksnapshot). S2 0.37 ± 0.01 bulk (X-004; мелочь ≥ 1.0); фикс. overhead пустого стрима ~12.8 КБ.
    • Occupancy-форма 48h (X-004, 2-символьное окно, форма математики, не объём пилота): +3.10 GB logical / ~+1.15 GB disk; 72h steady-state ~1.7 GB disk. Пилотный объём — только по §6 (22–40 ГБ/день), не умножением окна X-004.
    • Per-minute peak factors (X-004): DIFF msgs 1.00 / MB 1.49; TRADE 2.35 / 2.34; EVENTS 1.51. Волатильная сессия — отдельным soak-захватом (UTC 13:30–16:00); max_bytes sized против пика, не среднего.
    • PG: 60 строк раз в 30 мин (книга) + курсоры calc той же каденции + intake-чекпойнт трейдера (порядок 1 строки на окно, не per-symbol); UPDATE-чурна нет.
    • RTO рестарта: <= 2 мин (бары 30-мин, пропуск недопустим); худший случай (краш на границе) — ×2. RTO-неравенство из ADR-0001 §9 проверяется на старте.
    • Latency SLO live: p95/p99 wall latency не нормируется (не load-bearing: бары 30-мин, корректность = полнота бара + lag < слота). SLO: bar_complete=true (слот на каждую секунду) и отставание реплея < 1 слота на всех стримах.

    Что ломается первым при ×5 нагрузки — см. §11 (единый источник; порядок: реплей в RTO → диск очереди/архива → память calc на 600 книг).

    Soak-гейты (подробно — workspace soak-runbooks.md): S-1 occupancy+S2 точный (закрывает max_bytes числом); S-2 kill-archiver JetStream+файлы (диск стоит, дыра громкая, publish жив — иначе шаг 6 запрещён); S-3 peak волатильной сессии; S-4 week jitter log (Q-006(d), идёт); S-5 bars-catch-up burst (после первого паблишера).

    10. Decisions¶

    D1. Четыре сервиса через JetStream как границу durability¶

    • Status: accepted (Gate 4 2026-09-12; реализует вариант C из ADR-0001 D0).
    • Context: монолит связывает частоту деплоя стратегий со стоимостью старта WS+стаканов, теряет ring при рестарте, не хранит диффы. ADR-0001 уже отделил collector от trader; метрики и архив остались внутри trader — его деплой всё ещё трогает время, деньги и историю одновременно.
    • Drivers: независимый деплой calc/archiver/trader; durability рестарта каждого; пересчитываемая история; не платить за 600 символов сейчас, не закрывать путь.
    • Options: (a) оставить trader как есть (архив+метрики внутри) — деплой трейдера рвёт архив и пересчёт — rejected; (b) три сервиса без archiver (архив остаётся в trader) — та же связность по времени — rejected; © этот: proxy / archiver / calc / trader — принят.
    • Decision: Мы делим контур на четыре сервиса с NATS JetStream как границей durability и чекпойнтом книги + курсорами в PG.
    • Consequences: +деплой каждого независимо; +история пересчитываема; −сырьевой архив 22–40 ГБ/сутки; −RTO зависит от каденции.
    • Re-evaluation Trigger: поток на порядок выше или RTO вне цели при всех рычагах → RedPanda без смены контракта.
    • Mitigation: буфер proxy, чекпойнт+курсоры, kill-сьют, soaks S-1–S-5.
    • Verification: золотое свойство — прогон с убийством любого потребителя даёт те же бары, что непрерывный; критерии — workspace transition-plan + soak-runbooks.

    D2. Retention age-wins: 48h + max_bytes, лаг = громкая дыра¶

    • Status: accepted (Gate 4; conscious deviation от 72h ADR-0001).
    • Context: диск одного хоста ограничен; залипший консьюмер не должен останавливать ingress; тихая потеря хуже остановки.
    • Drivers: bounded disk; never backpressure; loud hole вместо silent loss.
    • Options: (a) ack-wins (interest/workqueue) — залипший консьюмер забивает диск, останавливает ingress — rejected (хуже на одном VM); (b) 72h без max_bytes (статус-кво ADR-0001) — без bound диска — rejected; © этот: limits + max_age 48h + max_bytes hard stop delete regardless of ack — принят.
    • Decision: Мы держим retention: limits + max_age 48h + max_bytes hard stop на md.*; лаг любого консьюмера — громкая дыра (штамп + num_pending-алерт), никогда backpressure в прокси.
    • Consequences: +диск ограничен; −долгий простой = дыра (не остановка); −max_bytes числом только после S-1 (до тех пор orientir ~100G).
    • Re-evaluation Trigger: occupancy S-1 показывает, что 48h не покрывает штатный простой + худший + буфер → поднять max_age/max_bytes формулой, не вкусом.
    • Mitigation: archiver durable+ack коммитит S3-прогресс; calc non-durable+DB-offset реплеит пока в retention; past retention → hole verdict.
    • Verification: kill-archiver soak S-2 (диск стоит, дыра громкая, publish жив); X-004 dry-run на изолированном стриме — все checks pass.

    D3. Archiver — отдельный сервис (deviation от D8 из ADR-0001)¶

    • Status: accepted (conscious boundary change; rationale записан).
    • Context: D8 сажал FileWriter в trader как durable consumer. Деплой трейдера (стратегии — часто) дёргал бы архив (деньги истории — редко и страшно).
    • Drivers: архив меняется редко и боится рестартов; трейдер деплоится часто.
    • Options: (a) оставить FileWriter в trader (статус-кво D8 из ADR-0001) — деплой трейдера дёргает архив, связность по времени — rejected; (b) writer в data proxy (край биржи) — баги parquet рестартуют WS, против разделения ответственности — rejected; © этот: отдельный archiver-сервис со своей единицей деплоя — свой durable-курсор, свой writer, свой S3-путь — принят. (Формально это тот же консьюмер, что жил бы sink-процессом; выигрыш — именно граница сервиса: независимый деплой и рестарт от trader.)
    • Decision: Мы выносим архив в отдельный сервис со своим durable-курсором (offset у брокера, ack после S3-верификации).
    • Consequences: +деплой трейдера не трогает архив; −ещё один сервис и его курсор.
    • Re-evaluation Trigger: I/O архива мешает кому-то делить хост → свой хост, контракт не меняется.
    • Verification: kill-archiver soak S-2; X-004 file-side метод (per-stream du).

    D4. Calc non-durable + ОТДЕЛЬНЫЕ курсоры в PG; resume exact-subject¶

    • Status: accepted (Gate 0/4; X-001 reproduced на 2.10.29).
    • Context: calc и trader — РАЗНЫЕ сервисы, общаются только через очередь (bars.*). Курсор calc (откуда дочитано сырьё) принадлежит жизненному циклу calc, а не трейдера: calc рестартится и догоняет независимо, трейдер на рестарт calc НЕ рестартится. Сегодня в мастере курсор живёт как колонки (seq, trades_seq, events_seq) таблицы book_checkpoint (trader/book_store.py:28-35) — это остаток монолита, где книга и курсор писались одним процессом. При разделении это ломается: writer курсора и writer чекпойнта — разные процессы с разными каденциями и разными отказами.
    • Drivers: независимость жизненных циклов calc/trader; транзакционность позиции+состояния ВНУТРИ calc; replay от границы бара, не с ack.
    • Options: (a) durable + ack после коммита — держать бар un-acked стоит сотни МБ RAM брокера + ack_wait длиннее бара — rejected; (b) без позиций вовсе (opt_start_time + фильтр u) — рабочий fallback, менее точен — не выбран; © оставить курсор колонками book_checkpoint — rejected: таблица принадлежит трейдеру/книге (writer — calc? trader? оба? — конфликт владельцев), курсор calc дёргается каденцией чужого сервиса, отказ PG у трейдера роняет прогресс calc и наоборот; (d) этот: ОТДЕЛЬНАЯ таблица курсоров calc per-(symbol|type) (stream seq + U/u) в той же PG16 trader DB отдельной схемой, calc владеет миграциями, bootstrap ensure создаёт до первого чтения — принят.
    • Decision: Мы храним курсоры calc в ОТДЕЛЬНОЙ таблице (не колонки book_checkpoint); resume — один ephemeral consumer на EXACT subject от per-subject seq+1; дыра детектится кодом (retention_hole + stream_first_seqs probe), не брокером. book_checkpoint остаётся владельцем только книги (writer — calc, читатель при рестарте — calc; трейдер книгу больше не трогает вовсе — он видит только бары).
    • Consequences: +жизненные циклы разделены; +миграции курсора не трогают книгу; −планировщику писать DDL + ensure/bootstrap с нуля (образец — tests/test_book_store_schema_bootstrap.py); −три владельца стейта в одном PG-инстансе (calc: книга + курсоры; trader: intake-чекпойнт) — разные таблицы/схемы, конфликта записи нет, но инстанс общий: его отказ бьёт по calc и trader сразу (§11); почему один инстанс — один VM, понодовый шардинг PG отложен.
    • Re-evaluation Trigger: PG становится связывающей ценой → отдельный ADR с миграцией.
    • Verification: fresh-infra тест (пустая PG → ensure создаёт таблицу до первого чтения); X-001 (first match at/after start; expired/future → empty fetch); kill-calc среди бара → кольцо полное, бар равен эталону; kill-trader НЕ трогает курсоры calc (проверяется раздельно).

    D5. Бар v1: всегда эмитим, тишина = NULL, штамп обязателен¶

    • Status: accepted направлением (Gate 4: редизайн под пустоту; детали полей — planner implementation по bars-contract; блокирует шаги ⅗/6).
    • Context: движок сегодня заливает тишину 0.0 + ffill на чтении — live/replay расходятся, бэктест ест молча то, что live съел молча.
    • Drivers: паритет live/replay/backtest; no silent loss (INV-002).
    • Options: (a) «0.0 IS null по конвенции» — неразличимо — rejected; (b) сузить INV-001 под 0.0 — узаконить молчание — rejected решением человека; © этот: отсутствующий ключ = NULL, штамп обязателен, нет stamp = бар невалиден — принят.
    • Decision: Мы эмитим ровно один бар на окно на символ всегда (пустое = NULL); каждый бар несёт полный штамп v1; bar_complete — bool сразу (parquet-совместимость рвём сознательно, без переходного периода).
    • Consequences: +паритет; −редизайн движка/моста (empty_row, _sanitize, ffill, Aggregate хранит U/u/pu + agg id, прокси штампует connection id); −старые parquet с float-колонкой несовместимы по схеме. Не противоречит D8 («старая история как есть»): бэктест читает оба формата разными путями (D8 — до штампа по bar_complete+пропускам ts), миграция старых файлов не делается.
    • Re-evaluation Trigger: штамп не покрывает исполнение (нужны тики в трейдере) → пересмотр контракта.
    • Verification: первый опубликованный бар валидируется по контракту целиком; тихий символ = NULL + complete=false + blind_sec=1800; дубликат поглощён.

    D6. Trader intake: строить полный комплект-механизм, а не сужать до guard¶

    • Status: accepted направлением (Gate 4: строить все — против рекомендации лида оставить guard до замеров; решение человека имеет силу; T=5 без замерного основания до тени).
    • Область: это ОДНО решение — «build-all vs narrow-to-guard». Его состав (wait-full-set, 3-state, stale-drop, Prometheus-экспортёр, order-id) — не отдельные ADR, а payload выбранного варианта; своих альтернатив у составляющих нет (альтернатива у всего механизма — вариант (a) ниже). Дедлайн окна как лимит вынесен формулой в §8 (Design Limits, wait_deadline); order-id как контракт идемпотентности — в §8 (Data) и таблице транзакций §7.
    • Context: портфельный трейдер на посимвольных барах от N шардов: опоздавший шард либо блокирует окно, либо торгуется без него — оба молча нельзя.
    • Drivers: комплектность окна без блокировки; явная деградация; наблюдаемость.
    • Options: (a) сузить до freshness-guard + HOLD как есть — дёшево, но комплектности окна нет и дыры немы — не выбран (человек решил строить); (b) этот: ждать комплект до deadline, дальше торговать доступным + маркировать missing, 3-state gate, stale-drop со счётчиком, Prometheus-экспортёр, order-id — принят.
    • Decision: Мы строим полный trader intake: wait-full-set (deadline формулой §8), 3-state (norm торгует / degraded только закрывает / poor flat до ручного сброса), stale-drop (ack+drop + счётчик), Prometheus-экспортёр, order-id из (символ + ts бара).
    • Consequences: +окно комплектно и немо никогда; −T=5 без замеров до тени (формула в §8, число после тени); −экспортёр/имена/правила отсутствуют — отдельная плановая задача (проводка — workspace OBS-SPEC).
    • Re-evaluation Trigger: замер bar-set latency в тени показывает, что T=5 не покрывает скос шардов → пересмотреть deadline числом, не механизмом.
    • Verification: S-5 bars-burst; двухрежимный прогон (полный комплект vs missing после deadline); сквозная проводка счётчик→штамп→метрика→алерт.

    D7. Единственность трейдера — порядком деплоя¶

    • Status: accepted (Gate 4: порядок деплоя как механизм единственности).
    • Context: два активных трейдера на один аккаунт — денежно необратимо; механизма fencing в коде нет.
    • Drivers: monetary irreversible; no mechanism today.
    • Options: (a) advisory-lock/лидерство в PG, exchange-side guard, kill-switch — механизм, не процедура — не выбран (человек решил порядком); (b) этот: писатель и трейдер — stop-first redeploy (overlap невозможен, одна реплика — планировщик кодирует), коллектор — start-first (перекрытие допустимо, дедуп 300s гасит) — принят.
    • Decision: Мы держим единственность трейдера порядком деплоя (stop-first, одна реплика) на пилоте (paper/testnet) и при cutover; cutover/retire без закодированного порядка запрещены. Переход на mainnet real-money — жёсткий гейт: не выпускать живые деньги без fencing-МЕХАНИЗМА (PG advisory-lock/ лидерство), решение C от 2026-09-13; сам механизм — в бэклоге.
    • Consequences: +без нового механизма на пилоте; −дисциплина деплоя вместо кода до mainnet; +живые деньги защищены механизмом, не дисциплиной (гейт перед mainnet).
    • Re-evaluation Trigger: любой инцидент двух писателей → вернуться к (a) немедленно; в любом случае fencing-механизм обязателен до mainnet real-money.
    • Verification: redeploy-прогон показывает отсутствие overlap (stop-first); тень коллектора показывает транзиентный дедуп.

    D8. S3 layout + backtest offline¶

    • Status: accepted (human 2026-09-12).
    • Context: портфельному чтению нужен cross-section за окно одним чтением; исследовательский бэктест не должен висеть на живом стриме.
    • Drivers: один daily read = полный cross-section; backtest не couples к live.
    • Options: (a) per-symbol-per-day файлы — больше файлов, хуже для cross-section — rejected; (b) live backtest consumer на bars.* — out of budget, couples research к live — rejected (NG5); © этот: 1 файл/день/тип, все символы, backtest offline только из S3 — принят.
    • Decision: Мы пишем <date>/<type>.parquet с колонкой символа; бэктест грузит диапазон дат из S3 и фильтрует дыры ровно как live degraded (по штампу как только он есть; до штампа — по bar_complete=false + пропускам ts).
    • Consequences: +паритет G3; −миграция Hive→daily НЕ требуется (вердикт «забей», старая история как есть).
    • Re-evaluation Trigger: паттерн чтения меняется (symbol-long вместо cross-section) → пересмотр layout.
    • Verification: листинг архива + прогон live-фильтра на S3-диапазоне.

    D9. Файловый предел тени — daily merge в S3¶

    • Status: accepted направлением (Gate 4: Q-005(b)).
    • Context: во время тени (два layout параллельно — старый Hive и новый daily) файлы удваиваются; диск одного хоста ограничен и может быть съеден тенью до cutover. Отдельно от D7 (fencing): это ресурсный предел, не единственность.
    • Drivers: bounded local disk во время тени; локальный файл удаляем только после подтверждённой копии в S3.
    • Options: (a) держать обе раскладки локально до cutover — диск удваивается без bound — rejected; (b) этот: в конце дня файлы сливаются в S3 (1 файл/день/тип) дописыванием, локальный удаляется только после copy-verify — принят.
    • Decision: Мы сливаем файлы в S3 в конце дня (1 файл/день/тип) с удалением локального только после проверки; граница локала ≤ ~1–2 суток (§8 File-disk bound).
    • Consequences: +диск тени ограничен формулой; −слияние обязано быть идемпотентным (рестарт среди слияния = повторное, владелец — archiver, §6).
    • Re-evaluation Trigger: коэффициент сжатия/объём тени не укладывается в ~1–2 суток локала → пересмотреть окно слияния или вынести staging на свой том.
    • Verification: file-watching soak (S-1) подтверждает границу локала и коэффициент сжатия; kill среди слияния → повторное слияние даёт тот же daily-файл.

    11. Risks + Failure Modes¶

    Классы: A невосстановим / B с биржи / C из персистентных данных / D потеря приемлема. Деградация — явная и поименованная; невалид — fail loud. Ретраи — явными константами в коде (таблица — в ADR-0001 §11, наследуется). DLQ отсутствует осознанно.

    Событие Класс Поведение
    Дырка в диффах (U/pu) C Без ресинка: остаёмся на книге от чекпойнта, бары неполные (штамп), дальше реплей
    Дырка в трейдах (agg_id) C Счётчик + WARNING; живой контур не останавливается; бар помечается через штамп
    Слепое окно (heartbeat молчит) C blind_sec в штампе; тихое окно без событий = NULL + complete=false + blind_sec=1800
    Отставший archiver/calc C JetStream копит; лаг = громкая дыра (gap + num_pending), не backpressure
    Диск под очередь кончился D discard: old: теряем старьё, поток жив
    Proxy лёг B Окно не получил никто; trade/kline — backfill из REST; книга — RAM calc; бары неполные
    Calc лёг C, fallback B Чекпойнт + курсоры + реплей; ретеншн превышен → hole; PG пуст → холодный старт
    Trader лёг C Позиции/баланс с биржи заново; resume bars с хвоста; calc НЕ рестартится
    NATS лёг C, overflow D Буфер proxy (~час); дольше — дроп со счётчиком и алертом → как дырка
    PG лёг (общий инстанс) C, fallback B Бьёт по calc и trader сразу: calc жив из RAM, коммиты книги/курсоров фейлятся громко, краш в окне → откат на предыдущую границу; trader не коммитит intake-чекпойнт (после рестарта добирает комплект из bars-хвоста), позиции не затронуты (с биржи, D10)
    Два трейдера денежный Запрещён порядком деплоя (D7); инцидент → вернуться к lock-механизму
    S3 PUT двусмыслен C Не удалять локально; алерт; повтор следующим циклом (copy-verify-delete)

    Что ломается первым при ×5 нагрузки: первым упирается реплей в RTO (CPU-bound питоновского клиента + скаляры) — шардирование по процессам, затем сплит calc; вторым — диск очереди/архива и слив буфера; третьим — память calc на 600 книг.

    Отложенные рычаги (триггеры возврата): дисковый WAL буфера (кап < часа / разъезд / падения чаще раза в месяц); репликация proxy (первый прод-инцидент); срез книги по mid ~50% (блоб мешает); чекпойнт слотов кольца (реплей вне RTO); RedPanda (десятки тысяч msg/s, контракт не меняется); сплит calc ×2–×3 (метрики непересекающиеся + CPU упёрся).

    13. Security¶

    • Trust boundaries — §5 (граница internal/untrusted на C4-L2). Internal — один VM (порты NATS/дашборда опубликованы на хосте — поза ADR-0001 §13 наследуется); всё внешнее (Binance, S3, браузер) — untrusted.
    • Auth/authz — как собрано в docker-compose.yml (фактическая поза ADR-0001 §13: PG — пароль обязателен + SCRAM; NATS — без creds пока один VM; dashboard — read-only + env-creds). Триггер: разъезд по хостам → до выноса любого порта за хост: NATS creds + TLS transit, dashboard за auth (PG SCRAM уже включён).
    • Encryption: transit внутри VM — plaintext loopback (триггер выше — TLS); at-rest — диск VM без полевого шифрования; S3-архив — SSE бакета. Полевого шифрования уровней книги нет (маркет-дата, не секрет).
    • Secrets: только env (BINANCE_API_KEY/SECRET, creds дашборда/архиватора); никогда в live_config.yaml и коде. Конфиг — только live_config.yaml, fail loud без in-code дефолтов; env — только секреты и wiring.
    • Audit log: append-only для живых денег — fills/blotter трейдера + live_state.json как фид; чекпойнт PG — не audit (регенерируем, перетирается).
    • PII/GDPR: неприменимо — в контуре только маркет-дата и derived метрики. При появлении user-identifying данных — пересмотр этого раздела.
