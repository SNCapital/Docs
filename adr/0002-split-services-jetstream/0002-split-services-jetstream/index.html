    0. Шапка¶

    1. Overview¶

    Исследовательская live-платформа делится на раздельные сервисы через NATS JetStream: data proxy держит край биржи, raw archiver пишет архив, metric calc считает бары со штампом качества, trader торгует только готовыми барами своей биржи. Ключевое свойство: рост — это добавление единиц деления (биржи × очереди/ноды × шарды символов), а не переписывание; тишина и дыры никогда не молчат (NULL-бары + штамп + явные состояния трейдера).

    2. Goals / Non-Goals / Deferred¶

    Goals (этот док фиксирует):

    • G1. Разделение на четыре сервиса с replayable очередью как границей: proxy × E (по одному на биржу), archiver, calc × E (шарды по символам, старт E = 1), trader × E (один на биржу/аккаунт). Очередь одна логически, скейлится по нодам.
    • G2. Контракт bars.*: 1 сообщение = 1 закрытый 30-минутный бар со всеми ключами и штампом качества (единственное исключение — identity-only gap-marker type:"gap" на том же subject при недоказуемом окне, §8/D5); биржа в теме (bars.binance.usdm.*); трейдер видит только бары своей биржи.
    • G3. Трейдер на биржу (на аккаунт): ордера напрямую в Trade API мимо шины, позиции — из user data stream со сверкой, локально не хранятся (D10 из ADR-0001).
    • G4. Штамп качества и ingress time как часть контракта данных: без них live и replay/backtest расходятся на границах баров. Receive time — received_ms (epoch ms) в теле каждого md.* события + заголовок X-Ingress-Ms (транспортный дедуп/триаж, теряется при архивации); поле в теле — долговременная копия, переживающая parquet и replay.

    Non-Goals (осознанно исключено):

    • N1. Тьюнинг пулов/тредов/TCP/батчей — runbook, по RULES.md I.2 (в доке только формулы и инварианты). Обновление 2026-09-22 (аудит конфига, решение «8-all»): эксплуатационные ручки — это обязательные fail-loud ключи live_config.yaml (archiver_*, pg_connect_timeout_s), а не env и не дефолты в коде; env остаётся только для секретов и wiring (B2_*, PGPASSWORD, NATS_URL). Удаление ключа из файла = отказ при старте с именем ключа; env-переменные ARCHIVER_*/PGCONNECT_TIMEOUT больше не читаются. Обновление 2026-09-23 (решение 3-A): пороги 3-state гейта (gate_*, D6/T-E4.3) — тоже обязательные ключи live_config.yaml; значения остаются TBD-soak и перенастраиваются без кода.
    • N2. PII/GDPR-механика — в контуре только маркет-дата (как в ADR-0001 §13).
    • N3. Мультиаккаунт внутри одной биржи и мультирегион — один аккаунт на биржу, один контур (триггер в шапке).
    • N4. S3 lifecycle/compression tuning сверх copy-verify-delete; детальный security-дизайн сверх trust boundary.

    Deferred (с триггерами возврата):

    • Сплит калькулятора по семействам очередей ×2–×3 — только когда метрики между семействами доказуемо не пересекаются; решением человека отложен («пока без шардов»).
    • Понодовый шардинг PG — будущее, не этот док.
    • Стартап ~32s на 12000 стримов (board-measured) — пункт soak, не constraint, пока не замерен на нашем хосте.

    3. Constraints¶

    Нумерация C* — локальная для этого ADR и НЕ продолжает нумерацию ADR-0001 (там C6/C7/C8 — про универсум/бар/конфиг, другой смысл). Ссылки на наследуемые constraints даются по их номерам в ADR-0001.

    Технические (наследуются из ADR-0001 §3, не дублирую: его C2 лимит REST 2400 weight/мин — лимит на IP, общий для collector/calc/trader; делится квотами rest_weight_quota_{collector,calc,trader} в live_config.yaml, сумма <= 2000 (~400 запаса ниже лимита биржи 2400/мин на IP — под всплески и не учтённых квотой вызывающих, estimate; загрузчик падает иначе), 429/418 ставит на паузу все REST-вызовы процесса до конца бана (trading_rest_ban_total{service,status}); bootstrap книг calc растянут под свою квоту, не пачкой; C3 срез REST depth, C4 каденции подписок, C5 роутинг fstream двумя соединениями). Новые и изменённые (локальные номера):

    • C6. Нагрузочный базис measured: сырьё 22–40 ГБ/сутки @60 символов (прод — 100 символов USD-M: линейно ~37–67 ГБ/сутки, estimate до S-1) (measurements.md §6 L6/L7; cross-check — measurements.md §9 sustained 350 КБ/с ×86400 ≈ 30.24 ГБ/сутки, середина диапазона). Отвергнуто как sizing-вход: 13 ГБ/день (board-estimate сжатого parquet) и 61.6s/1220 снапшотов (O6; арифметически несостоятельно: 86400/1220 = 70.8, не 61.6).
    • C7. Retention сырья D-001: 24h + max_bytes hard stop. Атрибуция deviation — цепочка: 72h ADR-0001 → 48h D-001 (Gate-4-accepted, решение человека 2026-09-12) → 24h этой веткой (commit 6a7aedb); формула «простой + худший + буфер» соблюдена на каждом шаге, число другое — bound диска + S3-прогресс архиватора. S2 ratio measured 0.37 ± 0.01 (bulk; мелкосообщённые потоки overhead-dominated, ratio ≥ 1.0) — X-004.
    • C8. Формат архива D-002: JetStream — WAL; локальная единица durability — immutable Parquet-сегмент по 60 секунд ВРЕМЕНИ ЗАПИСИ архиватором на тип. Время события остаётся отдельной колонкой; задержка события не является основанием для term(). После рестарта создаётся новый уникальный part, уже закрытый файл не перезаписывается. ACK-грань: close footer → fsync(file) → atomic rename → fsync(directory). MsgId хранится в parquet; повторные строки удаляются при merge и чтении. Дневные S3-объекты неизменяемы, дополнительные части идут в {day}/{kind}.late-{identity}.parquet. Полный pending merged-файл и точный manifest его входов сохраняются до verify и очистки; повторный merge не заменяет pending-файл остатками входных сегментов. Доступность S3 — эксплуатационное допущение: локальный файловый bound не обеспечивается при длительном отказе S3 и отдельно в этом изменении не строится.
    • C9. Темы: сырьё остаётся md.{market}.{kind}.{symbol} (переезд на md.binance.usdm.<symbol>.<type> закрыт отказом); биржа-в-теме только для нового семейства bars.binance.usdm.* (без .30m, заморожено кодом+тестом).
    • C10. Бар 30 минут, UTC-aligned; deduplication window 300s < 1800s окна бара (ретрай старше окна требует идемпотентного приёмника — арифметика, не решение).

    Организационные: пилот paper → testnet → mainnet; деплой stop-first для писателя/calc/трейдера (overlap невозможен — fencing порядком деплоя, Q-005; для calc аддитивный ring делает перекрытие вредным, единственность держит только порядок деплоя — без локов, решение 2026-09-13), start-first для коллектора (перекрытие на ingress допустимо — дубликаты гасятся детерминированным MsgId-дедапом 300s).

    Внешние: схема событий принадлежит Binance; сырьё повторяем 1:1 (D7 из ADR-0001).

    Допущения (ASSUMPTION с ценой ошибки):

    • A1. NATS в docker-сети compose, same host, no auth (Gate 0 decided). Порты NATS (4222/8222), дашборда и prometheus публикуются только на 127.0.0.1 (docker-compose.yml; пин — deploy/tests/test_compose_security.py): открытый наружу NATS без auth позволяет любому опубликовать фейковый bars.* или удалить стрим. Ошибка (разъезд по хостам): пересмотреть буфер D9, Security §13 (NATS creds + TLS) — триггер в шапке.
    • A2. Объём для сайзинга — 22–40 ГБ/день (не 13 с доски). Ошибка в меньшую сторону: диск очереди переполняется раньше расчёта (discard: old начнёт есть окно реплея).
    • A3. PG-чекпойнты книги (ADR-0001 D5) остаются источником восстановления книги (владелец — calc); курсоры calc и intake-чекпойнт трейдера — в той же PG16 trader DB отдельными таблицами/схемами (calc владеет своими миграциями, трейдер — своими). Один инстанс на всех троих — общий SPOF (§11), осознанно на одном VM; понодовый шардинг PG отложен. Bars-стрим — производное (пересчитывается из сырья + чекпойнтов), не замена.

    4. Context (C4-L1)¶

    Система — исследовательская live-платформа: стримит маркет-дату, считает метрики по 30-минутным барам, торгует трейдерами по одному на биржу, пишет архив в parquet → S3. Новое против ADR-0001: метрики вынесены в отдельный слой (calc), архив — отдельный сервис, трейдер потребляет только готовые бары своей биржи.

    Postgres (1 инстанс) Три владельца стейта, разные таблицы/схемы (конфликта записи нет): книга — чекпойнт по D5 из ADR-0001 (A3, writer/reader — calc) + курсоры calc per-(symbol|type) (writer — calc); intake-чекпойнт трейдера (набор комплекта за окно; в будущем — статистика торговли; writer/reader — trader; позиции сюда НЕ пишутся, D10). Один инстанс = общий SPOF (§11); понодовый шардинг — будущее, не этот док S
    volumes / dashboard Parquet staging, read-only фид S/A

    Trust boundary: как в ADR-0001 §5/§13 (internal — контур, untrusted — Binance/S3/браузер); управляющей связи proxy ↔ trader нет; каждый трейдер — единственный writer в Trade API своей биржи; деплоем писатель/calc/трейдер stop-first, коллектор start-first (Q-005).

    Phase 1 Summary¶

    Инварианты Phase 1 (constraint для следующих фаз): четыре сервиса (proxy × E, archiver, calc × E, trader × E; старт E = 1) + одна логическая очередь с двумя семействами (md.* сырьё 24h + max_bytes, bars.* короткие пересчитываемые); контракт трейдера — только бары своей биржи со штампом качества + ingress time; ордера и позиции — вне шины; сырьё остаётся на темах ADR-0001, биржа-в-теме только для bars.binance.usdm.*. Открыто и блокирует Phase ⅔: детали полей штампа Q-003, soak-замеры (S2-база, occupancy пилота, волатильная сессия), файловый предел тени. Числа — только measured (22–40 ГБ/день; S2 0.37 ± 0.01 bulk) или формулой.

    6. Components¶

    Только нетривиальные границы (остальное — код, не док):

    • metric calc внутри: книга + движок + штамп качества на единицу деления. Сплит ×2–×3 идёт по семействам очередей (диффы/книга, трейды, остальное) тогда и только тогда, когда метрики семейств не пересекаются: пересечение — общий шард, иначе дубли состояния и сшивка. Проверка непересекаемости и сам сплит — deferred решением человека («пока без шардов»).
    • trader intake: подписка на бары своей биржи, stale-drop, исполнение. Комплект баров за окно (wait-full-set 5 мин, D-001) собирается здесь же: deadline T+5 мин от закрытия окна, дальше торгуем доступным набором + маркируем отсутствующие шарды в штампе; отсутствующий шард никогда не блокирует past deadline.
    • archiver assembly: JetStream служит WAL; события складываются в immutable 60-секундные Parquet-сегменты (+30с grace). ACK отправляется только после durable local close (footer → fsync(file) → atomic rename → fsync(directory)), одной пачкой за весь сегмент (per-segment batch ack; строки внутри сегмента батчатся в row group по archiver_max_rows_per_group). Консьюмеры durable; расхождение живого конфига durable с live_config.yaml (ack_wait, max_ack_pending) лечится на старте сносом и пересозданием durable (converge_consumer; unacked ределивернутся, at-least-once сохранён). max_ack_pending sized от измеренного inbound x hold окна с запасом. S3 upload/verify/delete слитого дневного файла не входит в ACK-грань и ретраится независимо; дневной файл собирается из сегментов идемпотентно (рестарт среди слияния = повторное слияние, владелец — archiver). Shipped-marker закрывает основной дневной объект, но не запрещает новые дополнительные объекты. Состав каждого pending-объекта фиксируется durable manifest до публикации файла. После падения сначала повторяется verify/очистка этого объекта; повторное слияние его остаточных входов запрещено.

    7. Runtime¶

    Durability брокера: sync_interval: always (nats.conf) — fsync до PubAck; при 2s-интервале потеря питания хоста съедала бы уже подтверждённые md.*/bars.* (пин — deploy/tests/test_nats_sync_interval.py). Бюджет диска — per-stream nats_max_bytes_{md_diff,md_trade,md_events,bars} с суммой <= nats_jetstream_max_file_store (= max_file_store в nats.conf), загрузчик падает иначе: один max_bytes на каждый стрим давал 4x overcommit диска.

    Дедупликация везде: брокер оппортунистически (Nats-Msg-Id, окно 300s), консьюмер обязательно. Out-of-order внутри символа невозможен по построению (u монотонен, нарушение = дырка). Публикация бара: calc читает PG-чекпойнт на границу бара → применяет диффы (u-check), ведёт ring, закрывает бар + штамп → публикует 1 msg = 1 закрытый бар и получает broker ack → COMMIT чекпойнта (A3). Пустое окно даёт NULL-бар; тихие символы не скипаем. Транспортный сбой publish/ack (NatsError) не роняет процесс сразу: первый проход по символам границы идёт без ретраев — упавший бар (строка и штамп уже собраны, PendingBar) складывается в pending и после прохода дожимается общим retry-проходом с экспоненциальной паузой (0,5/½ с при дефолтных 3 попытках) под бюджетом calc_bars_publish_retry_budget_seconds; каждый retry логируется и учитывается в trading_calc_bars_publish_retries_total{symbol}, исчерпание попыток — в trading_calc_bars_publish_failed_total{symbol} и ERROR-логе с символом и временем бара. Недоставленные после ретраев бары calc не убивают, а переносятся на следующую границу (carry_over): на ней они стоят в pending первыми и повторяются её retry-проходом раньше свежих фейлов, а удерживается COMMIT чекпойнта только той границы, чей проход закончился с незакрытыми фейлами (boundary_status["ok"]=False → _checkpointing_clock пропускает коммит с ERROR-логом; calc/service.py:425-431,838-994). Процесс умирает, только когда очередь переноса превышает calc_bars_publish_carry_over_max_bars × число активных символов (_carry_over_or_raise, calc/service.py:67-85), а также на fail-loud ветках вне транспорта: отказ публикации gap-маркера, отсутствие engine по символу, ошибка конверта/штампа. Сбой PG-чекпойнта или calc_cursor calc не роняет: запись чекпойнта вынесена в отдельный writer-цикл (_checkpoint_writer_loop), который ретраит с капнутым экспоненциальным backoff (calc_pg_retry_initial_s/calc_pg_retry_max_s, live_config.yaml) и пишет только НОВЕЙШУЮ опубликованную границу, когда PG встаёт; каждый фейл — ERROR + trading_checkpoint_pg_failures_total. Публикация баров и потребление идут дальше из RAM. Книга, u и курсоры сериализуются синхронно в неизменяемый снимок на границе бара ДО первого await; writer получает снимок только после публикации баров. Ретраи не читают live-состояние, новая опубликованная граница заменяет ожидающий снимок. Книга и курсоры символа коммитятся ОДНОЙ транзакцией (write_boundary с cursor_writer), prune — отдельно после. Рестарт воспроизводит окно из md.*. Сбой между ack и COMMIT может дать дубль бара; трейдер обязан дедуплицировать (symbol, bar_ts) — и дедуп обязан переживать рестарт: трейдер захватывает окно в PG (trading_windows, UNIQUE (account, window_ts), trader/window_store.py) атомарно ДО отправки ордеров; уже захваченное окно пропускается (trading_duplicate_window_skips_total). Без транзакционного outbox обратный порядок (COMMIT перед publish) оставил бы неопубликованный бар за уже сохранённым курсором.

    Публикация в JetStream без Nats-Msg-Id запрещена везде: md.* публикует только collector (queue_publish.make_publisher), bars.* — только calc (calc/bars_publisher.py), оба с обязательным MsgId.     3-state gate трейдера (D6, trader/gate.py): norm торгует, degraded только сокращает позиции (никогда не открывает/растит), poor пропускает расчёт сигналов и ребалансировку, сохраняя позиции. При POOR продолжается сверка ордеров и состояния счёта. POOR — оценка текущего качества окна, а не аварийная блокировка: новое свежее проверенное окно автоматически заменяет её своей оценкой. При старте после перезапуска прежняя оценка качества не блокирует работу навсегда: до первой свежей проверенной границы сигналы и ребалансировка запрещены, затем действует оценка этого окна. Аварийный kill и риск-ограничения сохраняют отдельное состояние и свою политику; хороший бар их не сбрасывает. Триггеры — assess_window/assess_bar по WindowSet (шард отсутствует после wait_deadline -> missing; missing_frac, stamp.blind_sec, gap-счётчики по порогам GateThresholds, §8/§11):

    1. Читает PG: для каждого символа свой курсор per-(symbol|type) (stream seq + U/u)
    2. блоб книги на новейшую завершённую границу именно этого символа.

Проход — at-least-once: гонка tail-check→publish (calc/service.py:199-201 → :272-293) и ретрай старше Nats-Msg-Id-окна (300s, §7; calc/bars_publisher.py:47-50,204-313) могут дать дубль — его поглощает трейдер по (symbol, bar_ts); receiver-ключ уже обязателен (§7 выше + таблица транзакций; §8 «Бар v1»; приёмник trader/bars_reader.py:43-82), здесь не переопределяется.
    6. Лаг < слота по всем стримам → live — гейт, а не предупреждение: lag >= 1 → ReplayLagError до смены состояния (engine.py), переход удержан, символ получает вердикт skip по посимвольной изоляции (§11). Движок, не открывший ни одного слота (пустой реплей), отставания не имеет — лаг считается 0. Бар в трейдер — только с полным штампом; тихое окно = бар из NULL: blind_sec=1800 (ни одного сообщения) → bar_complete=false, blind_sec=0 (каждую секунду нёс heartbeat, реальных событий не было) → bar_complete=true, first_ts/last_ts = null.
    7. Битый новейший чекпойнт → попытка предыдущего пригодного. Нет пригодного чекпойнта → replay доступных trade/kline/mark событий без исторической книги; книжные метрики отсутствуют (NULL), качество окна неполное.
    8. Replay проверяет цепочку pu == prev.u (USD-M) / U == prev.u+1 (spot). Разрыв инвалидирует книгу, но не прекращает обработку независимых событий. Свежий REST snapshot допускается только для будущего live после replay, никогда для подстановки исторических книжных метрик.

    8. Data¶

    Парадигма: лог как источник истины (JetStream md.*) + регенерируемый чекпойнт книги (PG) + пересчитываемое производное (bars, ring, позиции). Монитор сидит в единственной точке публикации make_publisher (collector/queue_publish.py:142-155): один event loop и single-drainer FIFO (INV-E5-b/T-E5.5) держат водяной знак в истинном wire-порядке, включая скачки id от дропов буфера D9. Номер продвигается только после PubAck; ошибка NATS не превращает неотправленное событие в обработанное. Это производное сообщение, а не точная копия утраченного WS-фрейма. Если REST не вернул непрерывную историю, разрыв остаётся явно отмеченным. Depth backfill отсутствует: replay инвалидирует книгу при разрыве цепочки.

    • Ingress time пишется рядом с биржевым временем в каждом событии: без него live и replay расходятся на границах баров.
    • Ключ партиционирования: биржа → символ (книги независимы → параллельный реплей и шарды без skew по построению).

    Нагрузочный профиль входа (measured; пилот 60 символов USD-M, активный рынок):

    • Живой поток в очередь: ~380 msg/s @60 при max-периоде подписок (120 diffs + 20 mark + ~240 trades); ~3800 msg/s @600.
    • Дифф-байты: ~250–450 КБ/с @60 (max-период режет msg/s, не байты).
    • Суточный объём сырья: 22–40 ГБ/сутки (без booksnapshot). S2 0.37 ± 0.01 bulk (X-004; мелочь ≥ 1.0); фикс. overhead пустого стрима ~12.8 КБ.
    • Occupancy-форма +48h (X-004, 2-символьное окно, форма математики, не объём пилота): +3.10 GB logical / ~+1.15 GB disk; под текущие 24h — половина (~1.55 GB / ~0.58 GB); 72h steady-state ~1.7 GB disk. Пилотный объём — только по §6 (22–40 ГБ/день), не умножением окна X-004.
    • Per-minute peak factors (X-004): DIFF msgs 1.00 / MB 1.49; TRADE 2.35 / 2.34; EVENTS 1.51. Волатильная сессия — отдельным soak-захватом (UTC 13:30–16:00); max_bytes sized против пика, не среднего.
    • PG: 60 строк раз в 30 мин (книга) + курсоры calc той же каденции + intake-чекпойнт трейдера (порядок 1 строки на окно, не per-symbol); UPDATE-чурна нет.
    • RTO рестарта: <= 2 мин (бары 30-мин, пропуск недопустим); худший случай (краш на границе) — ×2. RTO-неравенство из ADR-0001 §9 проверяется на старте.
    • Latency SLO live: p95/p99 wall latency не нормируется (не load-bearing: бары 30-мин, корректность = полнота бара + lag < слота). SLO: bar_complete=true (слот на каждую секунду) и отставание реплея < 1 слота на всех стримах.

    Что ломается первым при ×5 нагрузки — см. §11 (единый источник; порядок: реплей в RTO → диск очереди/архива → память calc на 600 книг).

    Soak-гейты (подробно — workspace soak-runbooks.md): S-1 occupancy+S2 точный (закрывает max_bytes числом); S-2 kill-archiver JetStream+файлы (диск стоит, дыра громкая, publish жив — иначе шаг 6 запрещён); S-3 peak волатильной сессии; S-4 week jitter log (Q-006(d), идёт); S-5 bars-catch-up burst (после первого паблишера).

    10. Decisions¶

    D11. Полная история сигналов и динамический рынок (решение владельца 2026-09-25)¶

    Этот раздел имеет приоритет над прежними описаниями фиксированных 60/100 символов и ограниченного окна истории. Числа в нагрузочных замерах остаются характеристикой измеренного стенда, а не правилом выбора инструментов.

    INV-HISTORY-1. Замена транспорта не меняет входную историю стратегии. На каждом закрытом баре стратегии и распределитель капитала получают всю накопленную историю до этой границы включительно. Торгуется только итоговая строка. Скользящий lookback_days=30, увеличение его до 31 и отключение grace не являются исправлением. lookback_days: null означает всю историю; конечное окно в live-конфигурации запрещено. Grace измеряется от первого доступного валидного наблюдения инструмента в полной истории, а не от левого края каждый раз заново обрезанного DataFrame. Возраст инструмента сам по себе не заменяет фактически доступные данные для операторов.

    INV-HISTORY-2. Суточная retention JetStream ограничивает транспортный replay, но не историю расчёта сигналов. Закрытые бары сохраняются долговременно с ключом (market, symbol, bar_ts) независимо от доступности трейдера. На старте сначала загружается история, затем последовательно догоняется очередь, затем включается live. Повторное получение бара идемпотентно. Gap-marker не заменяет валидный бар, не становится нулевой ценой и не считается прогревом. Остановка трейдера дольше retention очереди не обнуляет накопленную историю. Хранилище создаётся production-путём до первой записи. Calc не дублирует долговременную историю в неиспользуемом RAM-кэше завершённых баров; его рабочее окно ограничено расчётом метрик, а полная история принадлежит хранилищу и трейдеру.

    INV-HISTORY-3. Первичный перенос прежнего архива выполняется явно, с проверкой рынка, интервала, ключей и отсутствия будущих данных. REST-свечи не подменяют отсутствующие исторические метрики стакана. При недостатке истории сервис сообщает состояние прогрева; отсутствие сигналов не объявляется успешным торговым запуском. Приёмка включает сравнение весов прежнего и нового пути на одной истории, включая перезапуск за пределами retention.

    INV-UNIVERSE-1. Множество сбора и торговый universe различны. Collector получает все поддерживаемые активные инструменты выбранного рынка из каталога биржи, без зашитого списка монет и без фильтра top-N по объёму. Calc считает бары этого множества, archiver сохраняет его данные. Листинги и прекращение торгов обрабатываются автоматически при обновлении каталога; ошибка каталога не подменяется старым статическим списком. Старый TON не включается из константы, но и запрет TON по имени не вводится: источником актуального статуса служит биржа. Историческая дата funding — дата расчёта ставки, а не доказательство наличия рыночных баров с этого момента. Cold replay начинает шкалу баров с первого рыночного события; предшествующая ставка сохраняется как контекст с исходной funding_time_ms, но не создаёт месяцы фиктивного catch-up. Funding-only replay не создаёт границу бара; записи funding после хвоста рыночных событий не передвигают этот хвост и явно отражаются в диагностике. Replay raw-событий и BARS читает фиксированное начальное num_pending своего consumer. Пустые потоки не ждут fetch timeout для каждого символа; новые поступления переходят в live через sequence handoff. Если объявленный снимок не дочитан из-за timeout или пустого ответа, восстановление завершается ошибкой, а не ложным успехом. Временные pull-подписки закрываются в любом исходе.

    Каталог обновляется каждые market_symbol_refresh_seconds (сейчас 300 секунд). Calc применяет новый снимок на следующей границе бара: для добавлений сначала выполняется отдельный cold replay в ещё не подключённых к live движках, затем они подключаются к живому потоку. Действующие движки повторно не проигрываются. Завершившие торги инструменты удаляются из текущего расчёта, их история сохраняется. При изменении множества collector заменяет только подключения и pollers затронутого рынка; очередь отправки и её буфер не перезапускаются. Полный список разбивается на WebSocket-подключения: MAX_STREAMS_PER_CONNECTION=1024 соответствует пределу подписок, MAX_COMBINED_STREAM_URL_BYTES=8000 ограничивает размер URL с запасом относительно типичного 8 KiB HTTP request-line. Это транспортные пределы, не лимит числа собираемых монет. Benchmark-подписка учитывается в каждом пакете. Временная сетевая ошибка обновления явно логируется; работающие подключения с последним успешно полученным каталогом сохраняются до следующей попытки. Первичный запуск без каталога и некорректная структура ответа завершаются ошибкой.

    INV-UNIVERSE-2. Торговый universe пересчитывается на каждой торговой границе (сейчас 30 минут), по среднему USD-объёму закрытого бара за предшествующие 30 календарных дней. При полной сетке это даёт тот же порядок, что сумма объёма; отсутствующие наблюдения не подменяются нулями. Размер окна задаётся временем, а не константой количества получасовых строк. Частота совпадает с расчётом весов: отдельный суточный снимок не задерживает листинги, делистинги и изменения ликвидности ещё на сутки. Длинное окно объёма уже сглаживает шум; добавочный hysteresis без измеренного требования не вводится.

    Выбирается не более end_range инструментов (сейчас 40) среди совместимых с исполнителем, торгуемых и достаточно прогретых. Текущий исполнитель допускает только quoteAsset=USDT и contractType=PERPETUAL из метаданных биржи; остальные активные контракты продолжают собираться, но не открываются этим исполнителем. При равном объёме порядок определяется символом. Нельзя сначала независимо выбрать 40 имён для каждой стратегии, а затем торговать их объединение большей мощности. Выбор причинный: только данные с временем не позже расчётной границы; одинаковые данные в live и backtest дают одинаковый выбор. Ожидаемое множество для quality gate фиксируется до ожидания баров текущей границы, по истории строго раньше неё. Пропавший текущий бар не меняет этот снимок задним числом.

    INV-UNIVERSE-3. Исключение из universe запрещает новые позиции, но не прекращает учёт, оценку и закрытие уже открытой позиции. Quality gate оценивает инструменты, нужные для текущего торгового решения и сопровождения позиций, а не автоматически все собранные новые листинги. Отсутствующие данные выбранного инструмента нельзя скрыть удалением его из знаменателя проверки качества.

    INV-HISTORY-4. Регрессионная приёмка обязательна: зрелый символ после 30 дней и после рестарта сохраняет доступность; история не усечена; неизвестный новый листинг попадает в сбор без изменения конфигурации; top-N меняется причинно на торговой границе и не превышает N при ties; исчезнувший инструмент не открывается заново, но имеющаяся позиция продолжает сопровождаться. Зелёный /healthz без этих проверок не доказывает сохранение торгового поведения.

    D12. Совместимость архива с Backblaze B2 (2026-09-25)¶

    Backblaze B2 отклоняет использованный If-None-Match при завершении multipart загрузки. Нельзя считать все S3-совместимые реализации поддерживающими условную запись AWS. Для B2 используются поддерживаемые операции; до загрузки проверяется наличие объекта, после неё обязательно проверяется содержимое. Совпавший объект повторно не записывается, несовпадение по существующему ключу завершает операцию ошибкой без удаления локальных файлов.

    На этом пути действует существующий контракт одного архиватора и stop-first развёртывания; операции одного процесса сериализованы. Это не атомарный server-side create-only для конкурирующих внешних writers: такие writers для пространства ключей архива не поддерживаются. Удалять локальные сегменты разрешено только после подтверждённой проверки долговременной копии.

    Отсутствием объекта считается только документированный ответ not-found. Ошибки сети и доступа не превращаются в отсутствие. Исключение транспорта может иметь response=None; обработчик обязан сохранить исходную ошибку, оставить локальные данные для повтора и не падать при разборе response.

    Источники контракта провайдеров: Backblaze Complete Multipart Upload, AWS CompleteMultipartUpload.

    • Consequences: +окно комплектно и немо никогда; −T=5 без замеров до тени (формула в §8, число после тени); −экспортёр/имена/правила частично реализованы в этом PR (/metrics на трейдере + deploy/alerts.yml + CI-гейт); оставшаяся проводка счётчиков — по OBS-SPEC.
    • Re-evaluation Trigger: замер bar-set latency в тени показывает, что T=5 не покрывает скос шардов → пересмотреть deadline числом, не механизмом.
    • Verification: S-5 bars-burst; двухрежимный прогон (полный комплект vs missing после deadline); сквозная проводка счётчик→штамп→метрика→алерт.

    D13. POOR — остановка торговых решений по качеству данных, не аварийный выход (2026-09-25)¶

    • Status: принято; исправляет ошибочный контракт POOR из D6.
    • Context: прежняя реализация превращала POOR в пустые целевые веса. Исполнитель трактовал их как команду закрыть позиции, хотя плохие данные не обосновывают продажу и могут сделать исполнение хуже.
    • Decision: При POOR трейдер пропускает расчёт стратегий и ребалансировку, сохраняет открытые позиции и продолжает сверять ордера и состояние счёта. Следующее свежее проверенное окно автоматически задаёт новое состояние качества; если оно norm, торговые решения возобновляются, если degraded — действует ограничение degraded, если poor — удержание продолжается. После рестарта старый POOR остаётся только диагностикой: до первой свежей проверенной границы нельзя считать сигналы или ребалансировать, а затем применяется её оценка.
    • Risk separation: аварийный stop/kill и риск-лимиты остаются самостоятельными механизмами со своей политикой, сохранением и восстановлением. Оценка качества norm не очищает и не перевзводит их. Их отдельная политика может закрыть позиции при срабатывании риска, даже пока качество данных удерживает обычные решения.
    • Consequences: удаляется ручное снятие POOR как средство возобновления торговли; операционное восстановление подтверждается свежими данными. Статус POOR сам по себе не создаёт ордеров и не меняет позиции.
    • Verification: плохое окно не вызывает расчёт стратегий или rebalance и сохраняет позиции; сверка продолжается; свежее norm-окно автоматически возобновляет расчёты; плохие окна сохраняют hold; рестарт ждёт свежую проверку; kill/risk latch остаётся активным после чистого окна.

    D7. Единственность трейдера — порядком деплоя¶

    • Status: accepted (Gate 4; пересмотрено решением человека 2026-09-23 — fencing-механизм не нужен, в том числе на mainnet).
    • Context: два активных трейдера на один аккаунт — денежно необратимо.
    • Drivers: monetary irreversible; один контур, одна реплика трейдера.
    • Options: (a) advisory-lock/лидерство в PG, exchange-side guard, kill-switch — механизм в коде — не выбран; (b) этот: писатель/calc/трейдер — stop-first redeploy (overlap невозможен, одна реплика, deploy/deploy_order.py падает на start-first для них), коллектор — start-first (перекрытие допустимо, дедуп 300s гасит) — принят.
    • Decision: Мы держим единственность трейдера механизмом деплоя (stop-first, одна реплика) на всех режимах, включая mainnet real-money; cutover/retire без закодированного порядка запрещены. Отдельный fencing-механизм не строим (решение человека 2026-09-23; прежний гейт «mainnet только с fencing» снят). При cutover со старого контура старый systemd-трейдер останавливается и отключается (systemctl disable --now) до старта нового — это часть deploy-порядка.
    • Consequences: +без нового механизма; −единственность держит деплой, а не код: ручной второй запуск или зомби-контейнер не блокируются.
    • Re-evaluation Trigger: любой инцидент двух писателей → вернуться к (a) немедленно.
    • Verification: redeploy-прогон показывает отсутствие overlap (stop-first); тень коллектора показывает транзиентный дедуп.

    D9. Файловый предел тени — daily merge в S3¶

    • Status: accepted (вердикт Q-005(b) — daily merge — записан после Gate 4, 2026-09-12).
    • Context: во время тени (два layout параллельно — старый Hive и новый daily) файлы удваиваются; диск одного хоста ограничен и может быть съеден тенью до cutover. Отдельно от D7 (fencing): это ресурсный предел, не единственность.
    • Drivers: bounded local disk во время тени; локальный файл удаляем только после подтверждённой копии в S3.
    • Options: (a) держать обе раскладки локально до cutover — диск удваивается без bound — rejected; (b) этот: закрывать durable Parquet-сегменты (60s + 30s grace), идемпотентно собирать их в дневной объект и грузить слитое в S3 — принят.
    • Decision: Мы закрываем сегменты каждые 60 секунд (+30с grace); после durable local close ACK-аем JetStream. Суточное слияние (00:00 UTC + merge delay) собирает их в дневной объект; минутные сегменты удаляются только после подтверждённого S3 copy-verify слитого файла (весь файл, не по сегменту). Post-ship политика: основной объект неизменяем. Новые сегменты дня образуют отдельные .late-* объекты с устойчивой идентичностью для повторной отправки. Durable manifest содержит точные имена входов; purge затрагивает только их. До удаления pending-файла retry использует именно его, не повторный merge. S3 create-only и проверка содержимого не позволяют заменить полный объект неполным либо другим объектом с тем же числом строк.
    • Consequences: +поздние уникальные события сохраняются; +S3 retry не блокирует ACK локально сохранённых сегментов; −read должен учитывать дополнительные объекты и дни записи позже дня события. ~1–2 суток — ожидаемый объём при доступном S3, не жёсткая гарантия диска при отказе S3.
    • Re-evaluation Trigger: коэффициент сжатия/объём тени не укладывается в ~1–2 суток локала → пересмотреть окно слияния или вынести staging на свой том.
    • Verification: file-watching soak (S-1) подтверждает границу локала и коэффициент сжатия; kill среди слияния → повторное слияние даёт тот же daily-файл.

    • Encryption: transit внутри VM — plaintext loopback (триггер выше — TLS); at-rest — диск VM без полевого шифрования; S3-архив — SSE бакета. Полевого шифрования уровней книги нет (маркет-дата, не секрет).
    • Secrets: только env (BINANCE_API_KEY/SECRET, creds дашборда/архиватора); никогда в live_config.yaml и коде. Конфиг — только live_config.yaml, fail loud без in-code дефолтов; env — только секреты и wiring.
    • Audit log: append-only для живых денег — fills/blotter трейдера + live_state.json как фид; чекпойнт PG — не audit (регенерируем, перетирается).
    • PII/GDPR: неприменимо — в контуре только маркет-дата и derived метрики. При появлении user-identifying данных — пересмотр этого раздела.

    Phase 4 Summary (consolidation + I.6 self-check)¶

    Инварианты: очередь — durability-граница под age-wins (24h + max_bytes); восстановление — только реплеем от границы бара по курсору PG + u; чекпойнт — блоб целиком + tx + ack после COMMIT; бары — производное пересчитываемое (всегда эмитим, тишина = NULL, штамп обязателен); трейдер — wait-full-set + 3-state + stale-drop, единственность порядком деплоя; архив — JetStream как WAL, durable segment commit (60s + 30s grace), затем idempotent daily merge и независимые copy-verify-delete слитого файла. Лимиты — формулами (§8), числа — только measured (22–40 ГБ/день; S2 0.37 ± 0.01 bulk; пики X-004) или конфиг после S-1.

    Прогон чек-листа I.6: каждый инвариант имеет проверку (§12 + soak-гейты §9); INV-001/INV-002 — partial: ядро present-only и stamp реализовано, но статус held зависит от сквозной проверки на реальном опубликованном баре и сценариях потерь; INV-003 — held (JetStream) + partial (файлы, до soak D9); статусы помечены явно в §8; очереди/хранилища имеют гарантии формулой (§8); деградации имеют класс восстановления (§11); констант тьюнинга без пометки нет (max_bytes — per-stream бюджеты в сумме 60 GB = max_file_store до уточнения по S-1; T=5 wait_deadline и N-stale — формула §8, число estimate, remeasure после тени); лимиты проходят фильтр I.2 (Contract/Consistency/Scale, Compliance — нет); required-параметров без читателя нет; шапка с триггером есть; диаграммы mermaid соответствуют тексту; противоречий между разделами нет; Non-Goals/Deferred заполнены; каждый инвариант виден в Observability; Security-границы указаны; у каждого решения Drivers до Decision; ASSUMPTION A1–A3 имеют цену ошибки; пустышек без SLO/механизма нет; вопрос «что ломается первым при ×5» отвечен (§9/§11).
