    ADR-0001 — заметки к реализации¶

    Вынесено из ADR, чтобы не перегружать дизайн-документ деталями уровня кода. Актуально на ветках feat/* поверх claude/nsc-90-livemetricsbridge-trader.

    Нумерация ADR — по RULES I.1 (§7 Runtime, §8 Data, §9 NFR, §11 Risks, D-идентификаторы стабильны). Ссылки вида §N ADR ниже — на разделы основного документа текущей нумерации.

    1. Конфигурация¶

    Конфиг — в live_config.yaml, секреты и wiring — в env (AGENTS.md). Лоадер alpha_engine/live/config.py:30 — fail loud, без in-code дефолтов.

    ADR не предписывает тьюнинги «на всякий случай» (YAGNI). Конкретные ключи добавляются только когда появляется caller, которому нужно другое значение — widening дешевле narrowing.

    Обязательство ветки №1 (O-C2): ключи ниже вводятся в live_config.yaml и в полевую таблицу alpha_engine/live/config.py с fail loud; in-code дефолты запрещены по C8/AGENTS.md. До ветки №1 таблица — спецификация имен и мест, значения уточняются замерами той же ветки:

    ключ где заметка
    nats.url env/wiring nats://nats:4222 в Docker, nats://127.0.0.1:4222 локально
    metrics.book_tick_ms live_config.yaml каденция книжных скаляров; RTO-неравенство §9 читает её из конфига
    nats.stream_compression live_config.yaml s2 — по измерениям ADR §9 / measurements.md §7, не инвариант ADR
    nats.duplicate_window live_config.yaml 5м (дефолт NATS 2м) — покрывает retry+reconnect; меньше буфера ~1ч
    nats.sync_interval nats.conf серверный 2s (дефолт минуты); верифицируется kill -9
    nats.retention live_config.yaml 3ч (30м штатно + 60м худший + 1ч буфер, с запасом), discard: old — формулой §8 ADR; суточный объём теперь measured 22-40 ГБ (measurements.md §6), 3 ч ≈ 3-5 ГБ на диске

    2. План тестирования¶

    Золотое свойство: прогон с убийством потребителя даёт те же бары, что и непрерывный прогон (приём как в parity-сьютах 38e0b72).

    2.1 Kill-сьют (ADR §11)¶

    тест что проверяет критерий
    kill трейдера на N сек реплей seq+1 + u > watermark бары за окно == эталон
    kill трейдера среди бара чекпойнт границы бара + реплей от неё текущий бар ПОЛОН, включая ob-часть (ключевой тест D5)
    kill трейдера на 5 секунд стартовая позиция реплея кольцо полное; короткий рестарт ловит то, что длинный маскирует
    kill коллектора дырка задетектилась (spot U, USD-M pu) бары помечены неполными, trade/kline добэкфиллены
    режим реплея Engine исторические тики (§7) полное кольцо, а не один слот
    переключение реплей → live _next_bar/_cur_bucket не разъезжаются на границе переключения
    рестарт трейдера (paper) D10 — не durable позиции не сравниваются; mainnet — сверка с биржей
    graceful shutdown данные уже в очереди ноль потерь
    round-trip чекпойнта блоб + (u, seq, trades_seq, events_seq) → реплей == непрерывная книга, включая слот первой секунды бара
    краш на границе бара коммит нового чекпойнта не прошёл откат на предыдущую границу, бар всё равно полон
    динамический универсум листинг/делистинг между границами баров не ломает чекпойнт; символ без снапшота стартует холодно
    дедуп повторная доставка Msg-Id бар не меняется (серверный дедуп + идемпотентность)
    kill -9 NATS sync_interval измерить фактическое окно, подтвердить секунды
    NATS выключен на N минут буфер коллектора D9 после подъёма бары == эталон
    PG выключен на N минут флаш фейлится громко, трейдер жив восстановление = обычный рестарт-путь
    глубина после дырки бакеты 5%/25% помечены недостоверными, не отданы как валидные

    2.2 Дополнительные проверки¶

    • Parity транспорта (ветка №1): один процесс, NATS за интерфейсом LiveTickBus (async write(market, event) + subscribe). Измерить реальные msg/s и bytes/s, пересчитать кап D9, обновить оценки ADR §9, kill -9 NATS → sync_interval. Доказать bar-parity.
    • Память трейдера (ветка №2): 60 стаканов — замерить RSS, сравнить с RUNBOOK 2-2.5 ГБ.
    • RTO рестарта трейдера (ветка №3): цель ≤2 мин (D4). Замерить средний/пик PG rows/s.
    • Go-парсера больше нет. --metrics-roots у бэктеста читает наши же parquet, которые пишет этот же питоновский движок (ParquetBarSink в live, tools/replay_metrics.py на истории). Следствия: расхождения каденции между бэктестом и live быть не может; парити с Go-портом больше не ограничивает изменения в compute_orderbook / book_scalars — цена правки теперь только в пересчёте уже записанных исторических метрик. Ссылки на internal/bookmgr/bookmgr.go и cmd/replay в докстрингах остаются как происхождение алгоритма, а не как контракт совместимости. Если не укладывается — вариант C (метрики отдельным сервисом) или Python 3.14+ (см. §4).
    • Динамический универсум: добавить/удалить символ между флашами, проверить per-symbol watermark.
    • Retention-границы: рестарт трейдера дольше 3ч (холодный старт) — первый бар неполный, деградированная глубина.

    2.3 Предварительные измерения (до/в ветке №1)¶

    • Nats-Msg-Id для forceOrder: собрать 7 дней type=forceorder, проверить уникальность o.T и необходимость композита S/q/p/ap/l/z. Блокер для старта ветки №1 — снять до разработки.
    • Время набора глубины после дырки: инструментировать resync_count/seq_gaps в BookScalars, получить измеренную границу «бары недостоверны» вместо эмпирической (делается в ветке №5 заодно с kill-сьютом).
    • Реальные msg/s и bytes/s диффов на 60 символах — пересчитать кап буфера D9 и оценки §5.
    • Пропускная способность NATS и стоимость веера консьюмеров — измерено, ADR §9 / measurements.md §7 (стоковый конфиг, 4 vCPU): 0.7-0.8 мс на консьюмера до 1200 штук; чтение ~26k msg/s на процесс с заголовками, линейно по процессам; потолок — питоновский клиент, не брокер; fast-parse вредит.
    • Стоимость compute_book_scalars — измерено и оптимизировано (NSC-51, ветка perf/book-scalars-cone): 5.31 -> 1.30 мс за счёт обхода 25%-конуса вместо материализации книги.
    • Недостоверные книжные дельта-ключи — починено (ветка fix/book-delta-metrics): приращения эмитятся по смене книги, а не по слоту кольца; 140 ключей ожили. Той же правкой __sum счётчиков book_updates_count/seq_gaps/resync_count перестал считать повторы. Осталось разово пересчитать историю через tools/replay_metrics.py — прежняя семантика с новой не совпадает на 143 ключах.

    3. NATS JetStream — детали¶

    • Streams: MD_DIFF (md.*.diff.*, 3ч, discard: old), MD_TRADE (md.*.trade.*, 3ч, discard: old — вынесен отдельно, высокий объём), MD_EVENTS (остальное: md.*.kline.*, md.*.mark.*, md.*.liq.*, md.*.info.*, md.*.funding.*, md.*.stats.*, 3ч, discard: old). MD_SNAP убран — публиковать в него нечего (D3). Унифицировано на 3ч — разного retention на один стрим у JetStream нет, объём поллеров в 3ч пренебрежим.
    • Retention MD_DIFF должен покрывать возраст самого старого чекпойнта, с которого реплеим: 30 мин штатно, 60 мин при откате на предыдущую границу, плюс буфер D9. 3 ч — с запасом.
    • retention: limits обязателен, workqueue ломает восстановление. Проверено: под limits ack двигает только курсор консьюмера и сообщение остаётся в логе (500/500 перечитано новым консьюмером с opt_start_seq=1); под workqueue ack удаляет сообщение (0/500) и реплей невозможен. Writer (D8) акает по ходу дела — под workqueue он молча уничтожал бы диффы, нужные трейдеру. Это инвариант корректности, а не тюнинг; проверять в тестах создания стримов.
    • Реплей — только новыми эфемерными консьюмерами с явным opt_start_seq. Существующий durable отмотать назад нельзя: его позиция принадлежит серверу (повторный bind отдаёт 0 сообщений).
    • Dedup: Nats-Msg-Id как JetStream хедер, не поле payload. Окно дедупа — настройка стрима. Оппортунистическая оптимизация, не гарантия: таблица в RAM, рестарт NATS её стирает. Гарантию даёт идемпотентность консьюмера.
    • sync_interval — серверный nats.conf, не live_config.yaml. Верифицируется kill -9 NATS в ветке №1.
    • Subjects / MsgId — см. таблицу §5 ADR (явные поля Binance, без хешей, dropped_invalid + WARN на невалидном payload).
    • Запасной путь: RedPanda (Kafka-протокол), контракт publish/subscribe не меняется. Триггер — десятки тысяч msg/s.

    4. RTO и параллелизм¶

    • Окно реплея — от границы бара, а не от места остановки: кольцо при старте пусто, ему нужны события с начала бара (D4). Продолжение с последнего ack дало бы после короткого рестарта пустое кольцо.
    • Три позиции, три стрима, все per-symbol: seq (MD_DIFF), trades_seq (MD_TRADE) и events_seq (MD_EVENTS) — колонки одной строки (market,symbol,bar_ts). Sequence разных стримов несравнимы.
    • Текущий план: реплей диффов — per-symbol консьюмеры (filter_subject + opt_start_seq = seq+1), реплей сделок — per-symbol консьюмеры (MD_TRADE, высокий объём, параллельно как диффы), реплей остальных событий — один consumer на MD_EVENTS (~10-50 msg/s без сделок).
    • Веер консьюмеров измерен и дёшев: 0.7-0.8 мс на консьюмера ровно до 1200 штук, 11-25 КБ памяти сервера на каждого, ноль ошибок (перезамер 2026-09: 2.3-2.6 мс/шт, доставка полная — measurements.md §7). Опасение про «шторм CreateConsumer» снято (ADR §9).
    • Доминирует доставка из JetStream (~26k msg/s на процесс с заголовками), затем парсинг и применение диффа (17 мкс), затем скаляры. После NSC-51 (compute_book_scalars по 25%-конусу) скаляр стоит 1.30 мс вместо 5.31, и скаляры перестали быть главной статьёй.
    • Реплей обязан шардироваться по процессам, а не только по консьюмерам. Замер: 1 процесс — 14.6 с на 432k сообщений при 14.5 с CPU (100% ядра), 4 процесса — 5.6 с. Соединения не помогают: упор в GIL, не в сокет.
    • Ограничение: источник правды — RTO-неравенство ADR §9 (после NSC-51 точка обрыва — единицы секунд). Трейдер должен проверять неравенство на старте и предупреждать.
    • Настройки чтения: AckNone на реплее (позиция из PG, не из ack'ов) — +5%; батч fetch 100-1000, fetch(5000) роняет соединение; push-консьюмеры непригодны для реплея — сервер отключает клиента как медленного.
    • nats-py[fast-parse] не подключать. Rust-парсер заголовков fast_mail_parser в нашем профиле пессимизация: контролируемое A/B даёт цену Nats-Msg-Id 3.3% / 19.5% / 5.5% (чистый / Rust / чистый повторно). Заголовок один и короткий, переход через PyO3 дороже питоновского разбора строки. Альтернативных клиентов нет: nats-python заброшен и синхронный, asyncio-nats-client — старое имя nats-py, Rust/C-биндингов не существует.
    • Заголовок стоит 14% (медианы 5 повторений: 24 457 против 21 037 msg/s). Планировать по ~26k msg/s на процесс, не по 31k.
    • Публикация ~22k msg/s на процесс (js.publish с ack, пачками по 3000). Живой поток 600 пар — 6000 msg/s, запас трёхкратный. Но слив часового буфера D9 (~21.6 млн сообщений) при одновременном приёме живого потока идёт со скоростью ~16k/s и занимает ~22 минуты — заложить в алерты, подъём брокера не возвращает норму мгновенно.
    • Брокер не узкое место ни разу: idle 13-23 МБ RSS, CPU 0-30% при чтении на полной скорости, ноль потерянных сообщений на всех прогонах. Стрим на диске ≈ объём payload'ов (не сжат по умолчанию) — compression: s2 из D2 живой рычаг.
    • Ephemeral-консьюмеры не мусорят: после unsubscribe состояние на сервере не накапливается; в прогонах с 1200 консьюмерами память возвращалась.
    • Если реплей не укладывается: рычаги — чекпойнт слотов кольца (§11 ADR), вариант C (метрики отдельным сервисом), или Python 3.14+ (free-threaded mode — снял бы нужду в отдельных процессах).
    • Ack: AckExplicit, ack_wait > максимального удержания пачки writer'ом (дефолт 5 мин при flush 60с). Редоставка до ack — дубли, дедуп по Nats-Msg-Id. Относится к FileWriter (D8); реплей книги и кольца акает не по этой схеме — там AckNone и позиция из PG.
    • max_ack_pending по умолчанию 1000 — измерено: без явного значения сервер перестаёт отдавать на тысяче неподтверждённых. Для writer'а поднять выше размера пачки.
    • Почему не «durable + ack после коммита в PG» вместо хранения seq: держать бар неподтверждённым стоит ~0.35-1 КБ памяти сервера на сообщение — 413 МБ на 60 символах, 4.1 ГБ на 600 (ADR §9; перезамер: ~352 Б → 152 МБ / ~1.5 ГБ, вывод тот же). Плюс ack_wait пришлось бы поднять выше длины бара. Два BIGINT в строке, которую и так пишем, дешевле.

    4.1 Роль FileWriter и durability всей системы¶

    FileWriter (binance_parser/live/writer.py:69) — это бэкап в parquet (market=*/type=*/dt=*/symbol=*/part-*.parquet, zstd) + services/archive.py:44 → S3 tar (ретеншн 3 дня). Не аналог NATS, но в D8 он тоже становится durable consumer'ом md.* в трейдере (ack после flush).

    Важно не сводить D8 только к «бэкап не теряет 60с». Durable consumer'ы — это durability всей downstream-системы: - NATS retention (3ч) + PG чекпойнт (D5, u/seq) + opt_start_seq = seq+1 — восстанавливают книгу и ring метрик (791 ключ) без потерь; - тот же механизм (ack после обработки) у FileWriter — гарантирует что и parquet-бэкап не теряет окно.

    То есть без D8 теряется не только история на диске, но и инвариант «рестарт трейдера не теряет события» для расчёта метрик и торговли: live-реплей зависит от NATS, а полнота бэкапа — от того же ack. D9-буфер — RAM перед NATS в коллекторе (~1ч), страхует NATS лёг до того как события попадут в JetStream.

    5. Деградации — операционные заметки¶

    • discard: old на MD_DIFF — теряем старьё, поток живёт. Обратное (new) остановило бы коллектор — хуже. Смена поведения vs LiveTickBus (live/tick_bus.py:66 молчаливый дроп → наблюдаемый pending в JetStream).
    • NATS лёг → буфер D9 держит ~час. PG лёг → трейдер живёт из RAM, запись чекпойнта фейлится громко; краш в этом окне → откат на предыдущую границу. Live-данные при этом не теряются — реплей идёт из NATS.
    • Коллектор упал с непустым буфером — RAM D9 теряется (осознанная цена D9).
    • Важно: FileWriter — часть общей durability: без ack после flush (D8) теряется и бэкап, и инвариант полноты данных для метрик/трейдера.

    6. Порядок веток¶

    #1 feat/queue-transport  — транспорт за LiveTickBus, измерения, kill -9 NATS (низкий риск)
#2 feat/collector-split  — коллектор в свой контейнер, книга в трейдер (высокий риск, только после #1)
#3 feat/pg-book-store    — PG чекпойнт блобом на границу бара + (u, seq, trades_seq, events_seq);
                           режим реплея в Engine и переключение в live; флаг полноты бара
                           (средний риск)
#4 feat/queue-writer     — FileWriter как durable consumer в трейдере (низкий риск, независим от #3; закрывает класс A для бэкапа и для downstream метрик/трейдера)
#5 feat/restart-resilience-tests — kill-сьют
#6 → Phase 2-4           — фьючерсы, funding, ордера

    3 и #4 независимы; #4 можно двигать раньше если 60-секундная дыра начнёт мешать метрикам/бэкапу.¶

    7. Требования к Engine для реплея (ветка №3)¶

    Сегодня живой движок исторические тики не принимает: wall_clock_anchor=True (metrics_engine/live_bridge.py:208) анкорит первый слот по time.time(), после чего каждый тик с bucket < _cur_bucket сворачивается в текущий слот и выходит (metrics_engine/engine.py:191,207). Проверено: реплей 1200 секунд истории в свежий движок даёт 36 слотов из 1800 при wall_clock_anchor=True и 1199 при False. Молча, без ошибки, с правдоподобной строкой на выходе. Без правок §7 ADR не работает.

    Что нужно сделать:

    1. Явный режим реплея. wall_clock_anchor=False (механизм есть, им пользуется tools/replay_metrics.py:114) плюс подавление эмита баров.
