    ADR-0001. Разделение live-контура на collector и trader¶

    0. Шапка¶
    Status Accepted
    Date Proposed 2026-08-27, decided 2026-09-01, revised 2026-09-02/03
    Deciders Backend team (NSC-87 / NSC-90 owners)
    Base claude/nsc-90-livemetricsbridge-trader
    Supersedes backlog/restart-resilience.md (фазы 1-4 переносятся сюда)
    Resolves NSC-87 (контейнеризация), NSC-90 (LiveMetricsBridge) — следующий шаг после них
    Re-evaluation Trigger Пересмотреть, если: живой поток превысит десятки тысяч msg/s; реплей перестанет укладываться в RTO из §9; появится managed-очередь с replay-семантикой; collector и trader разъедутся по хостам (пересмотреть буфер D9 и Security §13)

    Спутники: 0001-book-store-schema.md (формат чекпойнта D5), 0001-implementation-notes.md (тьюнинги, замеры, kill-сьют). Источник правды по числам — measurements.md; формулы — в этом документе, константы — в спутнике (критерии веток — спутник §6).

    1. Overview¶

    Live-контур делится на два процесса через durable лог: collector держит край биржи (WS + поллеры) и только публикует сырые события, trader держит книгу, метрики, стратегии и архив. Рестарт потребителя не теряет события: восстановление — реплеем лога от чекпойнта на границу бара. Пилот — 60 символов USD-M на одном VM; путь к 600 символам и разъезду по хостам не закрыт, но не оплачен заранее.

    2. Goals / Non-Goals / Deferred¶

    Goals (этот док фиксирует):

    • G1. Деплой стратегий/метрик не рвёт WS и стаканы (секунды вместо минут).
    • G2. Рестарт потребителя не теряет события (очередь — durability-граница).
    • G3. Книжная история пересчитываема (диффы архивируются сырьём 1:1).

    Non-Goals (осознанно исключено, не проектировать):

    • N1. Тьюнинг пулов/тредов/TCP/work_mem/heap — делегирован в runbook (deploy/RUNBOOK.md) и автомасштабирование (RULES I.2). В доке только формулы и инварианты.
    • N2. Точная каденция книжных скаляров как контракт — ключ metrics.book_tick_ms в live_config.yaml, обязателен с ветки №1 (fail loud, in-code дефолт запрещён по C8); док фиксирует только неравенство RTO из §9.
    • N3. PII/GDPR-механика сверх §13 — персональных данных в контуре нет (только маркет-дата).

    Deferred — см. §11.1 (единственный список рычагов с триггерами возврата).

    3. Constraints¶

    Технические (не двигать без пересмотра ADR):

    • C1. Один VM: 8 vCPU / 16 GB / NVMe (deploy/RUNBOOK.md). Свободно ~9.5 ГБ под очередь в RAM — поэтому retention в RAM невозможен (см. решение о брокере).
    • C2. Binance REST-лимит 2400 weight/мин; лимитеру доступно 2000 (common/rate_limiter.py:135, запас 400 вычтен). Один /depth USD-M limit=1000 весит 20 (live/orderbook.py:137): 60 символов = 1200 weight, 600 = 12000 (минимум 6 минут упора в лимитер).
    • C3. REST отдаёт максимум 1000 уровней (USD-M) / 5000 (spot) (config/settings.py:43). Top-1000 на BTCUSDT покрывает лишь ~0.15% от mid (замер §9/приложение) — ресинк даёт обрубок, а не книгу.
    • C4. WS-подписки (профиль max-период, measured 2026-09-03, measurements.md §2-3): depth @depth@500ms (ровно 2/s, байты те же), markPrice без суффикса (ровно ⅓ с), kline_1m (в очередь только closed, 1/мин), aggTrade (trade-driven, BTC ~16/s, альты ~2-4/s), forceOrder (редок: 17 шт/10 мин на 5 символов). Интервал kline — контракт данных, не рычаг.
    • C5. Роутинг fstream (иначе потоков нет физически): с 2026-03-06 (legacy retired 2026-04-23) unrouted wss://fstream.binance.com/stream отдаёт только Public (@depth); остальное — только .../market/stream, depth там нет (проверено живьём, measurements.md §4). Коллектор обязан держать два соединения: /public для depth, /market для остального. Код на момент ADR использует один unrouted base (config/settings.py:25-26) — чинится в ветке №2.
    • C6. Кандидаты универсума: пересечение спот-USDT × PERP-USDT — 355 символов (measured 2026-09-03; спот TRADING 1359, US-M TRADING 762, из них PERP USDT 526). Пилот 60 собирается из этих 355, где есть и спот-история, и перп.
    • C7. Бар 30 минут, UTC-aligned (bar_minutes: 30, live_config.yaml). Ring — 1800 слотов (engine.py:145, tick_ms=1000).
    • C8. Конфиг только live_config.yaml, fail loud без in-code дефолтов (alpha_engine/live/config.py:30); env — только секреты и wiring (BINANCE_API_*, nats.url). CLI-флагов для тюнинга нет (AGENTS.md).

    Организационные: пилот paper → testnet → mainnet; Go-парсера больше нет (--metrics-roots читает наши же parquet — расхождение каденции бэктест/live невозможно по построению).

    Внешние: схема событий принадлежит Binance; мы её не версионируем, а повторяем 1:1 (D7).

    Допущения (ASSUMPTION с ценой ошибки):

    • A1. T_repair ~ 1ч — починка NATS/сети человеком укладывается в час (кап буфера D9). Ошибка: простой дольше капа → дроп со счётчиком → дырка в диффах → бары неполные (§11).
    • A2. Профиль §9 (measured 2026-09-03, активный рынок, 5 символов → экстраполяция на 60/600) репрезентативен для пилота. Ошибка: рынок в разы активнее или скачок универсума → первым упирается реплей в RTO (§11, что ломается при ×5), затем диск очереди/архива.
    • A3. Один VM, loopback = internal без auth (§13). Ошибка (разъезд по хостам): пересмотреть буфер D9, Security §13 (NATS creds + PG SCRAM + TLS) — триггер в шапке.

    4. Context (C4-L1)¶

    Система — исследовательская live-платформа: стримит маркет-дату, считает 791 ключ метрик, торгует/симулирует по 30-минутным барам, пишет архив в parquet → S3. Внешние акторы: Binance (WS/REST, untrusted), оператор (дашборд read-only), S3-совместимое хранилище (архив).

    Trust boundary: всё внутри VM — internal (loopback, без auth — см. §13 с триггером); снаружи — Binance, S3, браузер — untrusted. Управляющей связи collector ↔ trader нет.

    Subjects (контракт, версионируется сменой с простоем):

    md.{market}.diff.{symbol}     диффы стакана
md.{market}.trade.{symbol}    aggTrade (+ trade при reconstruct_multileveled)
md.{market}.kline.{symbol}    только closed (k.x=true)
md.{market}.mark.{symbol}     markPrice / funding
md.{market}.liq.{symbol}      forceOrder
md.{market}.info.{symbol}     exchange_info (строки поллеров)
md.{market}.funding.{symbol}  funding settlement
md.{market}.stats.{symbol}    market_stats

    Streams (инвариант, не настройка): MD_DIFF (md.*.diff.*), MD_TRADE (md.*.trade.*), MD_EVENTS (остальное). retention: limits обязателен — под workqueue ack writer'а физически удалял бы диффы для реплея трейдера (замерено 500/500 vs 0/500, см. спутник §3). MD_SNAP отсутствует — публиковать нечего (D3).

    6. Components¶

    Только нетривиальные границы (остальное — код, не док):

    • OrderBook живёт только в trader (применение диффов, контроль непрерывности по U/pu, сшивка снапшота с потоком). В collector его нет; периодическая публикация полного стакана удаляется; запись книжных снапшотов в parquet переезжает в trader как архив. Детали — спутник §7.
    • Engine требует режима реплея (эмит баров подавлен + флаг полноты бара + громкий счётчик скачков слотов); живой движок исторические тики схлопывает молча — без этого §7 не работает. Детали — спутник §7 notes.
    • FileWriter — durable consumer в trader (ack после flush); offset у брокера, не в PG.

    7. Runtime¶

    Критические потоки. Дедупликация: где — брокер (оппортунистически, окно W_dedup) + консьюмер (обязательно); алгоритм — Nats-Msg-Id из явных полей Binance (§8); дубликат в окне — PubAck duplicate:true без записи; вне окна/после рестарта NATS — доставляется повторно, консьюмер идемпотентен (книга — абсолютный qty + фильтр u, ring — dedup-сет по MsgId на окно реплея, иначе аддитивные агрегаты удвоятся); out-of-order внутри символа невозможен по построению (u монотонен; нарушение = дырка, см. ниже).

    sequenceDiagram
  participant B as Binance WS
  participant C as collector
  participant J as JetStream
  participant T as trader
  participant P as Postgres
  B->>C: depth diff / trade / kline(mark/liq)
  alt невалидный payload / неизвестный stream
    C->>C: WARN + dropped_invalid, без публикации (fail loud)
  else валидное событие
    C->>J: publish raw + Nats-Msg-Id
    J-->>C: PubAck (duplicate:true при повторе в окне)
    J->>T: live deliver
    T->>T: apply diff (u-check), feed ring, close bar
    T->>P: COMMIT checkpoint (blob + u + seq/trades_seq/events_seq)
    T->>J: ack (после COMMIT)
  end
  Note over T,P: booksnapshot 30-мин пишется мимо очереди (архив)
    sequenceDiagram
  participant J as JetStream
  participant T as trader (restart)
  participant P as Postgres
  T->>P: read checkpoint @ bar boundary + seqs
  alt checkpoint найден и retention покрывает
    T->>J: per-symbol replay MD_DIFF from seq+1, MD_TRADE from trades_seq+1, MD_EVENTS from MIN(events_seq)+1
    J->>T: backlog (AckNone, фильтр u > u_snapshot, dedup по MsgId)
    T->>T: Engine в replay (эмит подавлен) → догнал хвост → live
  else нет чекпойнта / PG пуст / retention превышен
    T->>T: холодный старт: REST /depth параллельно + сшивка U<=lastUpdateId+1<=u, первый бар неполный
  end
    sequenceDiagram
  participant C as collector
  participant J as JetStream (down)
  participant T as trader
  C->>C: buffer в RAM (неблокирующий publish)
  Note over C: NATS лёг — копим до T_repair, алерт задолго до 100%
  J-->>C: подъём
  alt буфер в капе
    C->>J: drain буфера (живой поток + backlog; задержка убывает постепенно)
    J->>T: доставка без потерь
  else переполнение (нереалистично при капе на час)
    C->>C: дроп со счётчиком + громкий алерт
    J->>T: дырка → бары неполные (§11)
  end

    State machine сущности bar + режима trader (подвешенных состояний нет — у каждого timeout/recovery):

    stateDiagram-v2
  [*] --> ColdStart: no checkpoint / retention exceeded
  [*] --> Replay: checkpoint found
  ColdStart --> Live: REST sewn, first bar incomplete
  Replay --> Live: lag < 1 slot на всех стримах
  Replay --> ColdStart: log протух / codec unknown
  Live --> Replay: restart (replay от границы бара)
  Live --> Degraded: gap (pu/U mismatch) / PG down / NATS down
  Degraded --> Live: поток возобновлён / PG up (откат на предыдущую границу при краше в окно)
  state Bar {
    [*] --> Incomplete: gap / cold start / missing slot
    Incomplete --> Complete: слот на каждую секунду бара
    Complete --> Closed: граница бара (checkpoint COMMIT)
    Closed --> [*]
  }

    Протокол старта трейдера (норматив, детали — 0001-book-store-schema.md §5):

    1. Читает PG: для каждого символа свой блоб на новейшую завершённую границу именно этого символа + u + seq/trades_seq/events_seq (одна строка (market,symbol,bar_ts)).
    2. Диффы per-symbol от seq+1, фильтр u > u_snapshot, параллельно.
    3. Сделки per-symbol от trades_seq+1, идемпотентность по MsgId обязательна.
    4. События одним консьюмером MD_EVENTS от MIN(events_seq)+1 по символам границы (каждый символ отбрасывает старше своего), идемпотентность обязательна.
    5. Engine в replay (эмит баров подавлен) — цель дойти до «сейчас», не пересчитать бары.
    6. Лаг < слота по всем стримам → live.
    7. Бар в стратегию — только полный (слот на каждую секунду бара).
    8. Paper: позиции с нуля; mainnet: позиции/баланс с биржи, далее userDataStream.
    9. Нет чекпойнта/ретеншн превышен → холодный старт (единственный REST /depth).
    10. Дырка при живом чекпойнте → без ресинка: остаёмся на книге, бары неполные, дальше реплей.

    8. Data¶

    Парадигма: лог как источник истины (JetStream) + регенерируемый чекпойнт (PG) + пересчитываемое производное (ring/позиции). Event Sourcing в строгом смысле нет: храним не все эволюции сущности, а сырьё + снапшот для O(окно), производное не храним вовсе (D4).

    Владельцы стейта: книга — trader (RAM) + чекпойнт в PG; позиции очереди — PG (атомарно с книгой, Transactional Inbox); offset writer'а — брокер (durable consumer); сырьё — JetStream (retention формулой ниже).

    Контракты на уровне инвариантов:

    • Payload 1:1 с Binance (JSON, не бинарь — цена принята, не связывающее ограничение). Своей схемы между сервисами нет.
    • Nats-Msg-Id — только явные поля Binance, без хешей; невалидный payload / неизвестный stream не публикуется (WARN + dropped_invalid++, fail loud):
    поток Nats-Msg-Id уникальность
    diff {market}:{symbol}:diff:{u} data.u per-symbol монотонен
    aggTrade {market}:{symbol}:a:{a} data.a
    raw trade {market}:{symbol}:t:{t} data.t (только при reconstruct_multilevel)
    kline {market}:{symbol}:k:{k.i}:{k.t} k.t+k.i; только k.x=true (тихая смена архива: незакрытые свечи больше не храним, метрики не страдают — downstream их отбрасывал)
    mark {market}:{symbol}:m:{E} data.E, 1/с/символ
    liq {market}:{symbol}:liq:{T}:{S}:{q}:{p}:{ap}:{l}:{z} композит: у Binance нет id, один o.T неуникален в пределах мс
    info/funding/stats {market}:{symbol}:{kind}:{bucket_or_time} snapshot_ms / fundingTime / 5-мин бакет
    • Ключ партиционирования/порядка: symbol (книги per-symbol независимы → параллельный реплей; skew невозможен по построению — символы равномощны по порядку величины).
    • Порядок внутри символа — по u (детект дырок), позиция в логе — по seq (u не offset; E Binance не монотонен по стриму — не offset; серверный timestamp записи монотонен и годился бы, но seq точнее).
    • Консистентность: per-symbol strong order (через u), глобально eventual (бары закрываются по settlement); read-your-writes не требуется.
    • Доставка: at-least-once + идемпотентные консьюмеры + DLQ отсутствует осознанно (инвалид дропается громко, старое ротируется — см. §11). Exactly-once не заявляется.

    Design Limits (формулы; точные числа — только measured или в спутнике):

    Parameter / Invariant Value / Formula Rationale Consequence of Violation
    Retention (MD_*, discard: old) >= штатный простой + худший простой + буфер drain Пережить рестарт/откат на предыдущую границу без холодного старта Холодный старт: REST-шторм + первый бар неполный + обрубок глубины
    retention: limits (не workqueue) инвариант ack writer'а не должен удалять диффы трейдера Тихая потеря реплея, видимая только на следующем рестарте
    Dedup window W_dedup >= max_retry + max_reconnect + clock_skew Покрыть ретраи и простой на деплое Дубль бизнес-операции при ретраях (для ring — удвоение объёма)
    Collector buffer buffer_bytes >= throughput_peak * T_repair, T_repair ~ 1ч (время починки человеком) Без буфера рестарт NATS теряет данные у источника Дырка в диффах → бары неполные (§11)
    Checkpoint cadence строго на границу бара; keep >= 2 границы Снапшот среди бара не восстанавливает начало бара (дифф необратим); две границы страхуют краш на записи Невосстановимые секунды бара / удвоенный реплей при краше на границе
    Checkpoint atomicity снапшот + все три seq в одной tx; ack после COMMIT Позиция обязана соответствовать состоянию (Transactional Inbox) Дырка реплея (seq вперёд) или лишняя работа (seq назад — безопасно)
    Book depth stored целиком, без среза Срез ломает бакеты 5%/25% непредсказуемо по символам Недостоверные книжные метрики (хуже, чем честная неполнота)
    Live поток vs чтение live_msg_s << replay_msg_s_per_proc (measured: ~26k/s с заголовками, §9) Живой контур обязан быть на порядок ниже потолка реплея Реплей не укладывается в RTO (см. неравенство §9)

    Формат блоба и SQL — 0001-book-store-schema.md (в этом доке только инварианты выше).

    9. NFR + Scale¶

    Нагрузочный профиль входа (пилот → цель; measured, см. measurements.md §2-6, 10-мин live-окна, активный рынок; min/max-период подписок — §3 того же файла):

    • Живой поток в очередь: ~500-600 msg/s @60 симв. при дефолтных подписках (240 diffs + 60 mark + ~240 trades), ~380 msg/s при max-периоде (@depth@500ms + голый @markPrice); ~3800-6000 msg/s @600 симв.
    • Дифф-байты: ~250-450 КБ/с @60 в обоих профилях (max-период режет msg/s, не байты: апдейт несёт больше изменений — замерено L8).
    • Суточный объём сырья: ~22-40 ГБ/сутки (measured, без booksnapshot). Архив — крупнейшая статья хранения: ~40-120 ГБ резидентно на 160 ГБ NVMe (существующее правило архиватора expired dt > 3d, services/archive.py:44)
    • ~8-15 ТБ/год в S3 до сжатия (estimate из измеренного суточного объёма; ratio zstd замерить в ветке №1). Планировать отдельно от очереди.
    • PG: 60 строк раз в 30 мин (600 при 600 симв.), ~10-20 МБ на границу (measured порядок: ~160-320 КБ/символ при 10-20k уровней), живой объём ×2. UPDATE-чурна нет.
    • RTO рестарта трейдера: <= 2 мин (бары 30-мин, пропуск недопустим). Худший случай (краш на границе) — ×2, расчёт ниже.
    • RTO-неравенство (проверяется трейдером на старте, предупреждение при нарушении). Определения: cores — число replay-процессов (GIL: шардирование процессами, не потоками); msgs — сообщений на символ за бар; cadence_s = book_tick_ms/1000; k_skew >= 1 — отношение самого тяжёлого шарда к среднему (замеры дают skew 9-10x между символами, speedup 2.6x вместо 4x на 4 процессах — делить на cores без k_skew нельзя). Формула — оценка снизу:
    ((1800 / cadence_s) * scalar_cost + msgs * (1/26000 + 17us)) * symbols * k_skew / cores <= RTO

    Подстановка (max-период @60: msgs = 11400, scalar = 1.30мс, cadence = 60с, k_skew = 2): скаляры 39мс + сообщения 632мс = ~0.7с/символ → 4 процесса ≈ 20с, ×2 откат ≈ 40с — в RTO 120с. @600/4 ≈ 200с, ×2 ≈ 400с — вне RTO: 600 символов только после доп. шардирования / варианта C.

    measured (детали — measurements.md §7, спутник §4): доставка ~26k msg/s/процесс с Nats-Msg-Id (~31k без заголовков, цена ~14%, перепроверено 2026-09: 26.9k/31.1k); применение диффа ~17 мкс; скаляры книги ~1.30 мс после NSC-51 (было ~5.31); публикация ~19-24k msg/s/процесс; веер консьюмеров ~1-3 мс/шт до 1200 (доставка полная); pending-overhead ~352 Б/сообщение без тел (полный бар max-период @60 ≈ 241 МБ, дефолт ≈ 342 МБ, ×2 откат — вывод D5 тот же). Живой контур при 600 парах — ~13% одного ядра. Точка обрыва по каденции — единицы секунд (~3 с после NSC-51); при каденции 60 с запас двадцатикратный, но реплей обязан шардироваться по процессам (GIL: 1 проц. ~14.6 с vs 4 проц. ~5.6 с на 432k сообщений — speedup 2.6x, не 4x, см. k_skew выше). - Latency SLO live: p95/p99 wall latency не нормируется (не load-bearing: бары 30-мин, корректность = полнота бара + lag < слота). SLO: bar_complete=1 (слот на каждую секунду, §7 п.7) и отставание реплея < 1 слота на всех стримах. - Измерение глубины (measured, один снапшот/символ, spot — порядок величины, повторить на USD-M): top-1000 дотягивается до −0.138%/+0.234% (BTCUSDT) и ±9.3% (ADAUSDT) при бакетах скаляров 5%/25% — REST-обрубок недостаточен, отсюда вес чекпойнта D5.

    Что ломается первым при ×5 — см. §11.

    10. Decisions¶

    D0. Разделить live-контур на collector и trader через durable лог¶

    • Status: accepted. Dependencies: нет.
    • Context: один процесс связывает частоту деплоя стратегий со стоимостью старта WS+стаканов (минуты на полном универсуме), теряет до 60 с буфера writer'а и весь ring при рестарте, не хранит диффы (книжная история невосстановима), а существующая in-process граница (полный стакан 1 Гц/символ, ~10-15 МБ/с @60) не переживает превращения в сеть.
    • Drivers: частота деплоя независимо от цены старта; durability рестарта потребителя; пересчитываемость книжной истории; не платить за 600 символов сейчас, но не закрывать путь.
    • Options:
    • A. Монолит + персистентность стейта (сериализация ring/стаканов). Cons: не чинит деплой-рвёт-WS и kill -9; версионируемый формат ~80 полей × 1800 слотов × N. Rejected.
    • B. Разделение через Redis Streams. Cons: retention в RAM (~14 ГБ на 26 ч vs ~9.5 свободных) → durability-граница схлопывается до минут. Rejected.
    • B'. RabbitMQ classic / stream queues. Classic: сообщение живёт до ack — реплей 26 ч невозможен структурно. Stream queues: семантика подходит, но самая молодая фича + сырой rstream. Rejected на зрелости.
    • B''. Свой файловый лог без брокера. Cons: становимся вендором очереди (torn-write, ротация, offset'ы); при разъезде всё равно менять. Rejected.
    • C. Три сервиса (collector → metrics → trader). Pros: мгновенный рестарт трейдера, шардирование метрик. Cons: ровно то разделение, что NSC-90 схлопнул; платить сейчас не за что. Deferred.
    • D'. Сшивающий ресинк вместо стирающего. Cons: фантомная ликвидность навсегда без способа отличить протухшие уровни. Rejected.
    • D (этот). Pros: развязывает деплой/старт, чинит классы потерь очередью, открывает пересчёт истории. Cons: +2 сервиса, диффы — горячая зависимость, RTO завязан на каденцию. Принят.
    • Decision: Мы делим контур на collector (край биржи, без бизнес-логики) и trader (книга, метрики, стратегии, архив) с NATS JetStream как границей durability (D2) и чекпойнтом книги в PG (D5).
    • Consequences: +деплой трейдера в день без разрыва WS; +пересчитываемая история; −сырьевой архив 22-40 ГБ/сутки (measured); −RTO зависит от каденции (§9); дверь к 600 символам открыта (per-symbol реплей, R3, RedPanda).
    • Re-evaluation Trigger: поток на порядок выше или RTO вне цели при всех рычагах §11 → вариант C / RedPanda.
    • Mitigation: буфер D9, чекпойнт D5, kill-сьют (спутник §2).
    • Verification: золотое свойство — прогон с убийством потребителя даёт те же бары, что непрерывный (приём parity-сьютов 38e0b72); критерии веток — спутник §2.

    D1. Коллектор — край биржи, без бизнес-логики¶

    • Status: accepted. Dependencies: D0.
    • Context: любая строка кода в процессе с WS делает его деплой дорогим. Коллектор должен меняться редко по построению.
    • Drivers: редкость деплоя коллектора; ноль причин держать у него состояние.
    • Options: (a) коллектор со стаканом/метриками — быстрее локальные скаляры, но любая новая метрика пересоздаёт стаканы — rejected; (b) коллектор делает ресинк/держит /depth — дублирует REST-бюджет и знание рынка — rejected; © этот: только WS+reconnect+поллеры, парсинг минимума под MsgId — принят.
    • Decision: Мы публикуем строки поллеров в очередь и не пишем на диск, не считаем метрик, не держим стакан, не ресинкаем (REST при дырке берёт трейдер напрямую, D3); непрерывность считает трейдер. Подписки — max-профиль C4; соединения — два по C5.
    • Consequences: +коллектор живёт неделями; −строки поллеров пишет только консьюмер очереди (D8).
    • Re-evaluation Trigger: поллеры упёрлись в IP-бюджет коллектора → вынести поллеры отдельно; Binance снова меняет роутинг → пересмотреть C5.
    • Mitigation: правило ревью — «исследовательский код не входит в коллектор».
    • Verification: деплой трейдера не рвёт WS-соединения коллектора (kill-сьют); оба соединения живы, каденции соответствуют C4 (depth 2/s, mark ⅓ с).

    D2. Брокер — NATS JetStream с file storage¶

    • Status: accepted. Dependencies: D0.
    • Context: нужен тупой durable лог с retention и replay с offset; KV/дедуп/consumer-API — бонусы, не требования (стейт и offset у нас вне брокера — D5, D8).
    • Drivers: дисковый retention на 16 ГБ VM; replay произвольного offset новым консьюмером; смена URL при разъезде; зрелость file-storage.
    • Options: Redis Streams (RAM-retention — rejected, см. D0); RabbitMQ (см. D0); свой лог (см. D0); RedPanda — проходит по семантике, но ~2 ГБ RAM из дефицитных под пропускную на порядки выше нашей — запасной путь масштабирования, контракт publish/subscribe не меняется.
    • Decision: Мы используем NATS JetStream с file storage и тремя стримами MD_DIFF/MD_TRADE/MD_EVENTS под retention: limits.
    • Consequences: +реплей от границы бара; −окно kill -9 задаётся sync_interval (серверный, не ноль); −dedup-таблица в RAM (оппортунистична).
    • Re-evaluation Trigger: десятки тысяч msg/s → RedPanda без смены контракта.
    • Mitigation: идемпотентные консьюмеры (D7) как гарантия поверх оппортунистического дедупа; sync_interval верифицируется kill-тестом ветки №1.
    • Verification: перечитывание заакнутой истории новым консьюмером 500/500 под limits (0/500 под workqueue — инвариант в тестах создания стримов); kill -9 NATS измеряет фактическое окно.

    D3. Стакан живёт только в трейдере; сырые диффы — через очередь¶

    • Status: accepted. Dependencies: D0, D2.
    • Context: казалось, коллектору нужен стакан для детекта дырок/бутстрапа/истории; проверка показала — ни одна роль его не требует, а публикация полного стакана 1 Гц/символ не переживает сеть (~2 МБ/с @60, ~180 ГБ/сутки — measured: 1000+1000 уровней ≈ 28 КБ JSON, measurements.md §1/§5) и уже помечена TODO(NSC-51).
    • Drivers: пропускная способность очереди; пересчитываемость истории (G3); минимум знания рынка в коллекторе.
    • Options: (a) стакан в коллекторе + снапшоты 1 Гц — rejected по объёму; (b) скаляры в коллекторе — rejected (новая метрика = пересоздание стаканов, против D1); © этот: сырые диффы, трейдер собирает книгу, сам ходит REST только на холодном старте без PG.
    • Decision: Мы публикуем сырые диффы; трейдер держит единственный OrderBook, ведёт непрерывность, пишет 30-мин booksnapshot как архив (живой контур его не читает).
    • Consequences: +история пересчитываема; +TODO(NSC-51) закрыт удалением цикла; −диффы — горячая зависимость; −IP-бюджет /fapi/ у коллектора, трейдер ходит в REST только холодным стартом (60 симв. = 1200 weight; 600 = 12000 = минимум 6 минут в лимитер + стаггер + стыкующий фрейм).
    • Re-evaluation Trigger: дифф-поток на порядок выше → сжатие/бинарный кодек (контракт меняется с простоем).
    • Mitigation: чекпойнт D5 + буфер D9 + репликация (§11) против потери диффа; при дырке с живым чекпойнтом — без ресинка (REST даёт обрубок), остаёмся на книге.
    • Verification: kill коллектора → дырка задетектирована (U/pu), бары неполные, глубина не потеряна; каденция скаляров — event-time, live и реплей одним путём (детали — спутник §7).

    D4. Производный стейт не хранится, а пересчитывается реплеем от границы бара¶

    • Status: accepted. Dependencies: D0, D5.
    • Context: ring — чистая функция последних 1800 с событий; paper-позиции — чистая функция баров (backtest на живом потоке). Хранить их — версионируемый формат ради секунд пересчёта.
    • Drivers: отсутствие формата сериализации; детерминизм пересчёта.
    • Options: (a) продолжение с последнего ack — после короткого рестарта даёт пустой ring + ожидание целого бара живого потока (тихий отказ восстановления) — rejected; (b) сериализация ring/позиций — rejected (дорого ради частичного результата, не чинит kill -9); © этот: реплей от границы текущего бара по трём позициям — принят.
    • Decision: Мы храним только чекпойнт книги (D5); ring, paper-позиции/equity, LiqDeque, дельта-счётчики пересчитываются реплеем; окно — от границы бара, три стрима — три позиции.
    • Consequences: +нет форматов; −RTO обязан покрывать реплей (неравенство §9, шардирование по процессам обязательно — per-symbol веер дёшев: 0.7-2.6 мс/консьюмер до 1200, измерено дважды).
    • Re-evaluation Trigger: реплей бара не укладывается в RTO при целевой каденции → чекпойнт слотов кольца (§11) или вариант C.
    • Mitigation: трейдер проверяет RTO-неравенство на старте и предупреждает; каденция — явный ключ конфига.
    • Verification: kill на 5 секунд среди бара → кольцо полное, бар (включая ob-часть) равен эталону; длинный рестарт один не проверяет (маскирует неверную стартовую позицию).

    D5. Чекпойнт книги — блобом на границу бара + три позиции, одной транзакцией¶

    • Status: accepted (переработан 2026-09-02: блоб на границу вместо зеркала; 2026-09-03: MD_TRADE отдельно). Dependencies: D0, D4.
    • Context: снапшот «среди бара» не восстанавливает его начало (дифф необратим: qty перезаписывается); зеркало с любым лагом задачу не решает — дело в направлении, не в свежести.
    • Drivers: восстановимость любого бара из реальных диффов; транзакционность позиции+состояния; дешёвая запись/чтение.
    • Options: (a) зеркало текущего состояния — rejected (не восстанавливает начало бара); (b) строки уровней (market,symbol,side,price,qty) — 0.6-1.2 млн строк/границу @60 vs 60 строк блобом, COPY в партицию, UPDATE-чурн — rejected; © durable без ack до границы вместо хранения seq — держать бар un-acked стоит ~0.35-1 КБ/сообщение (955 Б в оригинале, ~352 Б в перезамере 2026-09: 152 МБ @60 / ~1.5 ГБ @600) + ack_wait выше длины бара — rejected; (d) без позиций вовсе (opt_start_time + фильтр u) — рабочий fallback, не выбран (менее точен); (e) этот: блоб целиком + u + seq/trades_seq/events_seq, две границы, COMMIT затем ack — принят.
    • Decision: Мы пишем раз в бар на границе: вся книга одним блобом без среза + u + три seq, одной транзакцией на символ; храним две последние границы.
    • Consequences: +PG-нагрузка — десятки МБ, без autovacuum-чурна; +глубина не теряется при дырке (остаёмся на книге, бары неполные); −PG — несущая конструкция (без него — холодный старт с обрубком).
    • Re-evaluation Trigger: размер блоба/время чтения мешает → срез по mid ~50% (D6) или слоты кольца (§11).
    • Mitigation: краш на границе → откат на предыдущую (реплей 30-60 мин, RTO ×2, в цели); новый листинг среди бара → холодный старт одного символа, первый бар неполный; codec неизвестен → чекпойнт выбрасывается, старт холодный (миграций блоба нет никогда).
    • Verification: round-trip блоб+позиции → реплей равен непрерывной книге включая слот первой секунды; краш на границе → бар полон с предыдущей границы.

    D6. Книга хранится целиком; рост принят¶

    • Status: accepted. Dependencies: D5.
    • Context: уровни копятся сутками (десятки тысяч/символ); любой top-N срез по счёту даёт разное покрытие по символам (BTCUSDT 0.15% vs ADAUSDT 9.3% на top-1000).
    • Drivers: корректность бакетов 5%/25% для всех символов одинаково.
    • Options: (a) срез top-N — rejected (символозависим); (b) срез по mid ~50% (двойной запас над 25%) — отложен как рычаг с измеренным триггером; © этот: целиком, рост мониторим — принят (при блобе и двух границах объём ограничен сверху).
    • Decision: Мы не срезаем книгу при записи чекпойнта.
    • Consequences: +корректность; −мониторить размер блоба/символ.
    • Re-evaluation Trigger: размер/время чтения мешает → срез по расстоянию от mid (~50%), протокол не трогает.
    • Mitigation: сжатие блоба (zstd, книга из монотонных цен жмётся); формат — спутник схемы.
    • Verification: бакеты 5%/25% после рестарта равны эталону, а не обрубку.

    D7. Сырой payload 1:1; Nats-Msg-Id из явных полей, без хешей¶

    • Status: accepted. Dependencies: D0, D2.
    • Context: собственная схема между сервисами = версионирование и интерпретация вместо сырья в архиве.
    • Drivers: отсутствие нашей схемы; нулевая сериализация в коллекторе; архив = настоящее сырьё.
    • Options: (a) нормализованная схема/msgpack/protobuf — компактнее, но версионирование + стоимость — rejected (объём не связывающее ограничение); (b) хеш-фолбэк при отсутствии полей — прячет ошибки — rejected (fail loud); © этот — принят.
    • Decision: Мы публикуем байты Binance как есть; коллектор извлекает только поля для Nats-Msg-Id (таблица §8); невалид/неизвестный stream не публикуется (WARN + метрика dropped_invalid).
    • Consequences: +схема принадлежит Binance; −JSON объёмнее бинаря (принято); −тихая смена архива: только closed klines (незакрытые downstream отбрасывал, метрики целы, история меняется — следствие уровня «что публикуем», не детали MsgId).
    • Re-evaluation Trigger: объём очереди/архива стал связывающим → бинарный кодек с миграционным окном.
    • Mitigation: идемпотентность консьюмера по тем же явным ключам обязательна (at-least-once).
    • Verification: повторная доставка MsgId не меняет бар (серверный дедуп + идемпотентность); forceOrder-композит проверен 7-дневной выборкой до ветки №1 (блокер).

    D8. Parquet пишет трейдер как durable consumer¶

    • Status: accepted. Dependencies: D0, D2.
    • Context: 60-секундный RAM-буфер writer'а — класс A (невосстановимая потеря) посреди системы «очередь как durability-граница».
    • Drivers: durability бэкапа и downstream-инварианта «рестарт не теряет события».
    • Options: (a) writer в коллекторе — баги parquet рестартуют WS — rejected (против D1); (b) третий сервис sink — тот же консьюмер, плюс контейнер, ноль выигрыша — rejected; © этот — принят.
    • Decision: Мы переносим FileWriter в трейдер как durable consumer всех md.* с явным AckExplicit после flush; offset у брокера; ack_wait формулой > max_hold; booksnapshot — мимо очереди напрямую.
    • Consequences: +класс A исчезает (рестарт дочитывает с ack); −дисковый I/O parquet в частично деплоящемся сервисе (потерь нет — очередь держит не-ack'нутое, цена ресурсная).
    • Re-evaluation Trigger: I/O writer'а мешает трейдеру → вынести writer в свой процесс (тот же консьюмер, другой контейнер).
    • Mitigation: редоставка до ack — дубли, дедуп по MsgId в буфере writer'а.
    • Verification: kill до flush → после рестарта parquet без дыр (offset с последнего ack).

    D9. Буфер коллектора — RAM на окно починки, с байтовым капом¶

    • Status: accepted. Dependencies: D2.
    • Context: без буфера любой рестарт NATS теряет данные у источника — чиним рестарт потребителя и ломаем рестарт брокера.
    • Drivers: пережить починку брокера/сети человеком без потери непрерывности; не заводить второй durability-механизм.
    • Options: (a) без буфера — rejected; (b) дисковый WAL — второй формат со своими багами рядом с JetStream; коллектор падает редко — отложен как рычаг; © этот: RAM, неблокирующий publish, кап формулой, переполнение — нереалистичный сценарий — принят.
    • Decision: Мы держим между WS-ридером и publish буфер в памяти на T_repair (≈ час), кап в байтах по замеру ветки №1; заполнение — метрика первого класса с ранним алертом.
    • Consequences: +рес тарт брокера переживается; −падение коллектора с непустым буфером теряет RAM (осознанная цена, редкий случай); −слив полного буфера долог (~22 мин @600 пар при 22k publish vs 6k live — задержка убывает постепенно, подъём ≠ мгновенная норма).
    • Re-evaluation Trigger: кап покрывает заметно меньше часа / разъезд по хостам / падения чаще раза в месяц → дисковый WAL (§11).
    • Mitigation: NATS рядом с коллектором (loopback), пока один VM — при разъезде размер пересмотреть.
    • Verification: NATS выключен N минут (< капа) → после подъёма бары равны эталону.

    D10. Позиции локально не хранятся¶

    • Status: accepted. Dependencies: D4.
    • Context: локальная копия позиций на живых деньгах — единственный способ разойтись с реальностью.
    • Drivers: невозможность расхождения с биржей по построению; детерминизм paper.
    • Options: (a) durable локальные позиции — расхождение с биржей возможно — rejected для mainnet; (b) этот: mainnet/testnet — биржа (positionRisk на старте + сверка userDataStream), paper — реплей с нуля — принят.
    • Decision: Мы не храним позиции/equity локально; paper стартует с нуля (упрощение, класс D), mainnet сверяется с биржей; live_state.json остаётся фидом дашборда (PG не участвует); day_start_equity: paper — скаляр с нуля, mainnet — фиксация баланса на 00:00 UTC.
    • Consequences: +неконсистентность невозможна; −paper-рестарт теряет позиции (не баг, класс D).
    • Re-evaluation Trigger: потеря paper-состояния мешает (длиннее минут) → крошечная закладка на границу бара (§11).
    • Mitigation: флаг полноты бара не зависит от позиций; mainnet-сверка — Phase 4 роадмапа.
    • Verification: рестарт в paper не сравнивает позиции; в mainnet — сверка с биржей.

    11. Risks + Failure Modes¶

    Классы: A невосстановим / B с биржи / C из персистентных данных / D потеря приемлема. Деградация — явная и поименованная; невалид — fail loud (AGENTS.md). Ретраев с константами нет — политика формулой: retry while bar_window_open, backoff <= retention_window, иначе пометить бар неполным. DLQ отсутствует осознанно: инвалид — в dropped_invalid (не DLQ), старое — ротируется (discard: old), неполнота — флагом бара, а не очередью.

    Событие Класс Поведение
    Дырка в диффах (U/pu) C Без ресинка: остаёмся на книге от чекпойнта, бары неполные, дальше реплей. Глубина не теряется; REST не ходим (дорого + обрубок). Fail-closed по полноте бара
    Дырка в трейдах (agg_id) C Только наблюдение: счётчик agg_id_gaps + WARNING с дельтой (образец — record_trade в health.py), живой контур не останавливается, авто-backfill нет. Бар помечается через существующий bar_complete
    Дырка в событиях (staleness mark/kline) C Только наблюдение: staleness-check (now - last > 2x каденции: mark ⅓с, kline closed 1/мин) + счётчик + WARNING, без действий. Редкие liq/info/funding не проверяются
    Отставший консьюмер C JetStream копит pending — потерь нет. Наблюдаемый lag вместо дропа
    Диск под очередь кончился D discard: old: теряем старьё, поток жив. discard: new остановил бы коллектор — хуже
    Коллектор лёг B Окно не получил никто. Trade/kline — backfill из REST-history; книга — RAM трейдера; бары неполные. Лечение — репликация (§11.1)
    Трейдер лёг C, fallback B §7: чекпойнт + реплей; RTO ~секунды-десятки секунд @60 (см. §9); краш на границе → предыдущая граница (RTO ×2); дольше retention / PG пуст → холодный старт, первый бар неполный
    NATS лёг C, overflow D Буфер D9 (~час); дольше — дроп со счётчиком и алертом → как дырка. Слив полного буфера ~22 мин — заложить в алерты
    Буфер переполнился D Нереалистично при капе на час (A1); алерт задолго до 100%; иначе дроп + громкий алерт
    PG лёг C, fallback B Трейдер жив из RAM; запись чекпойнта фейлится громко; краш в окне → откат на предыдущую границу; обе пусты → холодный старт. Чекпойнт регенерируем — деградация, не отказ
    Коллектор упал с непустым буфером D → B RAM теряется целиком (осознанная цена D9) → как «коллектор лёг»

    Что ломается первым при ×5 нагрузки: живой поток остаётся запасом (600 пар ~6k msg/s vs 26k/процесс), первым упирается реплей в RTO (CPU-bound питоновского клиента + скаляры) — лечится шардированием по процессам, затем вариант C; вторым — диск очереди/архива (22-40 ГБ/сутки ×5 = 110-200 ГБ/сутки; @600 символов — 220-400 ГБ/сутки) и слив буфера; третьим — память трейдера на 600 книг (замерить в ветке №2, не верить оценке RUNBOOK).

    12. Observability¶

    Каждый инвариант виден метрикой; трейсинг — через очереди:

    • Очередь: pending per-consumer, ack_lag, dedup_collision_rate (повторы MsgId в окне), retention_age_vs_checkpoint (возраст oldest vs самый старый чекпойнт — раннее предупреждение холодного старта).
    • Буфер коллектора: buffer_fill_ratio + алерт задолго до 100%; dropped_invalid + причина; publish_rate vs live_rate при drain.
    • Книга/реплей: replay_lag_slots, seq_gaps, resync_count, book_updates_count, book_age_ms, blob_bytes_per_symbol, checkpoint_age, bar_complete (флаг полноты — слот на каждую секунду).
    • Трейды/события (только наблюдение, без действий): agg_id_gaps (разрывы монотонного agg_id per-symbol — образец HealthCounters.record_trade), events_staleness (mark/kline старше 2x каденции). Реализация — health.py в ветках №2 (коллектор) и №3 (трейдер, replay-путь).
    • RTO: длительность реплея vs неравенство §9; нарушение — предупреждение на старте + метрика.
    • Writer: flush_lag, unacked_batch_age (< ack_wait с запасом).
    • Propagation через очереди — Nats-Msg-Id как idempotency/trace key (таблица §8); полный OTel trace_id/span_id не вводится (deferred: триггер — инцидент, не диагностируемый счётчиками + bar_complete). Дубли возникают не от Binance, а от нашего дизайна (реплей D5 и writer D8 по построению перечитывают обработанное); идемпотентность консьюмеров сохраняется.

    13. Security¶

    • Trust boundaries — §5 (граница internal/untrusted на C4-L2). Internal заканчивается на loopback одного VM; всё внешнее (Binance, S3, браузер) — untrusted.
    • Auth/authz: внутри VM аутентификация NATS/PG не включается осознанно (нет слушателей наружу, loopback; dashboard — read-only монтирование + пароль DASH_PASS). Триггер: разъезд по хостам → NATS creds + PG SCRAM + TLS transit, dashboard за Caddy auth.
    • Encryption: transit внутри VM — plaintext loopback (триггер выше — TLS); at-rest — диск VM (NVMe) без полевого шифрования; S3-архив — SSE бакета. Полевого шифрования уровней книги нет (маркет-дата, не секрет).
    • Secrets: только env (BINANCE_API_KEY/SECRET, creds дашборда/архиватора); никогда в live_config.yaml и коде; права 600, владелец trader (RUNBOOK step 2).
    • Audit log: append-only для живых денег — fills/blotter трейдера + live_state.json как фид; чекпойнт PG — не audit (регенерируем, перетирается).
    • PII/GDPR: неприменимо — в контуре только маркет-дата и derived метрики; masking/tokenization не требуются. При появлении user-identifying данных — пересмотр этого раздела.
