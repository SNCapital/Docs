    ADR-0001 — схема Postgres book store (D5)¶

    Вынесено из ADR. Детали реализации чекпойнта книги. Актуально на ветках feat/*. Инварианты — в ADR §8 (Data); здесь только формат, SQL и протокол. Нумерация ADR — по RULES I.1 (§7 Runtime, §8 Data, §9 NFR, §11 Risks); D-идентификаторы стабильны.

    1. Идея¶

    Трейдер хранит в PG чекпойнт книги на границу завершённого 30-минутного бара — регенерируемый, не источник истины. Источник истины — очередь (NATS JetStream) плюс реплей от этой границы.

    Почему именно на границу бара, а не «последнее состояние с отставанием ≤60с»: книжные скаляры штампуются в слоты кольца посекундно, а реплей идёт только вперёд. Из снапшота на 12:19 секунды 12:00–12:19 не пересобрать — чтобы получить книгу на 12:00:01, нужна книга на 12:00:00, а назад из более свежего состояния не уехать: дифф Binance перезаписывает qty на уровне, обратной операции нет. Снапшот на границе делает весь бар восстановимым из реальных диффов по построению.

    Паттерн — Transactional Inbox: снапшот и позиции очереди коммитятся атомарно, ack в JetStream — после COMMIT. Крэш между ними даёт дубли, они безопасны: применение диффа идемпотентно (qty абсолютный) плюс фильтр u > u_snapshot.

    2. Таблицы¶

    Две границы бара хранятся одновременно — текущая и предыдущая; старее удаляются. Это страховка на случай краша ровно в момент записи новой: откатываемся на предыдущую и реплеим 30-60 минут вместо 30.

    -- Одна таблица: ключ (market, symbol, bar_ts) везде. Три позиции стримов —
-- колонки одной строки символа, пишутся одной транзакцией (Transactional Inbox, D5).
CREATE TABLE book_checkpoint (
    market      TEXT   NOT NULL,          -- 'spot' | 'usdm'
    symbol      TEXT   NOT NULL,          -- 'BTCUSDT' (upper)
    bar_ts      BIGINT NOT NULL,          -- граница бара, ms UTC (кратна window_ms)
    u           BIGINT NOT NULL,          -- last_update_id книги на момент снапшота
    seq         BIGINT NOT NULL,          -- позиция в MD_DIFF на тот же момент
    trades_seq  BIGINT NOT NULL,          -- позиция в MD_TRADE на тот же момент
    events_seq  BIGINT NOT NULL,          -- позиция в MD_EVENTS на тот же момент
    codec       TEXT   NOT NULL,          -- формат блоба, см. §3
    book        BYTEA  NOT NULL,          -- вся книга целиком, без среза по глубине
    written_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (market, symbol, bar_ts)
);

    Почему блоб, а не строка на уровень. При записи раз в бар «дельта-записи» не работают: за полчаса грязной становится примерно половина книги, пишем всё равно целиком. А раз целиком — разница на порядок-два:

    строки (market,symbol,side,price,qty) блоб
    на границу, 60 симв. 0.6-1.2 млн строк, 60-120 МБ 60 строк, 10-20 МБ
    запись COPY в свежую партицию; INSERT ON CONFLICT не тянет тривиальна
    чтение при старте 0.6-1.2 млн строк 60 строк
    600 символов 6-12 млн строк, 0.6-1.2 ГБ 100-200 МБ
    SELECT ... WHERE price BETWEEN есть нет

    Запросимость по уровням теряется, и это осознанно: чекпойнт держит две последние границы и постоянно перетирается — для исследования это архив (parquet type=booksnapshot), а не живой стейт. Заодно исчезает UPDATE-чурн: тюнинг autovacuum перестаёт быть операционной задачей, потому что таблицы уровней больше нет.

    Почему bar_ts в ключе, а не одна строка на символ. Две границы должны сосуществовать, и новая пишется, пока старая ещё валидна. Удаление старых — отдельным DELETE ... WHERE market = :m AND symbol = :s AND bar_ts < :keep_from после успешного коммита новой.

    3. Формат блоба¶

    codec — версия формата, обязательна: блоб живёт полчаса и полностью регенерируем, поэтому миграций не пишем никогда. Правило простое: codec не распознан → чекпойнт выбрасывается, символ стартует холодно. Цена несовпадения версий — один неполный бар.

    Базовый формат v1:

    uint32  n_bids
uint32  n_asks
float64 bid_price[n_bids], float64 bid_qty[n_bids]   # по убыванию цены
float64 ask_price[n_asks], float64 ask_qty[n_asks]   # по возрастанию цены

    Порядок уже отсортирован — при чтении SortedDict строится без пересортировки. Сжатие (zstd) — по измерению ветки №3; книга из монотонных цен жмётся хорошо.

    4. Запись — раз в бар, на границе¶

    На границе бара, для каждого символа:

    BEGIN;
INSERT INTO book_checkpoint (market, symbol, bar_ts, u, seq, trades_seq, events_seq, codec, book)
VALUES ($1, $2, $3, $4, $5, $6, $7, 'v1', $8);
COMMIT;
-- ack: live-подписка трейдера акает непрерывно по ходу обработки (позиция реплея
-- всё равно из PG, не из ack); FileWriter (D8) акает после flush; сам реплей идёт
-- с AckNone — там ack'ать нечего. Держать сообщения un-acked до границы запрещено
-- (отвергнутый вариант D5-(c): цена удержания бара + ack_wait длиннее бара).
-- затем: DELETE FROM book_checkpoint WHERE market = $1 AND symbol = $2 AND bar_ts < :предыдущая_граница

    Точность seq. Записывается sequence последнего сообщения, эффект которого попал в этот снапшот — не «на момент начала транзакции». Снимок книги и seq берутся атомарно в процессе (книга и счётчик живут в одном asyncio-loop, диффы между ними не проскакивают). Ошибка в сторону меньшего seq безопасна — лишние диффы переприменятся идемпотентно; ошибка в сторону большего пропустит диффы, и это уже потеря.

    synchronous_commit = true → fsync на каждом коммите, окно kill -9 минимально; false — быстрее, окно шире (тьюнинг через live_config.yaml).

    Нагрузка. 60 строк раз в 30 минут (600 при 600 символах), ~10-20 МБ на границу, живой объём — вдвое больше (две границы). Никакого UPDATE-чурна.

    Чего уборка НЕ делает (отложено осознанно). DELETE ... WHERE market = :m AND symbol = :s AND bar_ts < :предыдущая_граница чистит прошлые границы только у символов, которые продолжают торговаться: он привязан к записи новой границы, а у делистнутого символа новой границы не будет никогда. Его последний чекпойнт остаётся в таблице навсегда — мёртвые ~160-320 КБ на символ.

    На пилоте это неважно: универсум меняется единицами символов в месяц, и даже сотня мёртвых записей — десятки мегабайт. Но по-хорошему нужна чистка по универсуму: при старте (или раз в сутки) удалять book_checkpoint для символов, которых нет в текущем symbols из live_config.yaml. Делать её надо аккуратно — символ может временно выпасть из конфига и вернуться, поэтому безопаснее удалять по возрасту (written_at старше нескольких суток) и логировать что именно удалено, а не молча вычищать по разнице множеств. Триггер возврата — §11 ADR.

    5. Чтение — протокол старта трейдера (§7 ADR)¶

    1. читает PG: для каждого символа — свой блок книги на границу последнего завершённого
   бара + (u, seq, trades_seq, events_seq). Новейшая завершённая граница выбирается
   per-symbol: часть символов может быть на границе N, часть (краш между коммитами)
   на N-1; символ без строки стартует холодно и остальных не блокирует
2. диффы: per-symbol консьюмеры md.{market}.diff.{symbol}, opt_start_seq = seq+1,
   параллельно → отбрасывает u <= u_snapshot, применяет остальные
3. сделки: per-symbol консьюмеры md.{market}.trade.{symbol}, opt_start_seq = trades_seq+1,
   параллельно → идемпотентность по Nats-Msg-Id обязательна (ring аддитивен)
4. события: один консьюмер на MD_EVENTS от MIN(events_seq)+1 по символам границы
   (позиций 60, консьюмер один — стартуем от самой старой, иначе пропуск);
   каждый символ отбрасывает события старше своего events_seq;
   → kline/mark/liq поля + LiqDeque; идемпотентность по Nats-Msg-Id обязательна
5. Engine в режиме реплея: эмит баров подавлен
6. догнали хвост по всем трём стримам → переключение в live
7. бар в стратегию, только если есть слот на каждую секунду бара
8. codec не распознан / нет чекпойнта / PG пуст / ретеншн MD_DIFF/MD_TRADE превышен
   → холодный старт: REST /depth, первый бар неполный
9. дырка (spot U != last_u+1, USD-M pu != last_u) при живом чекпойнте
   → остаёмся на текущей книге, бары за окно неполные, ресинка нет

    Per-symbol независимость: каждый символ восстанавливается своим блобом и своим u, один битый символ не блокирует остальные.

    Почему частичная граница возможна и почему это нормально. 60 символов чекаются 60 независимыми транзакциями на каждой 30-минутной границе. Крэш между коммитами (kill -9, ребут, OOM) оставляет часть символов на новой границе N, часть — на предыдущей N-1. Это штатный исход, а не исключение: каждый символ реплеит от своей границы (п.1), отставшие догоняют лишней работой (дубли идемпотентны), пропусков нет. Максимальная длина реплея — ~60 минут (символ с N-1 + долгое лежание), это цена RTO x2 из D5, а не потеря данных. Хранимых границ всегда максимум две (keep >= 2, §2): символ без строки ни на одной из них стартует холодно.

    Почему MD_EVENTS — один консьюмер от глобального MIN(events_seq). DIFF и TRADE реплеятся per-symbol, каждый от своей позиции, лишнего не читают (пп.2-3). EVENTS делят один консьюмер на всех (объем мал, ~10-50 msg/s, делить на 60 нечем), поэтому стартует от самой старой позиции — иначе символы со старым events_seq получат пропуск. Внутри одной границы указатели рядом (символы чекаются параллельно за секунды), лишнего почти нет. При расщеплении N/N-1 символы новой границы перечитают до ~30 минут чужих EVENTS — это 18-90k сообщений, 1-4 секунды реплея, допустимо: дубли отбрасываются по events_seq символа + Nats-Msg-Id. Отдельный консьюмер на группу границы не заводится осознанно (два эфемерных консьюмера ради секунд экономии при краше раз в месяц — лишний механизм).

    Writer (D8) использует отдельный durable consumer, его offset хранит брокер — в PG его нет: у writer'а семантика «продолжить с последнего ack», а не «с границы бара».

    6. Что в PG НЕ хранится¶

    Всё производное восстанавливается реплеем — это D4, и здесь он выполним:

    откуда берётся
    55 тиковых полей слота: трейды реплей MD_TRADE от trades_seq (per-symbol, параллельно)
    55 тиковых полей слота: клайны/mark/ликвидации/funding реплей MD_EVENTS от events_seq
    25 книжных полей слота блоб + реплей MD_DIFF от seq, скаляры пересчитываются
    LiqDeque (ob__liq_shock_*) forceOrder приходят в MD_EVENTS
    book_updates_count / seq_gaps / resync_count это дельты с прошлой выборки, а не тотал'ы (metrics_engine/book_replay.py:77) — переаккумулируются из реплеенных диффов
    _next_bar, _cur_bucket выводятся из выравнивания бара
    _cur — незакрытый слот <1 с, добирается хвостом реплея
    кольцо целиком результат всего вышеперечисленного
    paper-позиции, equity не durable (D10)

    7. Связанные решения¶

    • D4 — окно реплея от границы бара, а не от места остановки; три стрима — три позиции.
    • D6 — книга целиком, без среза; рост принят, рычаг отложен.
    • D8 — FileWriter как durable consumer, offset у брокера.
    • §11 ADR — отложенные рычаги и триггеры возврата.
    • §9 ADR + measurements.md §6-7 — измеренная стоимость реплея и ограничение по каденции книжных скаляров.
