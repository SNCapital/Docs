    Аудит фолбэков — где fallback уместен, где нужен fail-fast¶

    Дата: 2026-08-07. Ветка: feat/go-to-python-metrics-engine. Скан всех точек перехвата ошибок и fallback-цепочек в Python-коде (72 except + 38 fallback-упоминаний), разбор по трём зонам: live-трейдинг (alpha_engine/live/), метрики/бэктест (alpha_engine/metrics*, pipeline, portfolio, backtest), сборщик данных (binance_parser/).

    Критерии классификации¶

    Fallback уместен Нужен fail-fast
    Граница внешнего мира (сеть): bounded-ретрай + явный скип с логом Тихий фолбэк портит торговое состояние или данные
    Legacy-совместимость при чтении старых данных Широкий except Exception маскирует код-баги
    Пересоздаваемые артефакты (кэш, preload) Глушится единственный сигнал (диагностика/алерты)
    Self-heal через «венчурную правду» (reconcile) Потеря события/батча без следа и без компенсации

    Правило принятия решения: сеть → bounded-ретрай + явный скип с логом; парс на границе → узкие исключения + счётчик дропов; внутренний код → никогда Exception, re-raise; parquet/состояние → никогда тихо (ретрай или crash); торговое состояние → fail-closed.

    Часть 1. Нужен fail-fast¶

    Приоритет 1 — торговый риск / потеря данных¶

    1. alpha_engine/live/binance_futures.py:635 — глухой pass в maker-фолбэке¶

    Что ловится: повторный Exception от query_order в post-only логике (после cancel-гонки). Что происходит: pass — state остаётся устаревшим, executedQty может быть 0 при реальном partial-fill. Негативные последствия: remaining = qty вычисляется из устаревшего state → выставляется полный market-фолбэк поверх уже исполненной части → дублирование экспозиции на венче. Blotter потом починит reconcile, но лишний ордер уже стоит (реальный риск двойной позиции). Что нужно: как минимум logger.error + отказ от market-фолбэка при неопределённом статусе (fail-closed), либо re-query до исчерпания бюджета попыток с жёстким fallback на cancel-всего.

    2. alpha_engine/live/binance_futures.py:484 — битый positionAmt в reconcile¶

    Что ловится: (TypeError, ValueError) на строке позиции при float(positionAmt). Что происходит: continue — строка выпадает из реконсиляции без лога. Негативные последствия: позиция «исчезает» из blotter → blotter считает её нулевой → ребаланс повторно открывает уже открытую позицию на венче (двойной размер). Битый positionAmt — редкий, но дорогой сбой. Что нужно: warning с полной строкой + не выкидывать позицию молча: при битой строке — либо перезапросить аккаунт, либо пометить символ как «не реконсилируемый» и остановить по нему торговлю (fail-closed).

    3. binance_parser/live/writer.py:113 — безвозвратная потеря батча parquet¶

    Что ловится: Exception вокруг _write_parquet при флаше партиции. Что происходит: print + продолжение — но буфер уже очищен (snapshot взят раньше). Негативные последствия: батч записей теряется безвозвратно — дыра в parquet-данных без ретрая и без повторной постановки в очередь. Для сбора данных это тихая порча истории (бэктест на этих данных получит молчаливые пропуски). Что нужно: ретрай флаша, при неудаче — вернуть батч в очередь; при повторной неудаче — ронять процесс (данные первичны). Это единственный путь в парсере, где тихий фолбэк = потеря данных.

    4. alpha_engine/pipeline.py:488 — заглушён единственный unattended-сигнал¶

    Что ловится: Exception при подсчёте headline-цифр (summary PnL). Что происходит: logger.info — финальные цифры не печатаются, run продолжается. Негативные последствия: в unattended-запуске это единственный видимый итог прогона. Если у pnl нет ожидаемых колонок (реальная ошибка PnL-математики) — прогон «успешно» завершается без результата, ошибка остаётся незамеченной. Что нужно: logger.error с traceback + ненулевой exit code, либо re-raise.

    Приоритет 2 — маскирование код-багов (сузить except)¶

    5. binance_parser/live/ws_client.py:218 — код-баги неразличимы с сетевыми обрывами¶

    Что ловится: Exception вокруг всей WS-петли connect/receive. Что происходит: любой сбой трактуется как сетевой обрыв → consecutive_failures += 1, backoff, reconnect; эскалация только после 30 попыток (~30 мин). Негативные последствия: баг в обработчике кадра (например, в writer.write) маскируется бесконечным reconnect-циклом: тихие пропуски данных, потерянная наблюдаемость. Ровно этот класс багов уже давал «тихий бесконечный reconnect» в истории проекта. Что нужно: ловить только websockets/aiohttp-классы исключений (ConnectionClosed, ClientError, TimeoutError); всё прочее — re-raise (процесс падает с traceback). Оставить backoff/эскалацию только для сетевых.

    6. binance_parser/live/market_stats_poller.py:258 — Exception на r.json()¶

    Что ловится: Exception вокруг парсинга JSON ответа. Что происходит: log.warning + return None — цикл символа пропущен. Негативные последствия: вместе с транзиентными ошибками JSON маскируются и баги (json() падает на невалидном контракте ответа) — расхождение API вендора станет тихим пропуском данных навсегда. Что нужно: ловить JSONDecodeError (и ClientError/Timeout в соседнем блоке); прочее — наружу.

    7. binance_parser/live/periodic_poller.py:217 — Exception вокруг всей итерации¶

    Что ловится: Exception на parse+write одной итерации поллера. Что происходит: log.exception + continue. Негативные последствия: баг парсера/райтера поллера маскируется, поллер «живёт» и молча не пишет метрики. Что нужно: сузить до исключений ввода/вывода; баги формата — наружу.

    8. binance_parser/services/live.py:62 — слишком широкий catch в _validate_symbols¶

    Что ловится: Exception вокруг всего REST-чека exchangeInfo. Что происходит: print-warning, run продолжается. Негативные последствия: «soft check, never abort» осознан, но catch прячет и сетевые сбои, и баги; опечатанные символы уходят в подписку и молча не дают данных. Сетевой сбой не отличим от бага. Что нужно: сузить до aiohttp.ClientError/TimeoutError; прочее — наружу.

    9. binance_parser/history/downloader/fetch.py:57 — пропуск проверки SHA-256¶

    Что ловится: Exception при фетче чексуммы. Что происходит: logger.debug + None → проверка целостности пропускается, скачивание продолжается. Негативные последствия: повреждённый ZIP может пройти незамеченным (поймается только позже на экстракте, а часть — никогда); уровень debug — практически тихо. Ослабление гарантии целостности данных. Что нужно: поднять до warning и/или при недоступности чексуммы помечать файл как непроверенный в отчёте.

    10. binance_parser/history/downloader/batch.py:52 — тихий сброс чекпоинта¶

    Что ловится: Exception при чтении .download_checkpoint.json. Что происходит: self._done = set() — прогресс обнулён, без лога. Негативные последствия: повреждённый чекпоинт → полное повторное скачивание (сотни пар × месяцы) — время и трафик, без единого сообщения. Что нужно: warning с причиной + переименование битого файла (.corrupt), чтобы не повторялось молча.

    11. Тихие пропуски дней/шардов в читателях данных¶

    Места: alpha_engine/metrics/raw_data_reader.py:347 (_dt_in_window → False, день выпадает из окна), raw_data_reader.py:397 (битый шард → continue, «one bad shard shouldn't poison the whole warm start»), alpha_engine/metrics_engine/tick_reader.py:49 (битая dt-директория → continue), alpha_engine/metrics/go_metrics_reader.py:285 (битый шард → warning, но нет агрегированной статистики), go_metrics_reader.py:181 (discovery-сэмпл — молча). Негативные последствия: день/символ/ключ тихо выпадает из данных → бэктест и live видят молчаливые дыры (NaN-фреймы, пропущенные бары). По одному месту потеря микроскопическая, но на годы данных суммарно это сотни «исчезнувших» часов без следа в логах. Что нужно: единый паттерн — warning с путём файла + агрегированный счётчик скипов на конец загрузки (по аналогии с уже сделанным в live_bridge.py:394); битый шард — не молчать.

    12. alpha_engine/metrics/ob_updates_aggregator.py:373,382 — дроп событий depth без счётчика¶

    Что ловится: (TypeError, ValueError) при распаковке raw-pair и float(price)/float(qty). Что происходит: return — событие молча дропается. Негативные последствия: потерянные place/remove-события → заниженные счётчики бара (ob_updates метрики), искажение без диагностики. Что нужно: счётчик дропов (экспонировать в метрики/лог на конце бара).

    13. alpha_engine/portfolio/markowitz.py:280-282 — NaN-веса стратегий молча → 0¶

    Что ловится: ничего — неисключительный фолбэк reindex(...).fillna(0). Что происходит: стратегия с NaN-весами обнуляется в комбинации без сигнала. Негативные последствия: стратегия, упавшая в NaN (поломка фич, пустой бара), тихо исчезает из портфеля — распределение искажается без диагностики, в отличие от осознанного ew-фолбэка на 267 (там вырожденная ковариация, тут — поломка). Что нужно: отделить «легитимное отсутствие весов» от NaN-поломки: warning при NaN на входе combine (или атрибут-флаг).

    14. Мелкие глухие ловли (добавить лог, без редизайна)¶

    • alpha_engine/live/binance_futures.py:167,185 — (TypeError, ValueError) → continue без лога (строка выпадает из mark_prices/day_transfers; тихий, но копеечный эффект).
    • binance_futures.py:489 — битый entryPrice → entry = 0.0 молча (кривой avg_entry → искажённый realised PnL).
    • binance_futures.py:223,337 — leverageBracket/ensure_filters молча pass/пустой dict (нет max_notional_cap → риск -2027; хотя бы debug-лог).
    • alpha_engine/live/live_reader.py:174 — import-фолбэк LIVE_RECONSTRUCT_MULTILEVEL = False без лога.
    • alpha_engine/live/state.py:74,79,86 — битый файл состояния / точки истории молча сбрасываются (74 — добавить warning; 79/86 — debug).
    • alpha_engine/live/go_metrics_live.py:176 — continue без лога при битом parquet в latest_metric_ts.
    • binance_parser/models/rest.py:125-157 — NaN/0/""-сентинелы пишутся в parquet молча (downstream исполнитель ордеров без проверки NaN может строить невалидные ордера — хотя бы задокументировать + валидация перед ордером).
    • binance_parser/live/exchange_info_poller.py:157 — float(quoteVolume) → 0.0 молча исключает символ из фильтра MIN_QUOTE_VOLUME_24H_USD.

    Часть 2. Fallback уместен — оставить как есть¶

    Сетевой конверт (эталонный паттерн)¶

    binance_parser/live/funding_poller.py:76, exchange_info_poller.py:109, periodic_poller.py:152, market_stats_poller.py:273, history/downloader/funding_fetch.py:97, fetch.py:156 — единый шаблон: bounded-ретрай (1,3,10)/(2,5,15) + отдельный бюджет Retry-After (429/418) с капом + явный скип с логом. Осознанная устойчивость. Известное слабое место (не баг, а дизайн): скипнутые данные не компенсируются — дневной цикл exchange_info пропущен = день без метаданных, funding скипнут = дыра до следующего сеттлмента (8ч).

    Выводы¶

    1. Единого подхода в кодовой базе нет: один и тот же паттерн («битый шард пропускаем») в live_bridge.py:394 сделан видимым, а в raw_data_reader.py:397 и tick_reader.py:49 остался молчаливым.
    2. Реальный торговый риск — 2 места: binance_futures.py:635 (дублирующий market-ордер) и binance_futures.py:484 (повторное открытие позиции). Оба — глухие ловли в самом дорогом слое.
    3. Реальная потеря данных — 1 место: binance_parser/live/writer.py:113 (батч parquet без ретрая).
    4. Системная слабость конверта: стратегия «таймаут = починит reconcile» самокорректируется только если reconcile и day_transfers не падают одновременно; при двойном отказе расхождение blotter↔венча живёт дольше бара.
    5. Образец для остальных: атомарные писатели (cleanup + re-raise), bounded-ретраи поллеров, assert-канарейки rate_limiter, «отказ вместо NaN» в orderbook_aggregator.

    Предлагаемый план работ¶

    1. Fail-fast, приоритет 1: пункты 1-4 (два места в binance_futures, writer.py:113, pipeline.py:488).
    2. Fail-fast, приоритет 2: пункты 5-13 (сужение except, счётчики дропов, видимость скипов).
    3. Логи-дозаполнение: пункт 14 (мелкие глухие ловли — добавить warning/debug).
    4. После каждого шага — прогон тестов; регрессии по образцу tests/test_metrics_engine_regressions.py.
