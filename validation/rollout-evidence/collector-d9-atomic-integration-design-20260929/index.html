    Collector D9 atomic publish integration proposal, 2026-09-29¶

    This is a reviewable design, not an implementation or authority to upgrade the deployed broker. The deployed 2.10.29 publisher still sends one js.publish per event. The isolated pinned 2.15.0 primitive sent 60,000 cached mixed events in 6.152 seconds with exact readback, but it bypassed D9 and was unpaced. Prototype evidence establishes protocol behavior, not collector admission, freshness, restart or cutover acceptance. A matched version-only control ran the unchanged single-event D9 publisher on fresh pinned 2.15.0 FileStorage: 94,499 offered/admitted/ACKed, exact readback, but 8.585 seconds of post-offer drain after the 30-second steady/burst profile. This modestly improves the 2.10.29 control's 10.436-second post-offer drain while still failing capacity headroom. Its preserved result is /opt/trading/codex-operations/offline-20260929-0050/publisher-single-215-final1/results/publisher-single-215.json (SHA-256 cb378d61a06328c6454de8df16a1d973d353bfb08fc5ca93f50f54d9c991ed30). ADR-50 defines the zero-byte initial staging reply, final commit PubAck, contiguous sequences, duplicate rejection, 1,000-event batch cap and 10-second idle abandonment. The 2.15.0 release adds grouped sync for a single-replica always-sync atomic batch.

    Current boundary and proposed owner¶

    D9Buffer charges each admitted entry in total_bytes, transfers it to inflight_bytes on reservation, and releases both after the individual publisher returns. Its current drainer permits up to 200 tasks and excludes a second in-flight event for an active subject. make_publisher fetches a retained subject tail on first use, computes gap headers, sends one event, then commits its gap watermark on PubAck. run_live_tasks stops ingress before draining, with a configured 10-second shutdown deadline. The collector creates MD through ensure_collector_streams; the common stream creator currently does not request or fail-loud verify allow_atomic, and its MD retention is discard: old.

    The integration should replace the individual publish task loop with one batch coordinator for the MD stream. All collector WS and poller events still enter the same bounded D9 buffer. At most one atomic batch is unresolved globally, simplifying stream-sequence reconciliation and preserving per-subject order without relying on interleaved batch behavior. The coordinator reserves up to 100 events, with an initial 20 ms oldest-event fill deadline; both values are proposed acceptance candidates, not observed safe production settings. It should form a batch from ready subjects in round-robin order, allowing multiple queued events for a hot subject in that same batch while never taking its next event into a later batch before the current batch resolves. The current one-event-per-subject reservation API cannot do this; a batch reservation/requeue/release API must keep each subject active until the whole batch is resolved. A failed batch requeues its entries at the head in their original per-subject order. First-use tail lookups run in a bounded seed lane so one slow subject does not stall already seeded subjects; no event for an unseeded subject enters a batch before its seed succeeds.

    All original subject, payload bytes, MsgId and source headers remain unchanged. Add Nats-Batch-Id, sequential Nats-Batch-Sequence, and Nats-Batch-Commit: 1 only to the final real event; no synthetic data row or fast-ingest mode. The first event uses core NATS request and must receive an empty staging reply, intermediate events publish in order, and the final event uses request and must return the exact batch ID, count and final sequence. A staging reply is never treated as persistence. Protocol errors or an unexpected reply fail loudly. allow_atomic, server version/API compatibility, FileStorage, always-sync, stream epoch, duplicate window and intended retention settings must be verified at collector boot from production-created fresh infrastructure; current stream drift logging is insufficient for this new mandatory invariant. A 2.10 server must refuse collector startup rather than silently use individual publishes.

    Charges, headers and watermark state¶

    Admission remains a RAM-buffer event, not a durable local commit. Every reserved entry stays charged to total_bytes and inflight_bytes through final PubAck or a proved reconciliation verdict. The coordinator must also charge its temporary batch header maps, manifest serialization and subject indexes, or bound them separately within the same 1.3 GB collector envelope. Do not release charges on the first empty staging reply, final request timeout, disconnect or cancellation. Keep independent counters for offered, admitted, evicted/refused, staged, final-ACKed, reconciled, duplicate-rejected, failed and unresolved events; publish latency starts at D9 admission, not batch send. Export oldest admitted-unacked age, retained/in-flight bytes, batch fill/ACK latency and retry age. Existing trading_ingress_messages_total counts nonduplicate PubAcks and must not stand in for admission.

    For each batch, make a private per-subject copy of committed trade/diff watermarks and calculate gap headers in batch order. Repeated events of one subject advance only this tentative copy. Freeze the complete transmitted headers in the batch manifest before sending. Advance the real GapMonitor and seeded state only after final PubAck or exact committed readback; on authoritative rejection or proven absence, discard the tentative copy. The retained-tail seed must not overwrite a watermark advanced by a resolved batch. If readback is incomplete, leave the subject blocked and report an unresolved interval instead of publishing later events with an invented gap state.

    Durable batch identity and unknown final ACK¶

    Before the first staged send, obtain MD stream identity (created epoch, first/last sequence and configuration) and fsync a versioned pending manifest plus containing directory. Store unique batch ID, count, ordered subjects, payload bytes or lossless references, MsgIds, exact transmitted headers, first-attempt UTC, D9 admission timestamps/charges, and pre-batch last_seq. One globally outstanding collector batch and an MD-write-exclusive credential/ownership contract are prerequisites. Other MD writers must be absent or explicitly accounted for; a get_last_msg(subject) lookup or MsgId dedup ACK cannot locate an arbitrary lost batch. If exclusive writer ownership cannot be established, do not enable this protocol.

    With a final PubAck, check batch, count and seq; the candidate committed range is seq - count + 1 .. seq. Confirm the stream epoch and exact contiguous readback when reconciling or auditing. If the final ACK is lost, stop new batch sends, close the uncertain connection and reconnect to the same stream epoch. Scan the bounded sequence interval pre_batch_last_seq + 1 .. current_last_seq for the unique stored batch ID and sequential batch headers. Under the exclusive-writer invariant, a found batch must occupy exactly count contiguous rows with every subject, payload, MsgId and complete header map matching the manifest; partial is fatal. An unexpected writer, retention floor advance, oversized interval or stream reset also fails closed. An empty scan, even twice after the 10-second idle timeout, is not an authoritative abort: a final commit blocked on IO could complete later. Neither ADR-50's abandonment advisory nor the isolated probe proves a durable batch-status/abort API in the pinned 2.15 server. That capability remains unproved. A none verdict cannot authorize retry until a server-authoritative abort/fence is established, or an explicitly reviewed broker stop/restart has fenced every old publisher session so it cannot reconnect or resend and exact readback on the preserved stream epoch proves absence. Otherwise retain the manifest, keep charges, and block later batches. No blind resend follows a request timeout.

    After a proved abort/fence and absence, any retry must use the same event MsgIds and a new batch ID within the broker's dedup window, with a retained stream floor that proves no relevant eviction. If that deadline or proof is missing, keep the manifest and block publication for operator recovery. A final PubAck may be followed by asynchronous manifest cleanup; a crash before cleanup simply causes an idempotent readback reconciliation at restart. Never remove a pending manifest until its result is durable. Measure the manifest fsync and cleanup cost in the real D9 throughput test; the primitive 9,753/s excludes both.

    Rejection, shutdown and restart¶

    Server error 10201 means a preexisting MsgId rejected the whole atomic batch in the isolated contract test. It cannot be treated like today's successful per-event duplicate PubAck. Ordinary poller repeats and WS reconnects legitimately reemit MsgIds, so merely quarantining every 10201 batch would halt healthy traffic: this is a production release blocker, not an accepted initial policy. The smallest concrete recovery candidate starts only after the server has authoritatively rejected the entire batch. It logs and meters the exceptional path, retains the original charged entries, and publishes those events one at a time in original order using their unchanged MsgIds. Each singleton PubAck is journaled with its sequence and duplicate flag before its reservation is released. A duplicate ACK must be checked against the stored row's subject and venue identity, with a reviewed rule for receive-time/header differences; a collision fails closed. A crash between any singleton send, ACK and journal write creates a partially recovered batch, so startup must reconcile each entry against the journal and exact retained rows before continuing. Unknown singleton outcomes, dedup-window expiry or an evicted row block recovery; they cannot be retried blindly. This exceptional path loses batch atomicity and may lose throughput, so its journal, gap-watermark and paced-capacity behavior need separate tests and explicit acceptance before implementation. No silent singleton fallback is authorized by this design. Other protocol errors, a missing sequence, max-batch rejection, staging timeout or stream mismatch likewise fail loudly with charged entries retained until outcome classification.

    On graceful shutdown, stop WS/pollers first, complete or reconcile the active batch, then drain queued D9 entries. The current 10-second deadline is shorter than a 10-second batch idle expiry plus reconciliation, so an unknown final ACK cannot be made safe within that grace. Extend and test the stop budget as an explicit deployment change or exit nonzero with a durable unresolved manifest; do not report drained while charged or unresolved entries remain. Cancellation must shield manifest write, final-ACK classification and reservation accounting from partial cleanup. On process restart, block ingress and all new sends until every pending manifest is matched to the same stream epoch and reconciled; seed watermarks from the verified retained tail only after recovery. A hard process kill still loses unreserved RAM-only D9 entries. The manifest protects sent batches, not all admitted entries. A no-loss guarantee for every admitted entry across SIGKILL requires a separate durable D9 spool and its own capacity proof; this integration must state that limit rather than imply crash-safe admission.

    Acceptance before any live upgrade decision¶

    Unit tests first pin charged batch reservation/requeue order, multi-event same-subject tentative gaps, exact header freezing, ACK and error state transitions, cancellation and shutdown reporting. Disposable NATS 2.15 integration tests then cover fresh stream bootstrap, empty first reply, exact final ACK/sequence map, incomplete and duplicate rejection, precommit and post-ACK broker kill, lost-final-ACK client kill/restart, all/none/partial scan outcomes, epoch/floor changes, stalled final-commit IO, dedup-window boundary, and no-resend behavior. Inject a duplicate before a batch with unrelated unique events; prove the whole batch is rejected, then test the separately approved singleton recovery and a crash after each possible singleton ACK/journal boundary. Measure restart with pending manifests and queued RAM loss separately. No production-ready claim is possible while authoritative abort/fence and duplicate recovery remain unproved.

    The end-to-end offline load gate must replay a representative 780-symbol mixed-kind workload through the actual D9 admission wrapper, batch coordinator and always-sync FileStorage, with original subject/payload bytes and explicit provenance for any synthetic MsgIds/headers. Include hot repeated subjects and poller/liq/kline kinds missing from the 6,000-row four-kind cached trace. Count offered, admitted, evicted/refused, staged, final-ACKed, reconciled and exact readback independently; assert per-subject FIFO, zero unexpected duplicates/loss, bounded charged RAM and no guard/OOM events. Run at least 30 seconds at 2,700 offered/s plus a 5-second 5,400/s burst, then drain; require a nonpositive steady queue slope, no D9 drops and measured burst catch-up/freshness. Record client/broker CPU throttling, fsync/IO observations and concurrent archiver cost before claiming host headroom. The 100-event/20 ms proposal must be changed if this measured path cannot meet the reviewer's freshness and resource limits. The prior unpaced primitive benchmark alone does not pass this gate.

    Cutover authority and rollback boundary¶

    The deployed 2.10.29 image, config, volume and stream cursors remain intact. The user has authorized tested commits and staged paper deployment after the stated gates; changing the pinned broker to 2.15 and adopting the atomic protocol remain a separate version/protocol decision under the handoff, not implicit in that staged-paper authorization. Any approved 2.15 paper cutover needs an immutable image/config manifest, fresh isolated 2.15 volume and stream, stop-first unique writers, exact UTC old/new data boundary, and full paper recovery/soak acceptance. Never open a 2.15-mutated volume with the 2.10 binary. A rollback restores the preserved 2.10 generation on its own volume, records the unavailable interval and does not promise that 2.15 rows transfer into it. NATS' 2.15 upgrade/downgrade guidance does not endorse direct downgrade to 2.10. Existing runbook rollback rules require stopping incoming writers and preserving new state. None of this authorizes a production broker upgrade, venue call, deletion or real-money execution now.
