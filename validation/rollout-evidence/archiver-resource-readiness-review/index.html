    Archiver resource readiness review¶

    2026-09-29. Read-only production observations, source inspection and one isolated local writer-lifecycle diagnostic. No service start/restart, configuration change, broker snapshot, venue request or large backup. Root stopped the archiver after the observed memory-pressure finding. No proposed capacity experiment has been executed.

    Observed blocker¶

    The collector trial lasted 00:16:55–00:17:27 UTC. Parent recorded archiver 745.5/768 MiB and 97.77% CPU. At 00:22:41 UTC the archiver was running without restart/OOM, but its cgroup peak was exactly 805,306,368 bytes, the 768 MiB limit. memory.events:max=1193, oom=0, oom_kill=0: allocation pressure/reclaim reached the limit, despite the absence of a killed process. Current charge remained 766,042,112 bytes. Anonymous charge was 739,500,032 bytes; process anonymous PSS was 721,952 KiB. Broker connection pending bytes were zero; this is a broker output-queue measure, not proof that client queues were empty.

    Trial segments closed and acknowledged at 00:17:45 and 00:18:46 UTC. Their logged counts sum to 58,873 messages. High anonymous memory after those closures is real, but does not establish its owner. Python arena retention, Arrow allocator high-water storage, reachable client/writer objects, and unreachable cycles remain hypotheses requiring isolated measurements. No cyclic Arrow leak has been demonstrated. The four inspected archiver modules match the deployed v1 source manifest exactly; hashes and raw measurements are preserved in archiver-resource-readonly-snapshot.json.

    Concrete source risks¶

    • There are nine push subscriptions, one per kind across symbols. js.subscribe has no explicit local pending limits: installed nats-py defaults are 524,288 messages and 256 MiB payload bytes per subscription. Nine queues therefore permit 2.25 GiB of queued payload alone, before object overhead. Broker max_ack_pending=300000 is also per consumer; it is not an aggregate archiver byte cap. Slow-consumer overflow is not a designed, measured capacity control here.
    • _pending_acks[(kind, ingest_segment)] retains the complete NATS Msg, including its original payload, until segment close/fsync and acknowledgement. Row-group flush does not release it. With 60-second segments, 30-second grace and 30-second sweeps, normal retention can approach 120 seconds. At 2,000 messages/s this is about 240,000 retained messages; 3,000-byte payloads alone would consume 720 MB. This example is a capacity calculation, not a measured mean depth payload. The peak configuration still describes a 100-symbol catalogue, whereas the trial used 780 symbols.
    • Writer row buffers are per kind and ingest-time segment, not per symbol. The 5,000-row limit bounds row count, not retained bytes. Nested depth levels can make a row far larger than a trade. Conversion to Arrow coexists with the Python row list; Parquet encoding/compression requires additional transient memory. Active adjacent segments and independent kind executors add simultaneous allocations.
    • Definite long-run metadata growth: close_segment leaves an empty _pending[key] list and retains _closed keys without expiry. A local synthetic 64-segment lifecycle produced zero open writers/rows, but 64 pending dictionary entries and 64 closed keys. Evidence: archiver-retained-keys-diagnostic.json. This small per-segment growth cannot alone explain the observed hundreds of MB, but prevents a claim of strictly bounded steady-state memory.
    • Flush failure is potentially unbounded: write_rows replaces _pending[key] with a batch before flushing. If conversion/write fails, the batch remains; subsequent messages append and attempt the same failing flush. Consumer catches the error and continues without ack. Redelivery can append rows repeatedly even when the broker's count of distinct outstanding messages is bounded. A permanent malformed/writer failure needs its own regression/capacity diagnosis.
    • A sweep closes/acks segments, then awaits pending S3 retries before renewing outstanding messages or starting its next sleep/close cycle. Slow upload/HEAD can delay the next close and renewal substantially beyond the nominal 30-second cadence. S3 client read timeout is 300 seconds with retries; normal-time retention formulas do not bound that outage case.
    • Each message incurs an awaited default-threadpool decode and an awaited single-thread-per-kind writer dispatch. This introduces two scheduling round trips per message, plus JSON/model allocation and normalization. CPU near one full core does not identify which operation dominates; it also does not prove an aggregate throughput ceiling, since independent kinds can use multiple worker threads. Real mixed-kind service capacity remains unmeasured.
    • Daily merge reads 65,536 rows per Arrow batch, constructs Python message-ID/keep lists, performs one SQLite insert per non-null ID, and may produce an additional batch.take copy. A depth-heavy batch can exceed a 768 MiB process budget even if each ingest row group fits. S3 multipart uses 64 MiB chunks; previous/current chunks and HTTP checksum/buffering can coexist. Merge/upload needs a separate peak test concurrent with intake, not an intake-only proof.

    Smallest isolated proof¶

    Use a fresh private NATS broker and separate staging directory, with no connection to production NATS/PG, no venue endpoint, no real S3 credentials, and an egress-disabled container network. Pin the actual deployed archiver source/image and Python/Arrow/NATS versions. First retain the 768 MiB cap so the failure is reproducible; do not test on the production broker.

    1. Run the actual writer/segment lifecycle with synthetic trade/depth envelopes matching the cached measured payload-size/level-count distribution and 780 symbol identities. Include large depth tail examples rather than padding only small trades. Measure decoded Python rows, Arrow live allocation (pa.total_allocated_bytes/pool max), writer keys, pending rows, RSS and 50-ms cgroup peak/events through repeated row-group flush and at least ten segment closures. Quiesce/drain; take diagnostic-only GC and allocator-release snapshots separately. Those diagnostic actions distinguish unreachable cycles and allocator high-water from reachable retention; they must not be silently added to production as a workaround.
    2. Feed a fresh isolated JetStream through the actual subscriptions, decoder, writer, pending-ack/sweep and durable-ack path. Start at 2,700 messages/s (chosen collector publisher capacity), then a 5,400/s burst for at least one 120-second retention window; run at least 30 minutes for multiple closures. Replay a bounded synthetic backlog as a separate case. Record producer acknowledgements, consumer deliveries/pending/redelivery, local NATS queue bytes/messages, pending Msg retained bytes/count, oldest pending ack, per-kind rates and all allocator/RSS/cgroup measures. Every input ID must occur exactly once in finalized parquet after drain; payloads may be retained in dedup but not duplicated financially or dropped silently.
    3. Include a previous-day depth-heavy merge and an offline local copy/HEAD-verify sink while intake continues. Exercise actual merge and copy-verify-delete code with a local sink, recording the 65,536-row and 64 MiB chunk peaks. Simulate slow sink/failed flush explicitly; outstanding messages must remain accounted for and memory must stop growing or the run must fail loud. No external S3 request is required for this capacity proof; real cloud latency remains a separate acceptance gate.

    Pass requires no OOM/restart, no memory.events:max increments, no unaccounted loss, drain to zero pending acks and a stable post-warmup memory envelope rather than a per-segment upward staircase. For a release budget choose at least 20% headroom over the largest measured concurrent intake/merge/upload peak; this is an operational safety margin, not a proof of boundedness. A short intake-only pass cannot justify the cap. Sustained sink delay/backlog growth is a failure even if RSS happens to fit.

    Configuration decision¶

    Do not raise the production cap now. The observed 768 MiB budget is insufficient, but current source permits more retained work than that budget and contains independently growing metadata. A cap increase alone would hide the same issue until a larger burst or long outage.

    After concrete retention fixes/bounds and the isolated proof, a larger budget may be justified by a stable measured peak plus headroom. Existing repo compose declares 2 GiB for the archiver, whereas this deployed override is 0.75 GiB; that discrepancy is not evidence that 2 GiB is safe. The host's 16 GiB RAM and current 12.375 GiB summed ceilings permit considering a redistribution only after accounting for host page cache, kernel, Docker, backup/maintenance and other services. Lowering row-group count can reduce transient decoded depth memory but will not release retained Msg payloads or bound local NATS queues. Lowering max_ack_pending blindly may stall before durable close, and current validation enforces peak*(segment+grace+sweep) as a floor. Segment/grace changes alter the durability window and must be justified, not guessed.
