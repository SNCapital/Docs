    Isolated atomic publish prototype, 2026-09-29¶

    This is an offline protocol probe, not a collector change or a deployment decision. The deployed NATS 2.10.29 image and its volume were untouched. The test broker used a fresh, preserved file volume, sync_interval: always, a 512 MiB memory limit, one CPU, and no published ports. The client was limited to 1 GiB and two CPUs. The pulled image was verified as nats-server v2.15.0 and pinned by nats@sha256:cd3fcd4ecdda44e3a66728a5334af0a959bc3979b32810e033d1c547241cd0f4. The broker was stopped after the contract run.

    ADR-50 defines the initial zero-byte staging ACK, final commit PubAck with batch ID/count/final sequence, 1,000-message and 10-second idle limits, and rejection of a batch containing a stored duplicate MsgId. The 2.15.0 release notes identify grouped synchronization for atomic batches on a single-replica stream with always-sync. The server stream configuration uses allow_atomic. The prototype explicitly sets discard: new and max_age: 0 so an exhausted test stream cannot evict acknowledged rows.

    Four fresh file-backed streams tested the protocol through the installed Python client's core NATS request/publish calls:

    Scenario Observed result
    Three-event commit First reply was empty; final PubAck identified batch, count 3 and final sequence 3; all three events read back in sequence with expected subject, payload, MsgId and batch headers.
    Missing batch sequence Server returned error 10176; stream retained zero events.
    Preexisting duplicate MsgId Server returned error 10201; the original singleton remained the only stored event.
    Final commit without a reply inbox Two events committed; exact readback reconciled their IDs, payloads and expected headers without a final PubAck.

    Raw replies and counts are preserved at /opt/trading/codex-operations/offline-20260929-0050/publisher-results/atomic-contracts.json (SHA-256 046eb1ca2a5e9e09aa4ff71680e4cd6252164947540d884f47a2a2843ccd04fa), with the broker cgroup snapshot beside it. The broker config SHA-256 was 5ab37bbb5d181845d45473f21276a9d6a8b026a0902cbf10603c68d65e1f2cee. The initial contract run used an earlier verifier that checked every expected header value but did not reject an extra header. The later guarded capacity and crash runs used the corrected complete-header-map verifier against the broker. Its injected-extra-header regression was observed red then green, and 17 focused unit tests passed across the crash, atomic and prior capacity tools.

    The no-reply final commit simulates an unknown final-ACK outcome; it does not inject a network ACK loss or kill a client. A crash/restart proof should use separate fresh streams and one disposable 2.15 volume per case:

    1. Stage the first and middle events, receive the initial zero-byte ACK, flush the connection, then kill the broker before sending commit. Restart the same pinned binary on that disposable volume and require zero stored events and no matching MsgIds.
    2. Commit a batch, durably record its final PubAck, kill the broker after the phase marker, restart the same pinned binary and require exact contiguous readback of every subject, payload, MsgId and header.
    3. Persist and fsync a pending batch manifest before sending the final event with a reply inbox. Terminate the client after flushing the final send but before consuming the final reply. On client restart, reconcile the manifest by stream readback and accept only an all-or-none result. If all rows exist, map them by the final stream sequence and batch count; do not blindly resend a batch whose MsgIds may already be stored. Repeat the termination at both sides of the server commit boundary to cover the ambiguous outcome.

    The tool has crash-prepare and crash-reconcile commands, checked by focused fake-client tests and later run against the pinned broker. Each case needs its own fresh file-backed stream on a fresh disposable v2.15 broker volume. crash-prepare creates and fsyncs a manifest containing the exact three payloads, subjects, MsgIds and headers before publishing. It fsyncs the containing directory after the atomic rename. It then fsyncs a *.ready.json marker only after reaching the named phase and waits for an external kill. The after-ACK case also fsyncs a separate *.ack.json before its marker. The marker is the kill trigger; killing earlier does not establish that phase. The lost-ACK client subscribes to a unique reply inbox, sends the final commit with that reply address, flushes, and intentionally does not consume the PubAck. A NATS reader may already have buffered the reply, so this tests client process loss before application reconciliation, not packet loss at a precisely observed server instant.

    Use these exact client commands on a fresh internal-only broker aliased offline-atomic:4222, with a unique manifest basename and preserved results directory for each case:

    python tools/offline_atomic_publish_probe.py --mode crash-prepare --case before_commit --manifest /results/before.json
python tools/offline_atomic_publish_probe.py --mode crash-prepare --case after_ack --manifest /results/after.json
python tools/offline_atomic_publish_probe.py --mode crash-prepare --case lost_ack --manifest /results/loss.json

    Run only one case per fresh stream and volume. After its *.ready.json appears, externally kill the broker with SIGKILL for before_commit or after_ack, or the client with SIGKILL for lost_ack. Preserve every container and volume, restart the same pinned broker on its same isolated volume, and run the matching reconciliation command from a new capped client:

    python tools/offline_atomic_publish_probe.py --mode crash-reconcile --manifest /results/before.json --output /results/before-reconcile.json
python tools/offline_atomic_publish_probe.py --mode crash-reconcile --manifest /results/after.json --output /results/after-reconcile.json
python tools/offline_atomic_publish_probe.py --mode crash-reconcile --manifest /results/loss.json --output /results/loss-reconcile.json

    Reconciliation sends no messages. It requires zero stored rows for the uncommitted prefix, exact three-row subject/payload/header/MsgId readback plus the persisted PubAck for the post-ACK case, and an exact all-or-none result for the lost-ACK case. Partial rows, extra headers, duplicates, reordered per-subject rows, missing post-ACK data, or stored precommit rows fail. A lost-ACK none verdict does not authorize a blind resend; a production client would need a persisted batch reservation and explicit retry policy. The external coordinator must record source and broker config hashes, cgroup samples, ready-marker timestamp, kill/restart times, preserved Docker identities, and exit status; this tool alone does not observe disk flush latency or prove survival after power loss.

    The guarded follow-up used the same pinned image and configuration SHA-256 5ab37bbb5d181845d45473f21276a9d6a8b026a0902cbf10603c68d65e1f2cee. The atomic tool SHA-256 was 8fdb34311bb0b5bb1afe978a39d786cea919c009b93bf06884ad52bb8fdd9b73. Each case had a fresh volume and a 512 MiB/one-CPU broker; each client had a 1 GiB/two-CPU cap. Both containers had persistent external guards, and a host start gate was written only after each guard recorded verified and an initial cgroup sample. Every result, manifest, cgroup JSONL, marker, container and volume remains under /opt/trading/codex-operations/offline-20260929-0050/. No offline container remains running.

    All crash-run guard logs ended with the intended SIGKILL exit 137 or normal exit 0, and recorded no memory max/OOM events. The result JSON and exact UTC kill/restart files are in each run's results/ directory. The first precommit kill was requested 9.870 seconds after the marker, near the protocol's 10-second idle timeout, so it is confounded by possible expiry. The prearmed before-fast-final1 repeat requested kill 1.910 ms after the post-fsync marker; its manifest, watcher record, and result SHA-256 values are 3ffb68626ac16ba69154da5ef459e543267e3f8b30fb3a4fbcf89c130adb9d49, 84db8834c75c01c1e691210e479cecfe0f53a31182718cc15b116ed3bf9a1de1, and cc9b4850a346a194a73824c025942714516b2cb62e5bb3c3932ab94896cde7a6. The post-ACK kill was requested 5.162 seconds after its marker, not immediately. The first capacity attempt, atomic-capacity-final-1, is preserved but excluded: its app user could not write the root-owned result directory, and detached guards did not persist. The fresh final-2 run corrected both conditions and was isolated from later crash cases.

    The cached trace SHA-256 is bfff4a9abe984291c89c6dda263261df36794286e7ff7678ecf591af90c80777. It contains 6,000 original events across 780 symbols with original subject and payload bytes but no original MsgIds or transport headers. The capacity run repeated those rows ten times with explicitly synthetic unique MsgIds, ingress timestamps and computed gap headers; it cannot prove original header parity. It is an unpaced primitive throughput result, not a timed 2,700/s steady plus 5,400/s burst admission and freshness proof. The lost-ACK case establishes reconciliation after application process loss before consuming a reply; it does not establish a network ACK drop exactly at the commit boundary, nor retry after a none result. Batch memory reservations, concurrent-batch per-subject order, lost-ACK reconciliation and retry behavior in the production D9 publisher remain unimplemented and unaccepted. The v2.15 test volume must never be opened by the deployed 2.10 binary.
