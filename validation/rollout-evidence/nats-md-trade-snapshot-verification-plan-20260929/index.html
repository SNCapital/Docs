    MD_TRADE snapshot membership and payload verification plan¶

    This is a plan and bounded tooling record for the preserved native snapshot, not a recovery verdict. The original old broker stays stopped and its storage and /opt/trading/backups/remaining-20260928/MD_TRADE.snapshot remain read-only. Only generated tiny snapshots have been decoded; there has been no scan or restore of the original archive and no query of the original broker for this task.

    Known range and available artifacts¶

    nats-snapshot-range-review.md records the initial API response of 33,114,055 messages, sequences 80,736,259-113,850,313, and the separate restored report of 33,029,939 messages, sequences 80,820,380-113,850,318. The excluded initial-response prefix is exactly 84,121 sequences (80,736,259-80,820,379); five sequences were added at the tail. The initial response and archive are not atomic membership records. These arithmetic facts neither prove recoverability of the prefix nor prove payload parity of the overlapping 33,029,934 sequences.

    Preserved inputs are MD_TRADE.snapshot (2,142,066,961 bytes; SHA-256 c9922bf4de00e32a96c8a8b254720fb2ab00d4bc96c63800c94ab931dca0bd2a), MD_TRADE.json, and nats-restore-readback.json in /opt/trading/backups/remaining-20260928/. The readback report contains only two endpoint payload hashes, not a full scan. A targeted name search found no extracted MD_TRADE archive index, restored MD_TRADE store, or existing verifier tool. The separate nats-cold-20260929-0240/restored-data has an MD stream, so it is not this MD_TRADE restore. The original archive starts with S2 framing; NATS v2.10.29 streamSnapshot writes S2-compressed tar, message blocks, then msgs/index.db after a forced state write. Its full-state format contains stream bounds, per-block bounds and deletion maps. This sequence of writes is why block contents and the archived index must each be checked.

    Preferred bounded verifier after API feasibility review¶

    NATS v2.10.29 has a StreamStore interface with LoadMsg/LoadNextMsg, but its newFileStore constructor and the stored message's fields are unexported. A standalone Go program outside the NATS server package therefore cannot simply open the archived filestore and emit raw records. The constructor also requires a writable directory and may recover from a bad index.db by scanning blocks, clean up old metadata, enforce retention, and write state. Calling it on the original archive would be unsafe and would obscure whether recovery changed membership. A package-local test helper in a pinned NATS source checkout is possible, but adds upstream build/dependency and mutation-audit work. Constructor and recovery source, store interface and private fields.

    The smallest faithful first candidate is one package-local v2.10.29 filestore helper plus one independent API restore, with no custom index parser:

    1. Stream-decompress the S2/tar archive into a new writable copy of the MD_TRADE stream directory, using a narrowly scoped extractor that rejects unexpected paths, duplicates, errors.txt, missing msgs/index.db, truncation and oversized entries. Hash the extracted index and each block against tar-entry hashes before opening. A direct broker cold-open of the extracted metadata is not safe: its original one-day MaxAge can expire messages before an API override. The archive itself is never passed to a writable NATS path.
    2. Build a small test/helper inside a pinned v2.10.29 server package source copy. It calls the native unexported newFileStore with the copied directory and explicit cfg.MaxAge=0, then LoadNextMsg/LoadMsg and the package-private StoreMsg fields. It emits a fixed-width sequence-plus-digest manifest of length-framed raw subject, header bytes, payload bytes and nanosecond timestamp. It asserts strict sequence monotonicity, count and bounds. The constructor calls recoverFullState() and, on error, silently attempts recoverMsgs(). A reviewable audit-only fail-fast overlay in the disposable source copy must turn that fallback into an explicit error before any membership result is accepted; pin and hash the exact overlay diff. This overlay does not change retention or message decoding, and never touches the original broker or archive. Record pre/post file hashes and fail on unexplained mutation. The Go source and dependencies must be pinned and built in an isolated environment with no implicit downloads. This helper uses the native format decoder and avoids hand-parsing index.db.
    3. Independently restore the original read-only snapshot into a fresh isolated v2.10.29 broker with max_age=0 and no publishers. Obtain a restored per-message manifest via STREAM.MSG.GET with bounded batches. The API's StoredMsg has Header []byte, Data []byte, subject, sequence and time; JSON base64 carries raw stored header bytes. Compare exact sequence and digest with the helper manifest, plus count, bounds and byte totals. This avoids consumer-added delivery metadata and header parse/re-serialization. If batched GET does not preserve exact fields in a fixture, stop rather than downgrading silently to semantic header equality. Preserve both working volumes, logs, outputs, source/image digests and guard traces. Message GET request/response, StoredMsg fields.

    This compares effective message membership and full stored bytes of the archived files against the API restore, not two counts from one broker. It does not independently prove that every raw block record agrees with index.db if NATS accepts a stale but valid index. Any such ambiguity remains explicit; a second native-code pass that deliberately reconstructs membership from copied blocks without the index is needed if the indexed path and block membership must be proven separately. A fully independent custom binary index/block parser is last resort, not the first implementation.

    Before either large path, make tiny v2.10.29 snapshot fixtures with raw headers varying order/case and repeated keys, an empty payload, an interior deletion, a retention-trimmed prefix and a suffix added during snapshot. The package-local filestore read and independent API restore must give identical exact fields. Corrupt one copied header byte, omit one block, and corrupt index.db in separate fixture copies; comparison or fidelity checks must fail. In particular the corrupt-index fixture must prove the audit overlay rejects recoverFullState() failure rather than accepting a block-rebuilt result. A short nonzero archived MaxAge must remain intact after a delayed native read and restore with explicit max_age=0. The bounded tiny proof below now covers these contracts; no original archive was scanned or restored.

    Bounded implementation and fixture evidence, 2026-09-29¶

    The pinned upstream checkout is NATS v2.10.29 commit f91ddd892565760834f27404a92b80a57b8ec149 (tag object f207139f7b9ba0cf3982da9b1db6af0af32bb445; source archive SHA-256 766302401498ddc4293c5c75a234ab6cdf83d58ab2a6c0bf25e7ff9142f3ec22). The build image is Go 1.23.6 digest sha256:adfbe17b774398cb090ad257afd692f2b7e0e7aaa8ef0110a48f0a775e3964f4. Public dependencies were fetched once to an outside-repository cache, then builds used GOPROXY=off. The disposable checkout contains require_index.patch, whose audit-only switch rejects a missing/corrupt full-state index before NATS' block-recovery fallback. go list selected 48 platform production files, zero Cgo files and 60 upstream test files; only the two audit test files were compiled with production files for the successful narrow runs. No production repository package was patched.

    The implemented extract.go hashes the S2 source and each retained tar entry, requires a new output directory and exclusive manifest, checks path/duplicate/size constraints, and requires metadata, index and at least one block. The package-local server_audit_test.go emits sequence plus SHA-256 of length-framed raw subject, raw header, payload and nanosecond timestamp. It checks the extractor's copied-file hashes before opening and after stopping the native store, requires the index overlay, disables age expiry on the copied stream and uses exclusive binary/metadata sidecars. The offline_nats_snapshot_api.py producer accepts only an isolated snapshot-broker* hostname, checks the source SHA and finite byte/message/sequence/time limits, restores the raw snapshot on a fresh broker with max_age=0, reads JSON base64 hdrs/data through STREAM.MSG.GET, and emits the same digest format. The Python offline_nats_snapshot_compare.py compares complete fixed-width manifests and rejects matching partial pilots, mismatched stream state, missing/duplicate/truncated rows and digest differences.

    The full upstream go test ./server compile was stopped externally at 80% of a 2 GiB cap in two preserved attempts (build1 guard charge 1,719,021,568 bytes; serial build2 guard charge 1,721,192,448 bytes); neither produced test results or OOM. A narrowed compile excluding 60 upstream test files peaked at 838,270,976 bytes. Its first execution failed because /tmp was non-executable, then the same selected-file tests passed with GOTMPDIR on an executable bind mount. Final focused native/negative tests and extractor unit tests passed in backend-offline-20260929-nats-audit-build5; Python comparator tests passed 5/5 in backend-offline-20260929-snapshot-complete-green after the preserved red run. All guarded Go runs used an internal-only network, 2 GiB/2 CPU cap and external 80% cgroup guard; no OOM events occurred. Logs and cgroup samples remain under /opt/trading/codex-operations/offline-20260929-0050/nats-snapshot-audit/.

    Two preserved tiny native fixtures exercise snapshot timing. fixture2 appends a suffix only after the snapshot reader closes: initial state and archive both contain three messages, seq 3-6, with an interior deletion. fixture3 appends seq 7 after Snapshot() returns but before its reader is consumed: the initial response reports three messages, seq 3-6, while the archived index and native read contain four messages, seq 3-7. This is valid NATS concurrent-snapshot behavior, not archive corruption. The earlier fixture1 observed the same four-message archive and is preserved; the mistaken expectation that initial response must equal archived membership was corrected. Fixture2 audit peaked at 856,666,112 bytes and fixture3 at less than 1 GiB under the 2 GiB cgroup. The native helper accepted both complete indexed fixtures; the tests rejected missing/corrupt indexes and mutated/missing copied files. These are native-only checks, not an independent restore comparison.

    The tiny end-to-end proof used three fresh internal-only pinned 2.10.29 brokers (nats@sha256:5498ba57b9471840be3d15b033a4eec554d1c02fa6c2cc0ca2d888637f6c6e2f, 512 MiB/1 CPU) and three 1 GiB/2 CPU clients. Separate persistent external guards had verified and sampled both containers before each client start gate. Each broker had a fresh retained volume and no published ports; all were stopped after readback. fixture2 archived and restored manifests are byte-identical (SHA-256 1dae1d6883126b9df9a3970abc49202d8e350d1d80d284e13d5d0dfb41390249, three messages seq 3-6). Concurrent fixture3 manifests are byte-identical (46c208baa853c70a39995445d021be16eb42988fcdf90bddc5280e793c408d39, four messages seq 3-7), including the suffix absent from the initial snapshot response. The aged fixture snapshot was read more than two seconds after creation despite archived MaxAge=1s; native and restored manifests are byte-identical (5ab0ee95e92d240259ed390d14b38330fa91fc89896acdcd58f8d7a51688fac8, three messages seq 3-6), and the restored broker reported max_age=0. Each fixture has repeated mixed-case raw header lines, an empty payload at seq 5, a deleted interior seq 4 and a trimmed prefix. Thus equality covers exact raw header bytes and nanosecond time in the stored/API representations, not normalized consumer headers. Named volumes, config, logs, cgroup traces and manifests remain under /opt/trading/codex-operations/offline-20260929-0050/nats-snapshot-audit/restore-fixture2/, restore-fixture3/ and restore-aged/.

    Fail-closed checks passed for missing and corrupt copied indexes, missing/mutated copied blocks, raw header corruption of an otherwise complete manifest, invalid API timestamp/base64, matching partial manifests, and a non-offline broker URL before connection. The first baseline client failed before restore on file permissions; its logs/container are preserved. The corrected client passed on the same still-empty broker volume. Final targeted tests passed: selected-file Go native tests and extractor package tests, plus 9 Python API/comparator tests. No tiny test proves behavior or runtime at 33 million messages. The next step is a resource-budgeted original-archive extraction and at most 100,000-message native/API pilot within the existing authorization. The current API tool requires the whole restored stream to fit its message/sequence bounds; a bounded first-N diagnostic path must be implemented and tested before using it for a partial original-stream pilot. Partial output must remain rejected by the full-parity comparator. Large extraction and restore file-cache charge also need a measured safe resource plan before starting; the tiny proof does not establish that envelope. Even a full archive/restore parity would not recover or verify the excluded 84,121-sequence prefix.

    The acceptance domain is only membership actually present in the archived native snapshot. A result showing archive and restored membership/payload parity may cover 80,820,380-113,850,318 if the archive scan confirms that domain. It must separately report any archive/index discrepancy. It must never label 80,736,259-80,820,379 recovered or prove the original live stream had no earlier loss. The five suffix messages are checked only if physically present in the archive. Endpoint hashes and count arithmetic remain supporting checks, not substitutes for the full comparison.

    Resource and time gate before execution¶

    The latest filesystem check has about 67 GiB free and the host has 15 GiB RAM with no swap. The saved stream reports 12,069,960,742 restored message bytes; the compressed snapshot is 2.14 GB. Because the preferred method preserves both an extracted archive copy and an independent restored volume, reserve a fresh 36 GiB disk ceiling for the two stores, a fixed-width manifest (about 1.4-1.8 GiB for 33 million records), logs and headroom. Cap the extractor/verifier at 1 GiB RAM and each isolated broker at 2 GiB RAM with external cgroup guards; run only one broker at a time. These are proposed limits, not measured consumption. Reject a run if the host cannot reserve the full ceiling without impinging on other workloads. The earlier 24 GiB one-store estimate is insufficient for two retained copies.

    The tiny fixture and header-equality proof have passed. After implementing the bounded pilot path and validating its resource plan, compare at most 100,000 archived and restored messages with a 15-minute readback limit per path. Both preserve logs and stop on any correctness error or resource threshold. Estimate full elapsed time from measured native-store and batched-GET throughput; 33,029,939 records require about 55 minutes per pass at 10,000/s or 1.8 hours per pass at 5,000/s, plus archive extraction and restore time. No full-run duration is promised before these measurements. The operator must set a finite total deadline from the pilots; two complete read passes are required. A timeout or partial scan is explicitly inconclusive, never a parity pass. This plan needs an IO slot coordinated with the other offline workloads before any fixture, pilot or full run.
