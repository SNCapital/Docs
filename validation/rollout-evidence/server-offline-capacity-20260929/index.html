    Archiver retention diagnosis¶

    The new test_r1_closed_segments_release_writer_metadata reproduces 64 retained empty _pending entries after 64 finalized segments; the baseline also retained 64 _closed keys. Finalized metadata is now released, and every reopened existing base filename receives a fresh part UUID. The late-reopen regression preserves all three finalized parts. This small metadata leak does not explain hundreds of megabytes of anonymous memory.

    test_r2_pending_ack_keeps_control_handle_without_payload uses actual nats-py Msg instances: the baseline retains 16,777,216 payload bytes across 16 pending messages; the fix retains zero payload bytes. Msg.data and headers are released after successful row handling. The control handle still supports in_progress and ACK; ACK remains after segment close/fsync. No durability window changed. The persistent post-ACK anonymous-memory owner remains unresolved.

    The full cached sample smoke ran 01:03:50.111-01:04:09.999 UTC: 6,000 events, 780 symbols, diff 2,453 / trade 1,388 / hb 1,380 / mark 779.     Delivery backpressure constraint¶

    Inspection of the installed nats-py 2.16 code and pinned NATS 2.10.29 consumer implementation rules out simply setting a smaller local push queue. The client reports SlowConsumer and drops local delivery when that queue fills. Existing push durables cannot change flow-control/heartbeat or become pull consumers in place. Moreover, the current async message iterator does not send the deferred flow-control reply used by PushSubscription.next_msg(). The ordered-consumer helper changes ACK semantics and is unsuitable for segment-fsync durability. A new bounded consumer therefore needs explicit durable migration and restart proof, preserving old consumers and starting at the ACK floor rather than the last delivered sequence. No such migration has been deployed or accepted. The pinned source is NATS 2.10.29 consumer.go; installed client source copies are retained in archiver-client-8/.
