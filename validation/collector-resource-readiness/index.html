    Collector resource readiness - 2026-09-28¶

    Status: the payload-only D9 memory-budget defect is reproduced and corrected locally. P0.2 remains open: full-catalogue Linux cold/drain/live and concurrent calc/archiver/trader acceptance have not been measured. No collector rollout or resource purchase follows from these results.

    Scope and evidence¶

    Source baseline: 04e45d3; deployed collector inspected at 3efe4fe. Measurements were taken on 2026-09-28 around 14:10-14:30 UTC using CPython 3.13.12 on macOS. Production inspection was read-only. Public Binance exchangeInfo, aggTrade, depth and premiumIndex endpoints were read; no order endpoints were used. An approximately eight-second WebSocket sample used the actual USD-M public depth and market routes for BTCUSDT/ETHUSDT: 369 aggTrades, 33 depth updates and four markPrice updates. This is representative message-shape evidence, not a measured full-market ingress rate.

    The current exchangeInfo parser returned 780 TRADING USD-M instruments. The current URL-size batching produces three public-route connections with 376/378/26 instruments and eight market-route connections with 103/105/106/105/105/104/106/46 instruments. A successful two-symbol route probe does not establish progression for all eleven connections or REST pollers.

    The inspected old collector consumed 7.058 GiB in Docker stats at about 93% of one CPU. Its Docker memory limit was zero. /proc/1/status reported 7,386,492 KiB RSS and 7,379,144 KiB anonymous RSS; swap was zero. Tail logs showed buffer drops already exceeding 628,008,109. The configured D9 payload cap was 1,300,000,000 bytes. Existing operational evidence showed near-full fill and MD_TRADE advancing while MD_DIFF/MD_EVENTS barely advanced. These counters prove loss and unequal channel progression, but do not identify every missing sequence.

    An additional incident was recorded during the operations run: a NATS snapshot using jsck raised broker RSS to approximately 4.3 GiB and the host OOM killed the old collector at 14:17:35 UTC. The unchanged collector was restarted at 14:21:07 UTC after memory was freed. Snapshot/backup memory is therefore part of the simultaneous resource budget; do not repeat heavy broker operations during an already memory-constrained acceptance run. These incident observations come from the operations run, rather than this local benchmark.

    Reproduced memory defect¶

    D9 previously charged only len(payload). It retained a named tuple, bytes object, subject and message-ID strings, header dictionary, header values, retry metadata and deque storage in addition to those bytes. Old and baseline-new drain versions share this defect; changing stream layout or batch concurrency does not fix it.

    Each memory probe ran in a fresh process. It replayed observed WS message bodies through the actual compact serializer, subject/ID helpers and D9Buffer, with a fresh receive timestamp and header dictionary for every admission. Initial and final current RSS came from ps -o rss, converted from KiB to bytes. A 100,000-entry unsaturated probe measured:

    Observed channel Mean payload B Payload MB RSS increase MB RSS / payload Projected RSS increase at old 1.3 GB payload cap
    aggTrade 195.04 19.50 74.99 3.845 5.00 GB
    markPrice 208.00 20.80 75.97 3.653 4.75 GB
    depth 10,782.30 1,078.23 1,135.49 1.053 1.37 GB

    MB/GB are decimal here; Docker's GiB values are binary. The projections assume linear retained-entry scaling and exclude the service baseline. They demonstrate that the old configured buffer cannot guarantee a collector below 2 GiB. They do not attribute all observed production RSS to D9: allocator retention, pollers, network libraries, metrics and repair work were not separately profiled.

    Corrected memory contract¶

    collector_buffer_bytes now caps the conservative retained-entry charge across queued and in-flight entries together. The charge uses sys.getsizeof for the entry tuple, payload, subject, message ID, header dictionary and keys/values, integer size and reserved float retry timestamp. Every object charge is rounded up to 16 bytes; an additional 16 bytes covers the amortized deque slot. Shared references are intentionally charged per entry. The collector README describes these constants and the process-memory exclusions.

    A drain pop keeps its charge reserved until success or permanent aged-message drop. Failure/cancellation returns the same charge to the queue. Queued overflow still evicts oldest queued messages; reservations are never evicted. A new entry that cannot fit beside current reservations is rejected and counted/logged as lost. Direct unreserved front insertion cannot exceed capacity. All members of a 20-message batch settle before the next batch starts, including after a failure. Completed batch entries drop their batch references before releasing the charge. Concurrent retry insertion retains the existing completion-dependent head order; this is not a strict FIFO retry guarantee.

    This limits retained entry ownership; it does not claim that sys.getsizeof is an OS-enforced RSS limit. Network buffers, transient serialization, twenty publisher tasks, allocator slack and service baseline still need headroom.

    A saturated replay using the unchanged 1,300,000,000-byte configuration measured:

    Probe Admissions Retained entries Charged B Retained payload B Total RSS B RSS GiB Evictions
    Observed aggTrade bodies 1,800,000 1,331,967 1,299,999,792 259,791,311 1,095,286,784 1.020 468,033
    Observed depth bodies 150,000 112,469 1,299,998,656 1,212,685,224 1,379,794,944 1.285 37,531

    Initial RSS was approximately 79 MB. Both sampled saturated probes stayed below 2 GiB. The larger depth probe leaves about 0.715 GiB to the 2 GiB limit, including the measured local baseline. This is a local representative result, not a proof that the full collector with all connections, pollers and NATS client fits that limit on Linux. Evictions in these deliberate saturation probes are expected; zero-drop acceptance requires sustained drain throughput greater than ingress.

    Throughput and unequal progression¶

    The deployed old drain awaits one publication at a time. That publication can perform retained-message lookup, acquire its per-subject lock, fetch a trade gap and publish every repaired trade before publishing the current event. A large trade repair can therefore hold the entire serial D9 drain. Meanwhile WebSocket and poller producers continue enqueueing and evicting old records. This is a concrete mechanism compatible with trade advancing while diff/events starve; production attribution still needs publish-duration/age and per-channel input progression evidence.

    The baseline new drain starts twenty publications, but awaits the complete batch; a slow subject or repair can still delay the next batch. Per-subject locks preserve serialization for one busy symbol. A controlled benchmark exercised the actual old/new D9 drains and current queue_publish with a fake JetStream acknowledgement that sleeps 1 ms, existing subjects from the 780-instrument catalogue, and 1,000 queued trade messages. Retained seeding and sequential IDs prevent real REST backfill. Results before the accounting correction were:

    Drain Subjects Extra delay in first publish Messages/s
    Old serial 1 0 849
    Old serial 780 0 821
    New batch 20 1 0 840
    New batch 20 780 0 11,555
    Old serial 780 500 ms 577
    New batch 20 780 500 ms 1,699

    These are controlled acknowledgement-latency measurements on macOS, not actual broker throughput. The 100,000-entry aggTrade memory probe admitted about 274,392 serialized messages/s before correction; the 1.8-million-entry saturated corrected probe admitted about 184,034/s, including charge calculation and eviction. Probe sizes differ, so this is not a clean CPU regression estimate.

    The roughly 33 million retained trades per day in the operational snapshot imply about 382 stored trades/s, not 382 incoming live events/s: repairs, retention and other channels make them different quantities. Do not use that average to size the buffer or certify catchup. Local receive-minus-event ages included negative values, indicating clock offset; they cannot serve as production publication-age or RTO evidence without synchronized clocks.

    Regression evidence and remaining gates¶

    The new regression file on an isolated 04e45d3 archive produced 6 failures and 1 pass. It failed retained-object lower-bound checks, metadata-heavy oversize rejection, tiny-message budget enforcement and reservation/cancellation support. A separate isolated pre-fix regression also failed because the publish exception traceback retained an evicted header object during backoff. The correction clears result/exception references after logging and exits the exception handler before sleeping. A deterministic pre-child-start cancellation regression also failed before the outer cancellation cleanup: neither publish coroutine had begun, leaving both reservations stranded. Outer cleanup now requeues each unsettled batch entry once, preserving the never-attempted timestamp. The corrected focused suite produced 68 passes:

    collector/tests/test_buffer_memory_accounting.py, test_buffer.py, test_publish_decoupled_order.py, test_collector_publish_metric.py, test_gap_monitor.py, and test_poller_publish.py.

    Outstanding acceptance work:

    • Repeat saturation and realistic mixed-channel live ingress under the Linux collector image's actual 2 GiB cgroup limit. Record peak RSS, allocator recovery, CPU/event-loop delay, NATS client pending bytes and input versus publish rates.
    • Measure progression, publish age and gap/loss counters per channel and route on all 780 instruments, including actual REST quota/backfill behavior. Determine whether the batch bottleneck remains material before changing its scheduler.
    • Run cold/drain/live calc and archiver catchup concurrently; demonstrate catchup faster than ingress and measure a new RTO from real backlog. Measure trader full-history load rather than relying on its currently small RSS.
    • Record combined host peak with monitoring, database, retained broker state and maintenance/backup activity. Compose's approximately 24 GiB of maximum limits exceeds the roughly 15.6 GiB host and is not an admissible simultaneous budget.
    • Require no OOM, bounded reservations/pending queues, no consumer leaks and no unexplained drop growth over the intended soak. A healthy container or successful image build does not close this gate.

    Decision: retain the configured numeric buffer cap while correcting what it accounts for; stage the reviewed fix with measured headroom. No resource increase is justified from the local probe alone, and no full-catalogue production launch is authorized by this report.

    2026-09-29: bounded subject-fair drain¶

    The drainer replenishes its existing 20 concurrent ACK slots as publishes finish. Each subject has at most one active reservation, so later messages cannot overtake its failed head and a hot subject cannot occupy every network slot. Ready subjects rotate after ACK completion. Global oldest queued eviction remains the capacity policy; active reservations are not evictable. Backoff pauses new admissions after failure while already active ACK waits complete. Cancellation releases completed ACKs and requeues every unconfirmed reservation with its original attempt time.

    The global queued index and per-subject head indices use ordered maps, avoiding a scan of the entire backlog for each ACK. Retained entry charging reserves the full runtime size of singleton global/subject/ready maps, subject dictionary, active set and integer key for every entry. This is deliberately conservative for shared containers. Index maps compact when their allocation exceeds that singleton allocation per remaining entry, and clear when empty; draining a large queue does not leave its old hash capacity uncharged. This bounds retained buffer objects and indices, not the collector process RSS or NATS server memory.

    A local pre-change probe with 100 independent subjects and one held ACK completed 19 messages and left 80 queued after 50 ms; releasing the gate completed all 100. This identifies the batch barrier. Uniform-ACK isolated NATS measurements show that replenishment alone need not materially raise throughput; durability and actual subject traffic still require separate capacity evidence. Server sync policy and the 20-publisher limit are unchanged.

    Final focused scheduler validation: 49 passed. Separate regressions prove that new ingress and retry deadlines wake during an unrelated held ACK and that a self-cancelled publish cannot strand its removed reservation. The underfilled window reuses the existing idle sleep as its wait timeout. A saturated 64 MiB charge probe with 100,000 arrivals retained 30,840 tiny unique-subject messages, 15,887 messages with 2 KiB payload padding, or 5,511 with 10 KiB padding; each charged total stayed within capacity. Indices compacted to 1,512 bytes at one entry and 536 fixed empty-container bytes at zero entries. Sequential process max RSS was 116.9/140.9/192.8 MB from a 74.8 MB baseline, including allocator carryover; this is measured evidence, not a process-memory limit guarantee.

    Measured ACK window: 200¶

    The existing DRAIN_PUBLISH_INFLIGHT bound is 200. Matched same-host isolated NATS 2.10.29 FILE/S2 with sync-always enabled, actual archived wire payloads, 60,000 publishes and the final subject-fair drainer measured 2,206/2,209 messages per second at 20 slots and 2,722/2,688 at 200 slots. Observed live arrival rate was approximately 2,450 per second. Thus 20 cannot sustain that input, while 200 is the smallest tested window above it, with approximately 10% measured headroom. This changes an existing named bound, adds no configuration knob, and preserves one active ACK per subject. A preliminary 400-slot phase was slower (2,445 per second) and does not justify a larger bound. These isolated results justify a controlled full-catalogue trial; they do not prove sustained live capacity. Publisher ACKs, server durability, byte accounting, eviction, retry age and subject FIFO remain required. The dedicated 200-slot regression exercises a failed head, 200 occupied slots, cap rejection, cancellation requeue and ordered restart drain.

    Collector intake and confirmed publication counters¶

    trading_collector_buffer_attempts_total counts every normalized message handed to the production D9 wrapper before put_nowait, including refused new entries. It counts routed WS/poller messages after their validation/normalization, not every raw websocket frame or every event generated by the venue. trading_collector_buffer_admissions_total counts each successful buffer insertion. Later eviction or duplicate-window age expiry does not undo that admission. Neither counter repeats during a publication retry or waits for a broker ACK. The mandatory existing health-export loop exports both counters without a new configuration field, subject labels, or additional payload JSON parsing.

    Attempts minus admissions counts refused new messages. Existing trading_buffer_dropped_total also includes eviction and age expiry, so it must not be interpreted as attempts minus admissions. The existing trading_ingress_messages_total name/behavior is preserved for compatibility: it counts nonduplicate messages only after a JetStream PubAck. Its receive-lag and clock-skew observations also occur only for that acknowledged population. It is an output counter, not an intake or current queue-age measurement. Duplicate PubAcks have their existing separate counter.

    Capacity comparisons should use the attempt/admission rate as input and the nonduplicate confirmed-publication rate as output, alongside refusal, eviction, age-drop and duplicate counters. These are process-lifetime cumulative counters; compare deltas within the same collector run. A blocked publisher must not stop intake counters. Final regression coverage includes blocked/normal/duplicate ACKs, refused and evicted entries, retry isolation and idempotent metrics-bridge updates.
