    Продолжение paper-раскатки Backend из Codex CLI¶

    Состояние на 29 сентября 2026 года. Это инструкция для нового исполнителя, заменяющая устаревшие команды из предыдущих журналов. Исторические отчёты нужны для проверки фактов; прежние указания запускать сервисы не являются разрешением повторять не прошедший приёмку запуск.

    Задача и исходники¶

    Довести до конца оставшийся план Backend: устранить ресурсные блокеры, восстановить полный paper-контур, проверить историю и архив, провести 24–48 часов наблюдения, затем закончить функциональные и технические остатки из реестра. Запускать Codex CLI непосредственно на сервере, не через Codex Web. Оркестратор — GPT-6 Astra с low reasoning (лёгкий режим). Делегировать только ограниченные независимые части: для сложной реализации — GPT-6 Sol с medium reasoning, для простых задач — GPT-6 Luna с max reasoning. Держать число и объём делегаций экономными; не отдавать агентам весь план без конкретной границы и результата.

    Репозиторий: SNCapital/Backend. Перед работой получить текущий origin/main, проверить git status и записать исходный SHA. Использовать актуальный main как источник релиза; не продолжать работу от устаревшей ветки или переданного SHA без сверки с текущим origin/main.

    Пользователь разрешил коммитить и отправлять код. После завершения нужных проверок опубликовать готовые изменения в main до развёртывания. Перед релизом заново получить origin/main, подтвердить чистое состояние checkout и точное совпадение его SHA с текущим origin/main; релизный исходный код должен быть именно этим SHA. Не отправлять force push и не развёртывать незакоммиченный код. Внешние runtime- конфигурации и секреты хранить отдельно от Git-релиза; секреты не выводить и не коммитить. Исходный runtime/snapshot на сервере — историческое исключение, а не доказательство соответствия текущему origin/main: сохранить его неизменным как исходное состояние/точку отката и переходить с него только через описанные ниже stop-first gates. До прохождения этих gates runtime не менять.

    Полный реестр остатка с приоритетами, Linear ID и критериями приёмки находится в rollout-evidence/remaining-register.md. Прочитать его целиком: задачи P2/P3 не исчезают после запуска collector.

    Доступ и единственный исполнитель¶

    Сервер: root@194.247.187.40. Codex CLI работает непосредственно на сервере; проверить фактические checkout, SSH-доступ и подключения из этого окружения перед операциями. Использовать предоставленную пользователем авторизацию; не переносить личные ключи/токены из чужого окружения и не печатать секреты. Если доступа нет, назвать ровно недостающий доступ; до его появления продолжать независимые проверки кода. Не утверждать, что сервер проверен.

    Локальное расписание paper-backend («every 30 minutes») PAUSED при передаче. Не включать его обратно: сервером должен управлять один исполнитель. Эта инструкция не создаёт бесконечного фонового агента. При окончании доступного времени сохранять точную точку продолжения и безопасное состояние.

    Что уже принято и не требует повторной реализации¶

    1. Импортированы и полностью прочитаны 488 604 бара / 120 инструментов, с историческим cutoff 2026-09-28 14:30 UTC. Исходные файлы проверены хешами. Бары явно incomplete/full-blind; это не доказанное качественное покрытие.
    2. Штатный reader прошёл всю историю при ограниченной памяти. Полный trader restore и расчёт трёх настроенных стратегий прошли с 40 конечными весами: peak контейнера 1.465 GiB при лимите 2.25 GiB. Это доказательство на данном наборе, а не бессрочная гарантия памяти и качества данных.
    3. Исправлены funding pacing и Retry-After time sync, блокирующий inline REST gap backfill убран из живой публикации; точные gap headers сохранены.
    4. Очередь collector учитывает удерживаемые объекты и inflight, соблюдает порядок внутри subject при retry, не ждёт целую пачку перед освобождением слотов. Окно подтверждений 200. Насыщенный 1.3 GB учётный буфер проверен с 200 reservations под 2 GiB: пик около 579 MiB для trades и 1.15 GiB для depth.
    5. TERM/INT останавливает producers перед ограниченным drain. Последние два запуска подтвердили штатный выход с пустой очередью. Старые forced-stop gaps этим не восстановлены.
    6. Исправлено поглощение BTC mark price служебным benchmark. В owning batch сообщение публикуется, вспомогательные копии пропускаются. После каждого WS frame await asyncio.sleep(0) отдаёт управление другим готовым задачам. Это проверенный контракт fairness, не доказанная единственная причина прежних сетевых задержек.
    7. Raw funding reader проверяет acquisition receipts и точные интервалы: подтверждённый пустой интервал даёт ноль, неизвестный funding удерживаемой позиции останавливает backtest с инструментом/временем. Flat unknown не создаёт расход. PnL kernel и торговое исполнение не изменены.
    8. Добавлены настоящие pre-publish counters попыток/admissions D9. Старый trading_ingress_messages_total сохранён, но он считает nonduplicate PubAck. Нельзя использовать его как число входящих WS сообщений.
    9. NSC-33 и NSC-105 закрыты в узком кодовом объёме: quality/stamp contract и durable retry strategy history. Их серверная приёмка остаётся в NSC-116.

    Последняя общая unit-проверка: 2355 passed, 9 skipped, 1 xfailed. Релевантные pipeline/aggregation slow-load: 12 passed. Пропуски включают семь отсутствующих Go golden fixtures и два локальных promtool checks; это не доказательство полной интеграционной/серверной приёмки. Последние изменения после slow/load затронули counters и их описание, не funding/pipeline поведение.

    Первый блокер: производительность публикации¶

    Последний живой запуск 630cc80784a4 начался в 00:16:55 UTC. Через примерно 26 секунд независимый guard остановил его при 2.417% учётного буфера, около 31 MB. Drops и WS reconnects = 0; очередь затем успешно допубликована. В измеренном интервале NATS, включающем shutdown drain, было около 2084 msg/s; учётный объём очереди перед остановкой рос примерно на 1.282 MB/s.

    Прежнюю оценку «2450 входящих msg/s» и «10% запаса» отозвали: неверно интерпретировался post-ACK counter. Рост очереди доказывает дефицит, точная скорость admission старого запуска не установлена.

    Дальше работать на отдельном стенде без Binance и production streams:

    • Репрезентативные trade/depth/mark/hb и тяжёлые depth-хвосты, полный каталог, точные offered/admitted/ACKed/readback counters, per-subject FIFO и dedup.
    • Разделить Python/client/scheduler, NATS file store/fsync и нагрузку archiver: сравнить actual network MemoryStorage/FileStorage и при необходимости эквивалентный Go client. MemoryStorage — только диагностический стенд.
    • В замерах сохранять sync_interval: always; не ускорять production ценой более слабой гарантии durable ACK. Не увеличивать параллельность наугад.
    • Проверить устойчивую скорость, burst/catch-up, задержку event→receive→store, bounded memory и очередь без роста. Profile overhead не считать capacity.
    • NATS 2.10.29 закреплён digest. Atomic batch — отдельная смена протокола/версии с другим lost-final-ACK/dedup и rollback; сначала проверить первоисточники и изолированный прототип. Не обновлять broker по одному предположению.

    См. разбор последнего запуска и разбор batching.

    Второй блокер: память и производительность archiver¶

    Archiver достиг точного лимита 768 MiB: peak 805306368, memory.events max=1193, OOM=0. После закрытия/ACK сегментов удерживалось около 739.5 MB anonymous memory. Отсутствие OOM не означает достаточный запас.

    Доказанные риски: девять push-очередей по умолчанию до 256 MiB payload каждая; хранение целых Msg до fsync/ACK примерно 90–120 секунд; row limits без byte bound; растущие закрытые metadata keys; повторное накопление rows после failed flush; задержка sweep/renewal из-за S3; пики merge/upload вместе с intake. Два executor round trips на сообщение требуют измерения. Циклическая Arrow утечка пока не доказана. Не добавлять GC/release_unused и не повышать cap вслепую.

    Сначала воспроизвести на изолированном NATS/staging и локальном verified sink, без реальных S3 credentials. Измерить владельцев удерживаемой памяти, исправить конкретные небounded пути, проверить failed flush/slow sink/restart. Затем длительный mixed-kind поток, burst, backlog, несколько segment closures, параллельный daily merge/upload, точный readback всех ID и устойчивый пик с запасом без memory.max events. Подробный протокол: archiver-resource-readiness-review.md.

    После устранения обоих блокеров¶

    1. После публикации проверенных изменений в main получить текущий origin/main и собрать новый однозначно идентифицированный релиз ровно из его SHA. Проверить чистое состояние checkout, manifest/image hashes, внешнюю конфигурацию и откат. Не включать незакоммиченные изменения. Существующий исходный snapshot/runtime и volumes сохранять без изменений как историческую точку отката; мигрировать с них только этим stop-first процессом.
    2. Stop-first. Сначала готовые инфраструктура и archiver, затем только новый collector на динамическом полном каталоге: минимум 8 стабильных минут и законченный первый funding cycle. Проверять все виды данных, BTC mark, freshness, drops, очередь, REST, RAM/диск и archive readback.
    3. Последний short-trial guard: 2% учётного буфера, любые drops, три WS reconnects или устойчиво отсутствующие metrics останавливают collector; Docker grace 60 секунд при внутреннем drain deadline 10 секунд. Это предохранитель короткой пробы, не бессрочная политика нормальных reconnects.
    4. Только после gate запустить calc под ресурсным контролем. Подтвердить bootstrap/recovery по каждому инструменту, корректные checkpoints и несколько свежих settled bars в NATS/PG. Health endpoint сам по себе недостаточен.
    5. После полной доступной истории и новых bars запустить единственный paper trader: history → replay → live последовательно. Проверить quality hold, текущие цены, веса/позиции, strategy_pnl, API/dashboard и funding ledger.
    6. Начать явно датированный 24–48h full-stack soak. Контролировать память, CPU, REST, queue/lag/drop, storage growth, archive ACK/readback и restart/kill сценарии. Установить измеренные alert thresholds; настроить delivery только с предоставленными credentials/адресатами и разрешением на отправку.
    7. После приёмки аккуратно retire legacy по реестру, сохранив данные/откат. Затем закончить P2/P3; не объявлять весь план закрытым по одному soak.

    Funding, качество и оставшиеся задачи¶

    См. полный реестр. Особенно не потерять:

    • NSC-29 остаётся In Progress: Go-backed funding ещё не имеет надёжного raw sidecar/coverage; старые fixed 00/08/16 и zero fallback не являются корректным cashflow. Не переносить их в raw path. Проверить paper ledger и causal availability отдельно от economic event time. Не выдумывать receive-time.
    • Receipt coverage означает полноту ответа выбранного endpoint при явно заявленном source-trust assumption; economic_coverage_complete=false и historical availability unproven остаются честными ограничениями. Legacy файлы нельзя сертифицировать задним числом. Special payments не приняты.
    • BarsReader не сохраняет всю legacy quality metadata: импорт сам по себе не делает историю GOOD. Нужна реальная history/live/backtest quality matrix.
    • Старые raw/kline gaps, неопределённая membership MD_TRADE snapshot и gaps вынужденных остановок должны иметь manifest восстановленного/неизвестного. Не повторять тяжёлый backup, уже приводивший к OOM, без отдельного бюджета.
    • NSC-109/120: фактические account/strategy panels, alert delivery и измеренные пороги. NSC-117: сравнение cadence 1s/60s на одинаковом проверенном сырье и обоснованное решение re-fit. NSC-121 и P3: callers/dead code, dependencies, документы/CI, переносы модулей последними, локальные данные отдельным объёмом.

    Ресурсы и ограничения¶

    Хост около 15.6 GiB RAM. Текущие потолки в GiB: collector 2, calc 5, trader 2.25, NATS 1, PG 0.5, archiver 0.75, Prometheus 0.375, dashboard 0.25, Grafana 0.25; сумма 12.375. Это не доказанный совместный пик. 24 GB NATS — диск, memory store 256 MiB, контейнер RAM 1 GiB. MD cap 21 GB, BARS 1 GB. Настроенные 24h retention не доказывают вместимость 24h.

    Loopback ports: NATS 14222/18222, dashboard 28000, Prometheus 29090, Grafana 13000. Не публиковать сервисы/секреты наружу. Не менять торговые лимиты, капитал, universe или history horizon ради прохождения теста: symbols: null, lookback_days: null остаются полным объёмом.

    Пользователь отдельно потребовал не раздражать Binance. Старый IP-ban 28 сентября истёк; единственный контрольный /time дал 200 в 22:53 UTC. Повторять старую пробу на каждом продолжении не нужно. Сейчас нет разрешения на новые live пробы до offline gates. При новом 418/429 остановить соответствующие REST процессы, записать Retry-After/deadline и ждать с запасом; без retry storm. Перезапуск процессов не должен сбрасывать общий IP-бюджет: учитывать запросы предыдущего процесса и всех соседних сервисов. Не запускать параллельный funding backfill с независимым лимитером, будто он имеет отдельную IP-квоту.

    Не покупать ресурсы, не удалять datasets/volumes/snapshots, не включать real money, не менять legacy symlink автоматически. При OOM, memory pressure или нехватке диска остановить новые application services, сохранить данные и сообщить факты. Новые инфраструктурные сущности должны создаваться production-кодом идемпотентно. Соблюдать актуальные ADR/AGENTS; не возвращать удалённую replay-машину calc.

    Проверки и фиксация результата¶

    Любое изменение поведения: regression сначала, доказать red/green, затем финальные проверки после завершения правок. Не запускать тесты в production NATS/PG. Python 3.13+, зависимости requirements.txt и collector/requirements.txt.

    Unit: python -m pytest -q -n auto -m "not slow and not load and not integration and not realdata" --timeout=5. Integration — последовательно на отдельной инфраструктуре с нужными credentials. Релевантные slow/load — последовательно, явно not realdata; не считать skips выполненными gates. После каждого принятого этапа сохранять SHA/config/image IDs, команды, counts, timestamps, пики и оставшиеся ограничения.

    В Linear закрывать только действительно завершённые задачи после сверки их полного acceptance. NSC-33/105 уже Done; NSC-102/122/106 также были Done. NSC-116/29 In Progress; NSC-109/120/121/117 не закрыты. Полноценную раскатку, качество и финансовую корректность нельзя выводить из unit или healthz.

    Первый следующий шаг: проверить checkout/доступ/состояние, затем параллельно изолированно разобрать publisher capacity и archiver memory. Не начинать с очередного запуска collector. Сохранить журнал продолжения в рабочей копии; локальные отчёты старого ноутбука могут быть недоступны, основные выводы и доказательные ограничения уже включены в rollout-evidence этого репозитория.
