    Dev plan — ADR-0002 (split services + JetStream)¶

    Источник контракта: docs/adr/0002-split-services-jetstream/0002-split-services-jetstream.md (In Review, все фазы, Gate 4 accepted 2026-09-12). Рабочий материал: transition-plan.md, soak-runbooks.md, OBS-SPEC.md, bars-contract.md, X-004.md (сырые замеры) и research-notes.md (консолидированный след: D-/Q-/INV-/S-/X-001..003/registers/handover — id-ссылки в тексте ниже разрешаются там).

    Этот документ — план реализации. Слой 1 (этот файл сейчас): эпики крупными мазками + зависимости + волны. Слой 2 (дальше): детализация каждого эпика на задачи. Порядок правок дока — как ADR: правим, не переписываем молча.

    Статус-легенда¶

    • done — влито в мастер.
    • partial — часть в коде, требует достройки под ADR-0002.
    • greenfield — с нуля.
    • gated:X — заблокировано до X (эпик/soak/решение).

    Что уже есть (базис ADR-0001 + D-001 код)¶

    • collector: WS(2 соединения C5) + reconnect + поллеры + publish md.* c Nats-Msg-Id; RAM-буфер (collector/buffer.py). → основа для E5.
    • NATS JetStream: STREAM_SPECS (MD_DIFF/MD_TRADE/MD_EVENTS + BARS declared), 24h + max_bytes=100G, ensure_streams/check_stream_invariants (common/nats_wire.py). → основа для E0.
    • trader-монолит: book + engine + strategies + blotter + FileWriter + in-process bars через metrics/metrics_engine/live_bridge.py; чекпойнт книги + курсоры колонками book_checkpoint (trader/book_store.py). → разбирается в E2/E4.
    • Известный анти-инвариант в коде (E1 чинит): keys.empty_row() = все 0.0; engine._sanitize_row NaN/Inf→0.0; live_bridge.py:81 replace(0.0,nan).ffill().

    Волны выполнения¶

    • Волна 1 (параллельно, без E1): E0 (докрутить step 1: свести прод MD_* 72h→48h+max_bytes через update API, X-002/X-004 дрейф), E3 (shadow archiver, step 2), E5 (proxy: ingress time + conn-id + buffer cap/counter/alert), E2-consume-half (extract book+engine+replay exact-subject, курсоры в отдельную таблицу, без публикации).
    • Волна 2 (критич. путь): E1 целиком — Aggregate provenance → engine emit present-only → убрать ffill → quality stamp → bars wire + publisher → parquet nullable → валидация первого бара. Разблокирует publish-половины E2 и E4.
    • Волна 3: E2-publish (calc публикует bars.*), E4 (trader на барах), E7 (backtest offline), E6 (observability по мере появления счётчиков).
    • Волна 4 (гейты): E8 soaks (закрывают числа: max_bytes S-1, T=5/N-stale в тени, kill-archiver S-2), затем E9 cutover (stop-first/start-first, Q-005) → retire (point of no return, только после soaks).

    Слой 2 — детализация эпиков¶

    Правила для исполнителя (кодовая нейронка): делай ровно то, что написано в задаче; ничего не додумывай. Если в задаче стоит блок РЕШЕНИЕ ТРЕБУЕТСЯ — СТОП, не писать код, вернуть вопрос человеку. Каждая задача указывает: файлы, что сделать, что НЕ делать, verification (тест/команда). Verification обязателен: задача не закрыта без зелёного теста.

    E1 — детализация: bars contract (явный NULL + quality stamp + wire)¶

    Цель: заменить неявную пустоту (0.0 = «нет данных») на явный NULL в баре; добавить обязательный quality stamp; определить wire-формат bars.* и publisher/consumer. Контракт полей — bars-contract.md (авторитетный источник имён/типов; при расхождении с этим планом — контракт главнее, но сначала эскалировать расхождение человеку).

    Гейт входа: E0 (BARS-стрим существует и check_stream_invariants зелёный). Гейт выхода: «приёмка контракта» (см. DoD) на первом реально опубликованном баре.

    Жёсткие инварианты E1 (НАРУШАТЬ НЕЛЬЗЯ — это и есть смысл эпика)¶

    • INV-E1-a. Отсутствие данных по ключу = ключ ОТСУТСТВУЕТ в keys (NULL). ЗАПРЕЩЕНО: класть 0.0 вместо отсутствия; NaN; forward-fill; «добивку».
    • INV-E1-b. Настоящий ноль (реально посчитанное значение 0.0) — остаётся 0.0 и ПРИСУТСТВУЕТ в keys. То есть 0.0 и «отсутствует» — РАЗНЫЕ состояния.
    • INV-E1-c. Бар без stamp или с неполным stamp (хоть одно обязательное поле отсутствует, а его значение не проверено) — НЕ ПУБЛИКУЕТСЯ (fail loud, не дроп молча: WARN + счётчик).
    • INV-E1-d. bar_complete — булев тип в envelope, НЕ число 1.0/0.0, НЕ ключ внутри keys.
    • INV-E1-e. Ровно один бар на (symbol, окно) публикуется всегда, включая тихий символ (тогда keys пуст/минимален, bar_complete=false, blind_sec=1800).

    РЕШЕНИЯ, которые нужно принять ДО кодирования (не отдавать кодеру как есть)¶

    • РЕШЕНИЕ E1-D1 (источник diff_u_gaps/diff_lost_est/trade_agg_gaps). РЕШЕНО (человек, 2026-09-13): монитор монотонности id — в КОЛЛЕКТОРЕ; сигнал гэпа едет в calc NATS-хедером на СЛЕДУЮЩЕМ сообщении. Обоснование: детект — единая точка (коллектор — единственный, кто видит сырой поток per-connection), а флаг целостности дальше используют разные части системы (calc → штамп, observability, потенц. archiver). Aggregate U/u/pu НЕ хранит. OrderBook resync-логику НЕ трогаем (она про корректность книги, отдельная задача). Механизм (кодер реализует буквально):
    • Коллектор держит per-subject (символ×тип потока) последний монотонный id: u для diff (md.*.diff.*), a для aggTrade (md.*.trade.*).
    • На каждом сообщении: expected = last_id + 1. Если actual > expected → гэп: gap_count=1, lost_est = actual - expected. Если actual <= last_id → дубль/старьё, НЕ гэп (gap_count=0). Обновить last_id = actual.
    • Когда гэп обнаружен — на ЭТО сообщение (то, что вскрыло гэп) добавить NATS- хедеры: X-Gap-Count: 1, X-Gap-Lost: <lost_est>. Нет гэпа → хедеров нет. Payload остаётся 1:1 Binance (D7 — хедеры не payload; Nats-Msg-Id уже так).
    • calc/observability читают хедеры IN-ORDER и относят к окну сообщения-носителя (тип потока — из subject: diff → diff_u_gaps/diff_lost_est; trade → trade_agg_gaps). Гэп, вскрытый сообщением N, относится к окну, куда попал N (книга/трейды «поехали» с этого момента; для 30-мин баров аппроксимация приемлема — НЕ пытаться разносить потерю по предыдущему окну).
    • Свойство паритета: хедеры лежат в JetStream вместе с сообщением → replay воспроизводит те же счётчики, что live. НЕ пересчитывать гэпы в calc. Реализация детекта/хедеров — задача E5 (коллектор); сборка в штамп — T-E1.3 (calc). bars-contract.md п.3/п.28 править: U/u не в Aggregate, источник — хедеры коллектора. Статус: РЕШЕНО — T-E1.3 разблокирована (после E5 T-E5.3).
    • РЕШЕНИЕ E1-D2 (правило «present per key-family»). Нужно точное правило, КОГДА семейство ключей присутствует в баре, а когда отсутствует (NULL). РЕШЕНО (человек, 2026-09-13): по семействам. Правило (кодер реализует буквально):
    • trade-семейство (TRADE_KEYS в keys.py): присутствует iff в окне был хотя бы один слот с has_trade=True; иначе все trade-ключи отсутствуют.
    • book/orderbook-семейство (ob__*): присутствует iff в окне был хотя бы один слот с have_book=True; иначе все ob__* отсутствуют.
    • liquidations (LIQUIDATION_KEYS): присутствует iff в окне был liq-эвент (liq_buy_count>0 or liq_sell_count>0); иначе отсутствуют. live_liq (stamp) = были ли liq в ЖИВОМ фиде (см. T-E1.4).
    • kline/mark/funding (KLINE_FUNDING_MARK_KEYS): каждое под-семейство присутствует iff соответствующий have_kline/have_mark_price/have_funding был True хоть в одном слоте.
    • spread_max (SPREAD_KEYS): присутствует iff присутствует book-семейство. Это правило — единственное место, где «present» определяется. НЕ вычислять «present» как «значение != 0.0» (это и есть старый баг). Статус: РЕШЕНО — T-E1.1/T-E1.2 разблокированы.
