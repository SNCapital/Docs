    Зафиксированные решения¶

    Приняты в обсуждении, меняют параметры E3:

    Параметр Было Стало Почему
    SEGMENT_SECONDS 900 (15 мин) 60 Окно неподтверждённых сообщений падает с 15 мин до ~1.5; давление на max_ack_pending=150_000 снижается ~15x
    GRACE_SECONDS — 30 Дозапись опоздавших строк в свой сегмент вместо ошибки
    Закрытие сегмента start + 900s <= now start + 60s + 30s <= now Учитывает grace
    Ключ писателя kind (kind, segment_start_ms) Без этого grace не работает: один открытый сегмент на kind вытесняется следующим
    Владение писателем общий, 2 потока исполнитель на kind Устраняет гонку write_rows vs close_stale
    ARCHIVER_ACK_WAIT_MS 30_000 120_000 Продление in_progress() ходит раз в 30с при ack_wait 30с — нулевой запас, самостоятельный источник передоставок
    ARCHIVER_SWEEP_INTERVAL_S 30 30 (без изменений) Рычаг — ack_wait, а не частота sweep
    Выгрузка в S3 каждый закрытый сегмент суточное слияние, 00:05 UTC ~9 объектов в сутки вместо ~13 000

    Обоснование окна риска для суточного слияния: ack привязан к локальной durability (_ack_closed_segment → после fsync + os.replace, лог locally durable+acked), а не к S3. Пока минутки лежат только на диске, второй экземпляр данных — сам стрим: DEFAULT_RETENTION_HOURS = 48, limits-retention, сообщения живут 48ч после ack. Суточное окно = 24ч экспозиции при 48ч возможности перечитать. Сходится с ARCHIVER_MAX_LOCAL_STAGING_DAYS = 2 и с формулой из _check_staging_bound: local_days >= merge_window + verify_lag.

    Архиватор остаётся постоянно работающим сервисом. Раз в сутки запускается только этап слияния и выгрузки. Непрерывное потребление md.* и запись минуток остановить нельзя — упрётся max_ack_pending.

    Волна 1 — архиватор, целостность данных¶

    Гейт входа: нет. Критический путь.

    H1. Писатели по ключу (kind, segment_start_ms), исполнитель на kind¶

    done · archiver/daily_writer.py, archiver/service.py

    Сейчас _writers/_segments/_tmp_paths/_final_paths ключуются по kind (скаляр — один открытый сегмент на тип). write_rows идёт в поток через asyncio.to_thread из консьюмера, close_stale — из sweep-цикла, без локов: close_kind может закрыть и переименовать файл ровно во время write_table в другом потоке.

    • Все четыре словаря → ключ (kind, segment_start_ms).
    • _open(kind, day, seg), close_segment(kind, seg); close_stale(now) закрывает все пары, у которых seg + SEGMENT_MS + GRACE_MS <= now.
    • ThreadPoolExecutor(max_workers=1) на каждый kind. Все операции писателя для данного kind идут строго в его исполнитель.
    • close_stale и close_all раскладываются на per-kind вызовы, каждый — в свой исполнитель. Иначе sweep продолжит трогать чужие writer'ы и гонка останется на месте.

    Приёмка: конкурентный тест «запись + закрытие одного kind» не портит parquet; разные kind пишутся параллельно; close_all на shutdown закрывает всё.

    Заметка: _pending_acks уже ключуется (kind, segment_start_ms) — совпадает с новым ключом писателя, дополнительных изменений не требует.

    H2. Сегмент 60с + grace 30с¶

    done · archiver/daily_writer.py · зависит от H1

    • SEGMENT_SECONDS: 900 → 60, новая GRACE_SECONDS = 30.
    • Условие закрытия: seg + SEGMENT_MS + GRACE_MS <= now.
    • В течение grace одновременно открыты текущий сегмент и предыдущий.

    Приёмка: строка с ts внутри grace дозаписывается в свой сегмент, а не в текущий; после grace сегмент закрывается ровно один раз.

    H3. Запрет воскрешения закрытого сегмента + классификация ошибок¶

    done · archiver/daily_writer.py, archiver/service.py · зависит от H2

    Два дефекта, обнаруженные ревью, чинятся здесь.

    Дефект 1 — перезапись финализированного сегмента (потеря данных). close_kind делает self._segments.pop(kind, None). После закрытия по sweep состояние очищается, и передоставленное сообщение старого сегмента попадает в ветку «сегмента нет» → _open делает tmp_path.unlink(missing_ok=True) и создаёт новый writer без проверки, что финальный файл уже существует и выгружен. Следующий os.replace перезаписывает готовый файл одной поздней строкой. В S3 уходит PUT по тому же детерминированному ключу.

    Дефект 2 — бесконечная передоставка. Пока сегмент открыт, строка более старого сегмента даёт ValueError("Out-of-order segment"), который ловится в _consume_subject как "transient failure - no ack, will redeliver". Сбой не транзиентный: сегмент укатился вперёд, условие не разрешится никогда.

    Правки:

    • Множество закрытых (kind, seg) в памяти + проверка существования финального файла. Переоткрытие закрытого сегмента запрещено.
    • Строка позже grace → msg.term() + archiver_dropped_late_rows_total.
    • Перманентные ошибки (декод, схема, неизвестный kind, слишком поздняя строка) → term(), из передоставки уходят.
    • Транзиентные (диск, S3, брокер) → без ack, передоставка сохраняется.
    • Докстринг _consume_subject («one bad payload can't wedge the subject») привести в соответствие с поведением.

    Приёмка: передоставка сообщения уже закрытого сегмента не перезаписывает файл и не зацикливается; счётчик отброшенных растёт; транзиентная ошибка по-прежнему приводит к повтору.

    H4. ack_wait 30с → 120с¶

    done · archiver/service.py · независима

    ARCHIVER_ACK_WAIT_MS: 30_000 → 120_000. При минутных сегментах и grace 30с сообщение висит неподтверждённым ~90с — укладывается почти без продлений, in_progress() становится страховкой для застрявших случаев, а не основным путём.

    Цена: после падения архиватора передоставка начнётся через 2 мин вместо 30с. Для архиватора безразлично — он не в торговом пути.

    H5. Метрики опозданий¶

    partial · common/health.py, archiver/service.py · зависит от H3 (счётчики и snapshot-поля сделаны; Prometheus-экспорт ждёт E6)

    • archiver_late_rows_total{kind} — пришли с опозданием, но в пределах grace, записаны.
    • archiver_dropped_late_rows_total{kind} — позже grace, отброшены.
    • Лаг now - row_ts (gauge или гистограмма) — чтобы на soak увидеть, хватает ли 30 секунд, и подобрать число по факту, а не угадывать.

    Приёмка: метрики экспортируются, покрыты тестом.

    Волна 2 — слияние и выгрузка¶

    Гейт входа: H1-H3.

    Путь заливки переписывается: сейчас _archive_closed_file(path) грузит каждый закрытый сегмент сразу.

    H6. Суточное слияние минуток¶

    done · archiver/merge.py

    • Запуск 00:05 UTC для предыдущих суток. Не 00:00: сегмент 23:59 с grace закрывается в 00:00:30, при старте ровно в полночь он в слияние не попадёт.
    • Берутся только сегменты, для которых start + SEGMENT_MS + GRACE_MS прошло, а не «все файлы в папке за вчера».
    • Потоковая запись: 1440 файлов на kind нельзя собирать в память — читаем по одному, пишем row-group'ами в один ParquetWriter.
    • Та же атомарность, что в close_segment: .tmp + fsync + os.replace.

    Приёмка: слитый файл содержит объединение строк; потребление памяти не растёт с числом входных файлов; повторный запуск даёт тот же результат.

    H7. Выгрузка слитого файла + верификация¶

    done · archiver/s3_sink.py · зависит от H6

    Сейчас проверка после PUT — только ContentLength из HEAD. Для дневного файла на десятки мегабайт сверка по длине особенно слаба: побитая передача той же длины пройдёт как успешная.

    • Верификация по ETag или checksum.
    • Минутки удаляются только после успешной верификации.
    • Детерминированный ключ; повторный PUT идемпотентен.

    Приёмка: повреждение при передаче детектируется; минутки не удаляются при неуспешной верификации.

    H8. Идемпотентность и восстановление после крэша¶

    done · archiver/merge.py · зависит от H7

    • Крэш на середине слияния оставляет .tmp, который при старте игнорируется и пересобирается заново.
    • Повторный запуск слияния для того же дня безопасен.
    • Слияние обязано отрабатывать до ARCHIVER_MAX_LOCAL_STAGING_DAYS = 2, иначе получим D9 BREACH вместо выгрузки. Суточное укладывается с запасом.

    Приёмка: тест на прерванное слияние; тест на повторный прогон.

    Волна 3 — остальные блокеры¶

    Независимы друг от друга и от волн 1-2, можно параллельно.

    H9. Запрет отката курсора¶

    done · calc/cursor_store.py

    _UPSERT_SQL безусловно перезаписывает stream_seq в том числе меньшим значением — защиты от отката нет.

    Через WHERE, а не GREATEST: при GREATEST поле u может разъехаться со stream_seq независимо.

    ON CONFLICT (market, symbol, stream_type) DO UPDATE SET ...
  WHERE EXCLUDED.stream_seq > calc_cursor.stream_seq

    Плюс счётчик и WARN на попытку отката.

    Приёмка: запись меньшего stream_seq не меняет строку; счётчик растёт; u остаётся согласованным со stream_seq.

    done · deploy/alerts.yml, CI

    Сейчас единственный алерт на лаг консьюмера — > 999999999 с severity: warning, то есть не сработает никогда. Алертов на архиватор, S3 и остановку публикации коллектора нет вообще.

    • Дописать недостающие алерты с теми же TBD-порогами (реальные числа gated:E8 — выводятся из soak, придумать их нельзя).
    • Проверка в CI, запрещающая выкатку конфига с 999999999.

    Тогда отсутствие порогов становится видимым блокером, а не тихой дырой.

    Приёмка: CI падает на конфиге с плейсхолдером; новые алерты валидны как YAML.

    Волна 4 — жизненный цикл сервисов и мелкие долги¶

    Независимы друг от друга. H12 — гейт для H1: без него закрытие писателей на остановке, ради которого делается волна 1, не выполнится.

    H12. Обработка SIGTERM во всех трёх сервисах¶

    done · common/service_runner.py · calc/__main__.py, archiver/__main__.py, main.py, trader/service.py · блокирует приёмку H1

    asyncio.run(...) без add_signal_handler: по SIGTERM (то есть по docker stop, по рестарту в оркестраторе) корутина не отменяется штатно, и ветка finally с graceful shutdown не отрабатывает. Именно в ней закрываются NATS-соединения, флашатся буферы и — после H1 — закрываются писатели parquet.

    Без этого H1 даёт обещание, которого не выполняет: на остановке останутся незакрытые .tmp-файлы, и восстановление ляжет на передоставку вместо штатного закрытия.

    • add_signal_handler(SIGTERM/SIGINT) → отмена главной задачи.
    • Ограниченное время на graceful shutdown, затем принудительный выход.
    • Ненулевой код возврата при аварийной остановке.

    Приёмка: SIGTERM приводит к закрытию всех писателей и соединений; тест на отмену главной задачи; .tmp не остаётся.

    H13. Закрытие NATS-соединения publisher'а в calc¶

    done · calc/bars_publisher.py, calc/service.py

    make_bars_publisher(url) открывает собственное соединение (D1: calc не импортирует collector.*), но возвращает только publish — способа закрыть соединение нет. В finally у run_calc_service закрывается только live_nc. Утечка на каждом рестарте сервиса.

    Вернуть пару (publish, close) либо async-контекстменеджер; закрывать в том же finally, что и live_nc.

    Приёмка: тест, что после остановки сервиса соединение publisher'а закрыто.

    H14. Потеря бара при ошибке публикации¶

    done · calc/service.py, calc/bars_publisher.py

    Upstream обернул publish_bar в except NatsError и отделил транспортные сбои от программных — это улучшение, но бар для закрытого окна всё равно теряется навсегда: следующая итерация цикла строит present_row уже для другого bar_end_ms, повторить публикацию некому.

    Решение: ретрай с backoff + метрика + лог.

    Ограничение, которое определяет форму ретрая: await publish_bar стоит в последовательном цикле по символам внутри _drive_boundaries. Ретрай «на месте» задержит публикацию всех оставшихся символов того же бара, а при недоступном брокере — умножится на число символов и съест окно целиком. Поэтому ретрай выносится из основного прохода:

    1. Первый проход по символам — без ретрая. Символ, у которого публикация упала с NatsError, складывается в список неотправленных вместе с уже построенным present_row и stamp.
    2. После прохода — повтор только по неотправленным, с экспоненциальным backoff и двумя бюджетами: по числу попыток и по суммарному времени. Оба параметра — в live_config.yaml, не захардкожены (политика CLAUDE.md).
    3. Временной бюджет заведомо меньше периода бара, чтобы ретрай не пересёкся со следующей границей. Стартовые значения: 3 попытки, backoff 0.5/½ с, общий потолок 10 с — estimate,remeasure до E8, как wait_deadline_seconds.
    4. Исчерпан бюджет — бар признаётся потерянным: счётчик + ERROR с symbol, bar_end_ms, числом попыток и последней ошибкой.

    Дедуп по Nats-Msg-Id (make_msg_id("binance", symbol, bar_close_ms)) делает повтор безопасным: даже если предыдущая попытка на самом деле дошла, брокер отбросит дубль. То есть ретрай здесь идемпотентен по построению и не может породить второй бар.

    Метрики и лог:

    • calc_bars_publish_retries_total{symbol} — сколько повторов потребовалось.
    • calc_bars_publish_failed_total{symbol} — бар потерян после исчерпания бюджета. Это и есть сигнал для алерта (H11).
    • Успех с первой попытки не логируется (сейчас там logger.info на каждый бар); успех после ретрая — WARN с числом попыток; провал — ERROR.

    Приёмка: транспортный сбой с последующим восстановлением приводит к доставке бара, а не к потере; retries_total растёт; исчерпание бюджета даёт failed_total + ERROR; ретрай одного символа не задерживает публикацию остальных сверх временного бюджета; повторная публикация того же (symbol, bar_close_ms) не создаёт дубль в стриме.

    H16. Откат cutover в deploy_order¶

    done · deploy/deploy_order.py

    Есть cutover и retire, но нет закодированного действия отката для отмены cutover на середине: оператор поднимает stop-first сервис руками, без fail-loud защиты. При числе открытых блокеров в контуре вероятность отката на проде не теоретическая.

    Приёмка: план отката выводится из той же политики; неверный порядок отката невыразим.

    H17. metrics_source — дефолт внутрь config.py¶

    done · trader/config.py, main.py

    Поле nullable, дефолт None → "inprocess" разрешается в main.py:42 (cfg.metrics_source or "inprocess"), то есть вне config.py. При невалидном значении _coerce падает корректно, но отсутствующее подставляется молча — расходится с политикой CLAUDE.md «падать громко» и с докстрингом LiveConfig, который утверждает «All fields are required».

    Само послабление сделано осознанно (совместимость старых конфигов при выкатке, комментарий в _FIELDS), поэтому задача не «запретить», а перенести разрешение дефолта в LiveConfig.load() и поправить докстринг — чтобы дефолт был один и в одном месте.

    Связано: metrics_source — временный флаг переходного периода inprocess/bars без зафиксированного условия исчезновения. Условие снятия стоит записать здесь же, вместе с флагом present_only (см. «Вне скоупа»): оба снимаются одним решением.

    Приёмка: дефолт разрешается внутри config.py; докстринг соответствует поведению; main.py не содержит подстановки.
